本项目不手工维护接口文档：Swagger / OpenAPI 3.0.3 文档由 `server/openapi/` 遍历 `appRouter` 实时生成，随代码变化。

## 访问入口

| 入口 | 说明 | 鉴权 |
| --- | --- | --- |
| `/system/openapi` | 后台页面：默认「字段视图」（字段级入参构造 + 直接发送），可切换到内嵌 Swagger UI | 登录 + 菜单权限 `system:openapi:list` |
| `GET /api/docs` | Swagger UI 页面本身（可新窗口打开） | 同上 |
| `GET /api/openapi.json` | OpenAPI 3.0.3 文档（可交给 codegen / Apifox / Postman） | 同上 |

`NUXT_OPENAPI_ENABLED=false` 会整体关闭这三个入口（返回 404）。非生产环境只要登录即可访问，生产环境要求管理员或拥有 `system:openapi:list` 权限码。

Swagger UI 的样式与脚本来自本地 `swagger-ui-dist`（devDependency）：`nuxt.config.ts` 的 `build:before` 钩子在 dev / build 之前把它们同步到 `public/swagger-ui/`，因此开发环境由 Vite 提供、构建后随 `public/` 进入 `.output/public`，两种环境行为一致，也不需要生产镜像里的 `node_modules`，更不依赖外网 CDN。

> 这两个静态文件（`swagger-ui-bundle.js` / `swagger-ui.css`）是匿名可访问的开源资源，不含任何业务数据；接口文档本体（`/api/docs` 页面与 `/api/openapi.json`）仍然要求登录。
>
> 之所以不用 `nitro.serverAssets` / `nitro.publicAssets` 直接指向 `node_modules/swagger-ui-dist`：dev 模式下 serverAssets 不做全量挂载（`assets:` 存储里只有被 rollup 引用过的条目），publicAssets 在 dev 又由 Vite 接管静态资源，两者都会让 `/api/docs` 在开发环境读不到文件。

## 字段视图：把 Parameters 解析成可勾选字段

`/system/openapi` 默认为「字段视图」，它不是 iframe，而是直接消费 `/api/openapi.json` 自己渲染，目的是解决 tRPC 的 GET 入参只能是一个 JSON 字符串、Swagger UI 里必须手写 JSON 的问题。

- 左侧按 tag（tRPC 路由命名空间）分组列出全部接口，支持关键字过滤，默认选中第一个；
- 右侧把入参解析成**可勾选的字段**，勾选与否决定该字段是否进入最终入参 JSON；
- 两个 `GET`/`POST` 的 schema 来源不同：
  - `GET` 的 `input` 参数在 OpenAPI 里是字符串，字段结构取自扩展 `x-trpc-input-schema`；
  - `POST` 直接使用 `requestBody` 的 JSON Schema；
- **默认勾选规则**（`app/pages/system/openapi/useOpenapiFields.ts` 的 `initialValueFromSchema`）：
  - `required` 数组中的字段 —— 即 zod 侧无 `.default()`、非 `.nullish()` 的必填项；
  - 带 `default` 的字段 —— 例如查询接口的 `page`/`pageSize`，勾选后直接带出默认值，与实际发送内容一致；
  - 其余（可选且无默认值，如 `BaseSchema` 里的 `.nullish()` 查询条件）默认**不勾选**，避免下发一堆 `null`/空串。
- 值编辑器按 schema 类型选择：枚举下拉、布尔开关、数字/字符串输入框、嵌套 object 递归展开子字段、数组与自由 object 用 JSON 文本（解析成功才写回入参）。
- 「curl 预览」展示真实会发送的完整命令（`GET` 用 `-G --data-urlencode input=...`，`POST` 用 `-d`），JSON 里的单引号已按 shell 规则转义，复制出来可直接在终端执行；接口标题旁另有「复制 curl」按钮；
- 接口路径用 `CopyValueBadge` 展示，点击徽标右侧按钮即可复制路径；
- 「发送请求」以同源 `fetch` 携带 `nuxt-session` Cookie 调用真实接口，并展示状态码、耗时与响应 JSON。

复制能力统一走 `app/utils/clipboard.ts` 的 `copyToClipboard`：优先 `navigator.clipboard`，在 `http://IP:端口` 这类非安全上下文下回退到 textarea + `execCommand`，成功后由调用方给出图标与 toast 反馈（`CopyValueBadge` 与文档页共用这份实现）。

工具条还提供「选中必填 / 全选 / 清空」三个快捷操作（`initialValueFromSchema` / `allFieldsValue`）。勾选状态、请求预览与入参三者始终一致，因为入参就是 `modelValue` 本身，不存在额外的表单副本。

「Swagger UI」按钮保留原始 Swagger 视图，适合查看完整规范或做批量调试。

## 生成方式

`GET /api/openapi.json` 每次请求都实时生成，不做持久化：

```text
appRouter._def.procedures（168 个 procedure）
  ├─ HTTP 方法    ← procedure 类型：.query() → GET，.mutation() → POST
  ├─ 入参 schema  ← procedure 的 .input()（Zod → JSON Schema，覆盖率 100%）
  ├─ 响应体 schema ← 命名约定 + shared 响应契约（见下节）
  ├─ 安全声明     ← proc() 写入的 meta（auth / permission）
  └─ 原生路由     ← server/openapi/manualRoutes.ts 手工登记
```

**HTTP 方法与 tRPC 的类型严格对应**，用错方法 tRPC 会直接返回 `405 METHOD_NOT_SUPPORTED`：

| procedure 类型 | 文档中的方法 | 入参位置 |
| --- | --- | --- |
| `.query()` | `GET /api/trpc/<router>.<procedure>` | `input` 查询参数，值为 `encodeURIComponent(JSON.stringify(入参))` |
| `.mutation()` | `POST /api/trpc/<router>.<procedure>` | 请求体就是入参 JSON 本身 |

```bash
# query：整个入参序列化成 JSON 字符串放进 input
curl -G --data-urlencode 'input={"page":1,"pageSize":10}' \
  -b "nuxt-session=<cookie>" http://host/api/trpc/sysUser.page

# mutation：请求体就是入参 JSON
curl -X POST -H "content-type: application/json" \
  -b "nuxt-session=<cookie>" -d '{"id":"xxx"}' http://host/api/trpc/sysUser.remove
```

`.input()` 的真实结构：GET 放在 `x-trpc-input-schema` 扩展里（`input` 参数本身是字符串，Swagger UI 的输入框需要直接填这段 JSON，参数示例值由 schema 自动生成），POST 直接作为请求体 schema。响应体按 tRPC 的真实线格式描述为 `{ result: { data: <业务数据> } }`，业务数据结构同时写在 `x-trpc-data-schema` 扩展里便于工具直接消费。

## 响应体为什么是"推断"的

procedure 的实现统一是 `return xxxService(ctx).方法(input)`。运行时只有一个 Promise，TypeScript 类型已被擦除，**无法反射出响应结构**；而 Service 层的 `page` 返回 `OrmPageResp`，其 `list` 还是 `any[]`，用编译器反推同样拿不到元素结构。

因此生成器改用「命名约定 + shared 层已有的 Zod 响应契约」推断：

| procedure 名 | 200 响应 schema | 依据 |
| --- | --- | --- |
| `page` | `TrpcPageResponseSchema(itemSchema)` | `CommonRepo.page` 返回 `{ total, list, page, pageSize }` |
| `getOne` / `getById` | `itemSchema` | Service 声明 `Promise<XxxDto>` |
| `list` | `z.array(itemSchema)` | Service 声明 `Promise<XxxDto[]>` |
| `create` / `update` / `remove` | `z.boolean()` | Service 声明 `Promise<boolean>` |
| `batchDelete` | `z.number()` | Service 声明 `Promise<number>` |
| 其它 | `specialResponses` 逐条登记 | `server/openapi/responseSchemas.ts` |

`itemSchema` 取自 `shared/<模块>/output.ts` 的 `*RespSchema`（router 名 → 模块的映射表也在同一文件）。当前覆盖率写在文档的 `x-openapi-response-coverage` 里：

```json
{
  "total": 168,
  "inferred": 166,
  "bySource": { "rule": 134, "special": 32, "meta": 0 },
  "missing": ["auth.profile: ...", "sysJob.runNow: ..."]
}
```

### 已知精度边界

推断结果是「少字段」而非错字段。典型例子：用户列表走 `repo.pageWithDept`，真实响应多出 `deptName`，而 `SysUserRespSchema` 没有该字段。需要精确描述时用 procedure 级 meta 覆盖：

```ts
page: listProc.input(SysUserPageQuerySchema)
    .meta({
        openapi: {
            responseSchema: TrpcPageResponseSchema(
                SysUserRespSchema.extend({ deptName: z.string().nullish() })
            )
        }
    })
    .query(async ({ ctx, input }) => {
        return sysUserService(ctx).page(input)
    })
```

被 meta 覆盖的接口，`bySource.meta` 会加一，`x-response-inferred` 仍为 `true`。

## meta 增强接口文档

`proc()` 已经把鉴权与权限码写进 meta，因此文档默认就能显示每个接口需要什么权限。除此之外还支持 `meta.openapi`：

```ts
proc({ permission: 'system:job:run' })
    .input(z.string().nonempty('form.id.required'))
    .meta({
        openapi: {
            summary: '手动触发定时任务',        // 默认是 procedure 路径
            description: '自定义说明，覆盖自动生成的调用示例',
            tags: ['sysJob'],                  // 默认按 router 名分组
            method: 'post',                    // 默认按 procedure 类型：query → get，mutation → post
            path: '/api/trpc/sysJob.runNow',   // 默认按 procedure 路径生成
            hidden: false,                     // true 时从文档中移除
            responseSchema: MyResponseSchema   // 覆盖响应体推断
        }
    })
```

注意 `proc()` 内部已经调用过 `.meta()`，而 tRPC 的 `.meta()` 是**合并**语义，所以这里的 `openapi` 不会覆盖 `auth` / `permission` / `log`。

## 原生路由需要手工登记

`server/api/**`、`server/routes/**` 下的原生 Nitro 路由没有 procedure 可遍历，目前登记在 `server/openapi/manualRoutes.ts`：

| 路径 | 方法 | 说明 |
| --- | --- | --- |
| `/api/system/oss/upload` | POST | `multipart/form-data`，权限码 `system:oss:add` |
| `/api/system/user/avatar` | POST | `multipart/form-data`，仅要求登录 |
| `/auth/{platform}` | GET | OAuth 回调，302 重定向 |

**新增或修改原生路由时，需要同步更新这个文件**，否则文档会缺漏。原生路由的返回体是 `{ success: true, data }`，错误体是 `createError` 生成的 H3 错误结构，与 tRPC 的 `TRPCFormattedError` 不同。

## 导出静态文件

对接方需要一份文件快照时：

```bash
pnpm dev                          # 另开一个终端
pnpm openapi:export               # 输出到 openapi/openapi.json
```

可用环境变量覆盖默认行为：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `OPENAPI_URL` | `http://localhost:3001/api/openapi.json` | 文档地址 |
| `OPENAPI_OUTPUT` | `openapi/openapi.json` | 输出路径 |
| `OPENAPI_COOKIE` | 无 | 需要登录时提供的会话 Cookie |

## 后台菜单注册

页面 `/system/openapi` 需要在 `sys_menu` 中登记才会出现在侧边栏（也可以在后台「菜单管理」页手工新增）：

```sql
INSERT INTO sys_menu
  (id, parent_id, name, code, type, path, component, icon, sort_order, visible, status, remark, created_by, updated_by, is_deleted)
VALUES
  ('<menu_id>', '<系统管理目录 id>', 'API 文档', 'system:openapi:list', 1,
   '/system/openapi', 'system/openapi/index', 'i-lucide-file-json', 90, 0, 1,
   'OpenAPI 文档查看权限', '<admin_id>', '<admin_id>', 0);
```

`code` 必须与 `server/openapi/guard.ts` 里的 `OPENAPI_PERMISSION_CODE`（`system:openapi:list`）一致，否则生产环境只有管理员能打开文档。
