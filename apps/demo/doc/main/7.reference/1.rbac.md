## 体系组成

权限模型由五类数据构成，判断「能不能进页面」和「能不能看到某条数据」分别使用其中不同的部分。

| 数据 | 表 | 作用 |
| --- | --- | --- |
| 用户 | `sys_user` | 登录主体，`is_admin = 1` 视为超级管理员 |
| 角色 | `sys_role` | 权限集合的载体，含 `data_scope` 数据范围 |
| 菜单与按钮 | `sys_menu` | 前端导航节点 + 按钮权限码 |
| 用户角色 | `sys_user_role` | 用户与角色的关联关系 |
| 角色菜单 | `sys_role_menu` | 角色可访问的菜单与按钮 |
| 部门 | `sys_department` | 数据范围的划分依据（通过 `path` 表示层级） |

## 权限码规范

权限码统一使用 `资源:动作` 的形式，CRUD 四件套由工具函数生成：

| 函数 | 输入 | 输出 |
| --- | --- | --- |
| `crudPermissionCodes('system:user')` | 资源前缀 | `{ list, add, edit, del }` 四个权限码 |
| `buildPermissionCode('system:user', 'list')` | 资源前缀 + 动作 | `system:user:list` |
| `customPermissionCode('system:user', 'resetPwd')` | 资源前缀 + 自定义动作 | `system:user:resetPwd` |

标准动作固定为 `list` / `add` / `edit` / `del`，例如用户管理对应：

| 权限码 | 含义 |
| --- | --- |
| `system:user:list` | 查询列表、详情 |
| `system:user:add` | 新增 |
| `system:user:edit` | 修改 |
| `system:user:del` | 删除、批量删除 |

非 CRUD 动作按需自定义，例如任务的立即执行是 `system:job:run`，存储删除是 `system:storage:del`。定义见 `shared/auth/permission.ts`。

## 服务端校验链路

tRPC 接口通过 `proc()` 声明权限，由中间件依次处理：

| 中间件 | 行为 | 失败结果 |
| --- | --- | --- |
| `loggerMiddleware` | 按策略记录操作日志 | 不拦截 |
| `authMiddleware` | 要求有效会话 | `auth.unauthorized` |
| `permissionMiddleware(code)` | 未声明权限码时只要求登录；声明后校验权限码 | `auth.forbidden` |
| `demoReadonlyMiddleware` | demo 模式下拦截变更接口 | `system.demoReadonly` |
| `dataScopeMiddleware(applied)` | 标记是否叠加数据范围条件 | 不拦截 |

权限判定的两条捷径：

- `ctx.user.isAdmin === 1` 直接放行，不再查询权限码；
- 非管理员首次校验时调用 `authService(ctx).listPermissionCodes(user)`，结果缓存在 `ctx.permissionCodes`，同一次请求内只查询一次。

校验实现见 `server/trpc/middlewares/permission.ts`、`server/trpc/init.ts`。

## 前端使用

| 能力 | 用法 |
| --- | --- |
| 读取当前用户权限模型 | `useRbacProfile()`，返回 `profile`、`isAdmin`、`hasPermission`、`hasAnyPermission`、`hasAllPermissions` |
| 生成 CRUD 权限状态 | `useCrudPermissions('system:user')`，返回 `codes` 与 `canList` / `canAdd` / `canEdit` / `canDel` / `canOperate` |
| 按钮级控制 | `v-permission="'system:user:add'"`，支持传数组，任意一个命中即保留 |

`useCrudPermissions` 与 `v-permission` 都会对超级管理员放行。指令的行为是：命中权限时保留元素，未命中时**把元素从 DOM 中移除**（profile 尚未加载时先隐藏）。实现见 `app/composables/useCrudPermissions.ts`、`app/plugins/permission.ts`、`app/stores/rbacProfile.ts`。

前端权限数据来自 `auth.profile` 接口，服务端组装逻辑见 `server/sys-router/auth/AuthService.ts`：

| 返回项 | 内容 |
| --- | --- |
| `user` | 会话中的用户摘要 |
| `roles` | 已启用的角色列表 |
| `permissions` | 全部菜单与按钮权限码（扁平数组） |
| `menus` | 导航树，只包含可见（`visible = 0`）且非按钮（`type != 2`）的节点 |

`sys_menu.type` 的取值含义：`0` 目录、`1` 菜单、`2` 按钮权限（见 `shared/system/menu/view.ts`）。

## 数据范围

角色上的 `data_scope` 决定能读到哪些数据，取值为 `1` - `6`：

| 取值 | 含义 | 当前实现 |
| --- | --- | --- |
| `1` | 全部数据 | 任意角色命中即视为全部权限 |
| `2` | 自定义部门 | 保留扩展点，当前返回空集合（缺少角色-部门关联表） |
| `3` | 本部门 | 取当前用户所在部门 |
| `4` | 本部门及以下 | 按部门 `path` 前缀取本级与所有下级 |
| `5` | 仅本人 | 叠加本人条件 |
| `6` | 本部门及以下 + 本人 | 部门范围与本人条件取并集 |

数据范围的解析与拼接在 `server/drizzle/queries/buildScope.ts`：

1. 用户未登录或 `is_admin = 1` → 不限制；
2. 读取用户所有**启用且未删除**角色（`sys_user_role.status = 1`、`sys_role.status = 1`）的 `data_scope`；
3. 任一角色为 `1` → 不限制；
4. 否则按 `3` / `4` / `6` 收集部门范围，按 `5` / `6` 追加本人条件，两者用 `OR` 合并；
5. 结果缓存在 `ctx.dataPermission`，同一次请求内的多次查询不会重复解析。

「本人」字段的选取规则：`sys_user` 用主键，其它表优先用 `userId`，再退回 `createdBy`。

### 何时跳过数据范围

| 方式 | 效果 |
| --- | --- |
| `proc({ dataScope: false })` | 写入 `ctx.skipDataScope = true`，`buildScope` 不叠加范围条件 |
| 表上不存在 `deptId` / `userId` / `createdBy` 等可控字段 | 只叠加逻辑删除条件 |

已显式跳过数据范围的接口包括角色列表（`system:role:list`）与部门列表（`system:dept:list`），因为这两个页面的数据本身就是权限配置的输入。

## 缓存与生效时机

权限读取走 RBAC 三层缓存，默认 15 分钟，角色/菜单/用户角色等写操作会主动失效：

| 缓存 | 键 |
| --- | --- |
| 用户角色 | `cache:rbac:user:{userId}:roles` |
| 角色菜单 | `cache:rbac:role:{roleCode}:menu-list` |
| 管理员菜单 | `cache:rbac:admin:menu-list` |

缓存只优化数据库读取，鉴权始终由服务端中间件完成。前端 `profile` 存在 Pinia 中，默认只加载一次；改完权限后需要重新登录，或调用 `loadProfile(true)` 强制刷新。

## 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 接口返回 403 且提示无权限 | 当前用户角色未包含该权限码 | 在角色管理中勾选对应菜单/按钮，并确认缓存已失效 |
| 页面菜单看不到 | 菜单 `visible` 不为 `0`，或 `status` 未启用，或角色未关联 | 检查菜单配置与角色菜单关联 |
| 按钮消失 | `v-permission` 或 `useCrudPermissions` 判定未通过 | 核对权限码拼写与角色配置 |
| 改了数据范围看不到变化 | 请求级缓存与 RBAC 缓存的组合影响 | 重新登录后再验证 |
| 列表数据为空但库里明明有数据 | 数据范围过滤后无可见数据 | 检查角色 `data_scope` 与部门归属 |
