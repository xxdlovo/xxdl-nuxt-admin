## 它和业务日志的分工

本项目有两套日志，职责不同，不要混用：

| 维度 | 运行时日志（evlog） | 业务日志（[日志体系](/docs/main/reference/logs)） |
| --- | --- | --- |
| 形态 | 一个请求一条「宽事件」，单行 JSON | 一行数据库记录 |
| 存储 | `.data/evlogs/app/YYYY-MM-DD.jsonl` | `sys_system_log` / `sys_login_log` / `sys_job_log` |
| 用途 | 排查运行问题、性能、错误定位 | 管理端审计查询、按权限展示 |
| 触发 | 所有 `/api/trpc/**` 请求自动记录 | `loggerMiddleware` 按 mutation/query 策略 |
| 开关 | `nuxt.config.ts` 的 `evlog` 配置、环境变量 | `proc({ log })`、手动调用记录器 |

运行时日志不会写数据库，业务日志也不会写文件；两者互不影响，排查问题时通常先看运行时日志定位，再到业务日志里查操作人。

## 记录时机：一个请求一条宽事件

evlog 的 Nitro 插件在**请求开始**时就创建宽事件，在**响应结束**（afterResponse）时自动输出。业务代码只是往这个已经存在的事件里追加字段，**不是**「记不记录」的开关。

| 业务代码 | 事件里的变化 |
| --- | --- |
| 什么都不调用 | 只有 `method`、`path`、`requestId`、`status`、`durationMs`、`service`、`environment`、`timestamp` 等元信息 |
| `log.set({ demo: { ... } })` | 增加 `demo` 字段（递归合并，同名键会合并而不是整体替换） |
| `log.info('消息', { ... })` | 增加一条 `requestLogs` 条目，**不**产生新事件 |
| `log.warn()` / `log.error()` | 增加 `error` 字段并把事件 `level` 提升为 `warn` / `error` |
| `useLogger(event, 'server/demo-router')` | 覆盖事件的 `service` 字段 |

因此像 `demo.remove` 这种没有写任何埋点的接口，也会有日志——只是一条只有元信息的「骨架事件」。如果希望每个写操作都能一眼看出改了什么，就在对应分支补一行 `log.set`。

## 如何使用

### 取 logger

```ts
// server/demo-router/DemoService.ts
import { useLogger } from 'evlog'

export function demoService(ctx: Context) {
  // 第二个参数覆盖事件里的 service，缺省为 evlog.env.service（本项目是 xxdl-nuxt-admin）
  const log = useLogger(ctx.event, 'server/demo-router')

  return {
    async create(data: DemoAddDTO) {
      log.set({ demo: { action: 'create', id: data.id } })
      // ...
    },
  }
}
```

- `useLogger` 必须传入当前请求的 `event`：tRPC 里是 `ctx.event`，原生路由里就是 handler 的 `event`；
- 事件由插件自动 emit，业务代码**不要**手动调用 `emit`；
- 一次请求内可以多次调用 `log.set`，字段会合并到同一条事件。

### 领域服务（没有 `ctx`）怎么取 logger

`server/trade-router/domain/` 下的领域服务入参是 `db` / `executor`（例如 `walletService(db)`），拿不到 `ctx.event`，改用 `server/utils/evlogLogger.ts` 的 `resolveLogger()` 从当前请求上下文反查：

```ts
// server/trade-router/domain/goods/GoodsService.ts
import { resolveLogger } from '#server/utils/evlogLogger'

export function buildGoods(executor: AppExecutor) {
  // 领域服务没有 ctx：脱离请求上下文时自动降级为空实现，调用点无需判空
  const log = resolveLogger('server/trade-router/goods')
  // ...
}
```

- 处于请求链路内（含 `db.transaction(...)` 回调）→ 拿到真实 logger，日志并入**同一条**宽事件；
- 脱离请求上下文（定时任务、后台脚本、单测）→ 返回空实现，日志静默跳过，不影响资金逻辑；
- 领域层**只记写操作**（资金变动、库存变动、状态变更、对账），读方法由上层模块服务的日志覆盖；
- 日志要加在**实现层**（如 `buildGoods` / `buildWallet`），不要加在 `xxxService(db)` 这类薄包装上，否则同一操作会记两次。

### 常用 API

| 方法 | 作用 | 备注 |
| --- | --- | --- |
| `log.set(obj)` | 合并上下文 | 最常用；对象递归合并，数组会追加 |
| `log.info(msg, ctx?)` | 记一条消息 | 进入 `requestLogs` |
| `log.warn(msg, ctx?)` | 警告 | 事件 level 提升为 `warn` |
| `log.error(err, ctx?)` | 记录错误 | 事件 level 提升为 `error`，`err` 的堆栈会写入事件 |
| `log.fatal(msg, ctx?)` | 致命错误 | 事件 level 提升为 `fatal`，**不受采样影响**，一定保留 |
| `log.setLevel(level)` | 手动指定等级 | 显式等级优先于 `warn`/`error` 的自动推导 |

### 记录错误（含源码位置）

```ts
const error = new AppError('common.notExist')

log.error(error, { demo: { action: 'getById', id } })
throw error
```

- `AppError` 在**构造时**就完成了堆栈还原与抛出位置提取（`error.location`），业务代码不需要额外调用；
- 主机制是 `server/plugins/source-maps.ts` 启用的 Node source map 支持（等价于 `--enable-source-maps`）；堆栈仍指向打包产物时，`AppError` 会用产物同目录的 `.map` 同步兜底一次。
- 抛出对象、i18n key、HTTP 状态码都保持原样，日志记录不影响接口行为；细节见[服务端业务错误](/docs/main/features/error-handling/server-apperror)。

## 落盘：目录、轮转与等级

事件最终写入 `.data/evlogs/app/YYYY-MM-DD.jsonl`（NDJSON，一行一条），实现在 `server/plugins/evlog-drain.ts`，**所有环境**都会注册。

| 配置 | 默认值 | 覆盖方式 |
| --- | --- | --- |
| 目录 | `.data/evlogs/app` | `NUXT_EVLOG_FS_DIR`（运行时）/ `EVLOG_FS_DIR`（构建期） |
| 最低写入等级 | 项目 `.env` 的 `LOG_LEVEL`，缺省 `info` | `NUXT_EVLOG_FS_LEVEL`（运行时）/ `EVLOG_FS_LEVEL`（构建期） |
| 单文件大小上限 | 5MB | 常量 `MAX_SIZE_PER_FILE` |
| 保留文件数 | 14 | 常量 `MAX_FILES` |

行为细节：

- 按天分文件；单日写满 5MB 会轮转为 `YYYY-MM-DD.1.jsonl`、`YYYY-MM-DD.2.jsonl`……上限 `.999`；
- 每次写入后清理，只保留最近 14 个 `.jsonl` 文件（按日期 + 序号从旧到新删）；
- 保留是按**文件数**不是按天数：14 大致相当于两周，但如果某天频繁轮转，会更快占用名额；
- 等级顺序为 `trace < debug < info < warn < error < fatal`，**低于阈值的直接丢弃，不落盘**；
- 目录不可写（例如只读文件系统的容器）时只警告一次并停用该 drain，业务请求不受影响；
- evlog 会在日志目录里写一个内容为 `*` 的 `.gitignore`，目录本身已在项目 `.gitignore`（`.data`）中忽略。

## 如何只记录错误

| 方案 | 改哪里 | 影响范围 | 写法 |
| --- | --- | --- | --- |
| ① 只让错误落盘 | 环境变量 | 仅文件 | `NUXT_EVLOG_FS_LEVEL=error` |
| ② 控制台也只留错误 | `nuxt.config.ts` 的 `evlog.sampling` | 控制台 + 文件 | `sampling: { rates: { info: 0, debug: 0, warn: 0 } }` |
| ③ 不记录某些 procedure | `evlog.exclude` | 控制台 + 文件 | `exclude: ['/api/trpc/demo.page*']` |
| ④ 只记录部分 procedure | `evlog.include` | 控制台 + 文件 | `include: ['/api/trpc/demo.remove*']` |
| ⑤ 按业务字段过滤 | drain 层自己判断 | 仅文件 | 见下方片段 |

`sampling.rates` 是**按级别设置保留百分比**（`info: 10` 表示保留 10%），`error` 默认 100%，`fatal` 永远保留。

方案 ⑤ 的写法（在 `server/plugins/evlog-drain.ts` 的 hook 里加判断）：

```ts
nitroApp.hooks.hook('evlog:drain', (ctx) => {
  // 只落错误与致命
  if (ctx.event.level !== 'error' && ctx.event.level !== 'fatal') return

  return fsDrain(ctx)
})
```

::div{.my-6.rounded-xl.border.border-primary/30.bg-primary/5.p-5}
**注意**：① 和 ⑤ 只影响文件落盘；控制台仍会打印全部事件，因为 evlog 的终端输出发生在 drain 之前。要让控制台也安静，用 ② / ③ / ④。
::

## 查看日志

```ts
import { readFsLogs, tailFsLogs } from 'evlog/fs'

// 历史：只看错误与致命
for await (const event of readFsLogs({ level: ['error', 'fatal'] })) {
  console.log(event.timestamp, event.path, event.error)
}

// 实时跟随：轮询新增行（默认 500ms），fromEnd 表示只看启动之后的事件
const ac = new AbortController()
for await (const event of tailFsLogs({ fromEnd: true, signal: ac.signal })) {
  console.log(event.path, event.status)
}
```

日志是 NDJSON，也可以直接用命令行看：

```bash
tail -f ".data/evlogs/app/$(date +%F).jsonl"
```

```powershell
Get-Content ".data\evlogs\app\$((Get-Date).ToString('yyyy-MM-dd')).jsonl" -Wait -Tail 20
```

## 常见问题

### 为什么某个接口没有埋点，日志里还是有它？

事件是**请求级**的：插件为每个命中 `include` 的请求创建并输出宽事件，业务代码只负责补充字段。这类骨架事件只有 method/path/requestId/status/durationMs/service 等元信息，没有业务上下文。

### 为什么 `service` 有的是 `xxdl-nuxt-admin`？

`service` 默认取 `evlog.env.service`。业务模块调用 `useLogger(event, 'server/xxx-router')` 后会被覆盖，所以 `demo` 模块显示 `server/demo-router`，尚未补第二参数的模块（如 `sysDictData`）仍是默认值。想统一到模块名，逐个模块补第二参数即可。

### 日志是什么时候写的？会不会拖慢接口？

在响应结束后写，不阻塞业务逻辑；错误堆栈的 source map 查找只发生在**创建错误对象**时，且 Node 会缓存已加载的 map。

### 怎么把运行日志和业务日志对齐？

用 `requestId`。evlog 宽事件里的 `requestId` 会被复用为 `sys_system_log` / `sys_login_log` 的 `traceId`，`AppError.requestId` 也是同一个值（实现见 `server/utils/requestId.ts`）。排查时先在业务日志里拿到 `traceId`，再到 `.data/evlogs` 里按 `requestId` 搜索，就能看到那次请求的完整宽事件（含还原后的错误堆栈与业务字段）。

### 生产也会写文件吗？

会，所有环境都走同一个 drain。生产部署请把 `.data/evlogs` 挂成 volume：Dockerfile 只 COPY `.output`，`.data` 不在镜像里；只读文件系统会让该 drain 自动停用（日志不再落文件，接口不受影响）。

### 生产日志里的堆栈是源码位置吗？

是。`server/plugins/source-maps.ts` 开启了 Node 的 source map 支持，`.output/server/chunks/**_/xxx.mjs.map` 会把帧还原成 `server/**/*.ts:行号`。前提是构建产物保留了 `.map` 文件；如果裁剪掉 `.map`，堆栈会退回打包产物路径。

### 想整体关掉运行时日志怎么办？

三种粒度：`evlog: { enabled: false }` 关掉全部；`include`/`exclude` 控制范围；删掉 `server/plugins/evlog-drain.ts` 只保留控制台输出。

## 相关文件

| 文件 | 职责 |
| --- | --- |
| `nuxt.config.ts` | `evlog` 模块配置（`env.service`、`include`）与 `evlogFsDir` / `evlogFsLevel` |
| `server/plugins/evlog-drain.ts` | 文件落盘、轮转、按等级过滤 |
| `server/plugins/source-maps.ts` | 开启 Node source map，让堆栈指向源码 |
| `server/utils/appError.ts` | 业务错误类；构造时还原堆栈并暴露 `location` 与 `requestId` |
| `server/utils/requestId.ts` | 读取 evlog 的 requestId，供 `traceId` 与 `AppError` 复用 |
| `server/demo-router/DemoService.ts` | 埋点与错误记录示例 |
