## 什么时候需要原生路由

tRPC 覆盖不了以下场景，需要直接写 Nitro 事件处理器：

| 场景 | 原因 |
| --- | --- |
| 文件上传 | `multipart/form-data` 与二进制流不适合走 tRPC 的 JSON 入参 |
| OAuth 回调 | 需要 302 重定向与第三方平台的查询参数，不是 JSON-RPC 语义 |
| 第三方 webhook | 外部系统按自己的格式推送，无法约定 tRPC 入参 |
| 流式响应 / 下载 | 需要直接写响应体或设置 `Content-Type` |

其余业务接口一律走 tRPC。

## 文件路由约定

| 目录 | 路由前缀 | 示例 |
| --- | --- | --- |
| `server/api/**` | `/api/**` | `server/api/system/oss/upload.post.ts` → `POST /api/system/oss/upload` |
| `server/api/system/user/avatar.post.ts` | `/api/**` | `POST /api/system/user/avatar` |
| `server/api/trpc/[trpc].ts` | `/api/trpc` | tRPC 统一入口 |
| `server/routes/**` | 无前缀 | `server/routes/auth/[platform].get.ts` → `GET /auth/:platform` |

方法由文件名后缀决定：`.post.ts` / `.get.ts` / `.put.ts` / `.delete.ts`，动态段用 `[param]` 方括号。

## 标准写法

原生路由不会自动获得 tRPC 的任何便利，鉴权、日志、错误翻译都需要手工接线。标准模板如下（以 `server/api/system/oss/upload.post.ts` 为例）：

```ts
export default defineEventHandler(async (event) => {
    const t = createServerT(event)                 // 服务端翻译
    const start = Date.now()
    const ctx = await createContext(event)         // 复用 tRPC 上下文
    const operationLog = apiOperationLog(ctx, 'sysOss.upload', start)
    let requestParams: Record<string, unknown> = {}

    try {
        await assertUploadPermission(ctx)          // 手工鉴权
        const parts = await readMultipartFormData(event)
        // ...业务处理
        await operationLog.success({ action: '...', requestParams, requestResult })
        return { success: true, data }
    } catch (error) {
        await operationLog.failure(error, { action: '...', requestParams })
        // 与 tRPC 的 errorFormatter 共用同一份映射，不要在这里手写三元判断
        const statusCode = error instanceof AppError
            ? resolveAppErrorStatus(error.i18nKey).httpStatus
            : 500
        const message = error instanceof AppError
            ? t(error.i18nKey)
            : error instanceof Error ? error.message : t('module.system.oss.uploadFailed')

        throw createError({ statusCode, statusMessage: message, message })
    }
})
```

### 六个固定环节

1. **`createContext(event)`**：拿到 `db`、`session`、`user`，与 tRPC 保持一致的数据访问方式。
2. **`apiOperationLog(ctx, module, start)`**：创建操作日志记录器；模块名建议用 `<模块>.<动作>` 形式（如 `sysOss.upload`、`sysUser.avatarUpload`）。
3. **手工鉴权**：见下一节。
4. **读入参与业务处理**：`readMultipartFormData` 后按字段名取 `part`，注意校验 `filename` 与 `data.byteLength`。
5. **成功路径记录日志**：`operationLog.success({ action, requestParams, requestResult })`，日志内容会写入 `sys_system_log`，其中的请求方法/路径/耗时由 `apiOperationLog` 自动补齐。
6. **失败路径映射错误**：先 `operationLog.failure(...)`，再用 `createError` 抛 HTTP 错误。

### 鉴权必须自己写

```ts
async function assertUploadPermission(ctx: Awaited<ReturnType<typeof createContext>>) {
    const user = ctx.user
    if (!user) {
        throw new AppError('auth.unauthorized')
    }
    if (user.isAdmin === 1) {
        return
    }
    const permissionCodes = await authService(ctx).listPermissionCodes(user)
    if (!permissionCodes.includes(crudPermissionCodes('system:oss').add)) {
        throw new AppError('auth.forbidden')
    }
}
```

规则与 `permissionMiddleware` 保持一致：未登录 → `auth.unauthorized`；管理员直通；其余用户通过 `authService(ctx).listPermissionCodes(user)` 比对权限码。

### 错误映射

与 tRPC 共用 `server/utils/appError.ts` 的 `resolveAppErrorStatus`（模板里的 `statusCode` 就取自它），避免两处规则漂移：

| 错误类型 | HTTP 状态 |
| --- | --- |
| `AppError('auth.unauthorized')` | 401 |
| `AppError('auth.forbidden')` / `AppError('system.demoReadonly')` | 403 |
| `AppError('common.notExist')` | 404 |
| 其他 `AppError` | 400 |
| 其他 `Error` | 500 |

文案统一用 `createServerT(event)(i18nKey)` 翻译——**原生路由不会调用 `errorFormatter`**，不翻译的话前端只能拿到 i18n key。`createServerT` 依据 `i18n_locale` cookie 选择语言，缺失时回退英文。

### 返回格式

原生路由不强制统一响应体，但当前上传类接口统一返回 `{ success: true, data }`，前端按该结构取值。

## 实例一：文件上传

`server/api/system/oss/upload.post.ts`：

- 入参：`multipart/form-data`，字段 `configId`（指定存储配置）与 `file`（文件本体）。
- 校验：缺少文件名或内容长度 → `AppError('module.system.oss.uploadFileRequired')`。
- 处理：`sysOssService(ctx).uploadFile({ configId, fileName, contentType, body })`，由 Service 完成 provider 上传与 `sys_oss` 记录落库。
- 权限码：`system:oss:add`。

`server/api/system/user/avatar.post.ts` 是更简的变体：只接收 `file`，额外校验 `contentType.startsWith('image/')`，存储配置取默认可用配置（`getDefaultUploadConfig()`），权限只要求登录。

## 实例二：OAuth 回调

`server/routes/auth/[platform].get.ts` 是原生路由的另一种形态——它不返回 JSON，而是全程使用 `sendRedirect`：

- 路由参数 `platform` 归一化后与支持列表比对，不支持则重定向 `/login?oauthError=auth.oauthPlatformUnsupported`。
- 从 `sys_oauth_config` 读取启用配置，缺 clientId/clientSecret 会记登录失败日志并重定向。
- 回调成功：建号/绑定 → `setUserSession` → `logRecorder(ctx).loginSuccess()` → 重定向 `/system/home`。
- 回调失败：`logRecorder(ctx).loginFailure(...)` → 重定向 `/login?oauthError=<key>`。
- 错误 key 通过 `toI18nKey(error)` 提取：`AppError` 取 `i18nKey`，普通 `Error` 取 `message`，兜底 `auth.oauthFailed`。

## 与 tRPC 的能力对照

| 能力 | tRPC 接口 | 原生路由 |
| --- | --- | --- |
| 登录校验 | 中间件自动完成 | 手工判断 `ctx.user` |
| 权限码校验 | `proc({ permission })` 自动完成 | 手工调用 `listPermissionCodes` 比对 |
| 数据权限 | `CommonRepo` 查询自动叠加 | 使用 `CommonRepo` 时同样生效，手写 SQL 需自行处理 |
| 入参校验 | `.input(schema)` | 手工校验并抛 `AppError` |
| 错误翻译 | `errorFormatter` 自动完成 | 必须 `createServerT(event)` 手工翻译 |
| 操作日志 | `loggerMiddleware` 自动记录 | 必须 `apiOperationLog` 手工记录 |
| demo 只读保护 | `proc({ readonly: true })` | 无自动保护，需要自行判断 |

## 常见错误

1. **忘记翻译**：直接 `throw createError({ statusMessage: 'module.system.oss.uploadFailed' })`，前端会原样显示 i18n key。
2. **状态码映射缺失**：把所有 `AppError` 都返回 400，前端无法区分未登录与无权限。
3. **忘记调用 `operationLog.failure`**：失败请求在系统日志中完全没有记录，排查困难。
4. **直接使用 tRPC 的错误结构**：原生路由的响应体是 `createError` 生成的 H3 错误，结构与 `TRPCFormattedError` 不同，前端需要分别处理。
5. **不校验文件大小与类型**：上传接口必须校验 `byteLength` 与 `contentType`，否则会把任意内容写入对象存储。
