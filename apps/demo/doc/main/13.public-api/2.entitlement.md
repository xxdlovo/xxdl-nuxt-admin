---
title: 能力与配额（entitlement）
description: 功能目录与等级矩阵的取值规则、服务端 assertEntitlement 与计量器注册、前端 useEntitlement 与 v-feature 的用法，以及 fail-closed 等硬约定。
---

entitlement 把「某个会员等级能不能用某功能、能建多少个」收敛成一张扁平的能力表：`feature_key → 数值`。服务端按同一张表强制校验，前端按同一张表隐藏或禁用入口，两边口径由 `#admin/shared/entitlement/types` 里的纯函数保证一致。

## 一、三个概念

| 概念 | 载体 | 谁维护 | 作用 |
| --- | --- | --- | --- |
| 功能目录 | `sys_member_feature` | 后台「功能与配额」页（`/system/member-feature`） | 登记系统里所有受控能力：`feature_key`、`kind`、`unit`、`default_value`、`resolver_key`、`admin_bypass`、`user_show` |
| 等级矩阵 | `sys_member_level_feature` | 后台「会员等级」页的「等级能力矩阵」按钮 | 每个等级 × 每项功能一个 `value`；没有行表示该等级未配置，回落到目录默认值 |
| 执行 | `resolveEntitlements` + `assertEntitlement` + `v-feature` | 框架 | 服务端拒绝、前端隐藏/禁用 |

`feature_key` 是**代码契约**：它同时出现在业务代码的 `assertEntitlement(ctx, 'student.max')` 与前端 `v-feature="'student.max'"` 里，因此**创建后不可修改**（服务端会拒绝改动并抛 `module.system.memberFeature.featureKeyImmutable`）。改名等于换一个能力，旧代码里的键会变成「未登记」，按 fail-closed 一律拒绝。

解析与执行是一条单链：

```text
sys_member_feature（目录：kind / default_value / resolver_key / admin_bypass / user_show）
        │
sys_member_level_feature（矩阵：level_id + feature_key → value，显式配置优先）
        │
sys_member（会员档案 → level_id）──→ resolveEntitlements(ctx)（每个请求一次，写入 ctx.entitlements）
        │
        ├─ 服务端：assertEntitlement(ctx, key, { delta, used }) → 放行 / 抛 AppError
        └─ 前端：auth.profile.entitlements → useEntitlement() / v-feature（仅影响体验）
```

优先级只有一条：**矩阵显式值 > 目录 `default_value` > 按类型的兜底值**（`switch` 兜底 1、`quota` 兜底 0；正常建表时 `default_value` 非空，兜底基本不会触发）。管理员绕过在合并阶段完成：`is_admin = 1` 且该功能 `admin_bypass = 1` 时，`switch` 置 1、`quota` 置 `-1`（不限）。

## 二、取值语义

### `kind = 'switch'`

| 值 | 含义 | 服务端行为 | 前端行为 |
| --- | --- | --- | --- |
| `0` | 关闭 | `assertEntitlement` 抛拒绝 | `can()` 为 false，`v-feature` 移除 / 禁用 |
| `1` | 开启 | 放行 | `can()` 为 true |
| 其它值 | 视为关闭 | 拒绝 | false |

### `kind = 'quota'`

| 值 | 含义 | 服务端判定 |
| --- | --- | --- |
| `-1` | 不限 | 直接放行，**不查计量器** |
| `0` | 不可创建 | `used + delta > 0` 恒成立，一律拒绝（管理员绕过时除外） |
| `N > 0` | 上限 N | `used + delta <= N` 放行，否则拒绝 |

配额判定依赖「已用量」。已用量有两个来源：调用方显式传 `used`，或由 `resolver_key` 指向的**计量器**现场统计。两者都没有时不会把用量当成 0 放行，而是 **fail-closed 拒绝**。

### 目录上的两个开关

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `admin_bypass` | `1`（默认） | 管理员（`sys_user.is_admin = 1`）绕过：开关置 1、配额置不限 |
| | `0` | 管理员也受限（如平台级资源总量） |
| `user_show` | `1`（默认） | 向端用户展示名称、额度与具体上限 |
| | `0` | **仅后端强制**：能力照常生效，`hiddenFeatures` 会带上该键，用户侧不显示名称 / 额度；被拒时只提示「当前操作不可用」，不暴露上限 |

隐藏项的「不显示」是展示层约定，不是放行——服务端仍然拦截。后台自己的「功能与配额」页不受 `user_show` 影响，仍然能看到完整配置。

## 三、服务端 API

统一从下面的入口导入：

```ts
import {
  assertEntitlement,
  assertEntitlements,
  hasEntitlement,
  remainingEntitlement,
  getEntitlement,
  listEntitlementResolvers,
  registerEntitlementResolver,
  defineUsageResolvers
} from '#admin/server/exports/entitlement'
```

`server/exports/` 不在 Nitro 的自动导入扫描范围内（只扫 `server/utils`、`server/api`、`server/middleware`、`server/plugins`、`server/routes`），所以门面**必须显式 import**，不会被全局自动注入，也不会和内部同名函数打架。

### `assertEntitlement(ctx, key, { delta?, used? })`

创建 / 使用受控能力前调用，是服务端唯一的强制入口。

| 项 | 说明 |
| --- | --- |
| 参数 `ctx` | tRPC Context；必须是**已登录**用户，且 `authMiddleware` 已把能力档案写进 `ctx.entitlements` |
| 参数 `key` | 功能目录里的 `feature_key` |
| 参数 `delta` | 本次操作占用的数量，默认 `1`（批量导入传行数） |
| 参数 `used` | 调用方已知的当前用量；不传则由 `resolver_key` / 功能键对应的计量器统计 |
| 返回 | `Promise<void>`；正常返回即放行 |
| 失败 | 未登录 → `auth.unauthorized`；未登记 → 拒绝；开关关闭 → 拒绝；配额超限 → `quotaExceeded`（`user_show = 1`）或通用 `denied`（`user_show = 0`）；配额缺少用量来源 → 拒绝 |

```ts
// 单个创建：默认 delta = 1
await assertEntitlement(ctx, 'student.max')

// 批量导入：一次占 N 个额度
await assertEntitlement(ctx, 'student.max', { delta: rows.length })

// 用量已经在上一步查出来了，直接传，省一次统计
await assertEntitlement(ctx, 'class.max', { used: currentClassCount, delta: 1 })
```

所有拒绝都会先记一条 warn 日志（含 `key` / `reason` / `userId`）再抛错，原因码有 `unregistered`、`switchOff`、`quotaExceeded`、`resolverMissing`，排查时按功能键过滤即可。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
`assertEntitlement` 只读 `ctx.entitlements`，**不会自己查库**。它依赖 auth 中间件在请求进入时解析好能力档案；在定时任务、脚本或没有该中间件的原生路由里直接调用，会因档案缺失按未登记拒绝。这类入口请先构造能力档案再调用，或改用普通业务查询。

登录态也一样：`ctx.user` 缺失时直接抛 `auth.unauthorized`，不会「因为拿不到身份」而放行。
::

### 其余方法

| 方法 | 用途 | 参数 | 返回 / 失败行为 |
| --- | --- | --- | --- |
| `assertEntitlements(ctx, keys[])` | 一次校验多个能力（例如「新建班级并导入学员」同时要求 `class.max` 与 `student.max`） | 能力键数组，逐个按 `delta = 1` 校验（顺序执行，便于定位第一个失败项） | 全部通过才返回；第一个不满足的键立即抛错，错误语义同 `assertEntitlement` |
| `hasEntitlement(ctx, key)` | 只读判断，用于分支展示或决定是否跳过可选动作；**同步、不查计量器** | `key` | `boolean`；`switch` 看是否 1，`quota` 看是否不限或 > 0；管理员按 `adminBypass` 返回 true；未登记 / 未登录返回 `false`，不抛错 |
| `remainingEntitlement(ctx, key, used?)` | 算配额剩余量，供展示或提前判断；**异步** | `key`；`used` 省略时用已注册计量器 | `Promise<number \| null>`。配额：不限返回 `null`，否则 `max(0, 上限 - used)`；开关：也返回 `null`（开关没有额度语义，判断开关用 `hasEntitlement`）；管理员绕过返回 `null`；未登录 / 未登记 / 缺计量器且没传 `used` 返回 `0`（fail-closed） |
| `getEntitlement(ctx, key)` | 读原始数值，不改判语义 | `key` | `number`；未登记 / 未加载按 0；不限返回 `-1` |
| `listEntitlementResolvers()` | 诊断与启动自检：列出已注册的计量器键 | 无 | `string[]`；后台保存配额功能时会用它校验 `resolver_key` 是否已注册 |

`hasEntitlement` 与 `remainingEntitlement` **只读**，不做拒绝、不记拒绝日志；真正拦截仍然必须调用 `assertEntitlement`。`hasEntitlement` 对配额只回答「额度是否 > 0 或 不限」，**不代表这次一定还能建一个**——配额是否用满只有异步断言知道。`remainingEntitlement` 受 `user_show` 影响吗？不受：隐藏只改变拒绝文案与展示，剩余量照常按真实上限计算，别把隐藏当成 0。

### 注册计量器

配额功能必须能拿到「当前已用多少」。计量器是宿主应用在启动时注册的函数：

```ts
// server/plugins/entitlement-usage.ts（宿主应用）
import { defineUsageResolvers } from '#admin/server/exports/entitlement'

export default defineNitroPlugin(() => {
  defineUsageResolvers({
    // 学生数：student.max / student.export 共用同一个计量器
    studentCount: async (ctx, userId) => {
      const [row] = await ctx.db
        .select({ count: sql<number>`count(*)` })
        .from(students)
        .where(eq(students.ownerId, userId))
      return Number(row?.count ?? 0)
    },
    classCount: async (ctx, userId) => {
      const [row] = await ctx.db
        .select({ count: sql<number>`count(*)` })
        .from(classes)
        .where(eq(classes.ownerId, userId))
      return Number(row?.count ?? 0)
    }
  })
})
```

- `registerEntitlementResolver(resolverKey, fn)` 是单个注册版本，`defineUsageResolvers({...})` 是批量注册版本；重复注册以最后一次为准。
- 计量器签名是 `(ctx, userId) => number | Promise<number>`，返回**当前已用数量**，不是剩余量。
- 多个功能可以共用一个计量器，例如 `student.max` 与 `student.export` 都配 `resolver_key = 'studentCount'`。守卫优先用 `resolver_key`，没填才回退功能键本身。
- 注册必须发生在进程启动阶段（`server/plugins/*.ts`），不要放在请求处理里；后台保存配额功能时会校验该键已注册，未注册直接报错。

## 四、前端 API

前端的判定与后端同源，但**只用于体验**：

```vue
<script setup lang="ts">
const { can, quota, remaining, isHidden, isUnlimited, levelName } = useEntitlement()
</script>
```

| 成员 | 说明 |
| --- | --- |
| `can(key)` | 功能是否可用：`switch` 看是否 1；`quota` 看是否不限或上限 > 0 |
| `quota(key)` | 配额原始值；`-1` 表示不限，未加载 / 未登记按 0 |
| `remaining(key, used)` | 剩余量；不限返回 `null`，否则 `max(0, 上限 - used)`；`used` 需由页面从列表接口拿 |
| `isHidden(key)` | 是否隐藏功能（`user_show = 0`），展示层据此不显示名称 / 额度 |
| `isUnlimited(key)` | 配额是否不限 |
| `levelName` | 当前会员等级名称；无档案 / 无等级时为 `null` |
| `profile` | 完整能力档案，一般不用直接读 |

注意 `can('student.max')` 对配额只表示「该等级配了额度」，**不代表这一次还能再建一个**——是否还有剩余要看 `remaining(key, used)`，最终仍以服务端 `assertEntitlement` 为准。

### `v-feature` 与 `v-feature:disable`

| 写法 | 不满足时 |
| --- | --- |
| `v-feature="'report.export'"` | 从 DOM 移除元素（与 `v-permission` 一致） |
| `v-feature="['class.max', 'student.max']"` | 数组表示**全部满足**才保留 |
| `v-feature:disable="'report.export'"` | 不移除，改为 `disabled` + `aria-disabled` + 提示文案 |

```vue
<template>
  <UButton v-feature="'student.max'" icon="i-lucide-plus">新增学员</UButton>
  <UButton v-feature:disable="'report.export'" icon="i-lucide-download">导出报表</UButton>
</template>
```

`v-feature` 与 `v-permission` **完全独立**，各自持有 effectScope 与元素状态，可以叠加在同一元素上；两者都满足时才可见 / 可用。profile 尚未加载时指令先隐藏元素，加载后再决定显示或移除，避免未授权入口闪现；能力未登记或档案缺失一律按不满足处理。

## 五、完整示例：学生系统

假设有两个受控能力：`student.max`（配额，学生数上限）与 `report.export`（开关，是否允许导出报表）。

**1）目录配置**（后台「功能与配额」页新建，或直接写表）：

| feature_key | name | kind | unit | default_value | resolver_key | admin_bypass | user_show |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `student.max` | 学员数量上限 | `quota` | 人 | `10` | `studentCount` | `1` | `1` |
| `report.export` | 报表导出 | `switch` | — | `0` | 空 | `1` | `0` |

再到「会员等级 → 等级能力矩阵」为各等级赋值：基础版 `student.max = 5`、`report.export = 0`；专业版 `student.max = 100`、`report.export = 1`。

**2）注册计量器**：见上一节 `server/plugins/entitlement-usage.ts`。

**3）服务端断言**：

```ts
// server/trade-router/modules/student/SysStudentService.ts（示意）
import { assertEntitlement } from '#admin/server/exports/entitlement'
import type { Context } from '#admin/server/trpc/context'

export function sysStudentService(ctx: Context) {
  return {
    async create(input: { name: string }) {
      await assertEntitlement(ctx, 'student.max') // 满额时抛 quotaExceeded
      // 断言通过后再写业务数据
      await ctx.db.insert(students).values({ ownerId: ctx.user!.id, name: input.name })
    }
  }
}
```

导出接口同理：`await assertEntitlement(ctx, 'report.export')`。`report.export` 的 `user_show = 0`，被拒时只返回「当前操作不可用」。

**4）前端用法**：

```vue
<script setup lang="ts">
const { can, remaining } = useEntitlement()
const used = ref(0) // 由学员列表接口返回的 total 赋值
</script>

<template>
  <div>
    <UButton v-feature="'student.max'" icon="i-lucide-plus">新增学员</UButton>
    <UButton v-feature:disable="'report.export'" icon="i-lucide-download">导出报表</UButton>
    <p v-if="can('student.max')">
      还可添加 {{ remaining('student.max', used) ?? '不限' }} 人
    </p>
  </div>
</template>
```

## 七、注意事项

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**1. 先注册计量器，再上线配额功能。** 配额功能没有计量器、调用方又没传 `used` 时会 fail-closed 拒绝——上线后表现是「所有请求都 403」，而不是「悄悄放行」。

**2. 未知 `feature_key` 一律拒绝。** 这是为了防拼错：写错键不会变成「无限制」，而是直接不可用。上线前用 `listEntitlementResolvers()` 与目录页对一遍。

**3. 隐藏功能仍然会拦截。** `user_show = 0` 只是不向端用户展示名称与额度，服务端照常拒绝；不要把它当成「对用户不可见所以可以放松校验」。

**4. `v-feature` 不是安全边界。** 它只操作 DOM，用户可以绕过；所有写接口必须在服务端调 `assertEntitlement`。反过来，前端 `can()` 返回 true 也不代表一定成功——配额是「已用量 + 本次增量」在服务端算的。
::
