billing 门面把余额领域服务收成四个函数：**扣钱、加钱、查余额、断言余额充足**。宿主业务不需要理解冻结状态机、流水表与赠送金批次，只要遵守一条规则——同一笔业务始终用同一个 `bizNo`。

本页的签名来自 `packages/admin-trade/server/exports/billing.ts`，导入方式是：

```ts
import {
  chargeBalance,
  creditBalance,
  getBalance,
  assertBalance,
  walletService,
  walletServiceIn,
  orderService,
  rechargeService,
  memberService,
  memberLevelOrderService,
  memberLevelOrderServiceIn
} from '#trade/server/exports/billing'
// 或从汇总出口一次性拿：'#trade/server/exports'
```

`server/exports/` 不在 Nitro 的自动导入扫描范围内，门面必须显式 import；这正是它作为「稳定 API」的边界——没有全局注入，也不会和内部同名函数冲突。

## 一、一次性扣款：`chargeBalance` 的定位

`chargeBalance` 是**一次性扣款**：内部在**同一个事务**里先 `freeze` 再 `confirm`，调用返回时余额已经实际减少，**不可撤销**。适合「钱已经确定要收」的场景：开通服务、扣次卡、结算一笔已完成的业务。

| 维度 | `chargeBalance`（一次性） | 两步：`freeze` → `confirm` / `release` |
| --- | --- | --- |
| 事务 | 冻结 + 确认在同一事务，不会留下悬挂冻结单 | 冻结与确认是两个独立动作，中间可能隔几分钟到几天 |
| 生效时间 | 立即实扣 | 冻结时只占可用余额，确认时才实扣 |
| 可撤销 | **不可撤销**（要退只能再走一笔入账） | 业务失败可 `release` 原样退回 |
| 适用 | 服务开通、次卡核销、已完成的结算 | 商城下单 → 支付 → 发货、在线支付等结果未定的场景 |
| 入口 | `chargeBalance` | `walletService(db).freeze` / `confirm` / `release` |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**余额扣款不会创建订单。**`chargeBalance` 只动钱包（余额、流水、赠送金批次），不写 `sys_order`、不扣库存、不核销优惠码，也不产生支付单。需要商品快照、订单状态、履约、IP 或在线支付时，请直接用 `orderService`——订单侧的冻结业务号就是订单号，与这里的 `bizNo` 共用同一把唯一键，自己用 `chargeBalance` 拼订单只会互相占用。

另外，`chargeBalance` 的 `bizNo` 是**全局唯一键**（不按用户隔离）。同一 `bizNo` 再次调用时，只有 `userId` 与 `amount` 都与首次一致才按幂等返回 `reused: true`；被别的用户或别的金额占用会抛 `system.repeatSubmit`，避免跨用户串账或按首次金额谎报本次金额。
::

## 二、API

| 函数 | 用途 | 幂等语义 | 失败行为 |
| --- | --- | --- | --- |
| `chargeBalance(ctx, input)` | 一次性扣款（冻结 + 确认同事务） | 同一 `bizNo` + 同一用户 + 同一金额 → `reused: true`，余额不变 | 余额不足抛 `module.system.member.balanceInsufficient` 且整事务回滚（未扣款）；`bizNo` 被他人 / 他额占用抛 `system.repeatSubmit` |
| `creditBalance(ctx, input)` | 余额入账（充值 / 补偿 / 退款 / 赠送） | 同一 `bizType + bizNo + account` → `reused: true`，不重复入账 | 非入账类 `bizType` 抛 `common.pleaseCheckValue`；金额非法抛 `module.system.member.amountInvalid` / `module.system.member.amountTooLarge` |
| `getBalance(ctx, userId)` | 读余额快照 | 纯读，无幂等概念 | 没有钱包行返回 `null`；空 `userId` 抛 `common.pleaseCheckValue` |
| `assertBalance(ctx, userId, amount)` | 断言可用余额充足 | 纯读，不做任何写入 | 不足抛既有 `module.system.member.balanceInsufficient`；非法金额抛金额错误 |

四个函数第一个参数都是 `ctx`。实现取 `ctx.db`；**脱离请求**（脚本、定时任务、启动任务）时回落到连接池，因此传 `{ db }` 或 `undefined` 也能工作，但正常业务代码应当传当前 tRPC / Nitro 上下文。

### `chargeBalance(ctx, { userId, amount, bizNo, bizType?, reason?, operatorId? })`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `userId` | `string` | 是 | 被扣款的用户；空字符串抛 `common.pleaseCheckValue` |
| `amount` | `string` | 是 | 金额（元，两位小数）。接受 `"12"` / `"12.00"`，归一后必须为正数且不超上限 |
| `bizNo` | `string` | 是 | 业务单号，**全局唯一**，长度 ≤ 64；空字符串抛 `common.pleaseCheckValue` |
| `bizType` | `WalletBizType` | 否 | 默认 `consume_confirm`；只影响流水展示与去重键，不能拿来区分同一笔业务 |
| `reason` | `string \| null` | 否 | 写进冻结单 `subject` 与流水备注，建议写清业务来源 |
| `operatorId` | `string \| null` | 否 | 操作人；用户自助扣款传 `null`，后台代操作传当前管理员 id |

返回：

```ts
{
  freezeId: string          // 本次冻结单 id（排查用）
  amount: string            // 归一后的实扣金额
  reused: boolean           // true = 这笔业务之前已扣过，本次未重复扣
  balance: BalanceSnapshot  // 扣款后的余额快照
}
```

`BalanceSnapshot` 的字段（注意不是领域层的 `WalletSnapshot`）：

| 字段 | 含义 |
| --- | --- |
| `recharge` | 充值金余额 |
| `gift` | 赠送金余额 |
| `frozenRecharge` | 冻结中的充值金 |
| `frozenGift` | 冻结中的赠送金 |
| `availableRecharge` | 可用充值金 = `recharge - frozenRecharge` |
| `availableGift` | 可用赠送金 = `gift - frozenGift` |

类型可直接从门面导入：`import type { BalanceSnapshot } from '#trade/server/exports/billing'`。

```ts
const result = await chargeBalance(ctx, {
  userId: ctx.user.id,
  amount: '29.90',
  bizNo: `SERVICE${requestId}`,
  bizType: 'consume_confirm',
  reason: '开通 XX 服务'
})

if (!result.reused) {
  // 首次扣款成功，继续做业务后置
}
```

### `creditBalance(ctx, { userId, amount, bizNo, account?, bizType?, reason?, operatorId? })`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `userId` | `string` | 是 | 入账用户；不存在钱包会先创建 |
| `amount` | `string` | 是 | 入账金额（元，两位小数），必须为正数 |
| `bizNo` | `string` | 是 | 业务单号，长度 ≤ 64 |
| `account` | `'recharge' \| 'gift'` | 否 | 默认 `recharge`；`gift` 入赠送金并建批次 |
| `bizType` | `WalletBizType` | 否 | 默认 `recharge`；**只接受入账语义**：`recharge` / `register_bonus` / `gift_system` / `gift_campaign` / `adjust` |
| `reason` | `string \| null` | 否 | 流水备注 |
| `operatorId` | `string \| null` | 否 | 操作人 |

返回 `{ reused: boolean, balance: BalanceSnapshot }`。

```ts
await creditBalance(ctx, {
  userId,
  amount: '10.00',
  bizNo: `REFUND${refundNo}`,
  bizType: 'adjust',          // 补偿 / 退款用 adjust；系统赠送用 gift_system
  reason: '订单退款补偿'
})
```

两个约束：

- `consume_confirm` / `level_open` / `gift_expire` 是**扣款语义**，传进来会抛 `common.pleaseCheckValue`，防止把「支出」记成「收入」破坏 `余额 = Σ(in) − Σ(out)` 的账实等式。
- 门面没有暴露赠送金的来源与过期时间：`account: 'gift'` 会按默认 `source = 'system'`、**永久有效**建批次。需要指定活动来源或过期时间时，直接调 `walletService(db).credit({ ..., giftSource, giftExpireAt })`。

### `getBalance(ctx, userId)`

```ts
const balance = await getBalance(ctx, ctx.user.id)
if (!balance) {
  // 该用户还没有钱包行（从未充值 / 从未扣款），不是 0 元快照
}
```

返回 `BalanceSnapshot | null`。`null` 表示**没有钱包行**；已有钱包但余额为 0 返回的是字段全为 `"0.00"` 的快照，两者含义不同。

### `assertBalance(ctx, userId, amount)`

```ts
await assertBalance(ctx, ctx.user.id, '29.90')
```

- 判定口径与冻结完全一致：可用 = `availableRecharge + availableGift`（即余额 − 冻结）。
- 纯读：不会建钱包、不会冻结、不会写任何流水。
- 不足抛既有 `module.system.member.balanceInsufficient`。
- 它是**预检，不是锁**：检查通过到真正扣款之间余额仍可能被别处花掉。真正的防线是 `chargeBalance` / `freeze` 里带守卫的条件更新，余额不足时条件更新影响 0 行并回滚。

## 三、`bizType` 取值

`bizType` 对应 `sys_member_balance_log.biz_type`，决定余额流水页的业务类型展示与统计口径。真实枚举来自 `domain/wallet/types.ts` 的 `WalletBizType`：

| 值 | 方向 | 含义 | 典型写入方 |
| --- | --- | --- | --- |
| `recharge` | 入 | 充值到账 | 充值回调 / `creditBalance` 默认值 |
| `register_bonus` | 入 | 注册赠金 | 注册赠送 |
| `gift_system` | 入 | 系统赠送 | 后台发放 / 系统补偿 |
| `gift_campaign` | 入 | 活动赠送 | 活动发券 / 赠送金活动 |
| `adjust` | 入 / 出 | 手工调账（加 / 减） | 后台调账；`creditBalance` 的补偿常用它 |
| `consume_confirm` | 出 | 业务消费确认实扣 | `chargeBalance` 默认值、订单余额支付确认 |
| `level_open` | 出 | 会员等级开通 / 续费扣款 | 等级开通单 |
| `gift_expire` | 出 | 赠送金过期扣减 | 赠送金过期任务 |

两点：

- `creditBalance` 只允许前五个（入账语义）；`chargeBalance` 接受整个 `WalletBizType`，但业务上应使用扣款语义的值（默认 `consume_confirm`）。
- `bizType` **参与幂等键**（`bizType:bizNo:account`），不是纯展示字段。同一笔业务重试时必须保持同一个 `bizType`，否则会被当成两笔不同业务写入两条流水。

## 四、幂等键约定

| 层 | 唯一键 | 冲突时 |
| --- | --- | --- |
| 冻结单 | `uk_member_freeze_biz(biz_no)` | `freeze` 先按 `bizNo` 回读，命中即 `reused: true` |
| 余额流水 | `uk_member_log_dedup(dedup_key)`，键为 `bizType:bizNo:account` | 撞键回滚，外层核实凭据后返回 `reused: true` |
| 赠送金批次 | `uk_member_gift_biz(biz_no)` | 赠送金入账的第二道闸门 |

约定：

1. **一笔业务只用一个 `bizNo`**，且重试时保持不变。不要每次请求重新生成（时间戳 / 随机数 / UUID），否则幂等完全失效。
2. `bizNo` 建议直接用业务单号：`ORDER202611200001`、`RECHARGE...`、`class_purchase:xxx`。长度上限 64，超长抛 `module.system.member.bizNoTooLong`。
3. 同一 `bizNo` 换用户或换金额会被拒绝（`system.repeatSubmit`）；**同一 `bizNo` 换 `bizType` / `account` 也会绕过流水去重**，所以这两个参数在重试时同样要保持一致。
4. 退款 / 补偿是**新业务**，必须用新的 `bizNo`（例如 `REFUND...`），不能拿原扣款单号反向入账。
5. `creditBalance` 的幂等键还包含 `account`：同一 `bizNo` 分别入充值金与赠送金会被视为两笔（这通常是刻意的，但要自己确认）。

## 五、完整示例：购买班级额度

宿主业务「购买班级额度」：先校验能力与余额，再一次性扣款，最后写自己的额度表。

```ts
// server/api/class-purchase/create.post.ts（示意）
import { assertBalance, chargeBalance } from '#trade/server/exports/billing'
import { assertEntitlement } from '#admin/server/exports/entitlement'

export async function purchaseClassQuota(ctx: any, input: {
  purchaseId: string
  amount: string
  quantity: number
}) {
  const userId = ctx.user.id
  // 由购买单主键生成，重试时保持不变
  const bizNo = `class_purchase:${input.purchaseId}`

  // 1) 能力校验（可选）：本次要新增 quantity 个班级
  await assertEntitlement(ctx, 'class.max', { delta: input.quantity })

  // 2) 余额预检：只读，不足直接报错，不产生任何写入
  await assertBalance(ctx, userId, input.amount)

  // 3) 一次性扣款：同事务冻结 + 确认，按 bizNo 幂等
  const { reused, balance, freezeId } = await chargeBalance(ctx, {
    userId,
    amount: input.amount,
    bizNo,
    bizType: 'consume_confirm',
    reason: `购买班级额度 x${input.quantity}`
  })

  if (reused) {
    // 重复提交：钱已经扣过，不要再加额度
    return { reused: true, balance }
  }

  // 4) 写自己的业务表
  await db.insert(classQuotaGrants).values({
    userId,
    bizNo,
    quantity: input.quantity,
    freezeId
  })

  return { reused: false, balance }
}
```

失败与回滚：

| 失败点 | 结果 | 处理 |
| --- | --- | --- |
| `assertEntitlement` 失败 | 未扣款、未写业务表 | 直接返回拒绝；调用方无需补偿 |
| `assertBalance` 失败 | 未扣款、未写业务表 | 返回余额不足；引导充值 |
| `chargeBalance` 失败 | 整事务回滚，**没扣款** | 直接报错即可；修复后可用同一个 `bizNo` 重试 |
| 第 4 步写业务表失败 | **钱已扣**（`chargeBalance` 已提交） | 需要补偿：用新 `bizNo` 调 `creditBalance` 退回，或把第 4 步与扣款放进同一个事务（见进阶） |

最后一行是宿主业务最容易忽略的：`chargeBalance` 自己是一个完整事务，**不会**和调用方后续的写入一起回滚。要求「扣款与发额度同生共死」时，不能只用 `chargeBalance`，而应把两步放进同一个数据库事务：

```ts
import { walletServiceIn } from '#trade/server/exports/billing'

await db.transaction(async (tx) => {
  const wallet = walletServiceIn(tx)
  const frozen = await wallet.freeze({ userId, bizNo, amount, ttlMinutes: 0 })
  await wallet.confirm({ freezeId: frozen.freezeId, bizType: 'consume_confirm' })
  await tx.insert(classQuotaGrants).values({ userId, bizNo, quantity })
})
```

`walletServiceIn(tx)` 绑定已有事务，由调用方保证提交 / 回滚；`walletService(db)` 则是每个写方法自己开事务。两者是同一份实现，只是事务边界不同。

## 六、注意事项

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**1. 赠送金优先混扣。**`chargeBalance` 内部的 `freeze` 按「先花可用赠送金、不足再落充值金」拆分（`walletService.freeze` 的既有规则），门面没有另立一套。想拿到本次扣款在两种账户上的拆分，用 `walletService(db).freeze` 的返回值（`giftAmount` / `rechargeAmount`）；`chargeBalance` 只返回扣款后的快照。

**2. 金额一律用字符串。**统一「元 + 两位小数字符串」（如 `"29.90"`），由 `normalizeMoney` 归一；不要在前端做浮点运算后传数字，也不要把「分」传进来。

**3. 并发下 `assertBalance` 与扣款之间存在竞态。**预检通过不代表扣款一定成功；真正的兜底是 `freeze` 的条件更新（`recharge_balance - frozen_recharge >= ?`），扣不到就影响 0 行并抛 `module.system.member.balanceInsufficient`。不要把 `assertBalance` 当成锁。

**4. 余额扣款不是订单。**要订单 / 商品 / 履约 / 在线支付，请走 `orderService`，不要用 `chargeBalance` 拼一套订单状态。

**5. `bizNo` 是全局唯一键。**不同用户也不能复用同一个业务单号；跨用户撞键会直接报错，而不是各自扣各自的。
::

## 七、进阶：直接使用领域服务

门面覆盖日常 90% 的场景；需要两步冻结、对账、订单链路、手工调账、优惠码或等级开通单时，直接用下面这些工厂（都已从 `#trade/server/exports/billing` 原样导出）：

| 导出 | 一句话用途 | 详细文档 |
| --- | --- | --- |
| `walletService(db)` | 独立事务的余额领域服务：`freeze` / `confirm` / `release` / `credit` / `adjust` / `getWallet` / `assertConsistency` | [余额支付与对账](/docs/main/payment-flow/consistency) |
| `walletServiceIn(tx)` | 绑定已有事务的同一套方法，用于「业务写入 + 资金变动」原子提交 | [余额支付（冻结 → 确认）](/docs/main/payment-flow/order-payment) |
| `orderService(db)` | 订单域唯一入口：下单、确认、取消、支付成功、交付、同步、超时关单（含库存 / 优惠码 / 履约） | [交易模块总览](/docs/main/trade/overview)、[订单链路](/docs/main/trade/orders) |
| `rechargeService(db)` | 充值单创建与到账（`credit(outTradeNo)`），充值回调的业务侧入口 | [充值到账](/docs/main/payment-flow/recharge) |
| `memberService(db)` | 会员档案、等级、优惠码解析与核销 | [交易模块](/docs/main/trade/overview)、[支付流程](/docs/main/payment-flow/overview) |
| `memberLevelOrderService(db)` | 会员等级开通 / 续费订单的创建、支付与同步 | [端到端支付流程](/docs/main/payment-flow/overview) |
| `memberLevelOrderServiceIn(tx)` | 上者的**事务内版本**：开通留痕与会员档案变更必须同事务时使用 | 同上 |

选择原则：

- 只是「扣一笔钱 / 加一笔钱」→ 门面的 `chargeBalance` / `creditBalance`。
- 需要「先占住钱、结果未定」→ `walletService(db).freeze`，再按结果 `confirm` 或 `release`。
- 需要订单、商品、库存、优惠码、履约、在线支付 → `orderService`，不要把钱包动作拆出来自己拼。
- 需要充值 → `rechargeService`；需要等级开通 → `memberLevelOrderService`。
