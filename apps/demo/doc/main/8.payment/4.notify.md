## 一、回调入口

回调地址是 `POST /api/pay/notify/{channel}`，实现文件 `server/api/pay/notify/[channel].post.ts`。它是**原生 Nitro 端点而不是 tRPC 接口**，原因写在文件头注释里：

- 平台无法携带会话，所以必须免登录，鉴权完全依赖渠道验签；
- 必须先读**原始报文**再解析（Stripe 等平台验签依赖原文）；
- 响应体由适配器决定（虎皮椒要求纯文本 `success`）。

处理链路：

```text
POST /api/pay/notify/{channel}
   ├─ getRouterParam(event, 'channel')          渠道平台标识
   ├─ readRawBody(event, 'utf8')                原始报文（先读原文）
   ├─ getRequestHeaders(event)                  请求头统一转小写、数组用逗号连接
   ├─ parseNotifyBody(rawBody, contentType)     解析成对象
   ├─ getRequestInfo(event)                     → { ip, userAgent }
   └─ payNotifyDispatcher(useDb(), { onPaid: (order) => dispatchPaidOrder(order, useDb()) })
          │      第二个参数注入业务后置分派（见「业务接入」页）
          └─ handleNotify(channel, { headers, rawBody, body },
                          { clientIp: ip, userAgent, source: 'notify' })
                 └─ setResponseStatus / setResponseHeader / 返回 body 字符串
```

`onPaid` 是回调链路上的业务扩展点：订单被置为已支付后（首次必然触发；同一事件若还没有成功日志，重试时也会补调一次），它按 `sys_pay_order.biz_type` 把事实分派给充值域 / 订单域。分派规则、注入约定与失败语义见[业务接入：bizType 分派](/docs/main/payment/integration)。

`parseNotifyBody()` 的分支规则：`content-type` 含 `application/json`、或报文以 `{` 开头 → `JSON.parse`（解析失败返回 `{}`）；其余一律按 `application/x-www-form-urlencoded` 用 `URLSearchParams` 解析。空报文返回 `{}`。

`{channel}` 是渠道平台标识（`xunhupay` / `mock` / 未来扩展的 `codepay`、`stripe`、`alipay_f2f`）。dispatcher 内部会 `trim().toLowerCase()` 归一化，适配器注册表也按小写键查找，所以大小写不影响路由。

## 三、handleNotify 的处理顺序

`server/trade-router/domain/pay/PayNotifyDispatcher.ts` 是真实回调与本地模拟回调**共用**的实现，`source` 只是入参。步骤与每一步的结论：

| # | 步骤 | 失败时的结论 | 响应 |
| --- | --- | --- | --- |
| 1 | 逐个候选渠道验签 | 全部抛 `PaySignError` → `invalid_sign`，`dedup_key = 'invalid:' + sha256(rawBody)`，`message = '签名校验未通过'` | 400 `invalid sign` |
| 1' | 验签过程抛出非 `PaySignError` 的异常 | `error`，`out_trade_no` 写空串 | 500 `error` |
| 2 | IP 白名单：`isIpAllowed(meta.clientIp, channel.ipAllowlist)` | `ip_blocked`，`message` 记录实际 IP | 403 `ip blocked` |
| 3 | 按 `out_trade_no` 找本地订单 | `order_not_found`，**只记日志** | 适配器的成功响应（200 `success`） |
| 4 | 金额 / 币种核对 `sameAmount()` + `currency === order.currency` | `amount_mismatch`，**绝不改单** | 适配器的成功响应（200 `success`） |
| 5 | `status === 'OD'` → 幂等置为已支付 | `duplicate` 或 `status_mismatch` | 适配器的成功响应 |
| 6 | 非 `OD` → 只同步平台状态，不改资金结论 | 恒为 `success` | 适配器的成功响应 |

几个容易踩错的点：

- **第 1 步的候选渠道是复数**。`listEnabledChannelsByCode(db, channelCode)` 取出同一平台标识下所有启用渠道，逐个 `verifyAndParseNotify`；库里一条都没有时再退到 `buildEnvFallbackChannel()`（仅当它正是同一个 `channelCode`）。第一个验签通过的就是来源渠道；`PaySignError` 只代表「这个渠道不匹配」，会继续试下一个，其他异常则直接中断。
- **第 3、4 步仍然回 200 `success`**。这是平台协议决定的：订单还没落库（例如回调先于本地事务提交）不该让平台无限重试，金额不一致更要靠日志与人工介入，而不是靠平台重推。所以**这两类问题的唯一线索就是 `sys_pay_notify_log`**，支付回调日志页要常看。
- **IP 白名单在验签之后校验**。伪造请求连签名都过不了，白名单是额外加固；`ip_allowlist` 留空表示不校验，解析规则是逗号 / 空格 / 换行 / 分号分隔。
- **日志写入失败一律不影响响应**。`writeLog()` 把 `logRepo.insert()` 包在 `try/catch` 里静默忽略——日志写失败若导致返回非 success，平台会不停重试，形成雪崩。

## 四、支付成功的两道幂等锁

第 5 步（`result.status === 'OD'`）是资金落账的关键路径，代码用两层保险：

```text
1) logRepo.existsByDedupKey(result.dedupKey)
     命中 → applyNotifyCountUpdate(orderId, { lastNotifyAt })
            + 写一条 duplicate 日志（status 用变更前的值）
            → 直接返回 duplicate（**不调 onPaid**：成功日志存在即说明业务后置已完成）

2) orderRepo.markPaidIfPending(orderId, {
       paidAt, lastNotifyAt,
       providerStatus, providerOrderId, transactionId,
       providerData: mergeProviderData(order.providerData, 'lastNotify', result.raw)
   })
     SQL: update sys_pay_order
          set status='OD', paid_at=…, notify_count = notify_count + 1, …
          where id = :id and status <> 'OD'
     affected > 0 → 调 onPaid（首次置为已支付，把事实交给业务域）
     affected === 0 → 本次事件还没有成功日志 → 也调一次 onPaid（至少一次语义，补做业务后置）
                      → 写 duplicate 日志（'订单已是已支付状态，本次回调仅计数'）→ 返回 duplicate

3) 写入带 dedup_key 的日志（唯一索引 uk_pay_notify_dedup 兜底）
   捕获 ER_DUP_ENTRY / errno 1062 → 补一条 duplicate 日志（'并发回调重复处理'）
```

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
两道锁的分工：**日志表的唯一键 `uk_pay_notify_dedup` 负责「同一个平台事件只处理一次」**，**`markPaidIfPending` 的条件更新 `status <> 'OD'` 负责「并发下只有一条 UPDATE 真正生效」**。

`dedupKey` 由适配器生成，规则必须是「同一事件重复投递得到相同值」。虎皮椒用的是 `out_trade_no:provider_status:transaction_id`（或平台单号），**刻意不包含 `time` / `nonce_str`**——虎皮椒重试会重新生成这两个字段，用报文摘要做键会导致去重失效。
::

第 3 步之后的结论判定：`processResult` 取 `previousStatus`（本次更新前的状态）。

| 变更前状态 | `processResult` | `message` |
| --- | --- | --- |
| `WP` / `FL` 等 | `success` | 无 |
| `CD` / `CL` | `status_mismatch` | `资金已到账，订单由 {旧状态} 置为已支付` |

也就是说：钱到账这个事实优先于本地「已取消 / 已关闭」的状态，订单最终一定是 `OD`，但日志明确标记出「状态回正」，方便对账时解释为什么一笔关闭过的订单变成了已支付。

## 五、置为已支付之后触发业务分派

把订单置为已支付只完成了「资金结论」这一半，业务单据（会员充值单 / 交易订单）还得各自推进。为此 dispatcher 暴露了扩展点 `PayNotifyOptions.onPaid`，它是**至少一次**语义：`markPaidIfPending` 影响行数大于 0（首次置为已支付）之后调一次；影响行数为 0 且本次事件还没有成功日志时（说明后置可能没做完，或订单是被主动查询推进的）再补调一次。回调路由注入 `dispatchPaidOrder(order, useDb())`，再按 `biz_type` 分派——`recharge` 走 `rechargeService(db).credit()`，`order` 走 `orderService(db).markPaid()`，其它取值（含 `test`）保持 no-op。

`onPaid` 抛错会中断本次回调并返回 5xx，平台会重试；由于成功日志是在 `onPaid` 之后写的，重试时虽然支付单已是 `OD`，dispatcher 仍会在 duplicate 分支**再调用一次 `onPaid`**（至少一次语义，`PayNotifyDispatcher.ts:306-334`），所以平台重试本身就是业务后置的一条补偿路径。但幂等仍是硬要求；平台放弃重试、回调根本没到达时，只能靠补偿任务（充值侧 `rechargeRetry` / `member:reconcile`、订单侧 `order:expire-close` 的补做分支）。

完整的注入方式、两侧业务的幂等实现、主动同步与补偿路径见[业务接入：bizType 分派](/docs/main/payment/integration)。

## 六、非支付成功通知

`result.status !== 'OD'` 时走第 6 步，只做「平台状态同步 + 计数」，不改变资金结论：

```ts
const statusChange = canApplyStatusChange(order.status, result.status)

await orderRepo.applyNotifyCountUpdate(order.id, {
  lastNotifyAt: now,
  providerStatus: result.providerStatus ?? order.providerStatus,
  ...(statusChange ? { status: result.status } : {}),
  ...(statusChange && result.status === 'CD' ? { cancelledAt: now } : {})
})

await writeLog(resultLog)   // process_result = 'success'
```

`applyNotifyCountUpdate` 会把 `notify_count + 1`、刷新 `last_notify_at`；是否改 `status` 由领域层的 `canApplyStatusChange` 决定（规则见[下单、查询与状态流转](/docs/main/payment/orders)），mapper 只负责把值写下去。

## 七、本地模拟回调

真实回调需要公网可达的 `notify_url`，本地开发收不到。为此 dispatcher 暴露了 `simulatePaid(orderId, meta)`，测试页的「模拟支付成功」按钮走它：

```text
sysPayTest.simulatePaid(id)                       权限 system:payTest:simulate
   ├─ isSimulateEnabled() 为假 → AppError('module.system.payTest.simulateDisabled')
   └─ dispatcher.simulatePaid(orderId, meta)
        ├─ 订单不存在                     → common.notExist
        ├─ order.bizType !== 'test'       → module.system.payTest.simulateOnlyTest
        ├─ isPaidStatus(order.status)     → module.system.payTest.alreadyPaid
        ├─ 定位渠道 listEnabledChannelsByCodeForOrder()
        │     优先 order.channelId 命中的启用渠道 → 其次该渠道类型的第一条 → 再退到环境变量兜底
        ├─ provider.buildSimulatedNotify 未实现 → module.system.payTest.simulateUnsupported
        ├─ 适配器用配置里的密钥现算签名，造出与真实回调同构的报文
        └─ handleNotify(channelCode, input, { source: 'simulate' })
```

关键设计是：**模拟回调不走近路**。它复用同一个 `handleNotify`，因此验签、IP 白名单、金额核对、幂等、日志与真实回调完全一致——测试通过就意味着这条链路真的能用，而不是「测试专用逻辑」。

`isSimulateEnabled()`（`server/trade-router/modules/payTest/SysPayTestService.ts`）的判定：

| `NUXT_PAY_SIMULATE_ENABLED` | `NODE_ENV` | 是否允许 |
| --- | --- | --- |
| `true` | 任何环境 | 允许 |
| 未设置 / 其他值 | `production` | **不允许**（生产必须显式打开） |
| `false` | 任何环境 | 不允许 |
| 未设置 / 其他值 | 非 `production` | 允许 |

适配器侧的报文构造：`mock` 用 `merchant_id` + `sign_key` 造 HMAC-SHA256 签名；`xunhupay` 用 `appid` + `secret` 造 MD5 签名，并带上 `trade_order_id` / `total_fee` / `status: 'OD'` 等字段。两者的 `raw_body` 都是 `application/x-www-form-urlencoded` 形态，与真实回调一致。

## 八、主动查询产生的日志

主动查询（`PayOrderService.queryPayment`）在**状态真正变化**时会写一条 `source='query'` 的日志，字段上与回调日志的区别：

| 字段 | 查询日志的取值 | 原因 |
| --- | --- | --- |
| `source` | `query` | 与平台回调区分 |
| `dedup_key` | `null` | 查询没有「平台事件」概念；唯一索引允许多个 `NULL`，不会互相冲突 |
| `sign_valid` | `0` | 没有验签环节 |
| `process_result` | `success` | 状态已按保护规则推进，不存在失败语义 |
| `message` | `主动查询：{旧状态} → {新状态}` | 直接看出这一次推进了什么 |
| `raw_body` | 查询响应的 JSON | 排障用 |

写入被 `try/catch` 包住并静默忽略：查询日志写失败不能影响状态推进。另外，测试页轮询调用的 `sysPayTest.syncStatus` 声明了 `log: false`，所以**不写 `sys_system_log` 操作日志**，回调日志表里也只会在状态变化时出现记录。

## 九、排查入口

| 现象 | 先看哪里 |
| --- | --- |
| 平台一直重试 | 响应体不是它要求的格式：`buildNotifyResponse` 的 `content_type` / `body`（虎皮椒要求纯文本 `success`） |
| 回调没进来 | `notify_url` 是否公网可达（订单详情里的 `notify_url` 就是本单实际使用的地址） |
| 订单没变成已支付 | `sys_pay_notify_log` 里该 `out_trade_no` 的记录与 `process_result` |
| 有日志但状态没变 | 该笔订单的 `provider_data.lastNotify` 与 `provider_status`，对照 `statusMap` 的映射表 |
| 找不到日志 | 验签失败 / 处理异常的记录 `out_trade_no` 是空字符串，需要按 `channel_code` + 时间范围筛 |
| 疑似伪造请求 | `process_result = 'invalid_sign'` 且 `dedup_key` 以 `invalid:` 开头，同报文只会留一条 |

支付记录页详情里的「回调与查询记录」时间线（`sysPayOrder.notifyLogs`）与支付回调日志页查的是同一张表。
