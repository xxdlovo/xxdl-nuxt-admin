支付模块只管「钱」，不管「货」。一笔资金结论要变成「会员充值到账」或「交易订单完成」，靠的是支付单上唯一的业务线索——`sys_pay_order.biz_type`。本页讲清这条分派链路、两侧业务各自的幂等实现，以及回调失败后靠什么兜底。

## 一、分派入口

唯一入口是 `server/trade-router/domain/pay/PaidHandlers.ts` 的 `dispatchPaidOrder(order, db)`：

```text
POST /api/pay/notify/{channel}                      免登录回调路由
   └─ payNotifyDispatcher(useDb(), { onPaid }).handleNotify(...)
        ├─ 成功日志已存在（dedup_key 命中）→ duplicate，**不再分派**
        ├─ markPaidIfPending 影响行数 > 0（首次置为已支付）→ onPaid(paidOrder)
        └─ 影响行数 === 0 且本次事件没有成功日志 → onPaid(latestOrder)（补做一次）
             └─ dispatchPaidOrder(order, db)   server/trade-router/domain/pay/PaidHandlers.ts
                  ├─ bizType === 'recharge' → rechargeService(db).credit(order.outTradeNo, null)
                  ├─ bizType === 'order'    → orderService(db).markPaid(order.outTradeNo, null)
                  └─ 其它取值（含 'test'）   → 直接 return：只把支付单置为已支付，不做业务后置
```

| 代码位置 | 内容 |
| --- | --- |
| `PaidHandlers.ts:26-27` | 常量 `PAY_BIZ_TYPE_RECHARGE = 'recharge'`、`PAY_BIZ_TYPE_ORDER = 'order'` |
| `PaidHandlers.ts:29-43` | `dispatchPaidOrder(order: PayOrderRow, db: AppDb): Promise<void>`，三分支见上 |
| `PaidHandlers.ts:42` | 未知取值的注释即约定：**不抛错**，保持「只标记支付成功」的历史行为（支付测试单依赖它） |

`biz_type` 的真实取值与能不能被测试页模拟：

| `biz_type` | 写入方 | 支付成功后的行为 | 测试页「模拟支付成功」 |
| --- | --- | --- | --- |
| `test` | 扫码支付测试页 `sysPayTest.create`（也是列默认值） | no-op，只把支付单置为已支付 | ✅ 允许 |
| `recharge` | 会员自助充值 `sysMember.myRecharge` → `RechargeService.create` | `rechargeService(db).credit()`，充值金 / 赠送金入账 | ❌ 报 `module.system.payTest.simulateOnlyTest` |
| `order` | 交易订单在线支付 `sysOrder.myCreate` → `OrderService.create` | `orderService(db).markPaid()`，订单置为已完成 | ❌ 同上 |
| 其它自定义取值 | 未来业务 | no-op，需要先在 `dispatchPaidOrder` 里加分支 | ❌ 同上 |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**只有 `test` 允许模拟支付。**`simulatePaid()` 在定位订单后立刻校验 `order.bizType !== 'test'` → `module.system.payTest.simulateOnlyTest`（`PayNotifyDispatcher.ts:402-404`），所以 `recharge` / `order` 的单据**不能**用「模拟支付成功」按钮走捷径，必须走真实渠道回调或主动同步。

另外，测试页的 dispatcher 是 `payNotifyDispatcher(ctx.db)`，**没有注入 `onPaid`**（`server/trade-router/modules/payTest/SysPayTestService.ts:38`）；即使将来放宽 `bizType` 限制，测试页也不会触发业务后置。

还有一处细节：`sysPayTest.create` 的入参本身允许自带 `bizType`（`shared/system/payTest/input.ts:18`，留空才回落到 `'test'`，见 `SysPayTestService.ts:115`），所以用测试页也能造出 `recharge` / `order` 的支付单。这类单既不能模拟支付，一旦真的走渠道付掉，回调会按 `bizType` 去找一个并不存在的业务单号，抛 `module.system.memberRecharge.notFound` / `module.system.order.notFound` 并返回 5xx——**测试时不要随手填 `bizType`**。
::

## 二、注入口：onPaid

```ts
// server/trade-router/domain/pay/PayNotifyDispatcher.ts
export type PayNotifyOptions = {
  onPaid?: (order: PayOrderRow) => Promise<void>
}

export function payNotifyDispatcher(executor: AppExecutor, options: PayNotifyOptions = {}) { … }
```

回调路由的注入方式（`server/api/pay/notify/[channel].post.ts:66-74`）：

```ts
const outcome = await payNotifyDispatcher(useDb(), {
  onPaid: async (order) => {
    await dispatchPaidOrder(order, useDb())
  }
}).handleNotify(channelCode, { headers, rawBody, body }, { clientIp: ip, userAgent, source: 'notify' })
```

`onPaid` 是**至少一次**语义，两个调用点（`PayNotifyDispatcher.ts:281-366`）：

| 顺序 | 代码位置 | 说明 |
| --- | --- | --- |
| 1 | `:281-295` | `logRepo.existsByDedupKey(result.dedupKey)` 命中 → 只计数 + 写 duplicate 日志 → 直接返回，**不调用 `onPaid`**（成功日志是在 `onPaid` 之后写的，日志存在即可推断业务后置已完成） |
| 2 | `:297-304` | `orderRepo.markPaidIfPending(order.id, …)`，SQL 带 `where id = :id and status <> 'OD'` |
| 3 | `:306-334` | 影响行数 `=== 0` → 先 `findById` 重读、`await options.onPaid(latestOrder)`（`:316-320`）**补做一次**，再写 duplicate 日志并返回 duplicate |
| 4 | `:340-345` | 影响行数 `> 0`（首次置为已支付）→ 先 `findById` 重读、`await options.onPaid(paidOrder)` |
| 5 | `:347-366` | 写带 `dedup_key` 的 `success` / `status_mismatch` 日志（两个调用点都在它之前） |

四点约定：

- **两处都会调用 `onPaid`，业务侧必须幂等**。表中第 4 条是「首次置为已支付」；第 3 条无法区分「渠道重复投递、后置早已完成」与「上次置为已支付后业务后置失败 / 订单是被主动查询推进的」，所以一律再告知业务域一次——已完成时各业务侧会命中自己的唯一键 / 状态守卫，代价只是一次读。
- **只有成功日志存在时才会跳过**。日志写入在 `onPaid` 之后，因此「日志存在」等价于「后置已走完」；反过来 `onPaid` 抛错时日志（含 duplicate 日志）没写成，下一次同样的回调就会再次分派。
- **回调拿到的是重读后的订单行**（`:317` / `:342`），`status` 已是 `OD`，`biz_type` / `out_trade_no` 与库内一致。
- **与「支付单置为已支付」不在同一事务**。`dispatchPaidOrder` 收到的是 `AppDb`（连接），`rechargeService(db)` / `orderService(db)` 各自 `db.transaction()` 提交（`RechargeService.ts:357-368`、`OrderService.ts:554-556`），所以业务写入失败不会回滚支付单。

## 三、失败语义

`onPaid` 抛错会中断本次回调处理，回调路由没有 `try/catch`，异常冒泡给 Nitro 后返回 **5xx**，平台据此重试——而重试**确实会重新触发 `onPaid`**，平台重试本身因此也算业务后置的一条补偿路径。注意下面三点：

| 事实 | 后果 |
| --- | --- |
| 抛错发生在写日志（成功日志 `:348` / duplicate 日志 `:322`）之前 | 这次回调在 `sys_pay_notify_log` 里**完全不留痕**，只能从服务端错误日志排查；也正因为没有成功日志，重试时不会被 `existsByDedupKey` 短路 |
| 重试时支付单已是 `OD`，`markPaidIfPending` 影响行数为 0 | 走 `:306-334` 的 duplicate 分支，但该分支**会再调用一次 `onPaid`**（至少一次语义）；补齐后写 duplicate 日志并返回 200 |
| 业务侧写入是独立事务 | 业务单可能停在「未完成」，需要能扫出「支付单已支付但业务单未完成」的补偿路径 |

因此业务侧的硬要求是两条：**幂等**（唯一键 / 条件更新，重复调用不重复生效）+ **可补偿**（平台放弃重试或回调根本没到达时，有办法把漏掉的单捞出来补做，见第七节）。

常见抛错来源：支付单对应不到业务单（`module.system.memberRecharge.notFound`、`module.system.order.notFound`）、业务单已不是待支付（`module.system.order.notPayable`）。这些都是「数据不一致」而不是「偶发失败」，平台重试解决不了，主要价值是让问题尽早暴露（错误日志 + 支付单已 `OD` 而业务单未完成）。

## 四、业务侧发起支付

业务方不直接写 `sys_pay_order`，而是调 `payOrderService(db).createPayment(input, meta)`，把业务单号当商户订单号传进去：

```ts
// 会员充值：server/trade-router/domain/wallet/RechargeService.ts:132-141
const order = await payments.createPayment({
  outTradeNo,                        // 业务单号（buildOutTradeNo('RCH')），与充值单一一对应
  amount: payAmount,                 // 实付金额（已扣优惠码）
  subject: `会员充值 ${amount} 元`,
  bizType: 'recharge',               // ← 分派的唯一依据
  attach: `recharge:${rechargeId}`,  // 业务行主键的冗余快照，只用于排查/透传
  notifyUrl: input.notifyUrl ?? null,
  origin: input.origin ?? null       // 渠道未配 notify_url 时按 origin 推导回调地址
}, { operatorId })
```

```ts
// 交易订单在线支付：server/trade-router/domain/order/OrderService.ts:650-658
const payOrder = await payments.createPayment({
  outTradeNo: created.orderNo,       // 订单号即商户订单号
  amount: created.payAmount,
  subject: `订单 ${created.orderNo}`,
  bizType: 'order',
  attach: `order:${created.orderId}`,
  notifyUrl: input.notifyUrl ?? null,
  origin: input.origin ?? null
}, { operatorId: input.operatorId ?? null })
```

字段约定：

| 字段 | 约定 |
| --- | --- |
| `outTradeNo` | 就是业务单号（充值单 `RCH…`、订单号 `ORD…`），两侧都有唯一键，支付单与业务单靠它一一对应 |
| `bizType` | 分派依据，`dispatchPaidOrder` 只读它；会落进 `sys_pay_order.biz_type`（可用 `idx_pay_order_biz_type` 筛选） |
| `attach` | 形如 `recharge:{id}` / `order:{id}`，业务行主键的冗余，**分派不读它**，只用于排障 |
| `amount` | 实付金额（已扣优惠码 / 已按等级价计算），不是原价 |
| `origin` | 回调地址推导兜底；订单侧由 tRPC 层用 `getRequestURL(ctx.event).origin` 传入 |

## 五、各业务侧的幂等与结果

### 充值（`recharge`）

`RechargeService.credit(outTradeNo, operatorId)` 是**唯一的到账入口**，三重幂等保证：

| 保证 | 落点 |
| --- | --- |
| 充值单唯一键，`out_trade_no` 不重复 | `uk_member_recharge_out`（`server/drizzle/schema/system/memberRecharge.ts:31`） |
| 余额流水唯一键，同一业务事件只入账一次 | `uk_member_log_dedup`（`memberBalanceLog.ts:28`），键由 `buildDedupKey()` 生成，形如 `recharge:{outTradeNo}:recharge`（`wallet/utils.ts:97-99`） |
| 条件更新，并发下只有一条 UPDATE 生效 | `rechargeRepo.markCredited()` 的 `where status <> 'OD'`（`rechargeRepo.ts:47-72`） |

到账动作（`RechargeService.ts:183-240`）：

1. `findByOutTradeNo` 查不到 → `module.system.memberRecharge.notFound`；已经是 `OD` → 直接返回 `reused: true`；
2. `markCredited` 影响行数为 0 → 并发下已被其他请求到账，返回 `reused: true`；
3. 写**充值金**流水（`account='recharge'`，`bizNo = outTradeNo`）；
4. 赠送金 `> 0` 时写**赠送金**流水（`bizNo = {outTradeNo}:gift`，独立幂等键），并在 `sys_member_gift_grant` 建一条赠送金批次（`source='campaign'`，`WalletService.ts:351-375`）；
5. 充值单占用了优惠码时核销（`markCouponUsed`）。

### 交易订单（`order`）

`OrderService.markPaid(orderNo, operatorId)` → `markPaidTx`（`OrderService.ts:395-428`）：

| 行为 | 说明 |
| --- | --- |
| `orderRepo.markCompleted` 带 `where status='WP'` | 只生效一次；影响行数 0 → `OrderAlreadySettledError` → 外层重读后按「已处理」返回 `reused: true`（`OrderService.ts:579-593`） |
| **不动余额** | 在线支付的钱来自渠道，不是冻结的余额；`markPaidTx` 不调 `wallet.confirm` |
| 核销优惠码 + 累加销量 | `members.markCouponUsed()` + `goods.increaseSales()` |
| 服务类商品仍是 `fulfill_status = 'pending'` | 下单时写入（`OrderService.ts:236`），等后台「交付」把 `fulfill_status` 推到 `delivered` |
| 订单已不是 `WP`（已完成 / 已关闭） | 已完成直接幂等返回；已关闭抛 `module.system.order.notPayable` |

### 测试与未知取值

| `biz_type` | 行为 |
| --- | --- |
| `test` | no-op：只把支付单置为已支付，不碰任何业务表 |
| 自定义未知取值 | no-op，同样是「只标记支付成功」；接入新业务时必须自己加分支（见第八节） |

## 六、主动同步：不走回调，但复用同一幂等路径

回调依赖公网可达，本地开发与内网环境常常收不到，所以充值侧与订单侧各有一条主动同步入口。它们**不经过 `dispatchPaidOrder`**，而是直接调用业务域方法——与回调链路复用同一个幂等更新（`RechargeService.credit` / `OrderService.markPaid`），因此不会重复生效。

| 入口 | 落点 | 行为 |
| --- | --- | --- |
| `sysMember.myRechargeSync` | `SysMemberService.ts:315-390` | 本地充值单已终结（非 `WP`）→ 直接回报本地状态；渠道支付单 `OD` → `RechargeService.credit`；支付单 `CL` / `FL` → **反向关闭充值单**并把原因写进 `fail_reason`；仍未支付 → 回报本地 `WP` 让页面继续轮询 |
| `sysOrder.mySync`（会员） | `SysOrderService.ts:287-294` → `OrderService.sync` | 渠道 `OD` → `markPaid`；`CL` / `FL` → 就地自愈关单；其它 → `changed: false` |
| `sysOrder.sync`（后台「同步状态」） | `SysOrderService.ts:190-195` → `OrderService.sync` | 同上，`operatorId` 取当前登录用户 |

`OrderService.sync` 的分支（`OrderService.ts:790-846`）：

```text
sysOrder.sync(orderId)
  ├─ 订单不是 WP / 没有关联支付单 → 直接返回 changed: false
  ├─ payOrderService.queryPayment(payOrderId)     渠道查询（含 3 秒节流与过期兜底）
  ├─ 支付单 CL / FL → cancelOrder 就地自愈关单（释放冻结 → 释放优惠码 → 回滚库存 → 置 CL）
  ├─ 支付单 OD     → markPaid(orderNo)            与回调同一条幂等路径
  └─ 其它          → changed: false（仍待支付）
```

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
主动同步与回调的分工写在 `PaidHandlers.ts:12-18` 的头部注释里：`dispatchPaidOrder` **只由回调路由**通过 `onPaid` 调用；主动同步（`OrderService.sync` / `SysMemberService.myRechargeSync`）各自直接调业务侧幂等方法，因为此时已经知道业务类型，不必再按 `biz_type` 分派。两条链路复用同一个条件更新（`orderRepo.markCompleted` 的 `where status='WP'`），结果一致。
::

## 七、补偿与对账

| 手段 | 入口 | 权限 / 调度 | 扫描条件 | 动作 |
| --- | --- | --- | --- | --- |
| 未到账充值补偿（手工） | `sysMemberBalanceLog.rechargeRetry` | `system:memberBalanceLog:reconcile`（`modules/memberBalanceLog/index.ts:16,57`） | 充值单 `status='WP'` **且** 关联支付单 `status='OD'`，单次 50 条 | 逐单调 `RechargeService.credit`，返回每笔的结果 |
| 每日对账任务 | `member:reconcile` | 每天 03:00（`0 0 3 * * *`） | 全量钱包一致性校验 + 同样的待补偿充值单，单次 200 条 | `walletService.assertConsistency()` + `rechargeService.retryPending()` |
| 超时关单任务 | `order:expire-close` | 每 5 分钟（`0 0/5 * * * *`） | 订单 `status='WP'` 且 `expire_at <= now`，单次 200 条 | **先读本地支付单**：已是 `OD` → 不关单，改为 `markPaid` 补做业务后置（计入 `recoveredCount`）；否则释放冻结 → 释放优惠码 → 回滚库存 → 置 `CL` |

两个任务的 handler 都在 `server/sys-router/job/handlers.ts`（`member:reconcile` 在 `:130-152`，`order:expire-close` 在 `:163-170`），调度定义在 DDL 里（`doc/main/mysql-ddl-member-balance.sql:343`、`doc/main/mysql-ddl-goods-order.sql:174`）。补偿用的扫描 SQL 是 `rechargeRepo.listPendingWithPaidOrder()`（`rechargeRepo.ts:122-139`），它就是「支付单已支付但业务单未完成」的具体实现。

`order:expire-close` 的返回值是 `OrderExpireCloseResult`（`domain/order/types.ts:94-100`）：

| 字段 | 含义 |
| --- | --- |
| `scanned` | 本次扫到的过期未支付订单数 |
| `closedCount` | 真正被关成 `CL` 的数量 |
| `recoveredCount` | **本地支付单已 `OD`、被补做业务后置而没关单的数量**（异常信号：出现即说明有业务后置没走完——回调 `onPaid` 失败，或订单是被主动查询推进的） |
| `failures` | 逐单失败明细（`{ orderNo, message }`），单笔失败不影响其余订单 |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**订单侧的兜底是「不误关 + 补做后置」，不是「关掉后靠 sync 自愈」。**超时任务在关单前先看**本地支付单**（`OrderService.ts:741-787`）：如果它已经是 `OD`（回调到了但业务后置没做完，或订单是被主动查询推进的），这笔钱其实收到了，于是走 `markPaid` 把订单正常推进到 `OD` 并计入 `recoveredCount`，不再关单。

**残留风险收紧为一种：回调从未到达、且本地支付单仍是 `WP`。**任务只读本地状态、不发渠道请求（一次最多扫 200 单，逐单外呼不可接受），所以这种情况发现不了，订单会在 `expire_at`（订单侧 TTL 默认 15 分钟，`ORDER_TTL_MINUTES`）后被正常关成 `CL`；此后 `sysOrder.sync` 因订单已不是 `WP` 直接返回 `changed: false`（`OrderService.ts:797-804`），不会再自愈。更棘手的是这类单若之后又收到迟到的回调：`markPaidIfPending` 会先把支付单置为 `OD`，紧接着 `markPaid` 因订单已 `CL` 抛 `module.system.order.notPayable`，回调持续 5xx，订单仍停在 `CL`。

因此这一类只能人工对账（特征：渠道已扣款，本地 `sys_pay_order.status` 仍为 `WP`；或迟到回调后支付单 `OD` + 订单 `CL`），接入订单类业务时要把「支付窗口内同步一次」当成必须动作。
::

## 八、接入新业务的三步清单

1. **定 `biz_type` 常量并在发起支付时传入。**建议在支付域常量旁声明（参照 `PAY_BIZ_TYPE_*`），业务表上给业务单号建唯一键；`out_trade_no` 直接复用业务单号，`attach` 用 `xxx:{业务主键}` 的约定冗余一份。
2. **在 `dispatchPaidOrder` 里加分支。**形如 `if (order.bizType === 'xxx') { await xxxService(db).markPaid(order.outTradeNo, null); return }`；**未知取值必须保持 no-op，不要改成抛错**，否则 `test` 单与历史数据会开始报错。
3. **业务侧做到幂等 + 可补偿。**写入路径用唯一键或条件更新（`where status='WP'`）保证只生效一次；同时提供一条能扫「业务单未完成、支付单已支付」的补捞路径与手工入口（参照 `rechargeRetry` + `listPendingWithPaidOrder`）。

自查表：

| 检查项 | 通过标准 |
| --- | --- |
| 重复调用 `markPaid` / `credit` | 第二次返回「已处理」，余额 / 订单状态不变 |
| 同一支付事件被重复告知（平台重试、duplicate 分支补调 `onPaid`） | 业务侧幂等命中，不重复入账、不重复改状态 |
| `onPaid` 抛错后（平台重试或手工补偿） | 能把业务单补齐，且不重复入账 |
| 业务单不存在 | 抛明确错误码（让平台重试并暴露问题），不要静默吞掉 |
| 未知 `biz_type` | 回调正常返回 200，只把支付单置为已支付 |
| 关闭 / 失败方向 | 本地业务单被关闭时，能反向把支付单也关掉（参照 `myRechargeSync` / `OrderService.sync` 的自愈分支） |
