支付模块只管「钱」，不管「货」。一笔资金结论要变成「会员充值到账」「交易订单完成」或「会员等级开通生效」，靠的是支付单上唯一的业务线索——`sys_pay_order.biz_type`。本页是**分派实现**的唯一事实源：分派入口、`onPaid` 注入、失败语义与接入清单。各业务侧的到账 / 生效时序与补偿清单归 `10.payment-flow/*`，本页只做一句话引用。

## 一、分派入口

唯一入口是 `dispatchPaidOrder(order, db)`（`server/trade-router/domain/pay/PaidHandlers.ts`）：

```text
POST /api/pay/notify/{channel}                      免登录回调路由
   └─ payNotifyDispatcher(useDb(), { onPaid }).handleNotify(...)
        ├─ 成功日志已存在（dedup_key 命中）→ duplicate，**不再分派**
        ├─ markPaidIfPending 影响行数 > 0（首次置为已支付）→ onPaid(paidOrder)
        └─ 影响行数 === 0 且本次事件没有成功日志 → onPaid(latestOrder)（补做一次）
             └─ dispatchPaidOrder(order, db)   server/trade-router/domain/pay/PaidHandlers.ts
                  ├─ bizType === 'recharge'    → rechargeService(db).credit(order.outTradeNo, null)
                  ├─ bizType === 'order'       → orderService(db).markPaid(order.outTradeNo, null)
                  ├─ bizType === 'memberLevel' → memberLevelOrderService(db).markPaid(order.outTradeNo, null)
                  └─ 其它取值（含 'test'）      → 直接 return：只把支付单置为已支付，不做业务后置
```

| 符号 | 内容 |
| --- | --- |
| `PAY_BIZ_TYPE_RECHARGE` / `PAY_BIZ_TYPE_ORDER` / `PAY_BIZ_TYPE_MEMBER_LEVEL` | `PaidHandlers.ts` 里的三个业务类型常量 |
| `dispatchPaidOrder(order: PayOrderRow, db: AppDb): Promise<void>` | 三个分支 + 未知取值 no-op，见上 |
| 未知取值 | **不抛错**，保持「只标记支付成功」的历史行为（支付测试单依赖它） |

`biz_type` 的真实取值与能不能被测试页模拟：

| `biz_type` | 写入方 | 支付成功后的行为 | 测试页「模拟支付成功」 |
| --- | --- | --- | --- |
| `test` | 扫码支付测试页 `sysPayTest.create`（也是列默认值） | no-op，只把支付单置为已支付 | ✅ 允许 |
| `recharge` | 会员自助充值 `sysMember.myRecharge` → `RechargeService.create` | `rechargeService(db).credit()`，充值金 / 赠送金入账 | ❌ 报 `module.system.payTest.simulateOnlyTest` |
| `order` | 交易订单在线支付 `sysOrder.myCreate` → `OrderService.create` | `orderService(db).markPaid()`，订单置为已完成 | ❌ 同上 |
| `memberLevel` | 会员等级开通单 → `MemberLevelOrderService` 调 `payOrderService.createPayment` | `memberLevelOrderService(db).markPaid()`，开通单生效 | ❌ 同上 |
| 其它自定义取值 | 未来业务 | no-op，需要先在 `dispatchPaidOrder` 里加分支 | ❌ 同上 |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**只有 `test` 允许模拟支付。**`simulatePaid()`（`server/trade-router/domain/pay/PayNotifyDispatcher.ts`）在定位订单后立刻校验 `order.bizType !== 'test'` → `module.system.payTest.simulateOnlyTest`，所以 `recharge` / `order` / `memberLevel` 的单据**不能**用「模拟支付成功」按钮走捷径，必须走真实渠道回调或主动同步。

另外，测试页的 dispatcher 是 `payNotifyDispatcher(ctx.db)`，**没有注入 `onPaid`**（`server/trade-router/modules/payTest/SysPayTestService.ts`）；即使将来放宽 `bizType` 限制，测试页也不会触发业务后置。

还有一处细节：`sysPayTest.create` 的入参本身允许自带 `bizType`（`shared/system/payTest/input.ts`，留空才回落到 `'test'`，见 `SysPayTestService.create`），所以用测试页也能造出 `recharge` / `order` / `memberLevel` 的支付单。这类单既不能模拟支付，一旦真的走渠道付掉，回调会按 `bizType` 去找一个并不存在的业务单号，抛 `module.system.memberRecharge.notFound` / `module.system.order.notFound` 等并返回 5xx——**测试时不要随手填 `bizType`**。
::

## 二、注入口：onPaid

```ts
// server/trade-router/domain/pay/PayNotifyDispatcher.ts
export type PayNotifyOptions = {
  onPaid?: (order: PayOrderRow) => Promise<void>
}

export function payNotifyDispatcher(executor: AppExecutor, options: PayNotifyOptions = {}) { … }
```

回调路由的注入方式（`server/api/pay/notify/[channel].post.ts`）：

```ts
const outcome = await payNotifyDispatcher(useDb(), {
  onPaid: async (order) => {
    await dispatchPaidOrder(order, useDb())
  }
}).handleNotify(channelCode, { headers, rawBody, body }, { clientIp: ip, userAgent, source: 'notify' })
```

`onPaid` 是**至少一次**语义，`handleNotify` 内有两个调用点：

| 顺序 | 判定 | 说明 |
| --- | --- | --- |
| 1 | `logRepo.existsByDedupKey(result.dedupKey)` 命中 | 只计数 + 写 duplicate 日志 → 直接返回，**不调用 `onPaid`**（成功日志是在 `onPaid` 之后写的，日志存在即可推断业务后置已完成） |
| 2 | `orderRepo.markPaidIfPending(order.id, …)` | SQL 带 `where id = :id and status <> 'OD'` |
| 3 | 影响行数 `=== 0` | 先 `findById` 重读、`await options.onPaid(latestOrder)` **补做一次**，再写 duplicate 日志并返回 duplicate |
| 4 | 影响行数 `> 0`（首次置为已支付） | 先 `findById` 重读、`await options.onPaid(paidOrder)` |
| 5 | 写日志 | 写带 `dedup_key` 的 `success` / `status_mismatch` 日志（两个 `onPaid` 调用点都在它之前） |

四点约定：

- **两处都会调用 `onPaid`，业务侧必须幂等**。第 4 条是「首次置为已支付」；第 3 条无法区分「渠道重复投递、后置早已完成」与「上次置为已支付后业务后置失败 / 订单是被主动查询推进的」，所以一律再告知业务域一次——已完成时各业务侧会命中自己的唯一键 / 状态守卫，代价只是一次读。
- **只有成功日志存在时才会跳过**。日志写入在 `onPaid` 之后，因此「日志存在」等价于「后置已走完」；反过来 `onPaid` 抛错时日志（含 duplicate 日志）没写成，下一次同样的回调就会再次分派。
- **回调拿到的是重读后的订单行**，`status` 已是 `OD`，`biz_type` / `out_trade_no` 与库内一致。
- **与「支付单置为已支付」不在同一事务**。`dispatchPaidOrder` 收到的是 `AppDb`（连接），`rechargeService(db)` / `orderService(db)` / `memberLevelOrderService(db)` 各自 `db.transaction()` 提交，所以业务写入失败不会回滚支付单。

## 三、失败语义

`onPaid` 抛错会中断本次回调处理，回调路由没有 `try/catch`，异常冒泡给 Nitro 后返回 **5xx**，平台据此重试——而重试**确实会重新触发 `onPaid`**，平台重试本身因此也算业务后置的一条补偿路径。注意下面三点：

| 事实 | 后果 |
| --- | --- |
| 抛错发生在写日志（成功日志 / duplicate 日志）之前 | 这次回调在 `sys_pay_notify_log` 里**完全不留痕**，只能从服务端错误日志排查；也正因为没有成功日志，重试时不会被 `existsByDedupKey` 短路 |
| 重试时支付单已是 `OD`，`markPaidIfPending` 影响行数为 0 | 走 duplicate 分支，但该分支**会再调用一次 `onPaid`**（至少一次语义）；补齐后写 duplicate 日志并返回 200 |
| 业务侧写入是独立事务 | 业务单可能停在「未完成」，需要能扫出「支付单已支付但业务单未完成」的补偿路径 |

因此业务侧的硬要求是两条：**幂等**（唯一键 / 条件更新，重复调用不重复生效）+ **可补偿**（平台放弃重试或回调根本没到达时，有办法把漏掉的单捞出来补做，见[账实一致与补偿](/docs/main/payment-flow/consistency)）。

常见抛错来源：支付单对应不到业务单（`module.system.memberRecharge.notFound`、`module.system.order.notFound`）、业务单已不是待支付（`module.system.order.notPayable`）。这些都是「数据不一致」而不是「偶发失败」，平台重试解决不了，主要价值是让问题尽早暴露（错误日志 + 支付单已 `OD` 而业务单未完成）。

## 四、业务侧发起支付

业务方不直接写 `sys_pay_order`，而是调 `payOrderService(db).createPayment(input, meta)`，把业务单号当商户订单号传进去。

会员充值的调用在 `RechargeService.create`（`server/trade-router/domain/wallet/RechargeService.ts`）：

```ts
const order = await payments.createPayment({
  outTradeNo,                        // 业务单号（buildOutTradeNo('RCH')），与充值单一一对应
  amount: payAmount,                 // 实付金额（已扣优惠码）
  subject: `会员充值 ${amount} 元`,
  bizType: 'recharge',               // ← 分派的唯一依据
  attach: `recharge:${rechargeId}`,  // 业务行主键的冗余快照，只用于排查/透传
  notifyUrl: input.notifyUrl ?? null,
  origin: input.origin ?? null       // 渠道未配 notify_url 时按 origin 推导回调地址
}, { operatorId })
```

交易订单在线支付的调用在 `OrderService.create`（`server/trade-router/domain/order/OrderService.ts`）：

```ts
const payOrder = await payments.createPayment({
  outTradeNo: created.orderNo,       // 订单号即商户订单号
  amount: created.payAmount,
  subject: `订单 ${created.orderNo}`,
  bizType: 'order',
  attach: `order:${created.orderId}`,
  notifyUrl: input.notifyUrl ?? null,
  origin: input.origin ?? null
}, { operatorId: input.operatorId ?? null })
```

字段约定：

| 字段 | 约定 |
| --- | --- |
| `outTradeNo` | 就是业务单号（充值单 `RCH…`、订单号 `ORD…`、等级开通单同理），两侧都有唯一键，支付单与业务单靠它一一对应 |
| `bizType` | 分派依据，`dispatchPaidOrder` 只读它；会落进 `sys_pay_order.biz_type`（可用 `idx_pay_order_biz_type` 筛选） |
| `attach` | 形如 `recharge:{id}` / `order:{id}`，业务行主键的冗余，**分派不读它**，只用于排障 |
| `amount` | 实付金额（已扣优惠码 / 已按等级价计算），不是原价 |
| `origin` | 回调地址推导兜底；订单侧由 tRPC 层用 `getRequestURL(ctx.event).origin` 传入 |

## 五、各业务侧的结果（时序见 payment-flow）

业务侧「怎么到账 / 怎么完成」的完整时序、每一步失败留下什么，分别归[充值流程](/docs/main/payment-flow/recharge)与[订单支付流程](/docs/main/payment-flow/order-payment)。本页只保留分派视角需要知道的一句话：

| `biz_type` | 业务入口（本页只点名） | 关键结果 | 详见 |
| --- | --- | --- | --- |
| `recharge` | `RechargeService.credit`（`server/trade-router/domain/wallet/RechargeService.ts`） | 唯一到账入口；三重幂等（`uk_member_recharge_out`、`uk_member_log_dedup`、`markCredited` 的 `status <> 'OD'`），写充值金 / 赠送金流水并核销优惠码 | [充值流程 · 到账](/docs/main/payment-flow/recharge) |
| `order` | `OrderService.markPaid`（`server/trade-router/domain/order/OrderService.ts`） | 只推进订单状态 + 核销优惠码 + 累加销量，**不动余额**；服务类仍留 `fulfill_status = 'pending'`；订单已关闭抛 `module.system.order.notPayable` | [订单支付流程 · 回调推进](/docs/main/payment-flow/order-payment) |
| `memberLevel` | `MemberLevelOrderService.markPaid`（`server/trade-router/domain/member/MemberLevelOrderService.ts`） | 开通单 `status = 'WP' → 'OD'` 的条件更新；对 `CL` / `FL` 不抛错 | [开通与续费](/docs/main/member/open-renew) |
| `test` / 未知取值 | 无 | no-op：只把支付单置为已支付，不碰任何业务表 | 本页第一节 |

## 六、主动同步不经过 dispatchPaidOrder

`dispatchPaidOrder` **只由回调路由**通过 `onPaid` 调用（约定写在 `PaidHandlers.ts` 的头部注释里）。主动同步（`OrderService.sync` / `SysMemberService.myRechargeSync` / `MemberLevelOrderService.sync`）各自直接调业务侧幂等方法，因为此时已经知道业务类型，不必再按 `biz_type` 分派。两条链路复用同一个条件更新，结果一致：

- 充值侧的自助同步、反向关单与补偿：[充值流程](/docs/main/payment-flow/recharge)第九节。
- 订单侧的同步、自愈关单与超时关单：[订单支付流程](/docs/main/payment-flow/order-payment)第七、八节。
- 人工入口与失败矩阵：[账实一致与补偿](/docs/main/payment-flow/consistency)第五、六节。

## 七、补偿与对账（清单见 payment-flow）

「支付单已支付但业务单未完成」的扫描 SQL 是 `rechargeRepo.listPendingWithPaidOrder`（`server/trade-router/domain/wallet/repo/rechargeRepo.ts`），订单侧则由 `order:expire-close` 在关单前读本地支付单做补做。

补偿任务、扫描条件、人工入口与残留风险（回调从未到达、本地支付单仍是 `WP`；订单 TTL 15 分钟与渠道窗口 30 分钟不匹配等）统一维护在[账实一致与补偿](/docs/main/payment-flow/consistency)第四、五、六节，本页不再复制清单。这里只保留接入方必须记住的一条：**回调重试不是唯一补偿路径，业务侧必须自己可被扫描、可被补做。**

## 八、接入新业务的三步清单

1. **定 `biz_type` 常量并在发起支付时传入。**建议在支付域常量旁声明（参照 `PAY_BIZ_TYPE_*`），业务表上给业务单号建唯一键；`out_trade_no` 直接复用业务单号，`attach` 用 `xxx:{业务主键}` 的约定冗余一份。
2. **在 `dispatchPaidOrder` 里加分支。**形如 `if (order.bizType === 'xxx') { await xxxService(db).markPaid(order.outTradeNo, null); return }`；**未知取值必须保持 no-op，不要改成抛错**，否则 `test` 单与历史数据会开始报错。
3. **业务侧做到幂等 + 可补偿。**写入路径用唯一键或条件更新（`where status='WP'`）保证只生效一次；同时提供一条能扫「业务单未完成、支付单已支付」的补捞路径与手工入口（参照 `rechargeRetry` + `listPendingWithPaidOrder`）。

自查表：

| 检查项 | 通过标准 |
| --- | --- |
| 重复调用 `markPaid` / `credit` | 第二次返回「已处理」，余额 / 订单状态不变 |
| 同一支付事件被重复告知（平台重试、duplicate 分支补调 `onPaid`） | 业务侧幂等命中，不重复入账、不重复改状态 |
| `onPaid` 抛错后（平台重试或手工补偿） | 能把业务单补齐，且不重复入账 |
| 业务单不存在 | 抛明确错误码（让平台重试并暴露问题），不要静默吞掉 |
| 未知 `biz_type` | 回调正常返回 200，只把支付单置为已支付 |
| 关闭 / 失败方向 | 本地业务单被关闭时，能反向把支付单也关掉（参照 `myRechargeSync` / `OrderService.sync` 的自愈分支） |
