按下面的顺序操作，即可得到一个可登录的后台。

## 一、环境要求

| 项目 | 要求 |
| --- | --- |
| Node.js | 建议 `22.20.2`（见 `README.md`） |
| 包管理器 | `pnpm` |
| 数据库 | MySQL（需支持 `date_sub`、`on update current_timestamp` 等常规语法） |

## 二、安装依赖

```bash
pnpm install
```

`postinstall` 会执行 `nuxt prepare`，生成 `.nuxt` 类型产物。如果类型提示异常，可手动再跑一次：

```bash
pnpm post
```

## 三、配置环境变量

复制模板文件后按实际环境修改：

```bash
cp .env.example .env
```

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `DB_HOST` | 是 | 数据库地址 |
| `DB_DATABASE` | 是 | 数据库名 |
| `DB_USER` | 是 | 数据库账号 |
| `DB_PASSWORD` | 是 | 数据库密码 |
| `NUXT_SESSION_PASSWORD` | 是 | Session 加密密钥，生产环境请用至少 32 位随机字符串 |
| `NUXT_SESSION_COOKIE_SECURE` | 否 | `true` 要求 HTTPS；未设置时按 `NODE_ENV` 推断（production 默认 `true`，其余默认 `false`） |
| `NUXT_DEMO_MODE` | 否 | 设为 `true` 时启用演示只读保护 |
| `NUXT_PUBLIC_APP_NAME` | 否 | 站内展示的应用名称 |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` / `ADMIN_EMAIL` | 否 | 仅 `pnpm seed:admin` 使用 |
| `NODE_ENV` | 否 | `development` / `production` |
| `ENABLE_LOGGING` / `LOG_LEVEL` | 否 | 模板预留的日志开关与级别；**当前服务端代码并未读取这两个变量**，日志行为由 `LogRecorderService` 的内部策略决定 |

> **HTTP 部署最常见的坑**：用 `http://IP:端口` 访问时，浏览器会拒收带 `Secure` 标记的 Cookie，表现为「登录接口成功，但后续请求仍是未登录」。此时把 `NUXT_SESSION_COOKIE_SECURE` 显式设为 `false` 即可。详细原因见 [运行时配置与环境变量](/docs/main/backend-handbook/config-env)。

## 四、初始化数据库

先建库，再导入结构脚本：

```bash
mysql -u <user> -p <database> < doc/main/mysql-ddl.sql
mysql -u <user> -p <database> < doc/main/init.sql
```

- `doc/main/mysql-ddl.sql` 创建全部业务表，包含 `sys_user`、`sys_role`、`sys_menu`、`sys_department`、`sys_user_role`、`sys_role_menu`、`sys_dict_type`、`sys_dict_data`、`sys_config`、`sys_notice`、`sys_oss`、`sys_oss_config`、`sys_job`、`sys_job_log`、`sys_login_log`、`sys_system_log` 以及示例表 `demo`。
- `doc/main/init.sql` 写入菜单、权限、字典、角色等初始化数据。

> 注意：初始化数据脚本的文件名是 `doc/main/init.sql`（早期文档曾误写为 `init-self.sql`，现已统一）。

如果数据库表结构发生变化，可以用下面两个脚本同步 Schema：

```bash
pnpm db:pull   # 从数据库读取表结构，生成 Drizzle Schema
pnpm db:push   # 把 Schema 推送到数据库
```

## 五、创建管理员账号

用 `scripts/seed-admin.ts` 创建或重置管理员（会读取 `ADMIN_USERNAME`、`ADMIN_PASSWORD`、`ADMIN_EMAIL`）：

```bash
pnpm seed:admin
```

脚本行为：

- 账号已存在 → 重置密码、邮箱，并强制 `isAdmin = 1`、`status = 1`、`isDeleted = 0`；
- 账号不存在 → 新建，昵称为 `Administrator`，`isAdmin = 1`；
- `ADMIN_PASSWORD` 缺失或短于 6 位会直接抛错。

另外，`doc/main/mock_sql/generate-sys-user-data.ts.ts` 是一份批量生成演示用户数据的参考脚本，按需使用。

## 六、启动

```bash
pnpm dev
```

开发服务器监听 `0.0.0.0:3001`（配置见 `nuxt.config.ts` 的 `devServer`），因此：

- 本机访问：`http://localhost:3001`
- 局域网其它设备访问：`http://<你的IP>:3001`

启动后可以访问：

| 地址 | 内容 |
| --- | --- |
| `/system/home` | 后台首页（需登录） |
| `/login` | 登录页 |
| `/register` | 注册页 |
| `/landing` | 项目落地页 |
| `/docs/main/getting-started` | 本站文档 |

## 七、常用命令

| 命令 | 作用 |
| --- | --- |
| `pnpm dev` | 启动开发服务器（HMR） |
| `pnpm build` | 生产构建 |
| `pnpm preview` | 预览生产构建产物 |
| `pnpm generate` | 生成静态站点 |
| `pnpm typecheck` | Nuxt 类型检查 |
| `pnpm test` | 运行 Vitest |
| `pnpm test:type` | 对测试文件做类型检查（`scripts/typecheck-tests.ts`） |
| `pnpm db:push` | Schema 推送到数据库 |
| `pnpm db:pull` | 从数据库反向生成 Schema |
| `pnpm seed:admin` | 创建/重置管理员账号 |

## 八、生产部署要点

1. `pnpm build` 后以 `node .output/server/index.mjs`（或 `pnpm preview`）运行。
2. 必须注入 `NUXT_SESSION_PASSWORD`，不要使用开发用密钥。
3. HTTPS 部署保持 `NUXT_SESSION_COOKIE_SECURE=true`；纯 HTTP 部署必须设为 `false`。
4. 生产环境建议关闭 `NUXT_DEMO_MODE`。
5. `memory` 缓存是进程内缓存，多实例部署时不会共享，扩容前请先阅读 [缓存使用](/docs/main/features/cache/overview)。
6. 内置的到期任务派发默认**不会自动运行**，需要显式开启 `nitro.scheduledTasks`，见 [调度与触发](/docs/main/scheduled-jobs/dispatch)。
