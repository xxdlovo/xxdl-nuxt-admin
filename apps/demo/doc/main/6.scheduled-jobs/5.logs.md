## 记录时机

日志由 `server/sys-router/job/SysJobRunner.ts` 统一写入，Handler 内部不需要自己记录执行日志：

1. 校验任务与 Handler 是否可用；
2. 插入一条 `status = 0` 的日志（此时 `finished_at`、`duration_ms`、`result` 都为空）；
3. 把任务的 `running_status` 置为 `1`，写入 `last_run_at`；
4. 调用 Handler；
5. 无论成功还是失败，都更新同一条日志的结束时间与耗时；
6. 失败时额外写入 `error_message` 与 `error_stack`，并把异常继续抛出。

派发任务 `server/tasks/sys-job/dispatch.ts` 在运行时会向服务端控制台输出 `task refresh run...`，可作为「派发是否被触发」的第一手线索。

## 状态含义

`sys_job_log.status` 字典编码为 `job_log_status`：

| 值 | 含义 | 写入时机 |
| --- | --- | --- |
| `0` | 运行中 | 执行开始前插入 |
| `1` | 成功 | Handler 正常返回 |
| `2` | 失败 | Handler 抛出异常，或后续回写过程出错 |

`trigger_type` 字典编码为 `job_trigger_type`，取值为 `schedule`（调度触发）或 `manual`（手动触发）。

任务本身的 `running_status` 使用字典 `job_running_status`，`0` 表示空闲、`1` 表示执行中。

## 关键字段

| 字段 | 用途 |
| --- | --- |
| `job_id` / `job_name` / `job_code` | 定位是哪个任务，任务删除后日志仍保留可读信息 |
| `handler_code` / `cron_expression` | 执行时的配置快照，便于回溯「当时的表达式是什么」 |
| `started_at` / `finished_at` | 起止时间，格式 `YYYY-MM-DD HH:mm:ss` |
| `duration_ms` | 耗时，用于发现异常变慢的任务 |
| `result` | Handler 返回值，JSON 结构，成功时查看处理结果 |
| `error_message` | 失败摘要，同时会回写到任务的 `last_error` |
| `error_stack` | 完整堆栈，仅用于排查，不建议在列表页展示 |

## 查询接口

| 方法 | 权限码 | 说明 |
| --- | --- | --- |
| `sysJobLog.page` | `system:jobLog:list` | 分页查询，支持按任务名称、编码等条件过滤 |
| `sysJobLog.getById` | `system:jobLog:list` | 单条详情 |
| `sysJobLog.remove` | `system:jobLog:del` | 删除单条日志 |
| `sysJobLog.batchDelete` | `system:jobLog:del` | 批量删除 |

路由定义见 `server/sys-router/jobLog/index.ts`，查询 schema 见 `shared/system/jobLog/index.ts`。

## 后台页面

任务日志页位于 `/system/job-log`：

- 列表支持按条件过滤，条件里包含 `jobId`；
- 从任务列表点击「查看日志」会带上查询参数跳转，例如 `/system/job-log?jobId=xxx&jobName=yyy`，页面会随之刷新筛选条件；
- 详情弹窗展示 `result`、`error_message`、`error_stack` 等字段。

页面源码见 `app/pages/system/job-log/index.vue` 与 `app/pages/system/job-log/components/sys-job-log-detail.vue`。

## 与操作日志的关系

| 对比项 | 任务日志 `sys_job_log` | 系统操作日志 `sys_system_log` |
| --- | --- | --- |
| 记录对象 | 定时任务的每次执行 | tRPC 接口与 `server/api` 端点的调用 |
| 写入方式 | `SysJobRunner` 显式写入 | `loggerMiddleware` / `apiOperationLog` 自动写入 |
| 是否含请求上下文 | 否（没有 IP、User-Agent 等） | 是 |

后台「立即执行」这个动作本身是一次 tRPC mutation，会另有一条系统操作日志；任务实际执行的过程只写任务日志。

## 排查清单

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 日志长期停留在 `status = 0` | 进程在执行过程中被重启或崩溃，收尾逻辑未执行 | 检查部署日志与内存占用，必要时手动把任务 `running_status` 改回 `0` |
| `status = 2` 且 `error_message` 为 Handler 缺失 | 代码回滚或 `handler_code` 拼写错误 | 重新绑定到已注册的 Handler |
| `status = 2` 且堆栈指向 SQL 语法错误 | Handler 内 SQL 与当前表结构不一致 | 修正 SQL，或同步表结构 |
| 有任务日志但没有 `result` | Handler 未返回值，或返回了不可序列化的内容 | 让 `run` 返回普通对象 |
| 手动执行成功但任务不自动跑 | `scheduledTasks` 未启用，或 `next_run_at` 未到 | 参见[调度与执行](/docs/main/scheduled-jobs/dispatch) |
| 单次耗时明显变长 | 数据量增长或缺少索引 | 结合 `duration_ms` 观察趋势，优化 Handler 内的查询 |
| 日志表增长过快 | 高频任务持续产出日志 | 确认 `system:clean-log` 任务是否启用 |

## 日志清理

内置 Handler `system:clean-log` 会对以下两张表做**软删除**（`is_deleted` 置 `1`），保留 30 天内的数据：

| 表 | 条件 |
| --- | --- |
| `sys_system_log` | `is_deleted = 0 and created_at < now() - 30 day` |
| `sys_job_log` | `is_deleted = 0 and created_at < now() - 30 day` |

执行结果会返回两张表各自的影响行数，便于确认清理效果。默认不会自动运行，需要开启自动调度或手动触发。
