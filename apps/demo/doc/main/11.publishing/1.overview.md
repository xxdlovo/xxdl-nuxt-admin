## 发布的是什么

仓库里有两个可发布的包，都是一个完整的 Nuxt Layer：

| 包 | 目录 | 内容 |
| --- | --- | --- |
| `xxdl-admin-core` | `packages/admin-core` | 基座：认证、RBAC、系统管理、tRPC、Drizzle |
| `xxdl-admin-trade` | `packages/admin-trade` | 可选电商层：会员、商品、订单、支付、钱包 |

两者都**直接发布源码**（`.vue` / `.ts`），不做构建：

```json
{
  "main": "./nuxt.config.ts",
  "exports": { ".": "./nuxt.config.ts" }
}
```

业务项目 `extends` 之后，宿主 Nuxt 会照常编译这些文件，因此不需要 `dist` 目录，也不需要 `@nuxt/module-builder`。

## 版本号从哪来

**唯一来源是各自 `package.json` 的 `version`**。tag 只是触发信号，用来告诉 CI「该发哪个包、该是什么版本」。

CI 会强制校验二者一致，不一致直接失败。这样做的目的是杜绝「tag 写了 0.2.0，但包里还是 0.1.0」这类事故。

## tag 的三种形式

| tag 形式 | 发布范围 | 要求 |
| --- | --- | --- |
| `core-v0.1.1` | 只发 `xxdl-admin-core` | core 的 version 必须是 `0.1.1` |
| `trade-v0.2.0` | 只发 `xxdl-admin-trade` | trade 的 version 必须是 `0.2.0` |
| `v0.2.0` | 两个一起发 | 两个包的 version 必须都是 `0.2.0` |

注意 `core-v*` 和 `v*` 是两个独立的匹配规则：`v*` 不会匹配 `core-v0.1.1`（后者不以 `v` 开头）。

## dist-tag 规则

| 版本形态 | dist-tag | 用户安装 |
| --- | --- | --- |
| `0.1.1` | `latest` | `pnpm add -D xxdl-admin-core` |
| `0.2.0-beta.1` | `next` | `pnpm add -D xxdl-admin-core@next` |

即：版本号里带 `-` 的预发布版本不会自动成为 `latest`，避免半成品被默认安装。

## 两种发布方式的分工

| 场景 | 方式 | 是否需要人工 |
| --- | --- | --- |
| 日常发版 | CI 自动（推 tag） | 否 |
| 首次发布 / CI 配置尚未就绪 | 本地手动 | 是（需 2FA） |
| 紧急修复且 CI 不可用 | 本地手动 | 是 |

CI 用的是 **Trusted Publishing（OIDC）**，完全不需要长期 token；本地手动发布则要处理 2FA，两种方式的细节分别见：

- [手动发布](/docs/main/publishing/manual-publish)
- [CI 自动发布](/docs/main/publishing/ci-publish)

## 发布前会自动跑什么

无论哪种方式，发布前都会先过一遍这些检查（CI 里是 workflow 步骤，本地建议自己跑）：

| 检查 | 命令 | 作用 |
| --- | --- | --- |
| 类型检查 | `pnpm typecheck` | 双宿主（demo + playground）类型不通过就不发 |
| 分层契约 | `pnpm check:layers` | 单例依赖、跨层注入、宿主别名等问题 |
| 版本占用 | `npm view <pkg>@<version>` | 已存在则提前失败 |
| 打包校验 | `pnpm pack` | 确认包内容（swagger 资源、SQL、locales） |

## 包内容校验清单

`npm pack` 之后应确认：

- `public/swagger-ui/*` 在包里（`/api/docs` 依赖它）
- `sql/*.sql` 在包里
- `app/locales/{en,zh}.json` 在包里
- `README.md`、`LICENSE` 在包里
- **不含** `node_modules`、`.nuxt`、`.output`
