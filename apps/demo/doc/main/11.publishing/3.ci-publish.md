发布流程的最终形态是：**改版本号 → 推一个 tag → CI 自动发布**，全程不需要 token、OTP 或人工上传。

实现它需要三件事：npm 侧配置 Trusted Publishing、仓库里有 `publish.yml`、按约定推 tag。

## 一、npm 侧：配置 Trusted Publishing

每个包**各配一次**，不能通用。

### 1. 添加 Trusted Publisher

打开 `https://www.npmjs.com/package/<包名>/access` → **Trusted Publishing** → **Add trusted publisher**：

| 字段 | 值 |
| --- | --- |
| Publisher | GitHub Actions |
| Organization or user | `xxdlovo` |
| Repository | `xxdl-nuxt-admin` |
| Workflow filename | `publish.yml`（**必须精确匹配**） |
| Environment | 留空 |

保存后状态是 `Pending validation`。

### 2. Allowed actions

同一页面还有「允许哪些操作」，选**直接发布**：

| 选项 | 说明 | 需要吗 |
| --- | --- | --- |
| npm stage publish | CI 只能把包暂存，需人工批准 | ❌ 不需要 |
| **Publish directly** | CI 可直接发布上线 | ✅ **必须** |
| Manage dist-tags | 允许修改 `latest` / `next` | ✅ 建议勾 |

只开 stage publish 的话，workflow 里的 `npm publish` 会因没有直接发布权限而失败。

### 3. Publishing access（2FA 要求）

| 选项 | 含义 |
| --- | --- |
| Require 2FA or a granular access token with bypass 2FA | 默认，允许 token 绕过 2FA 发布 |
| **Require 2FA and disallow tokens** | 任何 token 都不能发布，只能交互式或 OIDC |

OIDC **不受这个设置影响**（它不是 token），所以走通自动发布后，建议选更严格的第二项 —— 这样即使有人拿到你的 token 也发不了包。

### 4. 验证配置

配置是 `Pending validation` 状态，**需要用一次成功的 OIDC 发布来激活**，npm 会给一个期限（约 48 小时）。

期限内发一个补丁版本即可，成功后状态变成 `Active`。

## 二、仓库侧：工作流做了什么

文件：`.github/workflows/publish.yml`

### 触发方式

| 触发 | 说明 |
| --- | --- |
| 推 `v*` tag | 两个包一起发 |
| 推 `core-v*` tag | 只发 core |
| 推 `trade-v*` tag | 只发 trade |
| 手动 `workflow_dispatch` | 可选发哪个包、可只做 dry-run |

> `workflow_dispatch`（网页上的 Run workflow 按钮）只有在**默认分支**上存在该 workflow 文件时才会显示。

### 执行步骤

```
Checkout
→ Setup pnpm（读 package.json 的 packageManager）
→ Setup Node
→ pnpm install --frozen-lockfile
→ pnpm typecheck              ← 闸门
→ pnpm check:layers           ← 闸门
→ 解析目标与版本（校验 tag 与 package.json 一致）
→ 检查版本是否已存在于 npm     ← 提前失败
→ pnpm pack（生成 tarball，校验内容）
→ npm publish <tgz>（OIDC + provenance）
```

### 两个关键实现细节

**为什么用 `pnpm pack` + `npm publish <tgz>`，而不是 `pnpm publish`：**

- `workspace:^` 这类 pnpm 专有协议只有 `pnpm pack` 会正确替换成实际版本号；用 `npm publish` 直接跑在 workspace 里会发出一个**装不上**的包。
- 但 OIDC 与 provenance 由 npm CLI 处理，pnpm 的 publish 不保证走同一路径。

两者结合：`pnpm pack` 负责打包正确，`npm publish` 负责认证正确。

**为什么发布顺序是 core 先、trade 后：**

trade 依赖 core 的版本（`xxdl-admin-core: workspace:^` → 发布时替换成 `^<core 版本>`）。core 没发出去时 trade 会装不上。

## 三、日常发版流程

### 只发 core

```bash
# 1. 改 packages/admin-core/package.json 的 version → 0.1.2

# 2. 提交
git add -A
git commit -m "release: core 0.1.2"
git push origin main

# 3. 打 tag 并推送
git tag core-v0.1.2
git push origin core-v0.1.2
```

### 只发 trade

```bash
# packages/admin-trade/package.json → 0.2.1
git add -A && git commit -m "release: trade 0.2.1" && git push origin main
git tag trade-v0.2.1
git push origin trade-v0.2.1
```

### 两个一起发（版本必须相同）

```bash
# 两个 package.json 都改成 0.2.0
git add -A && git commit -m "release: 0.2.0" && git push origin main
git tag v0.2.0
git push origin v0.2.0
```

### 手动触发（不推 tag）

`Actions → Publish to npm → Run workflow`：

| 参数 | 说明 |
| --- | --- |
| package | `all` / `xxdl-admin-core` / `xxdl-admin-trade` |
| dry_run | 勾上则只做检查与打包，不真正发布 |

版本号自动从 `package.json` 读取。适合「先验证一次会不会成功」，但正式发版建议用 tag —— tag 留下了版本与 commit 的对应关系。

## 四、版本号怎么控制

**规则：只改 `package.json` 的 `version`，tag 跟着它走。**

CI 会做这个校验：

```bash
if [[ "$CORE_VERSION" != "$EXPECTED" ]]; then
  echo "::error::版本不一致：tag 指向 $EXPECTED，但 package.json 是 $CORE_VERSION"
  exit 1
fi
```

所以版本写错时，不会出现「tag 说 0.2.0、实际发 0.1.0」的情况，而是直接失败并在日志里告诉你该改哪个文件。

### 语义化版本约定

| 变更类型 | 版本 |
| --- | --- |
| 破坏性改动（改契约、删字段） | 主版本 +1，如 `1.0.0` |
| 新增能力（加接口、加页面） | 次版本 +1，如 `0.2.0` |
| 修复与内部调整 | 补丁 +1，如 `0.1.1` |
| 预发布验证 | `0.2.0-beta.1`（自动发到 `next`） |

### 什么时候用 `core-v*` 而不是 `v*`

两个包的发版节奏通常不同：

- trade 依赖 core 的 `^0.1.x`，core 发补丁不影响 trade 的依赖范围 → 用 `core-v*` 单独发
- trade 需要用到 core 的新 API 时，先发 core，再发 trade（trade 发布时会自动把依赖写成 `^<新版本>`）

## 五、验证发布结果

```bash
npm view xxdl-admin-core version
npm view xxdl-admin-trade version
npm view xxdl-admin-core dist-tags
```

CI 日志里成功的标志：

```
npm notice Signed provenance statement with source and build information from GitHub Actions
npm notice Provenance statement published to transparency log: https://search.sigstore.dev/?logIndex=...
+ xxdl-admin-core@0.1.1
```

`Signed provenance statement` 出现即说明走的是 OIDC，而不是 token。
