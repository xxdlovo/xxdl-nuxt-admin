优惠码是**单张、不叠加**的营销工具：一次业务最多用一个 `code`，抵扣金额落 `discount_amount`，附带的赠送金落 `gift_amount`。校验与核销都在 `MemberService`（`packages/admin-trade/server/trade-router/domain/member/MemberService.ts`），后台页面是 `/system/member-coupon`。

## 一、表与限制维度

`sys_member_coupon`（Schema：`packages/admin-trade/server/drizzle/schema/system/memberCoupon.ts`），唯一键 `uk_member_coupon_code(code)`：

| 字段 | 含义 | 取值 / 默认 |
| --- | --- | --- |
| `code` | 券码 | 唯一；**创建后不可修改**（后台编辑会忽略该字段） |
| `name` | 名称 | 可空 |
| `type` / `value` | 优惠类型与面值 | `amount`：抵扣金额；`rate`：应付比例（`0.90` = 九折，必须落在 (0,1) 开区间） |
| `min_amount` | 使用门槛（按「原价」判） | 默认 `0.00` |
| `scene` | 适用场景 | `all` / `recharge`（充值）/ `consume`（商品消费） |
| `gift_amount` | 附带赠送金 | 默认 `0.00`，到账时随充值金入账 |
| `valid_from` / `valid_to` | 生效 / 失效时间 | 可空（空 = 不限） |
| `max_use` / `used_count` | 总次数上限 / 已核销数 | `max_use = 0` 表示**不限**；`used_count` 只由锁定累加 |
| `per_user_limit` | 每人次数 | 默认 `1`；`0` 表示不限 |
| `batch_no` | 批次号 | 纯展示与筛选 |
| `status` | `1` 启用 / `2` 作废 | 作废幂等，重复调用直接返回成功 |

五个限制维度相互独立、全部命中才可用：**场景 → 有效期 → 总量（`max_use`）→ 门槛（`min_amount`）→ 每人次数（`per_user_limit`）**，另外加一条「抵扣后应付必须 > 0」。

## 二、校验：`resolveCoupon`（只校验，不核销）

校验顺序固定，命中即抛业务错误（前端 toast 直接展示文案）：

| # | 条件 | 错误 key |
| --- | --- | --- |
| 1 | 码存在 | `module.system.member.couponNotFound` |
| 2 | `status = 2` 已作废 | `...couponVoided` |
| 3 | `status != 1`（停用 / NULL） | `...couponDisabled` |
| 4 | `valid_from > now` | `...couponNotStarted` |
| 5 | `valid_to <= now` | `...couponExpired` |
| 6 | `scene != 'all'` 且不等于本次场景 | `...couponSceneMismatch` |
| 7 | `max_use > 0 && used_count >= max_use` | `...couponUsedUp` |
| 8 | 原价 < `min_amount` | `...couponMinAmount`（message 带门槛值） |
| 9 | `per_user_limit > 0` 且 `已核销 + 已锁定 >= per_user_limit` | `...couponUserLimit` |
| 10 | 抵扣后应付 `<= 0` | `...couponNotApplicable`（message 带「需达到的金额」） |

折扣算法（`computeDiscount`）：

| 类型 | 算法 | 边界 |
| --- | --- | --- |
| `amount` | `discount = min(value, 原价)` | 面额大于订单金额时只抵到 0，不产生负金额 |
| `rate` | `discount = round(原价 × (100 − value%) / 100)`，`payable = 原价 − discount` | `value` 是**应付比例**，`0.90` 表示付九成 |

两个细节：

- 第 9 条的「已锁定」很关键——**同一用户并发提交两次充值，第二次会因为「核销 0 + 锁定 1 ≥ 1」被拒**，不会出现两笔订单同时挂同一张券。
- `skipAmountCheck = true` 用于「还没填金额就先校验券」（会员页的 `myCouponCheck`）：只跳过与金额相关的第 8 条（门槛）与第 10 条（应付 > 0），其余（含总量与每人次数）照常判。它是前置提示，**服务端在真正下单/充值时还会用完整参数再校验一次**。

## 三、三态：锁定 / 核销 / 释放

`sys_member_coupon_use`（`.../system/memberCouponUse.ts`），唯一键 `uk_member_coupon_use(coupon_id, biz_no)`：

```text
lockCoupon(bizNo)
  ├─ findByBizNo 命中 → { locked: true, reused: true }（幂等，不重复计数）
  ├─ insert status = 'locked'（撞唯一键时回读确认，查不到就原样抛出）
  └─ couponRepo.incrementUsedCount：带 (max_use = 0 or used_count < max_use) 守卫
        affectedRows = 0 → 并发抢最后一张 → 抛 couponUsedUp
                          │
        ┌─────────────────┴──────────────────┐
   markUsed(bizNo)                       markReleased(bizNo)
   where status = 'locked'               where status = 'locked'
   → 'used' + used_at                    → 'released' + released_at
```

| 状态 | 含义 | 计入 `per_user_limit` 吗 |
| --- | --- | --- |
| `locked` | 已占用、业务未终结 | 计入（`countLockedByUser`） |
| `used` | 已核销 | 计入（`countUsedByUser`） |
| `released` | 已释放，可再用 | **不计入** |

`markUsed` / `markReleased` 都带 `where status = 'locked'`，所以：已核销的券不会被反向改回 `released`；重复释放是幂等的空操作（影响 0 行）。

## 四、释放路径

| 触发 | 调用方 | `biz_no` |
| --- | --- | --- |
| 商品订单取消 | `OrderService` 取消分支 `members.releaseCoupon` | 订单号 `order_no` |
| 商品订单关闭（后台关闭 / `order:expire-close` 超时） | 同上 | 订单号 |
| 充值发起支付失败 | `RechargeService.create` 的 `catch` 内 | 充值单 `out_trade_no` |
| 充值单关闭（后台 `system:memberRecharge:close`） | `RechargeService.close` | 充值单 `out_trade_no` |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**等级开通单不是释放路径。**

`MemberLevelOrderService` 里没有 `resolveCoupon` / `lockCoupon`，开通等级不吃优惠码；`closeTx` 只做两件事：`FROZEN` 冻结释放 + 单据置 `CL`。所以在 `sys_member_coupon_use` 里永远查不到「等级开通」的占用记录。

另一条容易踩的坑：**后台补录充值单不锁券**（`SysMemberRechargeService.create` 直接落库），`credit` 里的 `markCouponUsed` 会作用在一条不存在的 `locked` 记录上，影响 0 行且静默无效果——补录带券时务必手工核对 `coupon_use` 与 `used_count`。
::

## 五、`max_use` 语义与总配额是否回退

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| `max_use = 0` 是什么意思 | **不限总量**（不是「一次都不能用」） | `couponRepo.incrementUsedCount` 的守卫写的是 `max_use = 0 or used_count < max_use`；`resolveCoupon` 里也是 `if (maxUse > 0 && usedCount >= maxUse)` 才拒绝 |
| 释放后总量配额会回退吗 | **当前不回退** | 全仓库只有 `incrementUsedCount`，**没有 `decrementUsedCount`**；`markReleased` 只改 `coupon_use.status`，不动 `coupon.used_count` |
| 释放后每人次数会回来吗 | **会** | 每人次数是实时统计 `used + locked`（`countUsedByUser` / `countLockedByUser`），`released` 不计入 |
| 作废会把已占用的次数退回吗 | **不会** | `voidCoupon` 只把 `status` 置 `2`（并幂等），不动 `used_count`，也不释放已锁定记录 |

「总量不回退」的实际影响与应对：

- **影响**：用户下单时锁券 → 订单取消释放 → 这张券的 `used_count` 已经 +1 且不退。若 `max_use` 设得很小（例如 1），一次「取消 + 重新下单」就会把整张券的总量消耗光，第二次提示 `couponUsedUp`，而 `per_user_limit` 却没超。表现是「券明明还在有效期、我也没用过，却说抢完了」。
- **应对一（推荐）**：`max_use` 按「需要覆盖的占用峰值」设置，单用户维度用 `per_user_limit` 约束；不要用 `max_use = 1` 去表达「仅限一人使用」。
- **应对二**：真要回收总量，只能人工修数——把 `sys_member_coupon.used_count` 减回去，并确认对应的 `sys_member_coupon_use.status` 已是 `released`。这是一次破坏性操作，请先导出 `uses` 记录留证。
- **影响面**：`coupon.used_count` 与 `Σ(coupon_use.status = 'used')` 会逐渐不相等，`used_count` 恒 `>=` 核销量。后台列表的「已用比例」（`usedRate = used_count / max_use`）统计的是**占用率**，不是核销率；判核销要看使用记录反查（`sysMemberCoupon.uses`）。

## 六、后台与会员侧入口

| 入口 | 位置 | 权限码 |
| --- | --- | --- |
| 优惠码列表 / 新增 / 编辑 / 删除 | `/system/member-coupon` | `system:memberCoupon:list` / `:add` / `:edit` / `:del` |
| 作废 | 列表行操作 | `system:memberCoupon:void`（高敏感，单独授码） |
| 使用记录反查（谁用了、用在哪个业务单） | 列表行「使用记录」 | `system:memberCoupon:list` |
| 会员自助校验 | `sysMember.myCouponCheck` | 登录即可（`protectedProcedure`） |
| 我的优惠码记录 | `sysMember.myCoupons` | 登录即可 |

「使用记录」反查会先校验券存在再分页（券 id 传错时报 `common.notExist`，而不是返回空列表），并带上使用人昵称 / 账号 / 手机号，是排查「这张券到底被谁锁了」最快的入口。

## 七、常见现象与定位

| 现象 | 先看什么 |
| --- | --- |
| 提示「抢完了」但没人用过 | `sys_member_coupon.used_count` 是否被历次锁定累加（取消订单不回退）；必要时按第五节的应对处理 |
| 提示「已达每人上限」 | `countUsedByUser + countLockedByUser`：可能是有一笔 `WP` 单据还挂着 `locked` 记录，把它关闭/取消即可释放 |
| 校验通过但下单报不可用 | 服务端用完整金额再校验一次（门槛、应付 > 0）；`myCouponCheck` 只是前置提示 |
| 充值到账了券没核销 | 后台补录单不锁券，`markUsed` 影响 0 行静默失败；查 `coupon_use` 是否有对应 `biz_no` 的 `locked` 行 |
| 券码写错了想改 | `code` 不可改，只能新建一张并作废旧券 |
