开通与续费的唯一入口是 `MemberLevelOrderService`（`packages/admin-trade/server/trade-router/domain/member/MemberLevelOrderService.ts`），一张单据表 `sys_member_level_order` 同时承载购买、续费与「后台手工调整」三类行为，用 `pay_mode` 区分。能不能开通由 `levelOpenPolicy.ts` 里的 `resolveLevelOpenDecision` 决定，列表接口与落单硬校验共用这一份规则。

## 一、三条通道

```text
sysMember.myOpenLevel({ levelId, payMode, requestId })
  │
  ├─ 幂等第一道：按 requestId 回读已有单据 → 命中即按幂等返回（余额/免费单是 OD，在线单带回原二维码）
  ├─ 校验：等级存在且启用；0 元等级已开通 / 长期等级已激活 → 拒绝
  │
  ├─ price = 0 ─────────────▶ createFreeTx
  │      落单 pay_mode='free'、pay_amount='0.00' → markPaid(WP→OD) → 写等级生效（同事务）
  │      不生成支付单、不扣款；用户传的 payMode 被忽略
  │
  ├─ payMode = 'balance' ───▶ createBalanceTx（全部在同一事务）
  │      落单 WP → wallet.freeze(bizNo = 'mlv:{requestId}', ttlMinutes = 0)
  │      → attachFreeze → wallet.confirm(bizType = 'level_open')
  │      → markPaid(WP→OD) → 写等级生效
  │      余额不足抛 module.system.member.balanceInsufficient，整事务回滚（不落单、不扣款）
  │
  └─ payMode = 'online' ────▶ 事务内落 WP 单（expire_at = now + 30 分钟）
         事务外 payOrderService.createPayment({ bizType: 'memberLevel' })
         → 成功：回填 pay_order_id / 渠道快照，返回二维码三件套
         → 失败：单据 WP → FL（不动余额）
         等待回调或 myLevelOrderSync 推进到 OD
```

| 项 | 免费 | 余额 | 在线 |
| --- | --- | --- | --- |
| `pay_mode` | `free` | `balance` | `online` |
| 支付单 | 无 | 无 | `bizType = memberLevel`，`attach = memberLevel:{orderId}` |
| 生效时机 | 落单即刻 | 同一事务内 | 回调 / 主动同步 |
| 单号前缀 | `MLV` | `MLV` | `MLV` |
| 失败终态 | — | 抛错回滚 | `FL`（可重试） |

两点刻意设计：

- **余额通道的冻结 `ttlMinutes = 0`**：不设过期，释放权只属于本链路（这里立即确认），避免 `member:expire-freeze` 在事务中途把冻结释放掉。
- **在线通道的渠道预检放在落单之前**（`assertChannelReady`）：宁愿提前报 `payChannel.notConfigured` / `notVerified`，也不留下「已落单但没有支付单」的悬挂单据；回填 `pay_order_id` 失败时**保持 WP 而不是置 FL**，因为支付单已经真实落到渠道侧了。

## 二、期限计算式

`computeLevelEffect` 先算、`writeLevelEffect` 后写，两者都接收 `now`，保证单据的 `start_at` / `end_at` 与写回 `sys_member` 的 `level_start_at` / `expire_at` 完全一致。

| 场景 | 判定 | `expire_at` | `level_start_at` | `level_source` |
| --- | --- | --- | --- | --- |
| 长期等级 | `is_long_term = 1` **或** `duration_days <= 0` | `NULL`（永不过期） | 本次生效时刻 | `open` |
| 同等级续费 | `member.level_id = 目标等级` | `max(now, 当前 expire_at) + duration_days` | **保持原值**（没有则记本次） | `renew` |
| 异等级（升级 / 降级） | 其它 | `now + duration_days`（**剩余期限清空**） | 本次生效时刻 | `upgrade` |

三条关键语义：

- **长期等级永不产生到期时间**：哪怕调用方传了 `endAt`，`recordManualTx` 也强制写 `NULL`，`expire_at` 为 `NULL` 的档案不会被 `member:expire-level` 扫到。
- **续费只顺延、不重置起点**：`startAt` 取 `member.levelStartAt ?? now`，所以「连续续费 3 次」的生效起点仍是第一次，账单周期可追溯。
- **异等级立即生效且清空剩余期限**：这是「升级即换套餐」的语义，不是「叠加时长」。从 A 等级（还剩 20 天）升到 B 等级（30 天），结果是 B 等级从今天起 30 天，那 20 天不再折算。
- 时间比较用字符串字典序（`'YYYY-MM-DD HH:mm:ss'`，与 MySQL 同墙钟），所以 `expireAt > now` 就是「未过期」。

## 三、幂等：五道闸门

```text
① uk_member_level_order_request  同一 requestId 只落一单
② uk_member_level_order_out      out_trade_no 唯一
③ markPaid 条件更新 WP → OD      affectedRows = 0 视为并发已生效
④ uk_member_freeze_biz           biz_no = 'mlv:{requestId}'（同一提交只冻结/扣款一次）
⑤ uk_member_log_dedup            流水 dedup_key = 'level_open:mlv:{requestId}:{account}'
```

| 闸门 | 落点 | 命中后的行为 |
| --- | --- | --- |
| 提交级幂等 | `levelOrderRepo.findByRequestId`（**不过滤 `is_deleted`**） | 直接返回原单，`reused: true`；`userId` 不匹配抛 `requestIdConflict` |
| 唯一键冲突回落 | `recoverByRequestId`（`isDuplicateKeyError` / `AlreadyAppliedError`） | 回读原单按幂等返回，绝不把内部错误抛给用户 |
| 单据号唯一 | `uk_member_level_order_out`（`out_trade_no`） | 撞键即说明同一单号已存在，按上面的回落路径处理 |
| 生效闸门 | `repo.markPaid` 的 `where status = 'WP'` | 0 行 → 抛内部 `LevelOrderSettledError`，外层重读后返回「已生效」 |
| 冻结幂等 | `wallet.freeze` 的 `findByBizNo` 先查 | 已存在返回首次结果（`reused: true`），不重复占用余额 |
| 流水幂等 | `buildDedupKey('level_open', bizNo, account)` | 唯一键冲突抛 `AlreadyAppliedError`，事务回滚后按已入账返回 |

另有第六道**兜底复用**：在线支付时若已存在「同用户 + 同等级 + `online` + 未超时」的 `WP` 单（`findPending`），直接复用原单与原二维码，避免连点两次生成两张都能付的码；已超时的旧单先本地关单再落新单。

`requestId` 由前端每次提交生成并**在重试时保持不变**——它是幂等的前提，每次点击都换新值等于放弃第一道闸门。

## 四、后台手工调整：`pay_mode = 'manual'`

后台「会员管理 → 修改等级」走 `SysMemberService.changeLevel` → `MemberService.changeLevel`（领域层），它是**唯一**会写 `manual` 单据的路径。

| 事项 | 行为 | 原因 |
| --- | --- | --- |
| 单据 | `levelOrderRepo.insertManual` 落一张 `OD` 单，`price_amount` / `pay_amount` 固定 `'0.00'` | 手工调整没收费，金额为 0 才自洽 |
| 资金 | `freeze_id` / `pay_order_id` / `pay_channel_code` / `expire_at` / `request_id` 全部 `NULL` | 人工操作没有支付单，也没有幂等键（`uk_member_level_order_request` 允许多个 NULL） |
| 余额 | **绝不写 `sys_member_balance_log`** | 写了就破坏「余额 = Σ流水」，对账立刻报差异 |
| 写入条件 | 只有「等级变了」或「到期时间变了」才写 | 只改备注、原样回传同一个到期时间，都不算开通/续费行为 |
| 事务 | 与改档案**同一事务**（`recordManualTx` 只挂在 `memberLevelOrderServiceIn(tx)` 上，独立版刻意不暴露） | 避免「档案改了、留痕没写」或反之 |
| 期限优先级 | ① 目标等级是长期 / `longTerm = true` → `NULL`；② 显式 `expireAt` → 写该值（`null` = 清空）；③ 都没有 → `now + durationDays` | 与后台表单的三个输入对应 |
| 不写留痕的三类 | 注册自动分配默认等级（`level_source = 'default'`）、到期降级（`auto_expire`）、只改备注 | 都不是「开通/续费」，写进去会把开通记录退化成操作日志 |

所以「会员开通记录」页看到 `pay_mode = manual` 的单，含义是**运营手工改过一次等级或期限**，不代表用户付过钱。

## 五、到期自动降级

`member:expire-level`（默认禁用，每 10 分钟）调 `memberService(db).expireLevels()`：

```text
1 memberRepo.listExpiredLevelCandidates(now, 200)
    where status = 1 and is_deleted = 0 and expire_at is not null and expire_at <= now
    order by expire_at asc limit 200
2 逐条独立事务 expireMemberLevel：
    fallback = memberService.findDefaultLevel()       ← sys_member_level.is_default = 1
    memberRepo.expireLevel({ id, now, levelId: fallback?.id ?? null })
      set level_id = fallback(无默认等级则 NULL), expire_at = NULL,
          level_start_at = now, level_source = 'auto_expire', level_changed_at = now
      where id = ? and is_deleted = 0 and expire_at is not null and expire_at <= now   ← 二次判定
3 返回 { scanned, changedCount, failures[] }，单条失败不影响其余
```

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**UPDATE 里为什么要再判一次 `expire_at <= now`。**

扫描与降级之间隔着若干次事务：用户可能刚好在这一刻续费成功，`expire_at` 已经被顺延到未来。如果 UPDATE 只按 `id` 更新，就会把刚续过费的会员直接打回默认等级。二次判定让这条 UPDATE 影响 0 行，`expireMemberLevel` 返回 `false` 并被跳过。

另外三个边界：`status <> 1`（停用账号）不扫；`expire_at is null`（长期等级 / 默认等级）不扫；**降级不写开通单**，因为它不是开通/续费行为。
::

## 六、状态机与关闭、同步

```text
WP 待支付 ──markPaid（条件 WP→OD）──▶ OD 已生效（终态）
WP ──closeTx──────────────────────▶ CL 已关闭（终态）
WP ──渠道下单失败────────────────▶ FL 发起失败
CL / FL ──迟到的支付回调──────────▶ markPaidTx 直接 no-op，返回 reused = true
```

| 动作 | 做什么 | 不做 / 注意 |
| --- | --- | --- |
| `close`（后台 `system:memberLevelOrder:edit`） | 仅 `WP` 可关；`CL` 幂等返回；若 `freeze_id` 仍为 `FROZEN` 一并 `wallet.release`（释放不改余额）；本地关成功后**尽力**关渠道支付单 | 渠道关单失败被静默——虎皮椒等平台没有取消接口，关本地不等于阻止用户继续扫码 |
| `sync`（`system:memberLevelOrder:query`） | 本地非 `WP` 或没有 `pay_order_id` 直接返回本地状态；渠道 `OD` → `markPaid`；渠道 `CL`/`FL` → 本地 `close` 并写原因 | 与 `myRechargeSync` 同构的三段结构 |
| 回调（`PaidHandlers` 分派 `memberLevel`） | 走同一个 `markPaid` | 对 `CL` / `FL` **不抛错**，避免支付回调因一张已关闭单反复 5xx 无限重试 |

## 七、常见现象与定位

| 现象 | 先查什么 | 依据 |
| --- | --- | --- |
| 点了开通没反应 / 提示不可开通 | `myLevelOptions` 返回的 `blockedReason`：`freeAlreadyOpened`（0 元等级已激活或有过免费成功单）或 `longTermActive`（长期等级已激活） | `resolveLevelOpenDecision` |
| 余额够却报余额不足 | 冻结按「赠送金优先、不足部分走充值金」拆分，可用额 = 余额 − 冻结 | `WalletService.freeze` |
| 重复点击生成两笔扣款 | `request_id` / `mlv:{requestId}` 是否每次都变 | 见第三节 |
| 单据 `OD` 但等级没变 | 等级写回与 `markPaid` 同事务，理论上不会分叉；查 `sys_job_log` / evlog 里的 `LevelOrderSettledError` | `markPaidTx` |
| 到期了还显示老等级 | 任务默认禁用；且需要 `sys_job.status = 1` + `next_run_at` 才会有调度 | 见[定时任务与运维](/docs/main/member/jobs) |
| 手工调整后看不到单据 | 只改备注 / 原样回传到期时间不写留痕 | `MemberService.changeLevel` |
