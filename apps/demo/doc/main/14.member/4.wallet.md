余额的唯一写入口是 `WalletService`（`packages/admin-trade/server/trade-router/domain/wallet/WalletService.ts`），充值到账链路的编排在 `RechargeService.ts`。三条硬规则：**所有余额变更都在事务里**、**幂等靠唯一索引**、**余额不会被扣成负数**（全部是带守卫的条件更新，`affectedRows = 0` 即余额不足）。

## 一、两张主表

`sys_member_wallet`（Schema：`packages/admin-trade/server/drizzle/schema/system/memberWallet.ts`），一行一个用户，唯一键 `uk_member_wallet_user(user_id)`：

| 列 | 含义 |
| --- | --- |
| `recharge_balance` | 充值金余额 |
| `gift_balance` | 赠送金余额 |
| `frozen_recharge` / `frozen_gift` | 两列冻结额（**占用**，不是扣款） |
| `total_recharge` / `total_gift` / `total_consume` | 累计充值 / 累计赠送 / 累计消费，只增不改 |
| `version` / `status` | 版本号与启停 |

对外展示的「可用」是算出来的，不落库：

```text
可用充值金 = recharge_balance - frozen_recharge
可用赠送金 = gift_balance     - frozen_gift
可用总额   = 可用充值金 + 可用赠送金
```

`sys_member_balance_log`（`.../system/memberBalanceLog.ts`）是账实依据，唯一键 `uk_member_log_dedup(dedup_key)`：

| 列 | 含义 |
| --- | --- |
| `account` | `recharge` / `gift`，**按账户分别记账** |
| `direction` | `in` / `out` |
| `amount` / `balance_before` / `balance_after` | 金额与变动前后余额（before 由 after ± amount 反推，同一事务内精确） |
| `biz_type` / `biz_no` | 业务类型与业务单号 |
| `dedup_key` | 幂等键，格式固定为 `{biz_type}:{biz_no}:{account}`（`buildDedupKey`） |
| `operator_id` / `reason` / `remark` | 操作人与原因 |

金额约定：对外一律「元 + 两位小数字符串」，内部一律换算成**整数分**做加减（`toCents` / `fromCents`，见 `packages/admin-trade/server/trade-router/domain/wallet/utils.ts`），单笔上限 `MAX_AMOUNT = 9999999999.99` 与 `decimal(12,2)` 对齐。所以库里不会出现 `0.30000000000000004` 这类值，写流水也不在 SQL 里对 `decimal` 做隐式浮点运算。

## 二、流水 `biz_type` 取值

| 值 | 含义 | 由谁写 |
| --- | --- | --- |
| `recharge` | 充值到账（`biz_no` = 充值单 `out_trade_no`；赠送金用 `{outTradeNo}:gift`） | `RechargeService.creditLoaded` |
| `register_bonus` | 注册赠金 | `MemberService.grantRegisterBonus` |
| `gift_system` | 系统赠送 | 后台「发放赠送金」（`system:member:grant`） |
| `gift_campaign` | 活动赠送 | 同上 / 充值券附带的赠送金 |
| `adjust` | 手工调账（加 / 减），`biz_no` = `adjust:{requestId}` | 后台「手工调账」（`system:member:adjust`） |
| `consume_confirm` | 业务消费确认实扣 | 订单侧 `wallet.confirm`（默认值） |
| `level_open` | 会员等级开通 / 续费扣款 | 开通域 `wallet.confirm({ bizType: 'level_open' })` |
| `gift_expire` | 赠送金过期扣减（`biz_no` = `gift_expire:{batchId}:{amount}`） | `member:expire-gift` 任务 |

**冻结与释放不写流水。** 它们属于「预扣状态」而不是余额变动，记录在 `sys_member_freeze` 的状态机与时间戳里。这是 `余额 = Σ(in) − Σ(out)` 能恒成立的前提。

## 三、冻结 → 确认 / 释放

```text
freeze({ userId, bizNo, amount, subject, attach, ttlMinutes })
  1 按 bizNo 回读：已存在 → 返回首次结果（reused: true），不重复占用
  2 ensureWallet（并发下撞唯一键则回读）
  3 拆分：可用赠送金优先，不足部分走充值金
  4 walletRepo.freezeFunds：两列冻结同时 +、条件带可用额判断 → 0 行即余额不足
  5 写 sys_member_freeze（status = 'FROZEN'，expire_at = ttl > 0 ? now + ttl : NULL）
```

| 动作 | 前置状态 | 余额变化 | 写流水 | 说明 |
| --- | --- | --- | --- | --- |
| `freeze` | — | `frozen_gift` / `frozen_recharge` 增加 | 否 | 默认 TTL 30 分钟；`ttlMinutes: 0` → `expire_at = NULL`，永不过期 |
| `confirm` | 必须 `FROZEN` | 冻结转实扣（`settleFrozen`），`total_consume` 累加 | 是，两个账户各一条 `out` | `bizType` 可覆盖为 `level_open`；同时按 FIFO 扣赠送金批次 |
| `release` | 必须 `FROZEN` | 只清冻结，**不改余额** | 否 | 用于业务失败 / 人工释放 |
| `expireFreezes` | `FROZEN` 且 `expire_at <= now` | 同 `release`，状态记 `EXPIRED` | 否 | 任务 `member:expire-freeze` |

`confirm` / `release` 都是「先条件更新状态（`markConfirmed` / `markReleased`），再动余额」：抢不到状态的那一次直接按幂等返回，因此重复确认、重复释放都只生效一次。`settleFrozen` / `releaseFunds` 返回 0 行说明冻结额与钱包对不上，抛 `module.system.member.walletInconsistent` 让整笔回滚，等人工或对账处理。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**谁释放自己创建的冻结，是一条硬约定。**

- **订单余额单**：`ttlMinutes = 0`（`expire_at = NULL`），释放权只归订单侧——用户取消、后台关闭、`order:expire-close` 超时任务；它就是余额单唯一的自动释放触发点。
- **等级开通单**：同样 `ttlMinutes = 0`，但冻结后**立即在同一事务内 confirm**，正常不会留下 `FROZEN` 的单子；`closeTx` 仍会先查状态、只在确实还冻结时释放。
- **`member:expire-freeze` 只捞 `expire_at` 非空的冻结**，所以上面两类（`ttl = 0`）永远不会被这个任务碰到；它兜的是宿主业务直接 `wallet.freeze(...)` 未传 TTL 的默认 30 分钟场景。
::

## 四、赠送金批次

`sys_member_gift_grant`（`.../system/memberGiftGrant.ts`，唯一键 `uk_member_gift_biz(biz_no)`）把赠送金按「批」管理，才能表达「这一批 3 个月后过期」：

| 列 | 含义 |
| --- | --- |
| `amount` / `remain_amount` | 批次面额 / 剩余额 |
| `source` | `register` / `system` / `campaign` |
| `expire_at` | `NULL` = 永不过期 |
| `biz_no` | 与入账流水同源（充值赠送金是 `{outTradeNo}:gift`） |
| `status` | `active` / `used`（用尽）/ `expired`（过期） |

不变量与顺序：

- **「有效批次剩余之和 = 赠送金余额」**（`giftGrantRepo.sumActiveRemain`，对账用它）；`credit` 时**先建批次再改余额**，就是为了让这条等式在任意时刻都成立。
- **扣减顺序**：`expire_at` 升序，永不过期的批次排最后（`listActiveByUser`），即先到期先花。
- **过期处理**（`expireGiftBatches`）只扣「可用」部分（`gift_balance - frozen_gift`）：被冻结占用的那部分留给下一轮，避免把可用余额扣成负数、也避免冻结单确认时失败；先扣批次台账、成功后才扣钱包余额，顺序反了会出现「余额减了、批次还在」。

## 五、账实一致

逐账户的等式（**不能看两账户合计**——充值金多 100、赠送金少 100 时合计仍然相等）：

```text
recharge_balance = Σ(in | account = recharge) − Σ(out | account = recharge)
gift_balance     = Σ(in | account = gift)     − Σ(out | account = gift)
Σ(active 批次 remain_amount) = gift_balance
coupon.used_count ≈ Σ(coupon_use.status = 'used')      ← 近似：释放不回退 used_count，见优惠码页
sys_member_recharge.status = 'OD'  ⇒ 该单号的 recharge 流水存在（且只有一条）
recharge_balance >= frozen_recharge ，gift_balance >= frozen_gift
```

| 入口 | 权限 / 调度 | 范围 | 返回 |
| --- | --- | --- | --- |
| `sysMemberBalanceLog.reconcile` | `system:memberBalanceLog:reconcile` | 传 `userId` 只校验该会员，否则全量分组 | `{ checkedCount, mismatches[], pendingRechargeCount }` |
| `sysMemberBalanceLog.rechargeRetry` | 同上 | 充值单 `WP` 且支付单 `OD`，单次 50 条 | 逐笔调 `credit` |
| 任务 `member:reconcile` | 每天 03:00（默认禁用） | 全量 `assertConsistency({ userId: null })` + `retryPending(200)` | 结果写 `sys_job_log.result` |

`WalletService.assertConsistency` 的返回是 `{ checkedUsers, mismatches: [{ userId, account, walletTotal, ledgerTotal, diff }] }`，**按账户逐条给出**；连「有流水但没有钱包行」「有钱包行但没有流水」两种情况都会报出来。它只校验、不改余额——差异交给人工处理，这是刻意的：自动「抹平」会把真实业务错误变成一笔看不见的调账。

## 六、手工调账与发放

| 动作 | 权限码 | 幂等键 | 约束 |
| --- | --- | --- | --- |
| 手工调账 | `system:member:adjust` | `adjust:{requestId}` → `dedup_key = adjust:adjust:{requestId}:{account}` | 必填原因（`adjustReasonRequired`）；减余额走条件更新，不足报 `balanceInsufficient`；扣赠送金时同步扣批次 |
| 发放赠送金 | `system:member:grant` | `gift:{requestId}` | 走 `wallet.credit`，同样先建批次 |
| 强制释放冻结 | `system:memberFreeze:release` | 冻结单 `biz_no` | 只清冻结，不动余额；已确认的单会被拒（`freezeNotFrozen`） |

补录充值单（`system:memberRecharge:add`）不发起支付、不锁券这条边界，见[充值流程](/docs/main/payment-flow/recharge)。
