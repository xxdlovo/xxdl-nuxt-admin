会员侧的自动化全部由定时任务完成：释放超时冻结、过期赠送金、补齐档案、日对账、等级到期降级，外加交易模块的超时关单。handler 注册在 `packages/admin-trade/server/jobs/handlers.ts`，由 trade 的 Nitro 插件在启动时 `registerSysJobHandlers` 注入基座；基座自己的执行器在 `packages/admin-core/server/sys-router/job/`。

## 一、六个任务总表

全部写在三个 DDL 里，**默认 `status = 0`（禁用）**：

| `job_code` | cron（`Asia/Shanghai`） | 做什么 | handler | 默认启用 |
| --- | --- | --- | --- | --- |
| `member:expire-freeze` | `0 0/10 * * * *`（每 10 分钟） | 释放超过 `expire_at` 仍未确认的消费冻结 | `walletService(db).expireFreezes()` | 否（`status = 0`） |
| `member:expire-gift` | `0 10 1 * * *`（每天 01:10） | 处理过期赠送金批次并写 `gift_expire` 扣减流水 | `walletService(db).expireGiftBatches()` | 否 |
| `member:backfill-profile` | `0 30 2 * * *`（每天 02:30） | 为没有档案的用户补建会员档案（幂等） | `memberService(db).onboard({ source: 'backfill' })` 循环 | 否 |
| `member:reconcile` | `0 0 3 * * *`（每天 03:00） | 全量钱包一致性校验 + 未到账充值补偿 | `assertConsistency({ userId: null })` + `rechargeService(db).retryPending(200, null)` | 否 |
| `member:expire-level` | `0 0/10 * * * *`（每 10 分钟） | 等级到期回落默认等级 | `memberService(db).expireLevels()` | 否 |
| `order:expire-close` | `0 0/5 * * * *`（每 5 分钟） | 关闭超时未支付订单：释放冻结 / 优惠码 / 回滚库存 | `orderService(db).expireClose()` | 否 |

DDL 位置：前 4 条在 `packages/admin-trade/sql/mysql-ddl-member-balance.sql`（`Part 3`，id 段 `...2001~2004`），`member:expire-level` 在 `packages/admin-trade/sql/mysql-ddl-member-level-price.sql`（`...2006`，按 `job_code` 幂等 upsert），`order:expire-close` 在 `packages/admin-trade/sql/mysql-ddl-goods-order.sql`（`...2005`）。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**`recharge:expire-close` 不存在。**

需求里常被提到「充值单超时自动关闭」，但代码里既没有这个 `job_code`，也没有对应 handler：`tradeJobHandlers` 只注册了上表 6 个；`sys_member_recharge.expire_at` 字段虽然写了 `now + 30 分钟`，但 `rechargeRepo` 没有 `listExpiredPending` 之类的扫描方法。

后果与替代手段：充值单不会自动过期，`WP` 会一直挂着，收尾只能靠三条路——会员页的 `myRechargeSync`（向渠道查一次并按结果到账或反向关闭）、后台「关闭充值单」（`system:memberRecharge:close`，会先确认未支付）、以及 `member:reconcile` 里的 `retryPending`（把「支付单已付但充值单未到账」的补上）。详见[充值流程](/docs/main/payment-flow/recharge)。
::

## 二、调度前提：`status = 1` 远远不够

派发任务的查询条件（`packages/admin-core/server/tasks/sys-job/dispatch.ts`）：

```text
where is_deleted = 0
  and status = 1                 ← 启用
  and running_status = 0         ← 上一轮没在跑
  and next_run_at <= now()       ← 已到下一次执行时间
order by next_run_at
```

所以「让任务跑起来」需要同时满足四点：

| # | 条件 | 说明 |
| --- | --- | --- |
| 1 | `sys_job.status = 1` | **必须从后台「启用」**（`sysJobService.enable`） |
| 2 | `sys_job.next_run_at` 有值且已到期 | 启用时按 `next_run_at(cron)` 重算；**手工 `UPDATE status = 1` 不会写这个字段，`next_run_at` 为 NULL 时 `lte(NULL, now)` 不成立，任务永远不被派发** |
| 3 | handler 已注册 | 未注册会在后台保存时报 `module.system.job.handlerMissing`（代码回滚后也会出现） |
| 4 | 自动调度已开启 | `nitro.scheduledTasks` 默认注释，需 `NUXT_JOB_SCHEDULER_ENABLED=true`；否则两个 task 只能手动调 |

细则：

- **手动执行不看 `status`**：`runSysJob` 只在 `triggerType === 'schedule'` 时检查 `status !== 1` 并返回 `{ skipped: true, reason: 'disabled' }`。所以禁用中的任务也能「立即执行」一次，这是验证 handler 是否可用的最快方式。
- **禁止并发靠 `running_status`**：派发条件里已有 `running_status = 0`；`SysJobRunner` 另外在 `running_status === 1 && concurrent === 0` 时跳过（`reason: 'running'`）。
- **错过不补跑**：单轮派发时若 `overdue > 60s` 且 `misfire_policy = 3`，直接跳过并把 `next_run_at` 推到下一次（`reason: 'misfire'`）；默认 `misfire_policy = 1`，会补跑一次。
- **执行完回写 `next_run_at`**：成功与失败都会按 `cron` 算下一次，但只有 `status === 1` 时才写（禁用态下写 NULL）。

## 三、逐个任务的细节

| 任务 | 扫描条件 | 单轮上限 | 返回结构 |
| --- | --- | --- | --- |
| `member:expire-freeze` | `sys_member_freeze`：`status = 'FROZEN' and expire_at <= now` | 200 | `{ scanned, releasedCount, releasedAmount }` |
| `member:expire-gift` | `sys_member_gift_grant`：`status = 'active' and remain_amount > 0 and expire_at is not null and expire_at <= now` | 200 | `{ scanned, expiredCount, expiredAmount }` |
| `member:backfill-profile` | 还没有会员档案的用户（`listUserIdsWithoutProfile`） | 200 | `{ scanned, createdCount, skippedCount, failureCount, failures }` |
| `member:reconcile` | 全量钱包 + 「充值单 WP 但支付单 OD」 | 200（补偿） | `{ checkedUsers, mismatchCount, mismatches, pendingRechargeScanned, recoveredCount, failedCount }` |
| `member:expire-level` | `sys_member`：`status = 1 and expire_at is not null and expire_at <= now` | 200 | `{ scanned, changedCount, failures }` |
| `order:expire-close` | `sys_order`：`status = 'WP' and expire_at <= now` | 200 | `{ scanned, closedCount, recoveredCount, failures }` |

三条与会员体系强相关的行为：

- **`member:expire-freeze` 只兜「默认 TTL」的冻结**：订单侧与等级开通侧的冻结都是 `ttlMinutes = 0`（`expire_at = NULL`），永远不会被它扫到——它们的释放权归各自的业务链路。
- **`member:expire-gift` 只扣「可用」部分**：某批次若被冻结占用，本轮只处理 `gift_balance - frozen_gift` 那一段，剩余额度留着等下一轮；顺序是「先扣批次台账、成功后才扣钱包余额」，反了会出现「余额减了、批次还在」。
- **`member:expire-level` 逐条独立事务**：单条失败不阻塞其余，`failures[]` 只回报不重试；降级 UPDATE 内部二次判 `expire_at <= now`，防止「扫描后、降级前用户刚续费」被误降级。详见[开通与续费](/docs/main/member/open-renew)。

## 四、结果、失败与告警钩子

任务执行日志由 `SysJobRunner.runSysJob` 统一写，**handler 自己不需要记执行日志**：

| 落点 | 内容 |
| --- | --- |
| `sys_job_log` | 每次执行一行：`status`（0 运行中 / 1 成功 / 2 失败）、`trigger_type`（schedule / manual）、`started_at` / `finished_at` / `duration_ms`、`result`（handler 返回值 JSON）、`error_message` / `error_stack` |
| `sys_job` | `last_run_at` / `last_success_at` / `last_fail_at` / `last_duration_ms` / `last_error` / `next_run_at` / `running_status` |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**告警要看 `result`，不能只看 `status`。**

`member:reconcile` 与 `member:expire-level` 的「差异 / 失败条目」是**返回值**，不是异常：即使 `mismatchCount > 0` 或 `failures[]` 非空，任务仍然是 `status = 1`（成功）。真正的失败只有两种：handler 抛错（`status = 2` + `last_error`）、或进程中途退出导致日志停在 `status = 0`。

所以监控口径建议两条：① `sys_job_log.status = 2` 或 `sys_job.last_error is not null` → 告警；② `member:reconcile` 的 `result.mismatchCount > 0` / `result.failedCount > 0` → 告警，`result.mismatches` 里逐条带 `userId` / `account` / `walletTotal` / `ledgerTotal` / `diff`。

**任务执行本身不写 `sys_system_log`。** 那张表只记 tRPC 接口与 `server/api` 端点的调用（`loggerMiddleware` / `apiOperationLog`），任务没有请求上下文。唯一相关的一条是「后台点『立即执行』」这个 mutation 会留下一条操作日志——它证明「谁在什么时候手动触发过」，不代表执行结果。两张表的对比见[执行日志与排查](/docs/main/scheduled-jobs/logs)。
::

## 五、手动执行入口

| 入口 | 位置 / 接口 | 权限 |
| --- | --- | --- |
| 后台页面 | `/system/job`，行操作「立即执行」 | `system:job:run` |
| tRPC | `sysJob.runNow(id)` → `runTask('sys-job:run', { triggerType: 'manual' })` | `system:job:run`，限流 9 次 / 60 秒 |
| 查看结果 | `/system/job-log`，可按 `jobId` 过滤 | `system:jobLog:list` |

手动执行会跳过 `status` 检查，但**仍受并发保护**与限流约束；执行结束后 `next_run_at` 只有在任务启用时才会被推进，所以「先手动跑通，再启用」是推荐的初始化顺序。

## 六、运维排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 任务「启用」了但从不执行 | `nitro.scheduledTasks` 未开启（`NUXT_JOB_SCHEDULER_ENABLED` 不为 `true`） | 先手动执行验证，再开自动调度 |
| 手工 `UPDATE status = 1` 后仍不执行 | `next_run_at` 为 NULL | 从后台点一次「启用」（会重算），或手动补 `next_run_at` |
| 报 `handlerMissing` | 未注册 / `job_code` 与 `handler_code` 拼错 / 代码回滚 | 对齐 `tradeJobHandlers` 里的 `code` |
| 日志停在 `status = 0` | 进程执行中崩溃 | 检查部署日志，必要时把 `running_status` 改回 0 |
| `member:reconcile` 天天报差异 | 有人绕过 `WalletService` 直接改余额，或历史数据问题 | 按 `mismatches` 逐账户核对，勿自动抹平 |
| 到期会员没降级 | 任务禁用；或 `sys_member_level` 没有 `is_default = 1` 的等级（降级后 `level_id` 变 NULL） | 启用任务；先配默认等级 |
| 赠送金「过期了但余额没变」 | 批次被冻结占用中（只扣可用部分），或任务未启用 | 等冻结结算后下一轮；确认任务状态 |
| 充值单长期停在 `WP` | 没有自动过期任务（见第一节提示块） | 用会员页同步 / 后台关闭 / `rechargeRetry` 收尾 |
