本页按「现象 → 先看什么 → 结论」组织。所有订单侧的排查入口都离不开三个字段：`status`（资金）、`fulfill_status`（履约）、`close_reason` / `fail_reason`（原因留痕），后台订单详情弹窗已经把这几项和完整时间轴放在一起（`app/pages/system/order/components/sys-order-detail.vue:111-124,285-318`）。

## 一、下单报「商品库存不足」

`module.system.order.stockNotEnough` 只在**条件 UPDATE 影响行数为 0** 时抛出（`server/trade-router/domain/goods/GoodsService.ts:159-166`）。

| 检查项 | 说明 |
| --- | --- |
| 商品是否 `unlimited_stock = 1` | 是则**不会**扣库存，也不会因为库存报错 |
| `stock >= quantity` | 扣减 SQL 要求 `stock >= :quantity`（`domain/goods/repo/goodsRepo.ts:52-62`），不是 `>` |
| 商品是否已被逻辑删除 | 扣减 SQL 带 `is_deleted = 0`；**商品不存在 / 已删同样返回影响行数 0，被统一报成「库存不足」**（`goodsRepo.ts:48-51` 注释） |
| 是否是服务类多份 | 服务类数量被强制为 1（`domain/order/OrderService.ts:179`），不会因为数量超库存报错 |

并发下的「超卖」不会发生：库存是条件 UPDATE，不是「先查再改」（`goodsRepo.ts:1-6`）。真正的风险是**下单失败后库存没回滚**——回滚只发生在这三处：在线支付单创建失败（`OrderService.ts:321`）、关闭订单（`:472`）、取消（同一路径）。若发现库存长期少算，按订单 `status = 'WP'` 且 `expire_at` 已过期、但超时任务未启用去查（见第八节）。

## 二、优惠码不可用

`resolveCoupon()` 在**下单事务内的第 6 步**执行（`domain/order/OrderService.ts:190-195`），全部错误码来自会员域（`domain/member/MemberService.ts:333-389`）：

| 错误码 | 含义 | 检查点 |
| --- | --- | --- |
| `module.system.member.couponNotFound` | 码不存在 | 是否输错；码是否在 `sys_member_coupon` 里 |
| `module.system.member.couponDisabled` / `couponVoided` | 已停用 / 已作废 | `status`（1 启用 / 2 作废） |
| `module.system.member.couponNotStarted` / `couponExpired` | 不在有效期 | `valid_from` / `valid_to` |
| `module.system.member.couponSceneMismatch` | 场景不匹配 | 订单只能用 `scene = 'consume'`（或 `all`）的券；`recharge` 场景的券在这里一定报错 |
| `module.system.member.couponMinAmount` | 没到门槛 | 门槛比对的是**商品金额**（`total_amount`，即券前金额） |
| `module.system.member.couponUsedUp` | 已用完 | `max_use` 与 `used_count` |
| `module.system.member.couponUserLimit` | 超过单用户上限 | 已用 + 已锁定的记录数（`perUserLimit`） |
| `module.system.order.payAmountInvalid` | 券把应付减到 ≤ 0 | 0 元订单不进入支付链路；换成门槛更低的券或不使用券 |

两个容易忽略的行为：

- **券是「锁定」而不是「核销」**：下单成功写的是 `sys_member_coupon_use` 的 `locked` 记录（`MemberService.ts:427-464`），订单关闭 / 在线支付失败时释放，只有支付成功才 `markUsed`。所以「券显示已锁定」是正常的中间态。
- **只有填了码才会走进这段逻辑**：`code` 为空直接返回 `null`，不报错（`MemberService.ts:333-337`）。

## 三、余额不足 / 冻结相关的报错

| 现象 | 结论 |
| --- | --- |
| 下单报 `module.system.member.balanceInsufficient` | 可用余额（赠送金 + 充值金，扣掉已冻结部分）不足。冻结拆分是「先赠送金、不足部分落充值金」，条件更新失败即抛此错（`domain/wallet/WalletService.ts:510-524`）。**整个下单事务回滚，订单不会落库**，所以数据库里查不到这单 |
| 下单成功但订单停 `WP` | 余额单的正常中间态：下单只**冻结**，`gift_amount` / `recharge_amount` 已回填，实扣要等「确认支付」（第四节）。页面提示语是「已冻结余额 ¥{}，请到「我的订单」确认支付」 |
| 确认时报 `module.system.order.freezeExpired` | 冻结单在确认前被人工释放了（或状态不是 `FROZEN`）。服务端会**用独立事务把订单关成 `CL`**，原因写「冻结已释放，订单自动关闭」，然后抛这个错（`domain/order/OrderService.ts:359-369,693-703`）。用户重新下单即可；若频繁出现，查是谁/什么任务在释放冻结 |
| `module.system.member.freezeNotFound` | `freeze_id` 指向的冻结单不存在（被硬删 / 数据不一致） |
| `module.system.member.walletInconsistent` | 冻结确认时余额扣减影响行数为 0，钱包数据与冻结单不一致，需要人工对账（`WalletService.ts:609-611`） |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**余额单的冻结永不自动过期。**`createTx` 传的是 `ttlMinutes: 0`，`expire_at` 落成 `null`（`domain/order/OrderService.ts:266-276`、`domain/wallet/WalletService.ts:526-529`）。所以「冻结被释放」只有三种来源：用户取消、后台关闭、超时任务关单。没有「冻结自动过期」这条路径，也就不会有「订单还在 `WP`、冻结却自己没了」的情况——出现这种组合一定是数据被人工改过。
::

## 四、在线支付单创建失败（订单变 `FL`）

现象：下单后订单状态是 `FL`，`fail_reason` 有值，用户看到的错误是 `module.system.order.payCreateFailed`（文案「发起支付失败：{message}」）。

处理顺序（代码见 `OrderService.ts:647-685`）：

```text
渠道下单（事务外）失败
   → 小事务 failOnlinePayment：
        markFailed(status = 'FL', fail_reason = message 截断 500)
        rollbackStock（把刚扣的库存还回去）
        releaseCoupon（释放锁定的优惠码）
   → 抛 module.system.order.payCreateFailed，并把原始 message 带出来
```

定位时看两处：

| 看哪里 | 期望 |
| --- | --- |
| 订单 `fail_reason` | 渠道返回的错误摘要（截断 500） |
| 支付记录页同一 `out_trade_no`（= 订单号）的 `FL` 支付单 | `provider_data.create` / `fail_reason` 里有渠道原始报文，见[下单、查询与状态流转](/docs/main/payment/orders)第四节 |

`fail_reason` 里 message 的常见来源是支付域的配置类错误：`module.system.payChannel.notConfigured`（没有可用渠道）、`providerUnsupported`（渠道类型未注册适配器）、`notifyUrlRequired`（回调地址推不出来）、`module.system.payOrder.amountInvalid` / `amountTooLarge`（金额问题）。这些错误码的判定规则见[渠道配置与适配器](/docs/main/payment/channels)。

`FL` 单只用于排查：它**已经回滚了库存与优惠码**，也允许删除，用户可以直接重新下单（`modules/order/SysOrderService.ts:98-115`）。注意重新下单要换新的 `requestId`（前端每次提交都会换）。

## 五、商城看不到二维码 / 二维码不刷新

| 现象 | 排查 |
| --- | --- |
| 下单成功后弹窗里提示「暂无二维码」 | 支付单的 `qr_image_url` / `qr_content` / `pay_url` 三者都为空。看支付单的 `provider_data.create` 与渠道响应字段兼容逻辑（`server/trade-router/domain/pay/providers/xunhupay.ts#pickResponseFields`），见[虎皮椒适配器](/docs/main/payment/xunhupay) |
| 二维码显示了但状态一直不更新 | 轮询走的是 `sysOrder.mySync`（5 秒一次、10 分钟超时、连续 3 次失败就停），它会外呼渠道查询；而 `PayOrderService.queryPayment` 有 **3 秒节流**。若渠道一直返回待支付，页面会一直停在 `WP`——先确认渠道侧是否真的收到钱，再看支付单 `provider_status` |
| 关掉弹窗后二维码没了，想再看 | 我的订单 → 详情 → 「查看支付码」按钮调 `myPayment`。它**只读本地支付单、不发渠道请求**，可以安全重复调用（`modules/order/SysOrderService.ts:296-328`）；余额单没有关联支付单，接口返回 `null` 字段，按钮也不会显示 |
| 轮询提示「自动同步已超时 / 连续失败」 | 10 分钟超时或连续 3 次请求失败，都是前端主动停机，不是服务端报错；手动点「同步」即可（文案键 `module.system.mall.pollTimeout` / `pollFailed`） |
| 订单已是 `OD` 但页面没变 | 轮询在恢复网络后才会推进；也可以直接点「同步」。服务端 `markPaid` 是幂等的，重复调用无副作用 |

## 六、服务类订单没有交付入口 / 交付遗漏

交付按钮的显示条件是 `status === 'OD' && fulfill_status === 'pending'`（`app/pages/system/order/index.vue:370-378`），服务端的校验是同一组条件（`domain/order/repo/orderRepo.ts:163-185`）。所以「看不到交付按钮」通常是下面三种：

| 订单状态 | 说明 |
| --- | --- |
| `fulfill_status = 'none'` | 这单的商品 `goods_type` 不是 `service`。**`goods_type` 是下单时的快照**，把商品改成服务类不会追溯历史单 |
| `status = WP` | 还没支付。余额单要先「确认支付」，在线单要等回调/同步 |
| `status = CL` / `FL` | 已关闭或发起失败，不可交付（`module.system.order.notFulfillable`） |

交付本身**不动资金**：`markFulfilled` 只写 `fulfill_status` / `fulfilled_at` / `fulfill_remark` / `fulfill_operator_id`（`domain/order/repo/orderRepo.ts:163-185`），也不产生余额流水。因此「已支付未交付」不会造成资金差异，只是服务没做完。

怎么发现遗漏：订单页的**待交付服务订单数**卡片是全量口径（`status = 'OD' and fulfill_status = 'pending'`，`orderRepo.ts:245-256`），这个数字长期不平就说明有交付积压；筛选「履约状态 = 待交付」可以直接列出这些单（`components/sys-order-search.vue:99-101`）。

## 七、订单删不掉

报 `module.system.order.deleteNotAllowed`（文案「只有已关闭或发起失败的订单可以删除（待支付订单请先关闭）」）。

| 状态 | 处理 |
| --- | --- |
| `WP` | 先「关闭订单」（会释放冻结 / 优惠码 / 回滚库存），再删 |
| `OD` | **不可删**：这是收入凭证。想纠正只能走退款流程（当前没有退款能力） |
| `CL` / `FL` | 可以删 |

批量删除时前端会先剔除不满足条件的行，只提交剩下的并在返回后提示跳过了几单（`app/pages/system/order/index.vue:290-322`）；服务端仍会逐单再校验一次（`modules/order/SysOrderService.ts:98-115,162-169`），所以绕过界面批量提交也不会误删。

另外提醒两点与删除有关的语义：

- 删除是**逻辑删除**（`is_deleted = 1`），只读查询都会过滤掉它；但唯一键 `uk_order_request` / `uk_order_no` **不包含 `is_deleted`**，所以「删掉一张 `CL` 单后用同一个 `requestId` 再下单」会撞唯一键并失败（详见第九节）。
- 商品删除没有「有订单不可删」的保护，这是刻意设计：订单字段是快照，删商品不影响历史单（`server/drizzle/schema/system/order.ts:9-12`）。

## 八、超时任务误关已支付订单（`recoveredCount`）

**结论先行：正常配置下不会「误关已支付订单」。**任务是安全的，因为它关单前先读**本地支付单**（`domain/order/OrderService.ts:741-787`）：

```text
status = 'WP' and expire_at <= now （单次 200 条）
   ├─ 本地支付单 status = 'OD'  → 不关单，改做 markPaid（计入 recoveredCount）
   └─ 其它                      → 释放冻结 → 释放优惠码 → 回滚库存 → 置 CL
```

但有两种真实风险要记住：

| 风险 | 表现 | 说明 |
| --- | --- | --- |
| 回调从未到达、本地支付单仍是 `WP` | 任务照常把这单关掉；此后 `sysOrder.sync` 因订单已非 `WP` 直接返回 `changed: false`，**不再自愈** | 任务只读本地状态、不发渠道请求（一次最多 200 单，逐单外呼不可接受）。这类单只能人工对账，特征：渠道已扣款、`sys_pay_order.status` 仍是 `WP` |
| 迟到回调打在已关闭的订单上 | 支付单会被置 `OD`，但 `markPaid` 抛 `module.system.order.notPayable`（订单已 `CL`），回调持续 5xx | 与上一条是同一批数据的两种表象 |

`recoveredCount > 0` 是**异常信号**：出现即说明有「支付单已支付但业务后置没走完」的单（回调 `onPaid` 失败，或订单是被主动查询推进的）。任务返回值的完整字段说明见[业务接入：bizType 分派](/docs/main/payment/integration)第七节。

还有一条**默认配置就存在的风险**：`sys_order.expire_at` 是下单后 15 分钟，而支付单的过期时间取渠道的 `order_timeout_minutes`（**默认 30 分钟**）。订单在第 15 分钟被关成 `CL` 后，用户手里的二维码在渠道侧还能付到第 30 分钟；真付了就是「钱在渠道、订单 `CL`、支付单 `OD`」，且没有任何接口能把 `CL` 改回 `OD`，只能人工处理。完整的成因与降低概率的做法见[订单支付流程](/docs/main/payment-flow/order-payment)第八节。

`failures` 里出现 `common.notExist` 通常意味着订单的 `pay_order_id` 指向了一张已被删掉的支付单。

任务本身的两个操作前提：DDL 里默认 `status = 0`，必须在定时任务页启用；且 handler 必须已注册（`server/sys-router/job/handlers.ts:163-170,172-180`），否则手动触发会报 `module.system.job.handlerMissing`。

## 九、重复提交与幂等键相关的坑

| 现象 | 原因 | 依据 |
| --- | --- | --- |
| 连点两次下单，落了两单 | `requestId` 是**每次提交现生成**的（`app/pages/system/mall/index.vue:422`），两次点击拿到两个不同的键。幂等键只保护「同一次请求被重复执行」 | `shared/system/order/input.ts:44-48` |
| 用同一个 `requestId` 提交两次，第二次返回原单并提示「该订单已存在」 | 这是设计行为：`reused: true` 表示命中幂等键 | `domain/order/OrderService.ts:627-641` |
| 删掉一张 `CL`/`FL` 单后用同一个 `requestId` 再下单，报内部错误 | `findByRequestId` 过滤 `is_deleted = 0`，而唯一键 `uk_order_request` 是全表的：预检通过、插入撞键，兜底再查也查不到（已删除），最终抛出内部错误 | `domain/order/repo/orderRepo.ts:50-58`、`server/drizzle/schema/system/order.ts:53` |
| 极低概率下单报内部错误（数据库唯一键冲突） | 订单号只生成一次、**没有撞号预检与重试**；`insert` 的 catch 把所有唯一键冲突都当成「同一 requestId 并发」，最终兜底查不到单而失败 | `OrderService.ts:207,244-251` |

结论：**前端每次提交都该用新的 `requestId`；需要「防连点」就禁用按钮，而不是复用旧键。**后台没有「新增订单」入口，不存在人工造单撞键的问题。

## 十、价格相关：等级价没生效 / 数字对不上

| 现象 | 检查点 |
| --- | --- |
| 会员按基础价成交（`price_source = 'base'`） | 该等级没配等级价，或会员档案没有等级（`level_id` 为 `null`）。`resolvePrice` 在没命中时也会带上 `level_id`，便于追溯（`domain/goods/GoodsService.ts:46-68`） |
| 商城列表与下单价格不一致 | 列表用批量解析（一次查全部商品的等级价）、下单用单条解析，规则相同；差异通常来自「两次请求之间等级价被改过」——商品弹窗保存等级价是**整体替换**，会删掉没提交的行 |
| 某个等级的价格莫名消失 | 保存等级价时提交的 items 不完整。整体替换的语义是「提交什么就是什么」，未提交的等级价会被物理删除（`domain/goods/repo/goodsLevelPriceRepo.ts:67-79`）；前端只有检测到改动才会调这个接口，以保护停用等级的行（`sys-goods-operate.vue:307,445-454`） |
| 商品价配成负数后商城/下单报 `module.system.member.amountInvalid` | 金额归一会拒绝负数，错误码来自钱包域，但触发点是商品价（`GoodsService.ts:50,64`、`domain/wallet/utils.ts:50-67`）。接口层不校验 `price` 正负，后台表单的 `:min="0"` 只在界面生效 |
| `price_source = 'member'` 从没出现过 | 会员协议价是**预留未实现**的能力，解析链路里没有这个分支（`domain/goods/types.ts:11-15`） |
