本页回答「钱和账为什么会不一致、怎么发现、怎么补」。结论先行：**业务侧的账实一致不靠事务跨模块，而靠「唯一键幂等 + 条件更新 + 可补偿」三件事**——因为支付单的状态推进与业务写入刻意不在同一个事务里（[业务接入：bizType 分派](/docs/main/payment/integration)第二节）。

## 一、三条等式

```text
① 可用额 = 余额 − 冻结额（按账户分别成立）
   available_recharge = recharge_balance − frozen_recharge
   available_gift     = gift_balance     − frozen_gift

② 余额 = Σ(in) − Σ(out)（按账户分别成立，只统计 sys_member_balance_log）
   recharge_balance = Σ(recharge 账户的 in) − Σ(recharge 账户的 out)
   gift_balance     = Σ(gift 账户的 in)     − Σ(gift 账户的 out)

③ 赠送金余额 = Σ(状态为 active 的批次 remain_amount)
```

| 等式 | 实现位置 | 谁在校验 |
| --- | --- | --- |
| ① | `toSnapshot()`（`WalletService.ts:118-138`） | 每次读钱包都会算，用户看到的就是可用额 |
| ② | 写流水与改余额在同一事务内成对发生（`WalletService.ts:377-400`） | `assertConsistency()`；全量对账任务 `member:reconcile` |
| ③ | `wallet.credit(account='gift')` 先建批次再加余额（`WalletService.ts:349-375`）；扣减时同步扣批次 | **没有落地校验**（见下） |

等式 ② 能被守住的关键是`insertLog` 的时机：**余额条件更新成功之后才写流水，两者在同一事务里**（`WalletService.ts:240-284`）。写流水撞唯一键时抛 `AlreadyAppliedError`，让整个事务回滚——所以「重复回调重复加钱」这种最常见的账实不一致在数据库层面根本不可能发生。

`balance_before` / `balance_after` 是反推出来的（`WalletService.ts:251-254`）：同一事务里刚做完条件更新，读到的就是本次操作后的真实值，`before = after ∓ amount` 因此精确。这两个字段是对账时定位「哪一步开始偏」的重要线索。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**等式 ③ 目前只有约定，没有校验。**

`giftGrantRepo.sumActiveRemain()`（`giftGrantRepo.ts:112-123`）的注释写着「对账用：应与钱包赠送金余额一致」，但**它没有任何调用方**，`assertConsistency` 也只看流水与余额。批次台账的维护在两处都偏「尽力而为」：

- `consumeGiftBatches()` 只扣得动的批次：`consumeRemain` 影响 0 行（批次余量不足）就跳过、继续下一批，不报错（`WalletService.ts:291-312`）。函数头上的注释说「失败不阻断资金主流程」（`WalletService.ts:286-290`），但它在 `confirm`（`:624`）与 `adjust`（`:480`）里都是**直接 `await`、没有 `try/catch`**——所以「跳过」是静默的，真正的数据库异常依然会让整个事务回滚；
- `adjust` 手工扣减赠送金时，若 active 批次剩余总额小于扣减额，循环结束后仍有 `remaining > 0`，**批次总额不会被继续扣**，此时 ③ 会偏大。

也就是说：**钱包赠送金余额是账实依据，批次表是到期台账。**当 ③ 不再成立时，受影响的不是余额，而是「赠送金什么时候被过期扣回」——`expireGiftBatches` 只扣得到批次里还剩的额度。怀疑批次数对不上时，直接按 `user_id + status='active'` 汇总 `remain_amount` 与 `sys_member_wallet.gift_balance` 手工比对。
::

## 二、为什么冻结 / 释放不写流水

`sys_member_freeze` 的 `FROZEN` 是一个**预扣状态**，不是余额变动：钱还在 `recharge_balance` / `gift_balance` 里，只是同时被记进了 `frozen_*`，于是「可用额」变小了。

| 动作 | 余额列 | 冻结列 | 流水 | 说明 |
| --- | --- | --- | --- | --- |
| `freeze` | 不变 | `frozen_*` + | **不写** | 预扣，只影响可用额 |
| `confirm` | `*_balance` − | `frozen_*` − | 写 `consume_confirm`（唯一一次） | 真正扣钱 |
| `release` | 不变 | `frozen_*` − | **不写** | 退回可用额，钱从未离开余额 |
| `expireFreezes` | 不变 | `frozen_*` − | **不写** | 同上，状态记为 `EXPIRED` |

这样设计的好处是等式 ② 保持干净：如果释放也写一条「入账」流水，`Σ(in)` 就会被凭空抬高，对账必须再引入「冻结中」这个维度去抵消。代价是**冻结单的状态与时间戳成为唯一的追溯线索**（`FROZEN → CONFIRMED / RELEASED / EXPIRED`，`confirmed_at` / `released_at` / `release_reason`），所以排查「钱被占住」时查的是 `sys_member_freeze`，不是流水。

`sys_member_freezes` 的状态流转全部是 `where status='FROZEN'` 的条件更新（`freezeRepo.ts:44-79`），因此**同一张冻结单只可能被确认或释放一次**；`WalletService.confirm` / `release` 对该状态的二次调用都在入口就幂等返回（`WalletService.ts:582-584`、`:666-668`）。

## 三、assertConsistency 的用法

```ts
// server/trade-router/domain/wallet/WalletService.ts:841-919
assertConsistency({ userId?: string | null })
  → { checkedUsers: number, mismatches: ReconcileMismatch[] }
// ReconcileMismatch = { userId, walletTotal, ledgerTotal, diff }
```

| 模式 | 查询 | 说明 |
| --- | --- | --- |
| 单用户（`userId` 有值） | `wallet.findByUserId` + `logs.sumNetByUser(userId)` | 流水净额按账户分组返回 `[{ account, net }]`（`balanceLogRepo.ts:75-89`） |
| 全量（`userId` 为空） | `wallet.listAllForReconcile()` + `logs.sumNetGroupByUser()` | 两条分组查询一次算完，避免逐用户回表（`walletRepo.ts:188-199`、`balanceLogRepo.ts:95-105`）。另外会**额外报出「有流水但没有钱包行」**的用户（人工清理过数据的痕迹，`WalletService.ts:899-916`） |

净额的 SQL 是 `sum(case when direction='in' then amount else -amount end)`，也就是等式 ② 的直接实现。

入口与权限：

| 入口 | 权限 | 返回 |
| --- | --- | --- |
| `sysMemberBalanceLog.reconcile`（后台余额流水页「一致性校验」） | `system:memberBalanceLog:reconcile`（`modules/memberBalanceLog/index.ts:16,51-54`） | `{ checkDate, checkedCount, mismatches, pendingRechargeCount }`，`pendingRechargeCount` 是**未到账补偿的待处理条数**（`SysMemberBalanceLogService.ts:144-156`） |
| `member:reconcile` 任务 | 每天 03:00 自动跑 | 结果写 `sys_job_log`：`{ checkedUsers, mismatchCount, mismatches[:20], pendingRechargeScanned, recoveredCount, failedCount }`（`handlers.ts:130-152`） |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**它只报不修。**对账任务的注释明确写了「只做校验与补偿，差异明细只回报不自动改余额」（`handlers.ts:124-129`）——补偿只针对**未到账的充值**，余额差异本身一律交人工。

还有一处实现与注释的差别要留意：函数头注释写的是「公式 `recharge_balance = Σ(in) − Σ(out)`（**按账户分别核对**）」（`WalletService.ts:836-840`），但实现比的是**两个账户的合计**：

```ts
// WalletService.ts:848-856（单用户分支；全量分支 :885-889 同构）
const walletTotal = addMoney(walletRow?.rechargeBalance ?? '0.00', walletRow?.giftBalance ?? '0.00')
const ledgerTotal = addMoney(rechargeLedger, giftLedger)
```

后果是：当充值金多出 X、赠送金同时少了 X 时，合计相同，**不会被报出来**。日常场景（赠送金过期、消费优先扣赠送金）不容易出现这种「互相抵消」的偏差，但严格来说校验粒度是「合计」而不是「分账户」。需要分账户确认时，按 `account` 分别汇总 `sys_member_balance_log` 与 `sys_member_wallet` 手工比对。
::

## 四、对账与补偿任务

全部 handler 在 `server/sys-router/job/handlers.ts`，调度定义在 DDL 的 `sys_job` 初始化数据里。

| 任务 | 调度 | 扫描条件 | 动作 | 返回值 |
| --- | --- | --- | --- | --- |
| `member:reconcile` | 每天 **03:00**（`0 0 3 * * *`，`mysql-ddl-member-balance.sql:343`） | 全量钱包 + 待补偿充值单（单次 200） | `walletService.assertConsistency()` + `rechargeService.retryPending(200, null)`（并发执行） | `checkedUsers` / `mismatchCount` / `mismatches[:20]` / `pendingRechargeScanned` / `recoveredCount` / `failedCount`（`handlers.ts:130-152`） |
| `member:expire-freeze` | 每 **10 分钟**（`0 0/10 * * * *`，`:340`） | `status='FROZEN' AND expire_at IS NOT NULL AND expire_at <= now`，单次 200（`freezeRepo.ts:82-94`） | 逐单 `markReleased(status='EXPIRED')` + `wallet.releaseFunds`；与钱包不一致时抛 `walletInconsistent` 整体回滚，保持 `FROZEN` 等人工处理（`WalletService.ts:798-834`） | `{ scanned, releasedCount, releasedAmount }` |
| `member:expire-gift` | 每天 **01:10**（`0 10 1 * * *`，`:341`） | `status='active' AND remain_amount > 0 AND expire_at <= now`，单次 200（`giftGrantRepo.ts:83-96`） | **只过期「可用」的那部分**（`gift_balance − frozen_gift`）：先扣批次 → 再扣余额 → 写 `gift_expire` 流水（幂等键带金额，同一批次分批过期不会互相顶掉）→ 余量为 0 时被 `markUsedIfEmpty` 置为 `used`（`WalletService.ts:719-795`） | `{ scanned, expiredCount, expiredAmount }` |
| `order:expire-close` | 每 **5 分钟**（`0 0/5 * * * *`，`mysql-ddl-goods-order.sql:174`） | `sys_order.status='WP' AND expire_at <= now`，单次 200 | 见[订单支付流程](/docs/main/payment-flow/order-payment)第八节 | `{ scanned, closedCount, recoveredCount, failures }` |
| `member:backfill-profile` | 每天 **02:30**（`0 30 2 * * *`，`:342`） | 没有会员档案的历史 `sys_user`，单次 200（`SysMemberService` 之外在 `MemberService.ts:497-499`） | 逐条 `member.onboard({ source: 'backfill' })`，幂等 | `{ scanned, createdCount, skippedCount, failureCount, failures[:20] }`（`handlers.ts:85-122`） |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**`member:expire-freeze` 在当前代码下扫不到任何余额单冻结。**

它依赖 `expire_at IS NOT NULL` 这个条件，而**当前唯一的冻结创建方**是订单下单（`OrderService.ts:268-276`），传的是 `ttlMinutes: 0`，于是 `expireAt = null`（`WalletService.ts:526-529`）。`DEFAULT_FREEZE_TTL_MINUTES = 30` 这个默认值（`WalletService.ts:44`）**没有任何实际调用方**——`wallet.freeze` 的全部调用点只有一个。

余额单冻结的释放触发点因此只有 `order:expire-close`（15 分钟）。如果这个任务停摆，余额单的冻结会一直占住可用额，且没有任何兜底；这一点在排查「用户说余额被占住」时要先确认。

另外，**充值单没有对应的超时任务**：`rechargeRepo` 没有 `listExpiredPending`，`sys_job` 里也没有 `recharge:expire-close`。充值单会一直停在 `WP`，只能靠会员自助同步 / 后台关闭 / 未到账补偿收尾。
::

批次的终态还有一个容易误解的地方：`sys_member_gift_grant.status` 的 `expired` 取值**实际上写不出来**。过期任务在扣完额度后先调 `markUsedIfEmpty`（条件 `remain_amount <= 0`，`active → used`，`WalletService.ts:782`），随后才判断「余量是否为 0」并调用 `markExpired`（`WalletService.ts:784-787`）——而 `markExpired` 的守卫是 `where status='active'`（`giftGrantRepo.ts:99-109`），此时状态已经是 `used`，**影响 0 行**。所以过期批次的终态是 `used`，`expired` 只存在于类型与 Schema 里。按状态筛选过期批次时不要只看 `expired`。

## 五、人工入口清单

| 想做什么 | 入口 | 权限 | 效果 / 注意 |
| --- | --- | --- | --- |
| 关掉一张不想要的充值单 | 后台充值单「关闭」→ `sysMemberRecharge.close` | `system:memberRecharge:close` | 只有 `WP` 可关；先确认未支付（本地支付单 `OD` 时抛 `paidCannotClose`，本地 `WP` 时再查一次渠道）；置 `CL` + 写 `fail_reason` + 关本地支付单 + 释放券 |
| 渠道已收款但充值单没到账 | 后台余额流水页「未到账补偿」→ `sysMemberBalanceLog.rechargeRetry` | `system:memberBalanceLog:reconcile` | 扫「充值单 `WP` + 支付单 `OD`」，单次 **50** 条，逐笔返回结果（`SysMemberBalanceLogService.ts:159-162`） |
| 怀疑余额不对 | 后台余额流水页「一致性校验」→ `reconcile` | `system:memberBalanceLog:reconcile` | 返回差异明细 + 待补偿条数，**不改数据** |
| 补一张历史充值（含直接补成已到账） | 后台充值单「补录」→ `sysMemberRecharge.create` | `system:memberRecharge:add` | 只落库不发起支付；给 `OD` 时先落 `WP` 再走 `credit`；单号缺省为 `PAY…`；已到账单不可改 / 不可删 |
| 手工扣回 / 补发余额 | `sysMember.adjust` / `sysMember.grant` | `system:member:adjust` / `system:member:grant` | 走 `WalletService.adjust`：必填原因，`bizNo = adjust:{requestId}` 防重复提交；扣赠送金时同步扣批次 |
| 释放一张冻结单 | 后台会员冻结页「释放」→ `sysMemberFreeze.release` | `system:memberFreeze:release` | `FROZEN → RELEASED` + 解冻。**若这是余额单的冻结，用户随后确认支付会失败**，订单被自动关成 `CL` 并提示 `freezeExpired` |
| 在线单付了但没完成 | 后台订单「同步状态」`sysOrder.sync` / 会员「同步状态」`mySync` | `system:order:sync` / 登录即可 | 查渠道：支付单 `OD` → 订单完成；`CL`/`FL` → 就地自愈关单。**订单已 `CL` 时直接返回 `changed: false`，救不回来** |
| 余额单实扣 | 后台订单「确认支付」`sysOrder.confirm` / 会员 `myConfirm` | `system:order:confirm` / 登录即可 | 确认冻结 + 核销券 + 加销量；重复点击幂等 |
| 关闭订单 | 后台订单「关闭」`sysOrder.close` / 会员 `myCancel` | `system:order:close` / 登录即可 | 释放冻结 → 释放券 → 回滚库存 → 置 `CL` |
| 服务交付 | 后台订单「交付」`sysOrder.fulfill` | `system:order:fulfill` | 只在 `status='OD'` 且 `fulfill_status='pending'` 时可用 |
| 支付单层面同步 / 关闭 | 支付记录页「同步状态」`sysPayOrder.syncStatus` / 「关闭」 | `system:payOrder:query` / `system:payOrder:edit` | 见[下单、查询与状态流转](/docs/main/payment/orders)；关闭是纯本地动作 |
| 看回调到底发生了什么 | 支付回调日志页 | `system:payNotifyLog:list` | 按 `out_trade_no` / `process_result` / `dedup_key` 查；`order_not_found`、`amount_mismatch` 这类结论只在这里留痕 |

## 六、失败矩阵

「表象」一列是用户或管理员实际看到的东西；「本地状态」是数据库里的样子；「恢复手段」按推荐顺序排列。

### 充值

| # | 步骤 | 表象 | 本地状态 | 恢复手段 |
| --- | --- | --- | --- | --- |
| 1 | 发起：没有启用渠道 | 报「未配置支付渠道」 | 无任何单据 | 配好渠道并「测试配置」通过后重试 |
| 2 | 发起：渠道未通过测试配置 | 报「渠道未通过测试配置（渠道名）」 | 无任何单据 | 去渠道配置点「测试配置」（`verifyStatus !== 1`，`RechargeService.ts:81-83`） |
| 3 | 发起：优惠码无效 | 报具体券错误码（不存在 / 停用 / 过期 / 场景不符 / 超限 / 未达门槛） | 无任何单据（`resolveCoupon` 在落单前） | 换券或不填券重试；前端本会先跑 `myCouponCheck`，这里是服务端兜底 |
| 4 | 发起：锁券失败（并发抢最后一张券等） | 报错；会员页会一直显示「待支付」且没有二维码 | 充值单 `WP`、`pay_order_id` 为空、无支付单（券已落 `locked` 或未落） | 后台关闭这张单；核对 `sys_member_coupon_use` 是否需要释放 |
| 5 | 发起：支付模块下单失败 | 报「发起支付失败」，渠道原始报文留在支付单 `provider_data` / `fail_reason` | 充值单 `FL` + `fail_reason`，券已释放；可能有同号 `FL` 支付单 | 修正渠道配置后重新发起（新单）；旧单可后台软删除 |
| 6 | 发起：`createPayment` 成功但回填 `pay_order_id` 失败 | 报「发起支付失败」，但渠道侧可能已生成可付的二维码 | 充值单 `FL`、`pay_order_id` 为空，同号支付单仍为 `WP` | 用户真扫码付款 → 回调会把充值单补成 `OD`（`credit` 的守卫是 `status <> 'OD'`）；否则按 `out_trade_no` 在支付记录页核对渠道账单，人工补录等额已到账单 |
| 7 | 到账：回调未到达（公网不可达 / 平台放弃重试） | 页面轮询 10 分钟后提示超时；或用户再过来说没到账 | 充值单 `WP`，本地支付单 `WP`（渠道侧可能已收钱） | 会员点「同步状态」→ `myRechargeSync` 查渠道并 `credit`；后台「未到账补偿」`rechargeRetry`（需支付单已 `OD`）；`member:reconcile` 每天 03:00 兜底 |
| 8 | 到账：回调到了但 `credit` 抛错 | 回调返回 5xx，**回调日志里完全不留痕**（抛错发生在写日志之前） | 充值单 `WP`，支付单 `OD` | 平台重试会自动重新分派（`onPaid` 至少一次）；没重试成功就用 `rechargeRetry` 或等 03:00 对账 |
| 9 | 到账：重复回调 / 重复补偿 | 无感（页面正常显示到账） | 第二次命中 `markCredited` 的 `status <> 'OD'` 或流水唯一键，返回 `reused: true` | 无需处理 |
| 10 | 关闭：已支付 | 后台报 `paidCannotClose` | 充值单仍 `WP`，支付单 `OD` | 不要关单；走同步或补偿到账（`credit` 只要求「非 `OD`」，因此`CL` 单也会被补成 `OD`） |
| 11 | 关闭：渠道查询失败时按本地状态关单，随后钱到了 | 用户先看到「已关闭」，稍后余额反而到账 | 支付单会被回调置 `OD`，充值单被 `credit` 置 `OD` | 属于自愈路径（充值侧对迟到支付安全）；核对流水即可 |
| 12 | 超时：用户一直没付 | 页面 10 分钟后停止轮询 | 充值单与支付单都停在 `WP`（**没有自动过期任务**） | 后台关闭；或等渠道侧支付单过期后由会员同步触发反向关单（支付单 `CL` → 充值单 `CL`） |

### 余额支付

| # | 步骤 | 表象 | 本地状态 | 恢复手段 |
| --- | --- | --- | --- | --- |
| 1 | 下单：余额不足 | 报余额不足 | **完全无痕**（订单 / 库存 / 券 / 冻结全部回滚） | 充值后重新下单 |
| 2 | 下单：券把应付减到 0 | 报 `payAmountInvalid` | 无痕 | 不支持 0 元单，换券 |
| 3 | 下单：重复提交同一 `requestId` | 提示「订单已存在」 | 原单原样返回 `reused: true` | 无需处理 |
| 4 | 确认：冻结已被人工释放 | 报「冻结已失效」；订单随后被自动关闭 | 冻结单 `RELEASED`，订单 `CL`，`close_reason='冻结已释放，订单自动关闭'` | 让用户重新下单；核对该冻结是否该释放（`system:memberFreeze:release` 是人工动作） |
| 5 | 确认：重复点击 | 提示成功，余额不再变 | 冻结单 `CONFIRMED`，流水唯一键命中 | 无需处理 |
| 6 | 确认：并发 | 一方按「已处理」返回 | `markCompleted` 只生效一次 | 无需处理 |
| 7 | 确认：结算时钱包与冻结额不一致 | 报「钱包数据不一致」 | 事务回滚，冻结单保持 `FROZEN` | 人工按 `sys_member_freeze` 与 `sys_member_wallet` 核对；必要时人工释放 |
| 8 | 超时未确认 | 订单到期后被关，可用额恢复 | 冻结单 `EXPIRED`，订单 `CL`（`close_reason='超时未支付'`），券与库存已回滚 | 无需处理；**前提是 `order:expire-close` 在跑**（`member:expire-freeze` 对 `ttl=0` 的冻结无效） |
| 9 | 超时后用户才点确认 | 报订单不可支付 | 订单 `CL` | 重新下单 |

### 在线支付

| # | 步骤 | 表象 | 本地状态 | 恢复手段 |
| --- | --- | --- | --- | --- |
| 1 | 下单：渠道下单失败 | 报「发起支付失败」 | 订单 `FL` + `fail_reason`；库存与券已回滚 | 修渠道后重新下单（新 `requestId`） |
| 2 | 下单：二维码为空 | 有订单但没码 | 订单 `WP`、支付单 `WP` | 看支付单 `provider_data.create` 与 `fail_reason`，见[排查手册](/docs/main/payment/troubleshooting) |
| 3 | 回调未到达 | 页面一直显示待支付 | 订单 `WP`、支付单 `WP`（渠道可能已收钱） | 会员 / 后台「同步状态」→ 渠道 `OD` 则 `markPaid`；否则等 `order:expire-close` |
| 4 | 回调到达但订单已被超时关闭（**默认配置下的高发场景**） | 用户付了钱，订单却显示已关闭 | 支付单 `OD`、订单 `CL`；回调持续 5xx | **只能人工**：`sync` 因订单非 `WP` 短路，后台也不能把 `CL` 改回 `OD`。给用户退款或线下补发，并在备注留痕。降低概率的办法是让订单 TTL 不小于渠道支付窗口 |
| 5 | 超时关单前发现本地支付单已 `OD` | 订单最终完成 | 订单 `OD`；任务结果 `recoveredCount > 0` | 无需处理，但 `recoveredCount` 出现即为异常信号：说明有业务后置没走完，去查回调日志 |
| 6 | 同步：支付单 `CL` / `FL` | 订单就地变成已关闭 | 订单 `CL`（原因「支付单已关闭 / 失败」），冻结 / 券 / 库存已回滚 | 无需处理；用户可重新下单 |
| 7 | 同步：订单已不是 `WP` | 报「状态未变化」并带上支付单状态 | 订单状态不变 | 若订单是 `CL` 而支付单是 `OD`，走上表第 4 行的人工路径 |
| 8 | 交付：订单未支付 | 报「不可交付」 | 订单 `WP` | 等支付成功 |
| 9 | 交付：非服务类商品 | 报「不可交付」 | `fulfill_status='none'` | 无需交付 |

## 七、排查清单

| 症状 | 按顺序查 | 结论特征 |
| --- | --- | --- |
| 「我充值了没到账」 | ① `sys_member_recharge`（按 `out_trade_no` 或会员）看 `status` / `pay_order_id` / `fail_reason` → ② `sys_pay_order`（同 `out_trade_no`）看 `status` / `paid_at` → ③ `sys_pay_notify_log`（同 `out_trade_no`）看 `process_result` / `message` → ④ `sys_member_balance_log`（`biz_no = out_trade_no`）看是否已有 `recharge` 流水 | ②`OD` + ①`WP` → 跑「未到账补偿」；③有 `order_not_found` / `amount_mismatch` → 数据不一致，看日志结论；④已有流水 → 已到账，问题在别处 |
| 「余额不对」 | 后台余额流水页「一致性校验」；`sys_member_wallet` 对 `sys_member_balance_log` 的净额（分账户看） | 有 `mismatches` → 按 `diff` 与 `balance_before/after` 找最早偏的那条流水 |
| 「钱被占住了」 | `sys_member_freeze`（`user_id` + `status='FROZEN'`）看 `biz_no` / `expire_at` | `expire_at` 为空（`ttl=0`）→ 是余额单冻结，只有 `order:expire-close` 会释放；确认任务是否在跑 |
| 「赠送金少了」 | `sys_member_gift_grant`（`user_id` + `status='active'`）看 `expire_at` / `remain_amount`；`sys_member_balance_log` 里 `biz_type='gift_expire'` 的流水 | 有 `gift_expire` 流水 → 被 01:10 的过期任务正常扣回；无流水但余额少 → 查 `consume_confirm` / `adjust` |
| 「券被扣了但没下单」 | `sys_member_coupon_use`（按 `biz_no`）看 `status` | `locked` 且业务单没有支付单 → 那张单卡在锁券失败 / 下单失败之间，需后台关闭或人工释放 |
| 「付了钱订单还是待支付」 | `sys_order.status` + `sys_pay_order.status` | 订单 `WP` + 支付单 `OD` → 同步即可完成（`expireClose` 也会补做，`recoveredCount++`） |
| 「付了钱订单已关闭」 | `sys_order.status='CL'` + `sys_pay_order.status='OD'` | 迟到支付，人工处理；见失败矩阵「在线支付 #4」 |
| 「回调好像没来」 | `sys_pay_notify_log` 按 `out_trade_no` / `created_at` 查；没有记录再查服务端错误日志 | 完全没记录 → 平台没打通或验签失败（`invalid_sign`）；有 record 但 `onPaid` 抛错 → 日志也没有（抛错在写日志之前） |
| 「任务没效果」 | `sys_job` 看是否启用与 `cron`，`sys_job_log` 看最近一次返回值 | `member:reconcile` 的 `mismatchCount` / `recoveredCount`、`order:expire-close` 的 `recoveredCount` / `failures` 是最直接的信号 |
