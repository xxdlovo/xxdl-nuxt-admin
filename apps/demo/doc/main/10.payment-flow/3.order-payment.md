title: 订单支付流程
description: 交易订单的余额支付（冻结 → 确认 / 释放）与在线支付（支付单 → 回调 / 同步自愈 → 超时关单）两条链路的分步说明与差异对照。
---

交易订单有两条支付链路，`sys_order.pay_mode` 是唯一分岔点（`domain/order/types.ts:11`）：

| `pay_mode` | 钱从哪来 | 下单时 | 支付成功时 | 有没有支付单 |
| --- | --- | --- | --- | --- |
| `balance` | 会员钱包余额 | **在事务里冻结**（赠送金优先） | `WalletService.confirm` 实扣冻结 | 没有 |
| `online` | 会员在渠道扫码付款 | 不冻结；事务外创建渠道支付单 | `OrderService.markPaid`，**不动余额** | 有（`bizType='order'`） |

两条链路共用同一套订单状态机与同一个幂等收敛点：`orderRepo.markCompleted` 的 `where status = 'WP'`（`orderRepo.ts:61`）。全部实现集中在 `server/trade-router/domain/order/OrderService.ts`，事务内能力是 `buildOrder(executor)`，事务与网络调用编排是 `orderService(db)`。

## 一、下单：两条链路共用的前半段

`orderService.create` → 外层先用 `requestId` 做一次幂等读（`OrderService.ts:627-631`）→ `settleWithIdempotentGuard` 包住 `createTx` 事务（`:634-641`）。

`createTx` 的执行顺序（`OrderService.ts:170-288`）：

| # | 动作 | 代码 | 失败的表现 |
| --- | --- | --- | --- |
| 1 | 按 `request_id` 查已有单，命中直接返回 `reused: true` | `:171-175` | 前端提示「订单已存在」，不重复落单 |
| 2 | `goods.assertPurchasable`（存在 + 上架） | `:177` | 商品下架 / 不存在 |
| 3 | 服务类商品必须填联系方式、数量恒为 1 | `:178-183` | `module.system.order.contactRequired` |
| 4 | 解析等级价：`members.getMember` → `goods.resolvePrice`，`totalAmount = 单价 × 数量`（分运算） | `:185-188` | |
| 5 | `members.resolveCoupon(scene='consume', amount=totalAmount)` | `:190-195` | 券错误码（与充值同一套校验，见[充值流程](/docs/main/payment-flow/recharge)第三节） |
| 6 | `payAmount <= 0` → 抛 `module.system.order.payAmountInvalid` | `:199-202` | 券把价格减到 0 时不进支付链路（不支持 0 元单） |
| 7 | `goods.decreaseStockOrThrow` 扣库存 | `:204` | 库存不足 → 整事务回滚 |
| 8 | `orderRepo.insert`：`status='WP'`、`expire_at = now + 15 分钟`、`fulfill_status = 服务类 ? 'pending' : 'none'` | `:206-243` | 撞 `uk_order_request` → `OrderAlreadySettledError` → 外层重读返回原单 |
| 9 | `members.lockCoupon(bizNo=orderNo)` | `:253-264` | 锁券失败 → 整事务回滚（券与库存都不留痕） |
| 10 | **仅余额单**：`WalletService.freeze({ bizNo: orderNo, amount: payAmount, ttlMinutes: 0, subject: 商品名, attach: orderId })` → `orderRepo.attachFreeze` | `:266-285` | 余额不足 → `balanceInsufficient` → 整事务回滚，**不落单** |

`ORDER_TTL_MINUTES = 15`、`ORDER_EXPIRE_BATCH_SIZE = 200`（`domain/order/types.ts:25,28`）。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**余额不足不落单。**`freezeFunds` 的 SQL 带双账户守卫（`gift_balance - frozen_gift >= giftAmount` 且 `recharge_balance - frozen_recharge >= rechargeAmount`，`walletRepo.ts:97-102`），余额不够时 `affectedRows = 0`，`WalletService.freeze` 抛 `module.system.member.balanceInsufficient`（`WalletService.ts:522-524`），整个下单事务回滚：**订单、库存扣减、券锁定全部撤销**。所以「用户点了下单但余额不够」在数据库里完全不留痕，也不消耗券的使用次数。

`ttlMinutes = 0` 是余额单的关键约定：`expireAt = ttl > 0 ? now + ttl : null`（`WalletService.ts:526-529`），冻结单**不设过期时间**，释放权只归订单侧（取消 / 后台关闭 / 超时任务）。这也是 `member:expire-freeze` 任务对余额单冻结无效的原因，详见[账实一致与补偿](/docs/main/payment-flow/consistency)第五节。
::

`requestId` 由前端每次提交生成（`app/pages/system/mall/index.vue:422` 用 `randomUuid()`），它是「防重复提交」的幂等键；`order_no` 由 `buildOutTradeNo('ORD')` 生成（`OrderService.ts:207`），随后被当作支付单的 `out_trade_no` 直接复用。

## 二、余额支付（1）：冻结

```ts
// OrderService.ts:266-285（createTx 内）
if (input.payMode === PAY_MODE_BALANCE) {
  // ttlMinutes = 0：冻结不设过期，释放权只归订单侧（取消 / 后台关闭 / 超时任务）
  const frozen = await wallet.freeze({
    userId: input.userId,
    bizNo: orderNo,
    amount: payAmount,
    subject: goodsRow.name,
    attach: orderId,
    ttlMinutes: 0,
    operatorId: input.operatorId ?? null
  })

  await repo.attachFreeze({
    id: orderId, freezeId: frozen.freezeId,
    giftAmount: frozen.giftAmount, rechargeAmount: frozen.rechargeAmount, ...
  })
}
```

冻结的拆分规则（`WalletService.ts:490-569`）：

```text
availableGift = gift_balance - frozen_gift
giftAmount    = min(availableGift, amount)
rechargeAmount = amount - giftAmount        ← 赠送金优先，不足部分落充值金
```

| 语义 | 落点 | 说明 |
| --- | --- | --- |
| 幂等 | `uk_member_freeze_biz(biz_no)`，`biz_no = orderNo` | 同一订单只冻结一次；重复调用返回首次结果并带 `reused: true`（`WalletService.ts:503-506`） |
| 防负余额 | `freezeFunds` 的条件更新 | 并发下只有一条 UPDATE 生效 |
| 只动冻结额 | `freezeFunds` 只加 `frozen_*` | **不写余额流水**（预扣不是余额变动） |
| 拆分明细 | `sys_order.gift_amount` / `recharge_amount` | 由 `attachFreeze` 回填，用户能看到「用了多少赠送金」 |
| 描述文案 | `wallet/utils.ts:102-111` `describeSplit` | 「赠送金 3.00 + 充值金 7.00」 |

## 三、余额支付（2）：确认实扣

入口有两个，都走 `OrderService.confirmTx`：

| 入口 | 说明 |
| --- | --- |
| 会员：`sysOrder.myConfirm` | `protectedProcedure`，先 `requireMyOrder` 校验归属，`operatorId = user.id`（`SysOrderService.ts:265-272`） |
| 后台：`sysOrder.confirm` | 权限 `system:order:confirm`（`modules/order/index.ts:25,59-62`） |

`confirmTx`（`OrderService.ts:332-389`）：

```text
1  row 不存在                        → common.notExist
2  row.status === 'OD'               → 幂等返回 reused: true
3  row.status !== 'WP'               → module.system.order.notPayable
4  row.pay_mode !== 'balance'        → module.system.order.wrongPayMode
5  WalletService.confirm(freezeId)   ← 真正的实扣
     抛 freezeNotFound / freezeNotFrozen → 转 OrderFreezeLostError（见下）
6  orderRepo.markCompleted（where status='WP'）
     affected 0 → OrderAlreadySettledError → 外层重读，按「已处理」返回
7  members.markCouponUsed(bizNo=orderNo)
8  goods.increaseSales
```

`WalletService.confirm` 内部（`WalletService.ts:572-648`）：

| 步骤 | 落点 | 幂等来源 |
| --- | --- | --- |
| 已是 `CONFIRMED` | 直接返回 `reused: true` | `:582-584` |
| 非 `FROZEN`（`RELEASED` / `EXPIRED`） | 抛 `module.system.member.freezeNotFrozen` | `:586-588` |
| `freezes.markConfirmed`（`where status='FROZEN'`） | `FROZEN → CONFIRMED`，写 `confirmed_at` | 影响 0 行 → 重读：已 `CONFIRMED` 则幂等返回，否则抛 `freezeNotFrozen`（`:591-600`） |
| `wallet.settleFrozen` | 余额 −、冻结额 −、`total_consume` +，四重守卫 | 影响 0 行 → `module.system.member.walletInconsistent`（`:602-611`） |
| 写 `consume_confirm` 流水（`gift` / `recharge` 各一条，金额 > 0 才写） | `dedup_key = consume_confirm:{orderNo}:{account}` | 唯一键；**只在确认瞬间写一次** |
| `consumeGiftBatches` | 按到期时间 FIFO 扣批次 `remain_amount`，用尽则置 `used` | 批次台账维护，失败不阻断资金主流程（`WalletService.ts:286-290` 注释） |

`settleFrozen` 的守卫（`walletRepo.ts:132-158`）是「余额够 + 冻结额够」，因此不会出现「扣成负数」或「扣了没解冻」。

失败分支 —— **冻结已被释放**（`OrderService.ts:359-369`、`:693-703`）：

```text
WalletService.confirm 抛 freezeNotFound / freezeNotFrozen
  → OrderFreezeLostError
      → 外层用独立事务 cancelTx({ reason: '冻结已释放，订单自动关闭', source: 'admin' })
      → 抛 module.system.order.freezeExpired 给用户
```

必须在独立事务里关单，否则「本次失败的事务回滚」会把关单一起回滚。触发场景：后台在「会员冻结」页人工释放了这张冻结单（`SysMemberFreezeService.ts:107-119`，权限 `system:memberFreeze:release`），或冻结单被 `member:expire-freeze` 置为 `EXPIRED`。

## 四、余额支付（3）：释放

取消 / 后台关闭 / 超时三条路径共用 `cancelTx`（`OrderService.ts:434-487`），顺序固定：

```text
1  row.status === 'CL'   → 幂等返回 reused: true
2  row.status !== 'WP'   → module.system.order.notClosable
3  WalletService.release(freezeId, reason)     冻结单释放（幂等）
     非 AppError 异常才上抛；状态类错误被吞掉（冻结被人工释放过）
4  members.releaseCoupon(bizNo=orderNo)        券回到可用
5  goods.rollbackStock(goodsId, quantity)      库存回补
6  orderRepo.markClosed（where status='WP'），写 closed_at 与 close_reason
```

`WalletService.release`（`WalletService.ts:651-710`）：已是 `RELEASED` / `EXPIRED` → 幂等返回 `reused: true`；只有 `FROZEN` 能释放（`freezes.markReleased` 带 `where status='FROZEN'`）；`wallet.releaseFunds` 只减 `frozen_*`，**不动余额、不写流水**。释放原因落 `release_reason`。

三种关闭来源与落库文案（`OrderService.ts:57-61`）：

| 来源 | 触发 | `close_reason` | 入口 |
| --- | --- | --- | --- |
| `user` | 会员自助取消 | 用户取消（`myCancel` 固定传「用户取消」，`SysOrderService.ts:275-284`） | `sysOrder.myCancel` |
| `admin` | 后台关闭 | 后台关闭，或入参 `reason` | `sysOrder.close`（权限 `system:order:close`）；同步自愈与冻结丢失也走这条 |
| `timeout` | 超时任务 | 超时未支付 | `order:expire-close` |

## 五、在线支付（1）：创建渠道支付单

`createTx` 结束时订单已经是 `WP`（**没有冻结**）。`payMode === 'online'` 时，渠道下单在**事务外**执行（网络调用，事务已提交，避免长事务，`OrderService.ts:647-658`）：

```ts
const payOrder = await payments.createPayment({
  outTradeNo: created.orderNo,        // 订单号即商户订单号
  amount: created.payAmount,
  subject: `订单 ${created.orderNo}`,
  bizType: 'order',
  attach: `order:${created.orderId}`,
  notifyUrl: input.notifyUrl ?? null,
  origin: input.origin ?? null
}, { operatorId: input.operatorId ?? null })
```

成功后用一个小事务回填 `pay_order_id` / `pay_channel_code`（`OrderService.ts:660-665`），并把二维码信息补进下单结果（`:667-674`）。下单失败时的收尾（`failOnlinePayment`，`:309-326`）：

| 动作 | 说明 |
| --- | --- |
| `orderRepo.markFailed`（`where status='WP'`） | 订单置 `FL`，`fail_reason` 截断到 500 字符 |
| `goods.rollbackStock` | 库存回补 |
| `members.releaseCoupon` | 券释放 |
| 抛 `module.system.order.payCreateFailed` | 前端提示，用户可以改支付方式重新下单 |

余额单的幂等返回会用 `fillPayInfo` 补二维码（`:876-895`）：若同一 `requestId` 重复提交，第二次不再调用渠道，而是**从本地支付单读回**二维码信息。

## 六、在线支付（2）：回调推进

```text
POST /api/pay/notify/{channel}   server/api/pay/notify/[channel].post.ts
  └─ payNotifyDispatcher(useDb(), { onPaid: → dispatchPaidOrder }).handleNotify(...)
       └─ dispatchPaidOrder(order, db)   bizType === 'order'
            └─ orderService(db).markPaid(order.outTradeNo, null)
```

`markPaidTx`（`OrderService.ts:395-428`）：

| 行为 | 说明 |
| --- | --- |
| `row.status === 'OD'` | 幂等返回 `reused: true` |
| `row.status !== 'WP'` | 抛 `module.system.order.notPayable`（**订单已关闭时回调会 5xx**，见第八节） |
| `orderRepo.markCompleted`（`where status='WP'`） | 置 `OD`、写 `paid_at` / `finished_at`；影响 0 行 → `OrderAlreadySettledError` → 外层重读按已处理返回（`:579-593`） |
| **不动余额** | 钱来自渠道，不是冻结的余额；`markPaidTx` 不调 `wallet.confirm`（`:391-395` 注释） |
| `members.markCouponUsed` + `goods.increaseSales` | 与余额单确认一致 |
| `fulfill_status` | 服务类仍是 `pending`，等后台「交付」；返回的 `giftAmount` / `rechargeAmount` 固定为 `'0.00'`（`:427`），因为在线单没有拆分明细 |

回调的幂等与失败语义（`onPaid` 是**至少一次**、抛错会 5xx 并让平台重试）在[业务接入：bizType 分派](/docs/main/payment/integration)第二、三节，本页不重复。

## 七、在线支付（3）：主动同步与自愈

回调依赖公网可达，所以会员与后台各有一个「同步状态」入口：

| 入口 | 权限 | 落点 |
| --- | --- | --- |
| `sysOrder.mySync`（会员） | 登录即可，先校验归属 | `OrderService.sync({ orderNo, operatorId: user.id })` |
| `sysOrder.sync`（后台） | `system:order:sync` | `OrderService.sync({ orderId, operatorId: 当前用户 })` |

`OrderService.sync`（`OrderService.ts:790-846`）：

```text
1  订单不是 'WP' 或没有 pay_order_id → { changed: false }（不请求渠道）
2  payOrderService.queryPayment(payOrderId)     向渠道查询（含 3 秒节流与过期兜底）
3  支付单 'CL' / 'FL'
     → cancelOrder({ reason: '支付单已关闭/失败', source: 'admin' })
       即就地自愈关单：释放冻结 → 释放券 → 回滚库存 → 置 'CL'
     → { changed: !reused }
4  支付单 'OD' → markPaid(orderNo, operatorId)  与回调同一条幂等路径
5  其它       → { changed: false, payOrderStatus }（仍待支付）
```

第 1 步的短路是个常见误解：**订单一旦不是 `WP`（已被关成 `CL` 或已完成 `OD`），同步就永远返回 `changed: false`**，不会再自愈。所以「超时关单之后才收到支付成功」这种单，靠 `sync` 救不回来。

`changed: false` 时前端给的是错误提示（会员页 `my-orders/index.vue:343-349`，后台 `order/index.vue:270-277` 是 warning 并带上支付单状态），用户据此判断是「还没付」还是「查不动」。

## 八、在线支付（4）：超时关单与 recoveredCount

`order:expire-close` 每 5 分钟跑一次（`0 0/5 * * * *`，`doc/main/mysql-ddl-goods-order.sql:174`），handler 直接调 `orderService(db).expireClose()`（`handlers.ts:163-170`）。扫描条件是 `status='WP' AND expire_at <= now`，单次 200 条（`orderRepo.ts:188-199`），**逐单一个事务，单笔失败不影响其余订单**。

```text
for 每张过期未支付订单：
  1  若有关联支付单，读**本地**支付单状态
        若是 'OD' → markPaid(orderNo, null) 补做业务后置，recoveredCount++（前提是真的改了状态）
                   continue（**不关单**）
  2  否则 cancelTx({ source: 'timeout', reason: '超时未支付' })
  3  真的关掉了且有关联支付单 → closeChannelPayment()（尽力关闭本地支付单，失败静默）
```

返回值 `OrderExpireCloseResult`（`domain/order/types.ts:94-100`）：

| 字段 | 含义 |
| --- | --- |
| `scanned` | 本次扫到的过期未支付订单数 |
| `closedCount` | 真正被关成 `CL` 的数量 |
| `recoveredCount` | **本地支付单已 `OD`、被补做业务后置而没关单的数量**。出现即说明有业务后置没走完（回调 `onPaid` 失败，或订单是被主动查询推进的） |
| `failures` | 逐单失败明细 `{ orderNo, message }` |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**默认配置下「订单先过期、渠道支付单还能付」是常态，不是异常。**

| 单据 | 过期时间 | 来源 |
| --- | --- | --- |
| `sys_order.expire_at` | 下单 + **15 分钟** | `ORDER_TTL_MINUTES`（`domain/order/types.ts:25`） |
| `sys_pay_order.expire_at` | 下单 + 渠道 `order_timeout_minutes`，**默认 30 分钟** | `PayOrderService.createPayment`（见[下单、查询与状态流转](/docs/main/payment/orders)第三节第 6 步） |

两者相差一倍。订单在 15 分钟被 `order:expire-close` 关成 `CL` 时，`closeChannelPayment` 只把**本地**支付单置为 `CL`（平台侧没有取消接口），用户手里的二维码在渠道侧仍然可付到 30 分钟。如果他在第 20 分钟付了：

```text
回调到达 → markPaidIfPending（where status <> 'OD'）→ 支付单被置为 'OD'（从 CL 也能被置为 OD）
        → dispatchPaidOrder → OrderService.markPaid
        → markPaidTx：row.status = 'CL' ≠ 'WP' → 抛 module.system.order.notPayable
        → 回调持续 5xx，平台反复重试，订单永远停在 'CL'
```

结果就是「钱在渠道、订单是 `CL`、支付单是 `OD`」。**补救手段只有人工**：`sysOrder.sync` 因订单不是 `WP` 直接短路（`:797-804`），后台订单页的 `update` 也只允许改备注（`SysOrderService.ts:148-153`），没有任何接口能把 `CL` 改回 `OD`。可行的处理是给用户退款或线下补发，并在支付记录 / 订单备注里留痕。

这条风险的成因与更完整的边界讨论见[业务接入：bizType 分派](/docs/main/payment/integration)第七节的提示块；本页只给出「时间参数不匹配」这个具体触发条件。要降低概率，应让订单 TTL 不小于渠道支付窗口（改 `ORDER_TTL_MINUTES` 或渠道 `order_timeout_minutes` 使两者一致），并在支付窗口内至少同步一次。
::

## 九、交付（服务类）

`sysOrder.fulfill`（权限 `system:order:fulfill`）→ `fulfillTx`（`OrderService.ts:490-517`）：

| 前置 | 行为 |
| --- | --- |
| 已 `delivered` | 幂等返回 `reused: true` |
| `status !== 'OD'` 或 `fulfill_status !== 'pending'` | 抛 `module.system.order.notFulfillable` |
| 通过 | `markFulfilled`（`where status='OD' AND fulfill_status='pending'`）→ `delivered`，写 `fulfilled_at` / `fulfill_remark` / `fulfill_operator_id` |

交付只改履约维度，不动资金、不动余额、不写流水。

## 十、两条链路对照

| 维度 | 余额支付 | 在线支付 |
| --- | --- | --- |
| 下单时资金动作 | 事务内冻结（赠送金优先、`ttlMinutes = 0`） | 无 |
| `sys_member_freeze` | 有（`biz_no = orderNo`） | 无 |
| `sys_pay_order` | 无 | 有（`out_trade_no = orderNo`，`biz_type = 'order'`） |
| 订单的 `freeze_id` / `gift_amount` / `recharge_amount` | 有值 | 空 |
| 支付成功入口 | `sysOrder.myConfirm` / `sysOrder.confirm` → `WalletService.confirm` | 回调 `markPaid` 或 `sysOrder.mySync` / `sysOrder.sync` → `markPaid` |
| 成功时是否写余额流水 | 写 `consume_confirm`（gift / recharge 各一条） | **不写** |
| 成功时是否扣赠送金批次 | 扣（FIFO，按到期时间） | 不涉及 |
| 超时 | `order:expire-close` 到点释放冻结（`member:expire-freeze` 对它无效） | `order:expire-close` 关单 + 尽力关本地支付单 |
| `expire_at` | 15 分钟（订单侧唯一释放触发点） | 订单 15 分钟；支付单按渠道配置（默认 30 分钟） |
| 迟到支付的后果 | 确认必失败 → 订单被自动关成 `CL`（发 `freezeExpired`） | 回调 5xx，订单停在 `CL`，纯人工 |
| 幂等键 | `uk_member_freeze_biz` + `uk_member_log_dedup` + `markCompleted` | `uk_order_no` / `uk_pay_order_out_trade_no` + `markCompleted` |

## 十一、页面行为细节

| 页面 | 行为 |
| --- | --- |
| 商城 `mall/index.vue` | 选 `payMode` 后下单：余额单提示「已冻结 {amount}」并跳转我的订单（`:429-435`）；在线单就地展示二维码并轮询（`:437-448`） |
| 我的订单 `my-orders/index.vue` | `status='WP' && payMode='balance'` 显示「确认支付」；`status='WP' && payMode='online'` 显示「同步状态」与「查看支付码」（模板 `:143-152`）；确认 / 取消 / 同步 / 看码分别是 `myConfirm`（`:305-318`）、`myCancel`（`:320-333`）、`mySync`（`:335-353`）、`myPayment`（`:355-366`）。**`myPayment` 只读本地支付单，不发渠道请求**，所以刷新页面后仍能重新看到二维码（`SysOrderService.ts:296-328`） |
| 订单管理 `order/index.vue` | 确认支付 / 关闭 / 同步 / 交付按钮分别由 `system:order:confirm|close|sync|fulfill` 控制（`:133-136`）；交付按钮只在 `status='OD'` 且 `fulfill_status='pending'` 时出现（`:371`）；关闭按钮只在 `status='WP'` 时出现（`:386`） |
