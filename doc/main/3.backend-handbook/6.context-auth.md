## createContext：每个请求的起点

`server/trpc/context.ts` 在每次 tRPC 请求开始时构造上下文：

```ts
export async function createContext(event: H3Event) {
  const session = await getUserSession(event)

  return {
    db: useDb(),
    event,
    session,
    user: session.user ?? null,
    currentPermissionCode: null as string | null,
    permissionCodes: null as string[] | null,
    dataPermission: null as DataPermission | null,
    skipDataScope: false
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `db` | Drizzle 实例 | 来自 `useDb()`，全进程共享一个连接池 |
| `event` | `H3Event` | 原始请求事件，供原生能力（读 cookie、写 session）使用 |
| `session` | session 对象 | 由 `getUserSession(event)` 解密得到 |
| `user` | `AuthUser \| null` | 未登录为 `null` |
| `currentPermissionCode` | `string \| null` | 当前接口要求的权限码，由权限中间件写入 |
| `permissionCodes` | `string[] \| null` | 当前用户权限码集合，惰性加载、请求内复用 |
| `dataPermission` | `DataPermission \| null` | 解析后的数据权限，请求内复用 |
| `skipDataScope` | `boolean` | `proc({ dataScope: false })` 写入的跳过标记 |

`AuthUser` 字段：`id`、`username`、`email`、`nickname`、`avatar`、`phone`、`gender`、`deptId`、`isAdmin`。这份数据同时是 session 里保存的用户快照。

## session 与 cookie

认证由 `nuxt-auth-utils` 提供，读写入口是自动导入的 `getUserSession` / `setUserSession` / `clearUserSession`，作用于 `ctx.event`。

cookie 规则在 `nuxt.config.ts` 的 `runtimeConfig.session` 中集中配置：

```ts
session: {
  password: '',            // 真实密钥由 NUXT_SESSION_PASSWORD 在运行时覆盖
  cookie: {
    path: '/',
    sameSite: 'lax',
    httpOnly: true,
    secure: sessionCookieSecure
  }
}
```

`secure` 的判定逻辑（`nuxt.config.ts` 顶部）：

1. 显式设置 `NUXT_SESSION_COOKIE_SECURE` 时以其为准；
2. 未设置时按 `NODE_ENV === 'production'` 判断——生产默认要求 HTTPS。

> 通过 `http://IP:端口` 访问时，浏览器会拒绝保存 `Secure` cookie，表现为「登录接口成功但后续仍是未登录」，此时需要在生产环境显式设置 `NUXT_SESSION_COOKIE_SECURE=false`。

登录成功后写入的 session 结构固定为 `{ user: <AuthUser>, loggedInAt: <ISO 字符串> }`。

## 密码工具

`server/utils/password.ts` 提供两个能力（底层为 `@adonisjs/hash`）：

| 函数 | 用途 |
| --- | --- |
| `verifyUserPassword(hash, plain)` | 校验明文与库中哈希是否匹配 |
| `isPlaceholderPassword(hash)` | 判断密码是否为占位标记，用于区分「OAuth 建号未设置密码」与「已设置真实密码」 |

密码校验只发生在 Service/路由层，Repo 不参与；查询用户详情时会剔除 `password` 字段，避免泄露到前端。

## 两处 auth 的职责区别

`auth` 相关代码分布在两个位置，职责完全不同：

### 一、OAuth 回调：原生路由

`server/routes/auth/[platform].get.ts` 处理 `GET /auth/:platform` 的回调：

- 支持平台：`github`、`google`、`gitlab`、`gitee`、`microsoft`（平台标识统一转小写比对）。
- 从 `sys_oauth_config` 读取启用中的配置，组装 `nuxt-auth-utils` 的 handler 配置；只传入配置行中真实存在的字段，避免空值遮蔽 `NUXT_OAUTH_<PLATFORM>_CLIENT_ID` 之类的环境变量兜底。
- 回调成功后归一化平台资料，调用 `sysOauthAccountService(ctx).loginByOAuth(...)` 完成建号/绑定，随后 `setUserSession` 写入会话，并用 `logRecorder` 记录登录日志。
- 失败时统一重定向到 `/login?oauthError=<i18nKey 或错误信息>`；成功重定向到 `/system/home`。
- 平台不支持、配置被禁用、缺少 clientId/clientSecret 都会记一条登录失败日志再重定向。

### 二、账号体系：tRPC `auth` 路由

`server/sys-router/auth/index.ts` 提供前端调用的账号接口：

| 方法 | procedure | 说明 |
| --- | --- | --- |
| `register` | `publicProcedure` | 注册，受系统参数 `systemRegisterEnum.key` 开关控制 |
| `login` | `publicProcedure` | 用户名密码登录，校验状态与密码后写 session，成败都记登录日志 |
| `logout` | `publicProcedure` | 清除 session |
| `me` | `publicProcedure` | 返回当前 session 中的 user（未登录为 `null`） |
| `profile` | `proc()` | 返回 RBAC profile（角色、权限码、菜单树） |
| `myProfile` | `proc()` | 当前用户资料，附带 `hasPassword` 状态位 |
| `updateProfile` | `proc()` | 更新资料并刷新 session 中的用户快照 |
| `changePassword` | `proc()` | 修改密码，必须校验原密码 |
| `setPassword` | `protectedProcedure` | 设置/修改密码，占位密码时无需原密码，已设置真实密码时必须校验原密码 |

`server/sys-router/auth/AuthService.ts` 只做 RBAC 读模型组装，不再做登录：

- `getRbacProfile(user)`：返回 `{ user, roles, permissions, menus }`，菜单树按 `sortOrder` 与名称排序，只保留可见（`visible = 0`）且非按钮（`type !== 2`）的菜单。
- `listPermissionCodes(user)`：返回扁平权限码集合，供权限中间件与原生路由鉴权使用。
- 两个方法都通过 RBAC 缓存读取角色与菜单，避免每次请求回表。

## 数据权限：buildScope

数据权限在 **Repo 查询阶段**生效，实现在 `server/drizzle/queries/buildScope.ts`。`sys_role.data_scope` 的取值含义：

| 值 | 含义 | 生效条件 |
| --- | --- | --- |
| `1` | 全部数据权限 | 不做范围限制（角色取到 1 即整体放开） |
| `2` | 自定数据权限 | 预留扩展点，当前返回空集合 |
| `3` | 本部门数据权限 | 条件为 `dept_id = 当前用户部门` |
| `4` | 本部门及以下数据权限 | 条件为部门 id 在「本部门 + 子部门」集合内 |
| `5` | 仅本人数据权限 | 按 `id` / `user_id` / `created_by` 匹配当前用户 |
| `6` | 部门及以下或本人数据权限 | 部门条件与本人条件用 `OR` 合并 |

### 解析流程（resolveDataPermission）

1. `ctx.dataPermission` 已存在则直接复用——一个请求内可能有多次查询，避免重复解析。
2. 未登录或 `isAdmin === 1` → 直接判定为「全部数据」，且 `hasDataScope = false`。
3. 查询当前用户的角色数据范围：`用户 → 用户角色 → 角色`，只取用户角色 `status = 1`、`isDeleted = 0` 且角色 `status = 1`、`isDeleted = 0` 的记录；任一角色为 `1` 则整体放开。
4. 按角色范围聚合出 `deptIds`：`3` 加入本部门，`4` / `6` 加入「本部门及以下」。
5. `includeSelf = 范围包含 5 或 6`。

### 部门与本人条件的拼装

- 当前用户部门优先取 `ctx.user.deptId`；老 session 没有该字段时按用户 id 回表查询并写回 `ctx.user.deptId`。
- 「本部门及以下」依据 `sys_department.path` 前缀匹配子部门；部门没有 `path` 时退化为只包含当前部门。
- 部门条件：表有 `deptId` 字段时用 `dept_id IN (...)`；`sys_department` 表本身用 `id IN (...)`。
- 本人条件：`sys_user` 表用 `id = 当前用户`；有 `userId` 字段的表用 `user_id = 当前用户`；否则退回 `created_by = 当前用户`。

### buildScope 的最终条件

```text
is_deleted = 0                    （表存在该字段时总是叠加）
+ 数据范围条件                     （部门范围与本人范围 OR 合并）
```

判定为「全部数据」或 `hasDataScope = false`，或命中了 `ctx.skipDataScope` 时，只保留 `is_deleted = 0`。如果表具备 `deptId` / `userId` / `createdBy` 等可控字段，但当前用户没有任何可用范围，则拼一个恒假条件 `1 = 0` 让查询返回空结果——**而不是放开权限**。

`buildScopedWhere(table, ctx, ...extraWhere)` 是对外使用的统一入口，通过 `mergeWhere` 把系统条件与业务条件用 `AND` 合并；`CommonRepo` 的所有查询都走它。

## 权限码从哪来

服务端校验只看 `sys_menu.code`，链路是：

```text
sys_menu.code → AuthService.listPermissionCodes() → ctx.permissionCodes → permissionMiddleware 比对
```

因此新增接口后必须同步新增菜单或按钮权限记录并授权给角色，否则除管理员外都会收到 `auth.forbidden`。
