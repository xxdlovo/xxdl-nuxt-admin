## 调用链与顺序

中间件通过 procedure 的 `.use()` 串联，`proc()` 已经把完整链路封装好，实际执行顺序固定为：

```text
loggerMiddleware  →  authMiddleware  →  permissionMiddleware  →  demoReadonlyMiddleware  →  dataScopeMiddleware
   操作日志           登录校验            权限码校验                 demo 只读                数据权限标记
```

来源可以对照 `server/trpc/init.ts`：

```ts
export const protectedProcedure = publicProcedure.use(loggerMiddleware).use(authMiddleware)

export const proc = (options: ProcOptions = {}) =>
  protectedProcedure
    .use(permissionMiddleware(options.permission))
    .use(demoReadonlyMiddleware(demoMode || options.readonly === true))
    .use(dataScopeMiddleware(options.dataScope !== false))
    .meta({ log: options.log})
```

- `publicProcedure` 与 `customProcedure` **不经过任何中间件**，因此登录、注册、OAuth 相关接口不记操作日志，也不做权限限制。
- `permissionProcedure(code)` 的链路是 `logger → auth → permission`，缺少 demo 只读与数据权限两个环节。

## 各中间件行为

### loggerMiddleware：操作日志

`server/trpc/middlewares/logger.ts`，负责把请求写入系统操作日志（`sys_system_log`）：

| 条件 | 是否记录 |
| --- | --- |
| `proc({ log: true })` | 记录 |
| `proc({ log: false })` | 不记录 |
| 未显式声明（`meta.log` 为 `undefined`），且类型是 `mutation` | 记录 |
| 未显式声明，且类型是 `query` | 不记录 |

`query` 默认不记录的原因很直接：`page` / `getOne` / `getById` 这类读操作过于频繁，写入审计日志会造成明显的写放大。

记录内容包含 tRPC 类型与路径、原始入参（`getRawInput()`）、耗时毫秒数与执行结果；成功与失败都会落库，失败走 `systemFailure`。经过 `proc()` 的接口 `log` 已被归一为默认值，只有未经过 `proc()` 的 procedure（例如 `protectedProcedure`）才会出现 `undefined`。

### authMiddleware：登录校验

`server/trpc/middlewares/auth.ts`：

```ts
const session = ctx.session ?? await getUserSession(ctx.event)
const user = ctx.user ?? session.user

if (!user) {
  throw new AppError('auth.unauthorized')
}

return next({ ctx: { ...ctx, session, user } })
```

- 优先复用 `createContext` 已解析的 session，缺失时再读一次 `getUserSession(event)`。
- 未登录抛 `AppError('auth.unauthorized')`，会被 `errorFormatter` 映射为 `UNAUTHORIZED` / HTTP 401。
- 校验通过后把 `session` 与 `user` 回写到 `ctx`，后续中间件与 Service 直接使用 `ctx.user`。

### permissionMiddleware：权限码校验

`server/trpc/middlewares/permission.ts`：

1. 未传权限码 → 直接放行（此时只要求登录，由 `authMiddleware` 保证）。
2. 把权限码写入 `ctx.currentPermissionCode`，供日志与排查使用。
3. 无 `ctx.user` → 抛 `AppError('auth.unauthorized')`。
4. `user.isAdmin === 1` → 直接放行，管理员绕过权限码校验。
5. 其余用户惰性加载 `ctx.permissionCodes`（同一请求只查一次），不包含该权限码则抛 `AppError('auth.forbidden')`。

权限码集合由 `authService(ctx).listPermissionCodes(user)` 从菜单表中汇总，并经过 RBAC 缓存（缓存机制见本站「缓存使用」章节）。

### demoReadonlyMiddleware：demo 模式只读保护

`server/trpc/middlewares/demo.ts`：

```ts
export function demoReadonlyMiddleware(enabled: boolean) {
  return async (opts: any) => {
    if (!enabled) return opts.next()
    throw new AppError('system.demoReadonly')
  }
}
```

- `enabled` 由 `proc()` 计算：`demoMode || options.readonly === true`。
- `demoMode` 来自 `NUXT_DEMO_MODE`，在模块加载时求值一次，不在每次请求重新读配置。
- 命中即抛 `AppError('system.demoReadonly')`，前端提示「演示环境不允许该操作」。

### dataScopeMiddleware：数据权限标记

`server/trpc/middlewares/dataScope.ts`：

```ts
export function dataScopeMiddleware(applied: boolean) {
  return async (opts: any) => {
    if (!applied) {
      opts.ctx.skipDataScope = true
    }
    return opts.next()
  }
}
```

它**本身不查询数据权限**，只在 `proc({ dataScope: false })` 时往上下文写一个标记位。真正的数据范围解析发生在 Repo 查询阶段：`buildScope` 读到 `ctx.skipDataScope` 就跳过部门/本人条件。

这样做的好处是不需要在 `buildScope` 里维护权限码白名单——是否跳过完全由接口声明决定。

## 参数怎么选

| 场景 | 写法 |
| --- | --- |
| 普通业务接口（默认） | `proc({ permission: 'system:xxx:list' })` |
| 只要求登录、不需要权限码 | `proc()` |
| 登录/注册/OAuth 等公开接口 | `publicProcedure` |
| 高频查询、不想写日志 | `proc({ permission: '...', log: false })` |
| 需要跨部门查看全量数据 | `proc({ permission: '...', dataScope: false })` |
| 编辑、删除等危险操作 | `proc({ permission: '...', readonly: true })` |

## 编写自定义中间件

新增通用逻辑（例如限流、租户校验）时，按参数化中间件模式实现，保持与现有中间件一致的写法：

```ts
import { AppError } from '#server/utils/appError'

export function exampleMiddleware(enabled: boolean) {
  return async (opts: any) => {
    if (!enabled) {
      return opts.next()
    }
    // 校验不通过时统一抛 AppError，交给 errorFormatter 翻译
    throw new AppError('system.exampleRejected')
  }
}
```

接入方式是在 `server/trpc/init.ts` 的 `proc()` 中追加一个 `.use()`，或者放在 `protectedProcedure` 的链路中。修改链路顺序必须同步更新本文档。

## 注意事项

1. 中间件内抛错一律使用 `AppError`，直接 `throw new Error()` 会退回 `system.serverError` 通用文案，前端无法定位原因。
2. `permissionMiddleware` 的权限码针对单个接口，不做通配，新增接口必须与 `sys_menu.code` 保持一致。
3. 管理员（`is_admin = 1`）会绕过权限码校验，但仍受 demo 只读与数据权限逻辑约束（数据权限对管理员直接判为「全部数据」）。
4. 中间件日志是同步等待写库的，给高频接口加 `log: true` 会明显增加响应耗时。
