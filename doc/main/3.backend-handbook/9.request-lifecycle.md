## 全链路时序

以一个分页查询接口（`$trpc.sysUser.page.query(...)`）为例，请求依次经过以下环节：

```text
app/pages/**                $trpc.sysUser.page.query(input)
   │
   ├─ customLink            错误统一 toast（先 clear 再 add）
   └─ httpLink              POST /api/trpc（一次调用一个请求；credentials: include，带 x-locale）
        │
server/api/trpc/[trpc].ts   createTRPCNuxtHandler({ endpoint, router, createContext })
        │
server/trpc/context.ts      createContext(event) → { db, event, session, user, ... }
        │
server/trpc/init.ts         proc() 组装的中间件链
        │
        ├─ loggerMiddleware        记录操作日志（query 默认不记）
        ├─ authMiddleware          校验登录，回写 ctx.session / ctx.user
        ├─ permissionMiddleware    比对权限码
        ├─ demoReadonlyMiddleware  demo 模式下拦截写操作
        └─ dataScopeMiddleware     仅写 skipDataScope 标记
        │
index.ts (router)           .input(schema) 由 Zod 校验，通过后调用 Service
        │
Service                    业务规则、生成主键、抛 AppError
        │
Repo (CommonRepo)           buildWhereBySchema → buildScopedWhere → buildScope
        │
MySQL                       实际查询 / 写入
        │
errorFormatter             错误归一化 + i18n 翻译
        │
前端                        表格渲染 / toast 提示
```

## 阶段拆解

### 一、前端调用

`$trpc` 由 `app/plugins/01.client.ts` 注册，链路上有两个 link：

| Link | 作用 |
| --- | --- |
| `customLink` | 捕获错误，先 `toast.clear()` 再 `toast.add({ title: data.type, description: message })` |
| `httpLink` | 请求 `POST /api/trpc`，`credentials: 'include'` 携带 session cookie，并注入 `x-locale` / `accept-language` 请求头 |

> 链路里没有 `retryLink`：请求失败不会自动重试，错误立即提示。
> 业务错误仍然由服务端映射为 4xx（`errorFormatter` + `resolveAppErrorStatus`），
> 便于前端按 `code` 分支、监控按状态码区分「请求有问题」与「服务端异常」。
>
> 使用 `httpLink` 而不是 `httpBatchLink`，同一时刻的多个调用会发出多个 HTTP 请求，不做批量合并。

### 二、服务端入口与上下文

`server/api/trpc/[trpc].ts` 用 `createTRPCNuxtHandler` 把 `appRouter` 挂到 `/api/trpc`，`createContext` 为每个请求创建上下文：

- `useDb()` 取连接池（模块级单例）。
- `getUserSession(event)` 解密 session，`user = session.user ?? null`。
- 初始化 `permissionCodes`、`dataPermission` 为 `null`（惰性加载），`skipDataScope` 为 `false`。

### 三、中间件链

按固定顺序执行（详见[中间件](/docs/main/backend-handbook/middlewares)）：

1. **日志**：`mutation` 默认记录，`query` 默认跳过；`proc({ log })` 可显式覆盖。因为日志中间件在链首，未登录、无权限等失败也会被记录为失败日志。
2. **登录校验**：未登录抛 `AppError('auth.unauthorized')`。
3. **权限码校验**：管理员直通；其他用户在权限码集合中比对，不匹配抛 `AppError('auth.forbidden')`。
4. **demo 只读**：命中即抛 `AppError('system.demoReadonly')`。
5. **数据权限标记**：仅在 `dataScope: false` 时写 `ctx.skipDataScope = true`。

### 四、入参校验

`.input(schema)` 的校验在中间件之后、resolver 之前执行：

- 校验失败产生 `ZodError`，由 `errorFormatter` 汇总所有字段错误消息，用「，」连接后返回；没有字段错误时回退到表单级错误或 `common.pleaseCheckValue`。
- 校验通过后 resolver 拿到强类型 `input`。

### 五、Service

- 生成主键（`randomUuid()`）、组装写入数据。
- 校验业务规则，例如定时任务会校验 handler 是否注册、时区是否支持、cron 能否解析。
- 查询未命中时抛 `AppError('common.notExist')`。
- 涉及字典/RBAC 的写操作在此处失效相关缓存。

### 六、数据访问与数据权限

Repo 的每一次查询都会经过两层条件构建：

```text
buildWhereBySchema(schema, table, dto)   → 业务查询条件（eq / like）
buildScopedWhere(table, ctx, ...条件)     → 系统条件 + 数据权限条件 + 业务条件（AND 合并）
```

`buildScope` 的逻辑：

- 表有 `isDeleted` 字段 → 追加 `is_deleted = 0`。
- `ctx.skipDataScope` 为真，或判定为「全部数据」，或用户没有任何数据范围配置 → 只保留基础条件。
- 否则按角色数据范围拼部门条件与本人条件，用 `OR` 合并；两者都为空但表具备可控字段时追加恒假条件 `1 = 0`，返回空结果而不是放开权限。

`resolveDataPermission` 的结果缓存在 `ctx.dataPermission`，一个请求内多次查询只解析一次。详见[上下文与鉴权](/docs/main/backend-handbook/context-auth)。

### 七、写操作额外发生的事

写接口（`create` / `updateById` / `remove` / `batchRemove`）在以上流程之外还会：

| 环节 | 行为 |
| --- | --- |
| 审计填充 | 新增自动补 `isDeleted = 0` 与 `createdBy` / `updatedBy`；更新强制剥离 `createdBy` / `createdAt` / `isDeleted` 并写 `updatedBy`；删除写 `isDeleted = 1` 与 `updatedBy` |
| 操作日志 | `mutation` 默认写入 `sys_system_log`，包含 tRPC 路径、原始入参、耗时与结果 |
| 缓存失效 | 字典、角色菜单、用户角色等写操作会失效对应的 memory 缓存 |
| demo 保护 | 声明了 `readonly: true` 的接口在 demo 模式下直接失败，不会进入 Service |

### 八、错误归一化与返回

`errorFormatter` 按错误来源分四条分支处理（`AppError` / Zod 校验错误 / 数据库错误 / 普通错误），输出统一的 `TRPCFormattedError`：`message`（已翻译）、`i18nKey`、`type`（错误分类，前端用作提示标题）、`code`、`httpStatus`、`timestamp`、`requestId`（本次请求的 evlog requestId，用于把前端报错对齐到运行日志）。

- `AppError` 会按 `resolveAppErrorStatus` 改写 `code` / `httpStatus`（400 / 401 / 403 / 404），其余分支沿用 tRPC 判定；
- 响应体默认**不含** `stack`，需要时用 `NUXT_TRPC_ERROR_STACK=true` 打开；
- 数据库错误的驱动原文与 SQL **一律只写日志、不返回客户端**；程序异常的原文只在非生产环境返回，生产环境统一为分类文案。

语言判定顺序为 `x-locale` 请求头 → `i18n_locale` cookie → `accept-language` → 默认 `en`。

## 各阶段失败模式

| 阶段 | 触发条件 | 结果 |
| --- | --- | --- |
| 前端 | 网络异常、5xx | `customLink` 直接 toast（不自动重试） |
| 未登录 | 无有效 session | `AppError('auth.unauthorized')` → `UNAUTHORIZED` / 401 |
| 无权限 | 权限码不在集合中 | `AppError('auth.forbidden')` → `FORBIDDEN` / 403 |
| demo 模式 | 接口声明 `readonly` | `AppError('system.demoReadonly')` → `FORBIDDEN` / 403 |
| 入参非法 | Zod 校验失败 | 字段消息聚合返回，`type` 为校验错误 |
| 记录不存在 | Service 查不到数据 | `AppError('common.notExist')` → `NOT_FOUND` / 404 |
| 数据权限 | 用户无任何可用范围 | 查询追加 `1 = 0`，返回空列表（不报错） |
| 数据库异常 | SQL 执行失败 | 识别 `cause.code` / `sql` / `constraint` → `system.dbError`；驱动原文与 SQL 只写日志，不返回客户端 |
| 未捕获异常 | 其他错误 | `system.serverError` 通用文案（原文仅非生产环境返回），响应不带 `stack` |

## 一个写操作的走查

以「新增定时任务」为例：

1. 前端提交表单，`useZodValidation` 用 `SysJobAddSchema` 先做一次前端校验。
2. `$trpc.sysJob.create.mutate(input)` → `POST /api/trpc`。
3. 中间件链：写日志 → 校验登录 → 校验 `system:job:add` → demo 模式拦截 → 数据权限标记。
4. 服务端用同一份 `SysJobAddSchema` 再校验一次入参。
5. `sysJobService(ctx).create(input)`：`validateTask()` 校验 handler / 时区 / cron，计算 `nextRunAt`，用 `randomUuid()` 生成 id，交给 Repo。
6. `CommonRepo.create` 填充 `isDeleted = 0` 与 `createdBy` / `updatedBy` 后写入。
7. `loggerMiddleware` 把 `mutation sysJob.create success <耗时>ms` 与入参写入 `sys_system_log`。
8. 返回 `true`，前端关闭弹窗并刷新列表；失败则 `customLink` 弹出服务端翻译好的错误消息。
