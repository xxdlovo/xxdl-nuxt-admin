## 一、sys_pay_channel 字段

渠道配置是支付模块的入口：每条记录代表「一个渠道平台 + 一套凭据 + 一套回调参数」。表结构定义在 `server/drizzle/schema/system/payChannel.ts`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(36) | 主键，由 `randomUuid()` 生成 |
| `config_key` | varchar(50) | 配置标识，唯一键 `uk_pay_channel_key`；前端示例 `xunhupay-personal` |
| `config_name` | varchar(50) | 配置名称，展示用（测试页渠道下拉显示的就是它） |
| `channel_code` | varchar(30) | 渠道类型，取值对应 `PayProvider.code`，当前只有 `xunhupay` / `mock` |
| `mode` | varchar(10) | 运行模式，默认 `live`；只有 `live`（正式）/ `test`（沙箱）两种取值 |
| `currency` | varchar(10) | 默认币种，默认 `CNY`；回调核对币种用同一字段 |
| `config` | json | 渠道私有配置；结构由所选渠道类型的 `fields` 决定，`secret` 字段存密文信封 |
| `notify_url` | varchar(500) | 异步回调地址；留空时下单会按请求 origin 推导 |
| `return_url` / `cancel_url` | varchar(500) | 同步跳转 / 取消跳转地址，适配器按需传给平台 |
| `order_timeout_minutes` | int | 默认 `30`；下单时用它计算订单的 `expire_at` |
| `is_default` | tinyint | 默认 `0`；全局唯一的默认渠道，下单不指定渠道时优先取它 |
| `verify_status` | tinyint | 默认 `0`：`0` 未验证 / `1` 已验证 / `2` 验证失败 |
| `verify_time` | timestamp | 最近一次「测试配置」的时间 |
| `verify_message` | varchar(500) | 最近一次验证的结论，写入前截断到 500 字符 |
| `status` | tinyint | 默认 `1`；渠道解析只取 `status = 1` 的行 |
| `sort_order` | int | 默认 `0`；同优先级渠道按它升序取 |
| `ip_allowlist` | varchar(500) | 回调来源 IP 白名单，逗号 / 空格 / 换行 / 分号分隔；留空表示不校验 |
| `remark` | varchar(255) | 备注 |
| `created_by` / `created_at` / `updated_by` / `updated_at` / `is_deleted` | 审计字段 | 逻辑删除，`is_deleted = 0` 才参与查询 |

索引：

- `idx_pay_channel_code_status(channel_code, status)`：按渠道类型取启用渠道。
- `idx_pay_channel_default_sort(is_default, sort_order)`：默认渠道优先的排序。
- `uk_pay_channel_key(config_key)`：配置标识唯一。

接口入参的约束写在同一份契约里（`shared/system/payChannel/input.ts`），与表结构保持一致：

| 字段 | 约束 |
| --- | --- |
| `configKey` | 必填，1–50 字符 |
| `configName` | 必填，1–50 字符 |
| `channelCode` | 必填，1–30 字符，且必须在适配器注册表里存在 |
| `mode` | `z.enum(['live', 'test'])`，默认 `live` |
| `currency` | 必填，最长 10，默认 `CNY` |
| `orderTimeoutMinutes` | 整数，1–1440，默认 `30` |
| `isDefault` / `status` | 数字，默认 `0` / `1` |
| `config` | `Record<string, unknown>`，具体字段由所选渠道类型的 `configSchema` 在 Service 层二次校验 |

## 二、密钥的字段级加解密

只有 `PayProviderField` 上标记 `secret: true` 的字段会被加密，其余字段保持明文（便于排障与筛选），所以 `config` 是**混合结构**：

```json
{
  "appid": "2024000000",
  "gateway": "https://api.dpweixin.com",
  "secret": {
    "v": 1,
    "alg": "aes-256-gcm",
    "iv": "…12 字节随机数的 base64…",
    "tag": "…GCM 认证标签的 base64…",
    "data": "…密文的 base64…"
  }
}
```

信封结构定义在 `server/trade-router/domain/pay/crypto.ts`，五个字段缺一不可：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `v` | `1` | 信封版本，当前固定为 `1` |
| `alg` | `'aes-256-gcm'` | 算法标识，与版本一起参与 `isSecretEnvelope()` 判定 |
| `iv` | base64 | 每次加密随机生成的 12 字节 IV |
| `tag` | base64 | GCM 认证标签，解密时 `setAuthTag` 校验 |
| `data` | base64 | 密文本身 |

### 主密钥来源与格式

`readRawKey()` 先读 `runtimeConfig.payConfigKey`（`nuxt.config.ts` 里声明为空字符串占位，运行时由环境变量 `NUXT_PAY_CONFIG_KEY` 覆盖），取不到再兜底 `process.env.NUXT_PAY_CONFIG_KEY`，兼容没有 Nitro 运行时的脚本。

**格式要求：解码后必须是 32 字节。**`decodeKey()` 对 64 位十六进制串按 hex 解码，其余按 base64 解码，所以下面两种写法都合法：

```bash
# 32 字节 → base64 后是 44 个字符
openssl rand -base64 32
# 或者 64 位 hex
openssl rand -hex 32
```

`describePayConfigKey()` 返回 `{ ready, reason }`，`reason` 区分 `ok` / `missing`（没配置）/ `invalid`（配置了但解码不是 32 字节）。这个区分很重要：否则「格式不对」会被误报成「没配置」，界面提示就会误导人。

### 导出函数与各自职责

| 函数 | 职责 |
| --- | --- |
| `encryptConfigSecrets(fields, config)` | 写库前加密：空值 / `undefined` 直接剔除；已是信封的原样保留（幂等）；严格按 `secret` 字段加密 |
| `decryptConfigSecrets(fields, config)` | 读取前解密；非信封值（历史明文数据）原样返回，保证向前兼容 |
| `maskConfigSecrets(fields, config)` | 返回前端前把密钥字段替换为掩码：长度大于 4 时保留末 4 位（`****abcd`），否则统一 `****` |
| `isSecretEnvelope(value)` | 判断一个值是否是合法信封（`v` / `alg` / `iv` / `tag` / `data` 全部匹配） |
| `isUnchangedSecretInput(value)` | 判断是否是「不修改」输入：`undefined` / `null` / 去空格后为空串 / 以 `****` 开头 |
| `describePayConfigKey()` | 返回 `{ ready, reason }`，供渠道配置页提示密钥是否可用及原因 |
| `encryptSecret(plain)` / `decryptSecret(envelope)` | 单值加解密；解密失败抛 `module.system.payChannel.decryptFailed`（通常意味着主密钥换过） |
| `hasPayConfigKey()` | `describePayConfigKey().ready` 的简写 |

### 「编辑时密钥留空 = 不修改」的语义

这条语义实现在 `server/trade-router/modules/payChannel/SysPayChannelService.ts` 的 `buildConfigForWrite()`，它同时管新增与修改：

1. 以库里已有的 `config` 为基线（`next`），逐字段处理本次提交的 `inputConfig`。
2. `secret` 字段且 `isUnchangedSecretInput(value)` → **跳过**：既不覆盖 `next`，也不参与校验。前端表单里回显的是掩码，用户不动它就不会把掩码写进库。
3. 非必填字段提交空值 → 同样视为「不修改」，否则 `min(1)` 这类规则会把「清空 gateway」判成校验失败。
4. 只有「本次真正提交的新值」才放进 `validationInput`，用 `provider.configSchema.partial()` 校验。若拿整个 `inputConfig` 去校验，留空的密钥会被 `min(1)` 判为失败。
5. 必填校验基于合并后的 `next`（老值 + 新值），缺失则抛 `module.system.payChannel.configFieldRequired`。
6. 如果本次确实提交了新的密钥值，先 `describePayConfigKey()` 确认服务端有可用主密钥，否则抛 `module.system.payChannel.configKeyMissing` / `configKeyInvalid`——**避免落库后永远解不开**。

写入链路的最后一步是 `encryptConfigSecrets()`；读取链路的出口是 `maskRow()` → `maskConfigSecrets()`，因此列表、详情、`getById` 接口返回的密钥永远是掩码，密文信封从不暴露给前端。

## 三、前端动态表单的来源

渠道配置弹窗的「渠道凭据」区域不写死任何字段，完全由后端元数据驱动。接口是 `sysPayChannel.providerMetas`，返回：

```ts
{
  providers: PayProviderMeta[]          // 已注册的适配器
  encryptionReady: boolean              // 主密钥是否可用
  encryptionReason: 'ok' | 'missing' | 'invalid'
}
```

每个 `PayProviderMeta.fields` 是 `SysPayProviderField` 的数组，类型定义在 `server/trade-router/domain/pay/types.ts`：

| 属性 | 说明 |
| --- | --- |
| `key` | 写入 `config` 的键名，例如 `appid` / `secret` / `gateway` |
| `label` | **i18n key**（`module.system.payChannel.field.*`），不是文案本身 |
| `type` | `text` / `password` / `number` / `switch` / `textarea` |
| `required` | 是否必填，`buildConfigForWrite` 据此做必填校验 |
| `secret` | 标记为密钥：落库加密、接口掩码、编辑留空不覆盖 |
| `placeholder` / `help` | 同样是 i18n key |
| `defaultValue` | 仅用于表单初始值，**绝不包含真实密钥** |

前端 `app/pages/system/pay-channel/components/sys-pay-channel-operate.vue` 按 `fields` 渲染控件，切换「渠道类型」下拉时表单字段即时变化。注意 `fields` 与 `configSchema` 必须同步增删（`server/trade-router/domain/pay/types.ts` 的注释明确要求）：前者驱动 UI 与加解密，后者做类型校验，两处不一致会出现「界面能填、后端不认」。

## 四、渠道解析优先级

解析入口在 `server/trade-router/domain/pay/PayChannelResolver.ts`，下单、查询、模拟回调都走它：

```text
resolvePayChannel(db, { channelId, channelCode, currency })
   ├─ 1. 显式 channelId → getPayChannelRuntimeById() → payChannelRepo.findById()
   │       （不过滤 status：已停用渠道的历史订单仍要能被查询/回调）
   ├─ 2. payChannelRepo.findEnabled({ channelCode, currency })
   │       where is_deleted=0 and status=1
   │       order by is_default desc, sort_order asc, created_at asc limit 1
   ├─ 3. buildEnvFallbackChannel()  环境变量兜底
   │       （仅当未指定 channelCode，或指定的就是 xunhupay）
   └─ 4. 都没有 → AppError('module.system.payChannel.notConfigured')
```

两个细节：

- **环境变量兜底渠道**要求 `NUXT_PAY_APP_ID` 与 `NUXT_PAY_APP_SECRET` 同时非空才生成，此时 `id = null`、`configKey = 'env:xunhupay'`、`channelCode = 'xunhupay'`、`mode = 'live'`、`currency = 'CNY'`，`gateway` 取 `NUXT_PAY_GATEWAY`（默认 `https://api.xunhupay.com`），`notifyUrl` 取 `NUXT_PAY_NOTIFY_URL`，`orderTimeoutMinutes = 30`。凭证优先级因此是「数据库渠道配置 > 环境变量」。
- **回调不走上面的单选逻辑**：`listEnabledChannelsByCode(db, channelCode)` 会取出同一 `channelCode` 下所有启用渠道，逐个调 `verifyAndParseNotify`，第一个验签通过的就是来源渠道；库里一个都没有时再退到环境变量渠道。这样同一个渠道平台配置多个账户也能正确回调。

## 五、测试配置（verify）

「测试配置」按钮对应 `sysPayChannel.verify`（权限 `system:payChannel:verify`），流程是「取渠道行 → 拼运行时配置（解密）→ `provider.verifyChannel()` → 结论写回」：

```text
verify(id)
   ├─ payChannelRepo.getById(id)              查不到 → AppError('common.notExist')
   ├─ toChannelRuntime(row)                    解密 config
   ├─ provider.verifyChannel(runtime)          适配器探测
   └─ repo.updateById(id, {
        verify_status: success ? 1 : 2,
        verify_time:   nowForMysql(),
        verify_message: truncateText(message, 500)
      })
```

`verify_status` 的三个取值与含义见 `shared/constants/business.ts` 的 `payChannelVerifyConfig`：

| 值 | 含义 | 徽标色 |
| --- | --- | --- |
| `0` | 未验证 | neutral |
| `1` | 已验证 | success |
| `2` | 验证失败 | error |

虎皮椒的探测方式（`server/trade-router/domain/pay/providers/xunhupay.ts`）是拿一个不存在的订单号 `verify-{timestamp}` 去 POST `{gateway}/payment/query.html`，然后按 `errcode` / `errmsg` 判断：

| 响应 | 结论 |
| --- | --- |
| `errcode === 0` | 通过：网关连通，签名与 APPID 校验通过 |
| `errmsg` 命中「签名 / sign / hash」 | 失败：SECRET 可能不正确 |
| `errmsg` 命中「appid / 应用」 | 失败：APPID 无效 |
| 其他错误（例如订单不存在） | 通过：请求已被受理，APPID 与签名都没被拒绝 |

mock 适配器的 `verifyChannel` 只校验配置完整性（`merchant_id` / `sign_key` 是否填了），不发起网络请求。

两点使用约定：

- **凭据变更后旧结论失效**：`updateById` 里只要本次提交了 `config` 或改了 `channel_code`，就会把 `verify_status` 重置为 `0`、清空 `verify_time` / `verify_message`。
- **扫码支付测试页会拦截**：`SysPayTestService.assertChannelReady()` 在 `verify_status !== 1` 时直接抛 `module.system.payChannel.notVerified`，提示先去「支付渠道配置」里验证凭据。

## 六、新增一个渠道适配器要做什么

适配器的契约是 `PayProvider`（`server/trade-router/domain/pay/types.ts`），每个方法都要实现：

| 成员 | 语义 |
| --- | --- |
| `code` | 渠道平台标识，必须与 `sys_pay_channel.channel_code`、`statusMap` 的键一致（统一小写） |
| `name` | 适配器名称，元数据里返回；展示文案优先取 `payChannelCodeRecord` 的 i18n key |
| `capabilities` | 能力位：`qrcode` / `redirect` / `jsapi` / `refund` / `query` / `sandbox` / `localQrRender`，前端据此决定展示二维码图片还是二维码内容 |
| `fields` | 渠道私有配置字段元数据，驱动动态表单与字段级加解密 |
| `configSchema` | 与 `fields` 同步的 Zod 校验；`readConfig()` 校验失败抛 `module.system.payChannel.configInvalid` |
| `createPayment(channel, input)` | 发起支付：按平台协议签名并请求，返回 `{ providerOrderId, payMode, qrImageUrl, qrContent, payUrl, providerStatus, raw }`；`raw` 会写进 `provider_data.create` |
| `queryPayment(channel, key)` | 按 `outTradeNo` 或 `providerOrderId` 查询，返回 `{ status, providerStatus, amount, transactionId, providerOrderId, paidAt, raw }`；`status` 必须是 `mapProviderStatus()` 的结果 |
| `closePayment?` | 可选：平台侧关单。虎皮椒与 mock 都**没有实现**，所以「关闭订单」只改本地状态 |
| `verifyAndParseNotify(channel, input)` | **必须内含验签**。验签失败抛 `PaySignError`（dispatcher 据此记 `invalid_sign` 并返回 4xx，绝不返回 success）；成功返回 `PayNotifyResult`，其中 `dedupKey` 是幂等键，同一事件重复投递必须得到相同值 |
| `buildNotifyResponse(result, ok)` | 平台要求的响应体。虎皮椒与 mock 都返回纯文本 `success`（失败 `invalid sign`），HTTP 200 / 400 |
| `verifyChannel(channel)` | 「测试配置」调用，返回 `{ success, message }` |
| `buildSimulatedNotify?` | 可选：用配置里的密钥现算签名，造一份本地模拟回调报文。未实现时测试页的「模拟支付成功」返回 `module.system.payTest.simulateUnsupported` |

新增步骤（不需要改表结构、不需要改路由、不需要改前端页面）：

1. 在 `server/trade-router/domain/pay/providers/` 下新建 `<code>.ts`，导出实现 `PayProvider` 的适配器对象。
2. 在 `server/trade-router/domain/pay/providers/index.ts` 的 `providers` 注册表里登记一行。
3. 在 `server/trade-router/domain/pay/statusMap.ts` 的 `STATUS_TABLE` 补一段「平台原始状态 → 统一状态」映射；**未登记的平台状态一律降级为 `WP`**，避免把未知状态误判成已支付。
4. 在 `shared/constants/business.ts` 的 `payChannelCodeRecord` 补展示文案（i18n key，`app/locales/zh.json` 里对应 `module.system.payChannel.code*`）。
5. 配置弹窗的凭据字段会自动出现——`providerMetas` 直接读注册表，无需改前端。

错误类型只有两个，别用普通 `Error` 混过去：

- `PaySignError`：验签失败。dispatcher 会继续试下一个候选渠道，全部失败才记 `invalid_sign`。
- `PayApiError`：渠道返回的业务错误（`errcode != 0`、HTTP 异常、响应不可解析）。它带 `raw`，下单失败时会作为 `provider_data` 落库，方便看原始报文。

### mock 适配器的启用条件

`mock` 是内置联调渠道（虎皮椒的 `notify_url` 必须公网可达，本地开发收不到异步回调），注册逻辑在 `server/trade-router/domain/pay/providers/index.ts#isMockEnabled()`：

| `NUXT_PAY_MOCK_ENABLED` | `NODE_ENV` | 是否注册 |
| --- | --- | --- |
| 未设置或其他值 | `production` | 否 |
| 未设置或其他值 | 非 `production` | 是 |
| `true` | 任何环境 | 是 |
| `false` | 任何环境 | 否 |

它的签名思路与真实渠道一致（按 key 升序拼 `key=value&...` 后 HMAC-SHA256），且 `queryPayment` 永远返回「待支付」——mock 没有远端状态存储，已支付订单由 `canApplyStatusChange` 统一保护、不会被降级。

## 七、is_default 的唯一性怎么保证

数据库**没有** `is_default` 的唯一索引（`sys_pay_channel` 只有 `config_key` 唯一），唯一性靠代码保证，入口是 `SysPayChannelService.setDefault()`：

```text
setDefault(id)
   ├─ repo.getById(id)                查不到 → AppError('common.notExist')
   ├─ repo.clearOtherDefaults(id)     update sys_pay_channel
   │                                  set is_default = 0, updated_by = 操作人
   │                                  where is_deleted = 0 and id <> :id
   └─ repo.updateById(id, { isDefault: 1 })
```

两步顺序固定「先清其他、再置自己」。含义与坑：

- 手工 SQL 或新增/编辑接口直接写 `is_default = 1`（`SysPayChannelAddSchema` / `UpdateSchema` 里的 `isDefault` 字段）**会**造出多个默认渠道，所以设默认请走「设为默认」按钮对应的 `system:payChannel:default` 接口。
- 即使真的出现多个默认渠道，解析侧也不会报错：`findEnabled` 按 `is_default desc, sort_order asc, created_at asc` 取第一条，行为是确定的，只是另一个默认渠道实际上永远不会被自动选中。
