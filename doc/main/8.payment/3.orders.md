## 一、sys_pay_order 字段

订单表是支付模块的主表，一行就是一笔「资金结论」。表结构定义在 `server/drizzle/schema/system/payOrder.ts`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(36) | 主键，`randomUuid()` 生成 |
| `out_trade_no` | varchar(64) | 商户订单号，**唯一索引 `uk_pay_order_out_trade_no`** |
| `channel_id` | varchar(36) | 渠道配置行 id；用环境变量兜底渠道下单时为 `null` |
| `channel_code` | varchar(30) | 渠道类型快照，回调与查询按它找适配器 |
| `provider_order_id` | varchar(128) | 平台订单号（虎皮椒的 `open_order_id` / `openid`） |
| `transaction_id` | varchar(128) | 平台交易号 |
| `biz_type` | varchar(50) | 业务类型，默认 `test`；会员充值用 `recharge`、交易订单用 `order`；只有 `test` 订单允许「模拟支付成功」 |
| `subject` | varchar(200) | 商品标题，必填 |
| `amount` | decimal(10,2) | 金额（元），上限 `99999999.99` |
| `currency` | varchar(10) | 默认 `CNY`，回调会核对币种 |
| `status` | varchar(10) | 默认 `WP`，取值见[总览](/docs/main/payment/overview)的状态表 |
| `provider_status` | varchar(32) | 平台原始状态，排障时与 `status` 对照看 |
| `pay_mode` | varchar(20) | 默认 `qrcode`；`qrcode` / `redirect` / `jsapi` / `web` |
| `qr_image_url` | varchar(500) | 平台直接返回的二维码图片地址 |
| `qr_content` | text | 需要本地渲染的二维码内容（mock 返回的是可复制文本） |
| `pay_url` | varchar(500) | 收银台 / 支付链接 |
| `notify_url` | varchar(500) | 本单实际使用的回调地址，下单时已确定 |
| `attach` | varchar(255) | 透传给平台的原样返回字段 |
| `client_ip` / `user_agent` | varchar(64) / varchar(255) | 发起端信息，UA 写入前截断 |
| `expire_at` | timestamp | 过期时间 = 下单时间 + `order_timeout_minutes` |
| `paid_at` / `cancelled_at` | timestamp | 支付成功 / 取消或关闭时间 |
| `last_query_at` | timestamp | 最近一次主动查询时间，节流依据 |
| `notify_count` | int | 默认 `0`，每收到一次有效回调 +1 |
| `last_notify_at` | timestamp | 最近一次回调时间 |
| `fail_reason` | varchar(500) | 发起失败原因（`FL` 订单主要靠它排查） |
| `provider_data` | json | 渠道原始报文，结构见下文 |
| `remark` | varchar(255) | 备注 |
| `created_by` / `created_at` / `updated_by` / `updated_at` / `is_deleted` | 审计字段 | 逻辑删除 |

`biz_type` 的真实取值：`test`（扫码支付测试页，也是列默认值）、`recharge`（会员充值，`sysMember.myRecharge` → `RechargeService.create` 传入）、`order`（交易订单在线支付，`sysOrder.myCreate` → `OrderService.create` 传入）；三者之外的取值在支付回调里保持 no-op。支付成功后的分派规则、幂等与补偿见[业务接入：bizType 分派](/docs/main/payment/integration)。

索引：

| 索引 | 列 | 用途 |
| --- | --- | --- |
| `uk_pay_order_out_trade_no` | `out_trade_no` | 唯一，订单号重复的最终兜底 |
| `idx_pay_order_status_created` | `status, created_at` | 按状态翻页、找过期未支付单 |
| `idx_pay_order_provider_order` | `provider_order_id` | 按平台单号定位 |
| `idx_pay_order_channel_created` | `channel_code, created_at` | 按渠道统计 |
| `idx_pay_order_created_by` | `created_by, created_at` | 按发起人筛选 |
| `idx_pay_order_biz_type` | `biz_type` | 业务类型筛选 |

## 二、领域服务 API

统一入口是 `server/trade-router/domain/pay/PayOrderService.ts` 的 `payOrderService(db)`（`db` 是 `AppExecutor`——连接或事务——而不是 tRPC `Context`，因为免登录的回调路由也要复用它）。上层 tRPC Service、测试页、未来的对账任务都只调这几个方法。

| 方法 | 入参 | 返回 | 副作用 |
| --- | --- | --- | --- |
| `getById(orderId)` | 订单 id | `PayOrderRow` | 无；查不到抛 `common.notExist` |
| `getByOutTradeNo(outTradeNo)` | 商户订单号 | `PayOrderRow \| null` | 无，**不抛错**（回调定位订单用，找不到就是找不到） |
| `createPayment(input, meta)` | 见下 | 新建的 `PayOrderRow` | 调适配器下单 + 写库；失败也写一条 `FL` 订单 |
| `queryPayment(orderId, meta)` | 订单 id | 更新后的 `PayOrderRow` | 调平台查询接口 + 可能推进状态 + 刷新 `last_query_at` |
| `closePayment(orderId, meta)` | 订单 id | 更新后的 `PayOrderRow` | 仅本地改 `status='CL'`、写 `cancelled_at`；非 `WP` 抛 `module.system.payOrder.notClosable` |
| `listExpiredPending(limit = 50)` | 条数上限 | `PayOrderRow[]` | 无；取 `status='WP' and expire_at < now` 的单据，供对账任务使用 |

`createPayment` 的入参（`CreatePayOrderInput`）与 `meta`（`PayOperatorMeta`）：

```ts
type CreatePayOrderInput = {
  channelId?: string | null      // 指定渠道配置行；与 channelCode 二选一
  channelCode?: string | null    // 指定渠道类型，由解析器挑一条启用渠道
  amount: string | number        // 元，两位小数归一
  subject: string                // 必填
  bizType?: string | null        // 默认 'test'；会员充值 'recharge'、交易订单 'order'
  attach?: string | null
  remark?: string | null
  notifyUrl?: string | null      // 覆盖渠道配置的回调地址
  returnUrl?: string | null
  cancelUrl?: string | null
  origin?: string | null         // 本次请求的 origin，用于推导回调地址
  outTradeNo?: string | null     // 指定订单号，留空自动生成
}

type PayOperatorMeta = {
  operatorId?: string | null
  clientIp?: string | null
  userAgent?: string | null
}
```

## 三、下单流程分步

`createPayment` 的执行顺序（与代码一一对应）：

1. **金额归一**：`normalizeAmount()` 把入参统一成「元 + 两位小数」字符串。`<= 0` 或非数字抛 `module.system.payOrder.amountInvalid`，超过 `99999999.99` 抛 `module.system.payOrder.amountTooLarge`（与 `decimal(10,2)` 对齐）。
2. **标题校验**：`subject` 去空格后不能为空，否则抛 `module.system.payOrder.subjectRequired`。
3. **解析渠道**：`resolvePayChannel(db, { channelId, channelCode })`；随后 `getPayProvider(channel.channelCode)`，未注册抛 `module.system.payChannel.providerUnsupported`。
4. **推导回调地址**：`resolveNotifyUrl()` 的优先级是 `override`（入参 `notifyUrl`）→ 渠道配置 `notify_url` → 按请求 origin 拼 `${origin}/api/pay/notify/${channelCode}`（会去掉 origin 末尾的 `/`）。三步都拿不到就抛 `module.system.payChannel.notifyUrlRequired`。
5. **确定订单号**：入参 `outTradeNo` 去空格后优先使用；否则 `pickOutTradeNo()` 循环最多 **3 次**调用 `buildOutTradeNo()` 并用 `orderRepo.existsOutTradeNo()` 预检，3 次都撞号抛 `module.system.payOrder.createFailed`。格式为 `前缀 + yyyyMMddHHmmss + 6 位随机大写字母数字`，默认前缀 `PAY`，例如 `PAY20260101120000A1B2C3`。预检只是降低冲突概率，**并发下的最终保证是唯一索引 `uk_pay_order_out_trade_no`**。
6. **计算过期时间**：`expire_at = nowForMysql(addMinutes(new Date(), channel.orderTimeoutMinutes))`；`order_timeout_minutes` 默认 30（环境变量兜底渠道固定 30）。
7. **调用适配器并落库**：
   - 成功 → 写一条 `status='WP'` 的订单，带 `pay_mode`、`provider_order_id`、`provider_status`、`qr_image_url`、`qr_content`、`pay_url`，以及 `provider_data = mergeProviderData(null, 'create', result.raw)`。
   - 失败 → **仍然写一条订单**：`status='FL'`、`pay_mode='qrcode'`、`fail_reason` 截断到 500 字符、`provider_data` 取 `PayApiError.raw`（普通错误退化为 `{ message }`），然后把 `module.system.payOrder.createFailed` 抛给调用方。这样「下单失败」在支付记录里也能查到原始报文，而不是只剩一条错误 Toast。
8. **回读返回**：最后用 `getByIdOrThrow(id)` 重新查一次，把 MySQL 生成的 `created_at` / `updated_at` 等默认值带回给调用方。

字段默认值：`biz_type` 取入参或 `'test'`，`currency` 取渠道配置或 `'CNY'`，`notify_count` 初始为 `0`。

## 四、provider_data 结构

`provider_data` 由 `mergeProviderData()` 累加写入，固定三个键：

| 键 | 写入时机 | 内容 |
| --- | --- | --- |
| `create` | 下单成功后 | `createPayment` 返回的 `result.raw`，即平台原始响应（二维码地址、支付链接、平台单号都从这里取） |
| `lastQuery` | 每次主动查询后 | `queryPayment` 返回的 `result.raw` |
| `lastNotify` | 支付成功回调处理成功后 | `verifyAndParseNotify` 返回的 `result.raw`，即回调报文 |

它是浅拷贝累加（`{ ...existing, [key]: value }`），**不会整体覆盖**：早期实现如果整体覆盖，回调报文会把下单响应挤掉，「平台下单时到底返回了什么」就永远看不到了。

排查用法：

- 二维码 / 支付链接为空 → 看 `create`，对照 `server/trade-router/domain/pay/providers/xunhupay.ts#pickResponseFields()` 的候选键名（虎皮椒有两种响应结构：官方文档的 `data.{url,url_qrcode,open_order_id}` 与实测的顶层平铺 + `openid`）。
- 状态没推进 → 看 `lastQuery` / `lastNotify` 里的 `status` / `trade_status` 字段，再对照 `statusMap` 的映射表。
- 下单直接失败 → 订单是 `FL`，看 `fail_reason` 与 `provider_data`（`PayApiError.raw` 通常是平台的错误 JSON）。
- 回调链路的原文同时写进了 `sys_pay_notify_log.raw_body`（截断 60 000 字符），两处可以互相印证。

## 五、queryPayment 的规则

主动查询既服务支付记录页的「同步状态」，也服务测试页的 5 秒轮询（`sysPayTest.syncStatus`，`log: false` 不写操作日志），还留给对账任务复用。规则按执行顺序如下：

1. **取订单**：查不到抛 `common.notExist`。
2. **已支付直接短路**：`isPaidStatus(order.status)` 为真时，只 `touchLastQuery()` 刷新 `last_query_at` 就返回，**不请求平台**。
3. **3 秒节流**：`secondsSinceMysqlDateTime(order.lastQueryAt) < MIN_ACTIVE_QUERY_INTERVAL_SECONDS`（常量 `3`，定义在 `PayOrderService.ts`）时，直接返回本地快照 `order`，既不请求平台也不改任何字段。轮询会周期性触发查询，节流保证对平台查询接口的调用不高于每 3 秒一次。
4. **取渠道运行时配置**：`getPayChannelRuntimeById(db, order.channelId)`；`channel_id` 为 `null` 的历史订单会退到环境变量兜底渠道。
5. **调适配器**：`provider.queryPayment(channel, { outTradeNo, providerOrderId })`；未注册抛 `providerUnsupported`（适配器抛出的 `PayApiError` 会直接向上冒泡，节流时间戳此时还没写）。
6. **组装更新**：`last_query_at = now`、`updated_by`、`provider_status`、`provider_order_id`、`transaction_id`（都保留旧值兜底）、`provider_data.lastQuery`。
7. **状态推进（受保护）**：只有 `canApplyStatusChange(order.status, result.status)` 认可的方向才改 `status`；推到 `OD` 时写 `paid_at = result.paidAt || now`，推到 `CD` 时写 `cancelled_at = now`。
8. **过期兜底关单**：状态没被推进、且订单仍是 `WP` 且 `isExpired(order.expireAt, now)` 为真 → 置 `status='CL'` 并写 `cancelled_at`。这就是「待支付订单超时后由查询顺手关掉」的实现。
9. **写日志**：**只有状态真正变化（`statusChanged`）才往 `sys_pay_notify_log` 写一条 `source='query'`** 的记录，`dedup_key = null`、`sign_valid = 0`、`process_result = 'success'`、`message = '主动查询：旧状态 → 新状态'`，`raw_body` 是本次查询响应的 JSON。不写的话轮询会把日志表刷满。
10. **日志写入失败静默忽略**（`try/catch` 空实现）——写日志不能阻断状态推进。
11. 返回重新查出的订单行。

`closePayment` 是纯本地动作：虎皮椒等平台没有取消接口，因此只允许把 `WP` 关成 `CL`（`isClosableStatus`），其他状态抛 `module.system.payOrder.notClosable`。

## 六、渠道状态到本地状态的映射

映射表在 `server/trade-router/domain/pay/statusMap.ts` 的 `STATUS_TABLE`，键是 `channel_code`，值是「平台状态 → 统一状态」：

| 渠道 | 平台状态 | 本地状态 | 状态 |
| --- | --- | --- | --- |
| `xunhupay` | `WP` / `OD` / `CD` | `WP` / `OD` / `CD` | 已实现 |
| `mock` | `pending` / `paid` / `closed` | `WP` / `OD` / `CL` | 已实现 |
| `codepay` | `0` / `1` | `WP` / `OD` | 预留，无适配器 |
| `stripe` | `requires_payment_method`、`requires_confirmation`、`requires_action`、`processing`、`requires_capture` | `WP` | 预留，无适配器 |
| `stripe` | `succeeded` / `canceled` | `OD` / `CD` | 预留，无适配器 |
| `alipay_f2f` | `WAIT_BUYER_PAY` / `TRADE_SUCCESS`、`TRADE_FINISHED` / `TRADE_CLOSED` | `WP` / `OD` / `CD` | 预留，无适配器 |

`mapProviderStatus(channelCode, providerStatus)` 的兜底规则：平台状态为空、渠道没登记、状态没登记 → 一律 `WP`；先精确匹配，再尝试把平台状态转大写匹配。**绝不猜成已支付**，这是资金相关代码的安全底线。

三个判定函数：

| 函数 | 规则 |
| --- | --- |
| `isPaidStatus(status)` | `status === 'OD'`。`OD` 是终态，已支付订单不能被一次过期查询改回待支付 |
| `isClosableStatus(status)` | `status === 'WP'`，只有未支付订单允许被本地关闭 |
| `isExpired(expireAt, now?)` | `expireAt` 非空且 `expireAt < (now ?? nowForMysql())`；两个字符串同格式，可直接比较 |
| `canApplyStatusChange(current, next)` | `current === next` → `false`；`isPaidStatus(current)` → `false`；`next === 'WP'` 且 `current` 是 `CD` / `CL` → `false`；其余 `true` |

`canApplyStatusChange` 的第三条规则是防状态抖动：已取消 / 已关闭的订单不接受迟到的「待支付」查询结果，但**接受**平台的支付成功事实（钱已到账，回调链路的 `markPaidIfPending` 只判断 `status <> 'OD'`，因此 `CD` / `CL` 也会被置为 `OD`，并记为 `status_mismatch` 级别的结论）。

## 七、时间约定

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**支付模块里所有写库的时间都必须走 `nowForMysql()`，不要用 `toISOString()`。**

`nowForMysql()` 输出的是**本地墙钟时间**（`YYYY-MM-DD HH:mm:ss`，本机 `+08:00`），与 MySQL `CURRENT_TIMESTAMP` / `ON UPDATE` 写入的格式和时区一致。`toISOString()` 按 UTC 输出，两者混用会让 `paid_at` / `expire_at` / `last_query_at` 比 `created_at` 整整差 8 小时。
::

```ts
// server/trade-router/domain/pay/utils.ts
export function nowForMysql(date: Date = new Date()) {
  const pad = (value: number) => String(value).padStart(2, '0')
  return `${date.getFullYear()}-${pad(date.getMonth() + 1)}-${pad(date.getDate())} `
    + `${pad(date.getHours())}:${pad(date.getMinutes())}:${pad(date.getSeconds())}`
}
```

同族工具：

| 工具 | 说明 |
| --- | --- |
| `nowForMysql(date?)` / `toMysqlDateTime(date)` | 本地墙钟字符串；后者是前者的别名 |
| `addMinutes(date, minutes)` | 在 `Date` 上加分钟，用于算 `expire_at` |
| `secondsSinceMysqlDateTime(value)` | 距离某个墙钟时间过去了多少秒：`new Date(value.replace(' ', 'T'))` 得本地时间戳再与 `Date.now()` 相减；空值或无法解析返回 `Number.POSITIVE_INFINITY`（当作「很久以前」，不阻塞查询） |
| `isExpired(expireAt, now?)` | 字符串直接比较，因此要求两侧格式完全一致 |
| `payOrderRepo.listExpiredPending(now, limit)` | 用 SQL `expire_at is not null and expire_at < :now` 比较，同样依赖格式一致 |

因为格式固定为定长字符串，字典序等于时间序——这是整个模块敢于用字符串比较时间的前提，改动 `nowForMysql()` 的格式会同时打破 `isExpired()`、节流与 `listExpiredPending()`。

支付成功后的业务后置（充值到账 / 订单完成、主动同步与补偿）见[业务接入：bizType 分派](/docs/main/payment/integration)；回调链路本身见[回调处理与幂等](/docs/main/payment/notify)。
