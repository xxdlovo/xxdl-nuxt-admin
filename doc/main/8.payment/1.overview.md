支付模块提供「配置渠道 → 统一下单 → 展示二维码 → 回调或查询推进状态 → 审计留痕」这一条完整链路的服务端能力，以及配套的四个后台页面和一个前端支付组件。

## 一、能力边界

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**当前只实现了虎皮椒（`xunhupay`）真实适配器 + 本地 `mock` 适配器。**

码支付（`codepay`）、Stripe（`stripe`）、支付宝当面付（`alipay_f2f`）**只在接口与映射表层面预留了位置，没有适配器实现**：它们出现在 `server/trade-router/domain/pay/statusMap.ts` 的状态映射表与 `shared/constants/business.ts` 的展示文案里，但**没有在 `server/trade-router/domain/pay/providers/index.ts` 注册**。因此 `getPayProvider('codepay')` 一律返回 `null`：渠道配置弹窗的「渠道类型」下拉由 `providerMetas`（只读注册表）驱动，列表里不会出现它们；若绕过界面直接提交这些 `channelCode`，接口会报 `module.system.payChannel.providerUnsupported`。
::

| 渠道 | 适配器 | 说明 |
| --- | --- | --- |
| `xunhupay` | `server/trade-router/domain/pay/providers/xunhupay.ts` | 虎皮椒，唯一接入的真实渠道；支持下单、查询、回调、测试配置、模拟回调 |
| `mock` | `server/trade-router/domain/pay/providers/mock.ts` | 内置联调渠道，按开关注册；不请求外网，可离线跑通全链路 |
| `codepay` / `stripe` / `alipay_f2f` | 无 | 仅 `statusMap.ts` 预留状态映射、`business.ts` 预留展示文案 |

其他边界：

- **没有退款**：`PayProviderCapabilities.refund` 在 `types.ts` 里声明为能力位，但两个适配器都是 `false`，`PayProvider` 也没有退款方法；`RF`（已退款）状态是预留值，当前没有任何写入方。
- **没有平台侧关单**：`closePayment` 是可选方法，虎皮椒与 mock 都没实现，所以「关闭订单」只改本地状态。
- **没有对账任务**：`PayOrderService.listExpiredPending()` 与 `PayNotifySource` 的 `reconcile` 是为将来的对账任务预留的接口，目前没有调用方。

## 二、分层调用链

支付（以及后续的会员 / 余额）相关代码统一收在 `server/trade-router/` 下，分两层：

```text
server/trade-router/
├── domain/    领域层：不依赖 tRPC ctx，回调路由、定时任务、其他业务模块都能直接复用
└── modules/   tRPC 模块层：Repo / Service / index，依赖 Context，对应一组接口与页面
```

调用链：

```text
tRPC 控制层      server/trade-router/modules/payChannel|payOrder|payNotifyLog|payTest/index.ts
                    │  只声明权限码与入参 schema，翻译 ctx / 请求信息
                    ▼
模块 Service     server/trade-router/modules/pay*/SysPay*Service.ts
                    │  测试场景编排、手工补录、渠道配置读写
                    ▼
支付领域层        server/trade-router/domain/pay/PayOrderService.ts（下单 / 查询 / 关闭）
                 server/trade-router/domain/pay/PayNotifyDispatcher.ts（回调验签 / 核对 / 幂等）
                 server/trade-router/domain/pay/PayChannelResolver.ts（选渠道 / 解密 / 拼运行时配置）
                    │  业务判断与状态流转，不写 SQL
                    ▼
mapper 层        server/trade-router/domain/pay/repo/payChannelRepo|payOrderRepo|payNotifyLogRepo.ts
                    │  唯一允许出现 drizzle 查询 / 原生 SQL 的地方
                    ▼
渠道适配器        server/trade-router/domain/pay/providers/xunhupay.ts、mock.ts
                    │  按平台协议签名、请求、验签
                    ▼
外部网关         虎皮椒 POST {gateway}/payment/do.html、/payment/query.html
```

**免登录的回调链路不走 tRPC**，它在领域层分叉后共用同一份 mapper：

```text
POST /api/pay/notify/{channel}   server/api/pay/notify/[channel].post.ts
   └─ payNotifyDispatcher(db).handleNotify()  →  server/trade-router/domain/pay/repo/*
```

### 「SQL 只允许出现在 mapper 层」这条约定

与[后端手册的 Repo 与 Service](/docs/main/backend-handbook/repo-service) 一致（Router 不写业务、Service 不写 SQL、Repo 不做业务判断），支付模块在这条约定上更严格，原因是它有两条完全不同的入口：

- tRPC 入口有 `ctx`，走普通的 `CommonRepo` 工厂；
- 回调入口没有 `ctx`，只有数据库执行器 `AppExecutor`。

所以 `server/trade-router/domain/pay/repo/*` 的工厂统一接收 `AppExecutor`（`server/drizzle/db.ts` 的 `AppDb | AppTx`，内部用 `asDb()` 收窄），两条链路复用同一份 SQL，事务内外也复用同一份：

| 约定 | 落地方式 |
| --- | --- |
| 领域层不接触 drizzle | `PayOrderService` / `PayNotifyDispatcher` / `PayChannelResolver` 只 import `./repo/*` |
| mapper 不做业务判断 | 状态能否流转、金额是否一致、验签结论都由领域层判定 |
| 无 `ctx` 的入口也能复用 | `SysPayTestRepo` 把 `ctx.db` 适配成 `AppExecutor` 后直接调 `server/trade-router/domain/pay/repo/*` |
| 业务判断集中在领域层 | `server/trade-router/domain/pay/statusMap.ts` 的 `canApplyStatusChange()` 是唯一的状态流转裁判 |

## 四、三张表概览

| 表 | Schema 文件 | 职责 | 关键唯一键 |
| --- | --- | --- | --- |
| `sys_pay_channel` | `server/drizzle/schema/system/payChannel.ts` | 渠道凭据与回调参数配置；渠道解析、密钥解密的数据源 | `uk_pay_channel_key(config_key)` |
| `sys_pay_order` | `server/drizzle/schema/system/payOrder.ts` | 支付订单主表，一行一笔资金结论 | `uk_pay_order_out_trade_no(out_trade_no)` |
| `sys_pay_notify_log` | `server/drizzle/schema/system/payNotifyLog.ts` | 回调与查询的审计日志，幂等依据 | `uk_pay_notify_dedup(dedup_key)` |

关于建表与 Schema：

- 三张表的**结构以 `server/drizzle/schema/system/pay*.ts` 为准**，字段、默认值、索引都在这里定义，`shared/system/pay*/common.ts` 与之保持一致。
- 这些 Schema 文件是 `pnpm db:pull` **从已有数据库反向生成**的产物：先在数据库建表（或直接改表），再执行 `pnpm db:pull` 重新生成；`pnpm db:push` 则是反过来把 Schema 推送到数据库。双向命令的通用说明见[数据库与环境变量](/docs/main/backend-handbook/config-env)。
- 改表结构后必须同步三处：Schema 文件（`db:pull`）、`shared/system/pay*/common.ts`（DTO 与查询条件）、以及受影响的 `server/trade-router/domain/pay/repo/*`。少了任何一处都会在运行时才暴露。

## 五、订单状态一览

状态定义在 `server/trade-router/domain/pay/statusMap.ts` 的 `UNIFIED_PAY_STATUSES` 与 `shared/constants/business.ts` 的 `payOrderStatusConfig`，共 6 个：

| 状态码 | 名称 | 含义 | 徽标色 | 是否可写 |
| --- | --- | --- | --- | --- |
| `WP` | 待支付 | 已下单，等待用户付款；允许被本地关闭、允许超时自动关闭 | warning | 下单成功后的初始状态 |
| `OD` | 已支付 | 资金已到账，**终态**；任何查询或回调都不能把它改回其他状态 | success | 回调幂等置为 / 查询推进 |
| `CD` | 已取消 | 平台侧取消（由状态映射得出） | neutral | 查询或回调推进 |
| `CL` | 已关闭 | 本地关闭，或 `WP` 订单过了 `expire_at` 被查询顺手关掉 | neutral | `closePayment` / 查询过期兜底 |
| `FL` | 发起失败 | 适配器调用失败时**仍然落库**的订单，纯为排查保留 | error | `createPayment` 失败分支 |
| `RF` | 已退款 | 预留值，当前没有任何写入方 | info | 无 |

支付状态是「资金结论」，因此**故意不放进字典表**：字典数据可以被后台随意改坏，而支付状态不允许被改名或改语义。前端徽标文案走 `module.system.payOrder.status.*`，颜色固定在 `payOrderStatusConfig` 里。

状态流转的保护规则集中在 `canApplyStatusChange()`：`OD` 永不回退；`CD` / `CL` 不接受迟到的「待支付」查询结果（防状态抖动），但接受平台的支付成功事实。详见[下单、查询与状态流转](/docs/main/payment/orders)。

## 六、环境变量与配置项

| 变量 | 读取位置 | 默认值 | 生效条件 |
| --- | --- | --- | --- |
| `NUXT_PAY_CONFIG_KEY` | `server/trade-router/domain/pay/crypto.ts`（先读 `runtimeConfig.payConfigKey`，再兜底 `process.env`） | 空 | 渠道密钥字段加解密的主密钥。解码后必须是 **32 字节**：64 位 hex 或 base64（44 字符）；缺配置报 `configKeyMissing`，格式不对报 `configKeyInvalid` |
| `NUXT_PAY_MOCK_ENABLED` | `server/trade-router/domain/pay/providers/index.ts` | 非生产环境默认开启 | `'false'` 关闭、`'true'` 开启（任何环境）；其他值按 `NODE_ENV !== 'production'` |
| `NUXT_PAY_SIMULATE_ENABLED` | `server/trade-router/modules/payTest/SysPayTestService.ts` | 非生产默认开启 | 生产环境必须显式 `'true'`；非生产环境只有显式 `'false'` 才关闭 |
| `NUXT_PAY_APP_ID` | `server/trade-router/domain/pay/PayChannelResolver.ts` | 无 | 与 `NUXT_PAY_APP_SECRET` **同时非空**才生成环境变量兜底渠道（`channelCode = xunhupay`） |
| `NUXT_PAY_APP_SECRET` | 同上 | 无 | 同上；两者构成兜底渠道的凭据 |
| `NUXT_PAY_GATEWAY` | 同上 | `https://api.xunhupay.com` | 仅在兜底渠道存在时参与 |
| `NUXT_PAY_NOTIFY_URL` | 同上 | `null` | 兜底渠道的 `notifyUrl`；为空时下单按请求 origin 推导 |

`runtimeConfig.payConfigKey` 在 `nuxt.config.ts` 里**必须留空字符串占位**，真实值只从环境变量注入，不能把密钥写进仓库。

凭证优先级是「数据库渠道配置（`status = 1`）> 环境变量」：只有当库里按 `channelCode` / `currency` 找不到启用渠道、且本次没有指定其他渠道类型时，才会用到 `NUXT_PAY_APP_ID` / `NUXT_PAY_APP_SECRET` 这一组。显式传了 `channelId` 却查不到时**不会**回退到环境变量，而是抛 `common.notExist`。

## 七、权限码与菜单

所有接口都用 `proc({ permission })` 显式声明权限码，权限码来源是 `sys_menu.code`（规则见[权限模型](/docs/main/reference/rbac)）。支付模块共 4 组：

| 模块 | 权限码 | 说明 |
| --- | --- | --- |
| 支付渠道配置 | `system:payChannel:list` | 列表、详情、`providerMetas`（渠道类型元数据） |
| | `system:payChannel:add` | 新增渠道 |
| | `system:payChannel:edit` | 编辑渠道 |
| | `system:payChannel:del` | 删除、批量删除 |
| | `system:payChannel:verify` | 「测试配置」（单独授权，便于只读角色排除） |
| | `system:payChannel:default` | 「设为默认」 |
| 支付记录 | `system:payOrder:list` | 列表、详情、回调时间线 |
| | `system:payOrder:add` | 手工补录订单 |
| | `system:payOrder:edit` | 编辑订单、关闭订单（`close`） |
| | `system:payOrder:del` | 删除、批量删除 |
| | `system:payOrder:query` | 「同步状态」（有副作用的写操作，单独授权） |
| 支付回调日志 | `system:payNotifyLog:list` | 列表与详情 |
| | `system:payNotifyLog:add` / `:edit` / `:del` | 常规 CRUD（日志一般只读） |
| 扫码支付测试 | `system:payTest:create` | 渠道下拉与发起扫码支付 |
| | `system:payTest:query` | 订单快照与状态同步 |
| | `system:payTest:simulate` | 本地模拟支付成功 |

两点：`sysPayTest.syncStatus` 用的是 `system:payTest:query` 并额外声明 `log: false`（轮询每 5 秒一次，写操作日志只会变成噪音）；`system:payOrder:query` 与 `system:payOrder:edit` 分开，是因为前者会主动请求渠道并推进本地状态。菜单与按钮级控制（`v-permission`）需要把上面的权限码配进 `sys_menu` 才能生效。
