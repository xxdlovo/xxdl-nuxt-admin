## 定位与能力

虎皮椒（xunhupay）是聚合支付网关，本模块的适配器实现位于 `server/pay/providers/xunhupay.ts`，在 `server/pay/providers/index.ts` 中以 `xunhuPayProvider` 登记，`code` 为 `xunhupay`、名称为「虎皮椒支付」。

它只实现「扫码支付」这一种发起方式：下单接口直接返回收款的二维码图片地址，不需要本地渲染二维码。

| 能力 | 值 | 含义 |
| --- | --- | --- |
| `qrcode` | `true` | 支持扫码支付，适配器 `payMode` 固定返回 `qrcode` |
| `redirect` | `true` | 支持 `return_url` 同步跳转 |
| `jsapi` | `false` | 不支持公众号/小程序内支付 |
| `refund` | `false` | 未实现退款 |
| `query` | `true` | 支持主动查询订单状态 |
| `sandbox` | `false` | 无沙箱环境，`mode` 选 `test` 也只影响本地标记 |
| `localQrRender` | `false` | 不做本地二维码渲染，`qrContent` 恒为 `null` |

接口地址完全以渠道配置的 `gateway` 为准（虎皮椒后台「我的支付渠道」显示的地址不一定是 `api.xunhupay.com`），用到的两个路径是：

| 路径 | 用途 | 请求方式 |
| --- | --- | --- |
| `/payment/do.html` | 下单 | `POST` + `application/json;charset=UTF-8` |
| `/payment/query.html` | 查询订单状态、以及「测试配置」探测 | `POST` + `application/json;charset=UTF-8` |

请求超时统一为 10 秒（`REQUEST_TIMEOUT_MS`，通过 `AbortController` 中断）。

## 渠道配置字段

适配器通过 `fields` 声明这三个配置项，渠道配置页的动态表单就是据此渲染的：

| key | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `appid` | `text` | 是 | — | 虎皮椒后台「我的应用」中的 APPID |
| `secret` | `password` | 是 | — | 标记 `secret: true`，落库前由 `server/pay/crypto.ts` 做 AES-256-GCM 字段级加密 |
| `gateway` | `text` | 是 | `https://api.xunhupay.com` | 只填到域名（含协议）；带上接口路径会被自动去掉 |

`configSchema` 对三者都是 `z.string().min(1)`，`gateway` 额外有 `default(DEFAULT_GATEWAY)`。读取配置统一走 `readConfig()`，它先做 schema 校验，校验失败抛 `module.system.payChannel.configInvalid` 并把每个 issue 的 `字段: 原因` 拼进 message。

## 网关归一化

`normalizeXunhuPayGateway()` 是这个适配器最容易踩坑的一处，`readConfig()` 每次都会调用它。

**为什么要做**：虎皮椒后台「我的支付渠道」展示的是**完整接口地址**（例如 `https://api.dpweixin.com/payment/do.html`），用户很容易把整段粘进 `gateway`。若不处理，下单地址会被拼成 `https://api.dpweixin.com/payment/do.html/payment/query.html`，网关返回一个 404 的 HTML 页面，而 `postJson()` 会因为「响应不是合法 JSON」报错——现象和真正的原因相隔很远。

处理步骤（按代码顺序）：

```text
输入 raw
  1. trim + 去掉结尾的所有 "/"；为空 → 返回 DEFAULT_GATEWAY
  2. 没有 http:// 或 https:// 前缀 → 补 "https://"（容忍只写 api.dpweixin.com）
  3. 去掉结尾的 /payment/do.html、/payment/query.html、/payment/refund.html（不区分大小写）
  4. 再去掉结尾的 /payment
  5. new URL() 解析，返回 `${url.origin}${url.pathname 去掉结尾斜杠}`
     —— 解析失败（例如空格拼错的地址）时直接返回第 4 步的字符串，不抛错
```

效果对照：

| 填写值 | 归一化结果 |
| --- | --- |
| （留空） | `https://api.xunhupay.com` |
| `api.dpweixin.com` | `https://api.dpweixin.com` |
| `https://api.dpweixin.com/` | `https://api.dpweixin.com` |
| `https://api.dpweixin.com/payment` | `https://api.dpweixin.com` |
| `https://api.dpweixin.com/payment/do.html` | `https://api.dpweixin.com` |
| `https://gateway.example.com/xunhupay` | `https://gateway.example.com/xunhupay` |

`DEFAULT_GATEWAY` 常量即 `https://api.xunhupay.com`，同时也是环境变量兜底渠道 `NUXT_PAY_GATEWAY` 未配置时的取值。

## 下单

`createPayment()` 的流程是「读配置 → 组装参数 → 签名 → POST `/payment/do.html` → 校验 `errcode` → 取字段」。

请求参数（`params`，全部为字符串）：

| 参数 | 值来源 | 说明 |
| --- | --- | --- |
| `version` | 固定 `'1.1'` | 协议版本 |
| `appid` | 渠道配置 | |
| `trade_order_id` | `input.outTradeNo` | 商户订单号 |
| `total_fee` | `formatAmount(input.amount)` | 元、两位小数字符串；非有限数或 `<= 0` 抛 `PayApiError('[xunhupay] 金额不合法')` |
| `title` | `input.subject` | 商品标题 |
| `notify_url` | `input.notifyUrl` | 异步回调地址 |
| `time` | `nowSeconds()` | 秒级时间戳字符串 |
| `nonce_str` | `makeNonce()` | `randomBytes(16).toString('hex')`，32 位十六进制 |
| `hash` | `makeXunhuPaySign(params, secret)` | 最后写入；签名时自身被排除 |
| `return_url` | 可选，`input.returnUrl` | 支付完成后的同步跳转地址 |
| `callback_url` | 可选，`input.cancelUrl` | 取消支付后的跳转地址 |
| `attach` | 可选，`input.attach` | 业务备注，原样透传 |

后三个参数**只在有值时写入**：空字符串虽然会被签名算法过滤掉，但仍会作为参数发给网关，因此代码选择根本不写。这也是「空值不参与签名」这条规则在调用侧的体现。

请求失败的分级报错（都来自 `postJson()`）：

| 情况 | 报错 |
| --- | --- |
| HTTP 状态非 2xx | `[xunhupay] HTTP <状态码>（<url>）：<响应前 200 字符>` |
| 响应不是合法 JSON | `[xunhupay] 响应不是合法 JSON（<url>）：<响应前 200 字符>` |
| 网络错误 / 超时 | `[xunhupay] <原始错误信息>（<url>）` |

响应处理：`assertErrcodeOk(result, '发起支付')` 要求 `errcode === 0`，否则抛 `PayApiError('[xunhupay] 发起支付失败：<errmsg>')`，并把**原始报文**作为 `raw` 挂在错误上——`PayOrderService.createPayment()` 会用它写一条 `FL`（发起失败）订单的 `provider_data`。

下单成功后适配器返回：

| 字段 | 取值 |
| --- | --- |
| `providerOrderId` | `pickResponseFields()` 结果，取不到则为空串 `''` |
| `payMode` | 固定 `'qrcode'` |
| `qrImageUrl` | 二维码图片地址，取不到为 `null` |
| `qrContent` | 固定 `null`（虎皮椒直接给图片地址，不做本地渲染） |
| `payUrl` | 支付链接，取不到为 `null` |
| `providerStatus` | 固定 `'WP'`（刚下单必然是待支付） |
| `raw` | 网关完整响应，落库进 `sys_pay_order.provider_data.create` |

## 签名算法

`makeXunhuPaySign(params, secret)` 是一个纯函数，规则如下：

1. **过滤空值**：丢掉 `undefined`、`null`、`''` 的参数；
2. **排除 `hash`**：`hash` 字段本身不参与签名（否则永远算不出来）；
3. **按参数名 ASCII 升序**：`Object.keys(filtered).sort()`，即默认的字符串升序；
4. **拼接**：`k=v` 用 `&` 连接，形如 `k1=v1&k2=v2`，值不做 URL 编码；
5. **末尾直接拼 `secret`**：不加 `&`，也不加 `=`；
6. **MD5 小写十六进制**：`createHash('md5').update(query + secret, 'utf8').digest('hex')`。

伪代码示例：

```text
params = {
  version: "1.1", appid: "2019xxxx", trade_order_id: "PAY20261001120000AB12CD",
  total_fee: "0.01", title: "扫码支付", notify_url: "https://example.com/api/pay/notify/xunhupay",
  time: "1760000000", nonce_str: "3f2a...", attach: ""
}
secret = "SECRET"

① 过滤：attach 为空串 → 剔除；hash 本来就不在 params 里
② 排序：appid, nonce_str, notify_url, time, title, total_fee, trade_order_id, version
③ 拼接：appid=2019xxxx&nonce_str=3f2a...&notify_url=https://example.com/api/pay/notify/xunhupay&time=1760000000&title=扫码支付&total_fee=0.01&trade_order_id=PAY20261001120000AB12CD&version=1.1
④ 追加密钥：③ 的字符串 + "SECRET"
⑤ 取 MD5 小写十六进制 → 这就是 hash
```

用 TypeScript 描述同一个过程：

```ts
const filtered: Record<string, string> = {}

for (const [key, value] of Object.entries(params)) {
  if (key === 'hash' || value === undefined || value === null || value === '') continue
  filtered[key] = String(value)
}

const query = Object.keys(filtered)
  .sort()
  .map(key => `${key}=${filtered[key]}`)
  .join('&')

const hash = createHash('md5').update(`${query}${secret}`, 'utf8').digest('hex')
```

回调验签复用同一个函数：把**回调报文的全部字段**（含 `hash` 自己，反正会被排除）传进去算一遍，再与报文里的 `hash` 比较。

## 响应字段兼容

不同版本、不同渠道的虎皮椒网关返回结构不一致，`pickResponseFields()` 负责抹平差异：

```text
A) 官方文档形态（结果嵌在 data 里）
{ "errcode": 0, "errmsg": "success", "hash": "...", "data": { "open_order_id": "...", "url_qrcode": "...", "url": "..." } }

B) 实测形态（结果平铺在顶层，平台单号键名是 openid）
{ "errcode": 0, "errmsg": "success!", "openid": "...", "url_qrcode": "...", "url": "...", "hash": "..." }
```

取值策略是「`data` 优先、顶层兜底」+「候选键名依次尝试」，且跳过 `undefined` / `null` / `''`。字段别名映射表：

| 用途 | 取值顺序（先 `data` 后顶层） | 归一化 |
| --- | --- | --- |
| 平台订单号 | `open_order_id` → `openid` → `openOrderId` → `order_id` → `orderId` | 转字符串 |
| 二维码图片地址 | `url_qrcode` → `qr_image_url` → `qrcode` → `qr_code` → `qrCode` | 转字符串 |
| 支付链接 | `url` → `pay_url` → `payUrl` | 转字符串 |
| 平台状态 | `status` → `trade_status` → `order_status` → `pay_status` | 缺省 `'WP'` |
| 交易号 | `transaction_id` → `transactionId` → `trade_no` | 转字符串或 `null` |
| 商户订单号 | `trade_order_id` → `out_trade_order` | 回调定位订单用 |
| 金额 | `total_fee` → `amount` | `Number()` 后必须有限且 `> 0`，否则为 `null`；合法则 `toFixed(2)` |

`errcode !== 0` 由 `assertErrcodeOk(result, action)` 统一拦截：抛出 `PayApiError('[xunhupay] <action>失败：<errmsg ?? '未知错误'>')`，把原始报文与 `errcode` 一并带上。下单的 `action` 是「发起支付」，查询的 `action` 是「查询订单」。

## 查询订单

`queryPayment(channel, { outTradeNo, providerOrderId })`：

- 两个键都没传 → 抛 `PayApiError('[xunhupay] 查询订单需要 out_trade_order 或 open_order_id')`；
- 参数只有 `appid`、`time`、`nonce_str`，外加 `out_trade_order`（优先）或 `open_order_id`（二选一，不会同时传）；
- 签名后 POST `/payment/query.html`，再走 `assertErrcodeOk(result, '查询订单')`；
- `providerStatus` 缺省 `'WP'`，统一状态由 `server/pay/statusMap.ts` 映射：`WP → WP`、`OD → OD`、`CD → CD`，未登记的平台状态一律降级为 `WP`（避免把未知状态误判成已支付）；
- `providerOrderId` 取不到时回退为调用方传入的 `key.providerOrderId`；
- 原始响应由调用方写入 `provider_data.lastQuery`。

## 回调

回调入口是免登录的原生路由 `POST /api/pay/notify/xunhupay`（`server/api/pay/notify/[channel].post.ts`），它把原始报文按表单解析后交给 `PayNotifyDispatcher`，由后者逐个候选渠道调用适配器的 `verifyAndParseNotify()`。

`verifyAndParseNotify()` 的校验顺序：

| 顺序 | 校验 | 不通过时 |
| --- | --- | --- |
| 1 | 报文里有 `hash` | 抛 `PaySignError('[xunhupay] 回调缺少 hash')` |
| 2 | `makeXunhuPaySign(body, secret)` 与报文 `hash` 相等 | 抛 `PaySignError('[xunhupay] 回调签名校验失败')` |
| 3 | 报文 `appid`（若有）与渠道配置一致 | 抛 `PaySignError('[xunhupay] 回调 appid 与渠道配置不一致')` |
| 4 | 能取到 `trade_order_id` | 抛 `PaySignError('[xunhupay] 回调缺少 trade_order_id')` |

通过后返回：

| 字段 | 说明 |
| --- | --- |
| `outTradeNo` | 必填，来自 `trade_order_id` / `out_trade_order` |
| `providerOrderId` / `transactionId` | 取不到为 `null` |
| `providerStatus` | 缺省 `'WP'` |
| `status` | `mapProviderStatus('xunhupay', providerStatus)` |
| `amount` | 报文的 `total_fee` / `amount`，供金额核对 |
| `currency` | `channel.currency \|\| 'CNY'` |
| `paidAt` | 恒为 `null`（由分发器用本地时间补） |
| `dedupKey` | `outTradeNo:providerStatus:transactionId \|\| providerOrderId` |

`dedupKey` 刻意不用报文摘要：虎皮椒重试时会重新生成 `time` / `nonce_str`，摘要每次都不同，去重会失效；用「订单 + 状态 + 交易号」才能正确识别重复通知。

`buildNotifyResponse()` 决定回给网关的响应体：

| 参数 | `statusCode` | `contentType` | `body` |
| --- | --- | --- | --- |
| `ok = true` | `200` | `text/plain; charset=utf-8` | `success` |
| `ok = false` | `400` | `text/plain; charset=utf-8` | `invalid sign` |

分发器在部分分支里也会**绕过适配器**直接返回纯文本响应，排查时注意区分：验签阶段全部候选渠道都没通过 → `400 invalid sign`；验签通过但来源 IP 不在白名单 → `403 ip blocked`；处理过程中抛非验签异常 → `500 error`。分发器的完整分支见 `/docs/main/payment/notify`。

## 「测试配置」的判定逻辑

渠道配置页的「测试配置」按钮调用 `sysPayChannel.verify`，最终落到适配器的 `verifyChannel()`：用 `/payment/query.html` 发一次**真实请求**来探测网关，用一个不可能存在的订单号 `verify-<时间戳>`。

| 情况 | 判定 | 返回 |
| --- | --- | --- |
| `readConfig()` 抛错（APPID/SECRET/网关缺失或校验失败） | 凭据不完整 | `{ success: false, message: <错误信息 \|\| '渠道凭据不完整'> }` |
| `errcode === 0` | 网关连通、签名与 APPID 都通过 | `{ success: true, message: '网关连通，签名与 APPID 校验通过' }` |
| `errmsg` 命中 `/签名\|sign\|hash/i` | 签名被拒 | `{ success: false, message: '签名校验失败（SECRET 可能不正确）：<errmsg>' }` |
| `errmsg` 命中 `/appid\|应用/i` | APPID 被拒 | `{ success: false, message: 'APPID 无效（errcode=<code>）：<errmsg>' }` |
| 其余错误（例如订单不存在） | **请求已被受理**，APPID 与签名都没被拒绝 | `{ success: true, message: '网关连通、APPID 与签名已被受理（errcode=<code>，<errmsg>）' }` |
| 网络/超时等异常 | 无法确认 | `{ success: false, message: <错误信息 \|\| '验证失败'> }` |

注意第 5 种情况是**有意的宽松判定**：虎皮椒先校验 APPID、再校验签名/订单号，所以「订单不存在」这类业务错误恰好证明凭据可用。实测中虎皮椒对错误 APPID 返回 `{"errcode":40029,"errmsg":"未知的APPID"}`，`errmsg` 命中 `appid` 规则，因此会被正确判为失败。

Service 层会把结论落回渠道行：成功 `verify_status = 1`，失败 `2`，同时写 `verify_time`（`nowForMysql()`）与截断到 500 字符的 `verify_message`。凭据或渠道类型一旦改动，`verify_status` 会被重置为 `0`，必须重新测试——这也是 `ScanPay` 组件拒绝未测试渠道的原因，详见 `/docs/main/payment/channels`。

## 本地模拟回调

`buildSimulatedNotify()` 用渠道配置里的真实 `secret` 现算签名，构造一份报文交给分发器，因此走的是**与真实回调完全相同**的验签、幂等、金额核对链路。

构造的字段：`trade_order_id`、`total_fee`、`transaction_id`（订单已有则复用，否则 `SIM<时间戳>`）、`open_order_id`（同上，否则 `SIMOPEN<时间戳>`）、`order_title`、`status` 固定 `'OD'`、`appid`、`time`、`nonce_str`，订单有 `attach` 时附带，最后补 `hash`。请求体编码为 `application/x-www-form-urlencoded`。

这条路径受三个开关限制：环境开关（生产环境需显式 `NUXT_PAY_SIMULATE_ENABLED=true`）、订单 `biz_type` 必须是 `test`、订单不能已支付。

## 常见错误对照

| 错误码 / 现象 | 原因 | 处理 |
| --- | --- | --- |
| `{"errcode":40029,"errmsg":"未知的APPID"}` | APPID 与网关不匹配（多账户、复制错、把「我的支付渠道」里的其它编号当成 APPID） | 用虎皮椒后台「我的应用」里的 APPID 覆盖渠道配置，改完重新「测试配置」 |
| 日志里出现 HTML 或 `响应不是合法 JSON`、`HTTP 404` | `gateway` 被填成了完整接口地址，拼出了 `.../payment/do.html/payment/query.html` | 只填到域名，例如 `https://api.dpweixin.com`；归一化会自动剥掉接口路径，但别指望它能修好任意错误地址 |
| 「测试配置」提示签名校验失败 | SECRET 不对、末尾多了空格、渠道与 APPID/SECRET 不是同一套 | 重新复制 SECRET；确认没有首尾空格；同一渠道的 APPID 与 SECRET 必须成对 |
| 返回 `200` 但界面上没有二维码也没有支付链接 | 网关返回的字段名不在别名表里，或该值为空 | 看该订单详情里的 `provider_data.create` 原始响应，再在 `pickResponseFields()` 的候选键名里补上；界面文案 `module.system.payTest.noQrcode` / `noQrcodeNoUrl` 就是在提示这个 |
| `errcode` 非 0 且消息带 `发起支付失败：` | 网关明确拒绝（参数、金额、权限等） | 报文原文在错误对象上，已写入失败订单的 `provider_data`；先按 `errmsg` 定位 |
| 有支付链接但没有二维码 | 网关只返回了 `url` | 组件会展示「打开支付链接」按钮，属正常分支 |
| 金额相关报错 | 金额非有限数、`<= 0`，或超过 `sys_pay_order.amount decimal(10,2)` 上限 | 传入 `0.01 ~ 99999999.99` 之间的元金额 |
| 下单成功但一直待支付 | 回调未到达（网关到不了本机），或用户未付款 | 用「查询状态」主动查询；本地联调用「模拟支付成功」。详见 `/docs/main/payment/troubleshooting` |

前端接入与组件用法见 `/docs/main/payment/frontend`，订单与记录页见 `/docs/main/payment/orders`。
