## 一、生成了订单但看不到二维码

先确认订单是什么状态：`/system/pay-order` 里如果那条订单是**发起失败**（`FL`），说明下单请求就被网关拒了，界面自然不会展示二维码，真正的原因在 `fail_reason` 与该订单详情里的 `provider_data`（失败分支写入的是错误对象携带的原始报文）。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 订单是 `WP`，二维码区提示「渠道未返回二维码，请使用支付链接」 | 网关只在 `url` 里返回了支付链接，`url_qrcode` 为空 | 这是正常分支，点「打开支付链接」完成支付；若该渠道本应返回图片，按下一行处理 |
| 订单是 `WP`，提示「渠道未返回二维码和支付链接」 | 网关返回的字段名不在 `pickResponseFields()` 的候选键名里，或值本身为空 | 打开订单详情查看 `provider_data.create` 原始响应，确认真实字段名后在 `server/trade-router/domain/pay/providers/xunhupay.ts` 的别名表里补齐 |
| 二维码图片是坏图标 | `qrImageUrl` 拿到了值但不是可访问的图片地址 | 同样先看 `provider_data.create`，确认网关给的是图片 URL 而非二维码内容字符串 |
| 订单是 `FL`（发起失败） | 网关返回 `errcode !== 0`、HTTP 非 2xx、响应不是 JSON 或网络失败 | 看 `fail_reason`（形如 `[xunhupay] 发起支付失败：<errmsg>`）与 `provider_data`；常见原因是 APPID 无效、网关地址填错 |
| 订单号重复被拒 | `out_trade_no` 命中唯一索引 | 不传 `outTradeNo` 让后端生成，或换一个订单号 |

补充：虎皮椒适配器不做本地二维码渲染（`localQrRender: false`、`qrContent` 恒为 `null`），所以界面上出现「复制二维码内容」文本框一定是别的渠道返回了 `qrContent`。

## 二、付款成功后页面状态不自动更新

本模块**没有**前端长连接或平台推送：状态推进完全靠「主动查询渠道」这一个动作，页面只是定时触发它。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 付款后几秒内没变化 | 默认 5 秒轮询一次，尚未到下一次 | 等待，或直接点「查询状态」 |
| 点了多次「查询状态」都像是没反应 | 服务端 3 秒节流：`lastQueryAt` 距现在不足 3 秒时直接返回本地快照，**不请求平台** | 隔 3 秒以上再点 |
| 一直不更新且出现「自动查询连续失败」 | 组件连续失败 3 次后停止轮询并 `emit('error')` | 按提示点手动「查询状态」，同时排查网关连通性/凭据 |
| 出现「自动查询已超时」 | 轮询累计时长超过 `pollTimeout`（默认 10 分钟） | 手动「查询状态」或重新下单 |
| 页面停留很久也不会自动刷新 | 组件卸载时会 `stop()`；`pollInterval <= 0` 时根本不轮询 | 支付记录页点「同步状态」（需要 `system:payOrder:query` 或管理员） |
| 状态一直是 `WP` | 用户未实际付款，或平台查询接口还没返回成功状态 | 平台侧确认到账后重新查询 |
| 状态自动变成 `CL`（已关闭） | 主动查询时发现订单已过期（`expire_at < 当前时间`）且平台仍未支付 | 属保护逻辑；重新下单 |

注意两点：轮询走的 `sysPayTest.syncStatus` 刻意关闭了操作日志（`log: false`），避免把系统日志刷满——状态真正变化时写的是**支付回调日志表**；已支付订单再次查询不回退，只会刷新 `last_query_at`。

## 三、「测试配置」提示 404 或返回 HTML

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 提示 `响应不是合法 JSON（...）：<!DOCTYPE html>...` | `gateway` 被填成了完整接口地址（如 `https://api.dpweixin.com/payment/do.html`），拼出了 `.../payment/do.html/payment/query.html` | 只填到域名，例如 `https://api.dpweixin.com`；`normalizeXunhuPayGateway()` 会自动剥掉 `/payment/do.html`、`/payment/query.html`、`/payment/refund.html`、结尾的 `/payment` 并补全 `https://` |
| 提示 `HTTP 404（...）` 且地址里带接口路径 | 同上 | 同上 |
| 提示 `HTTP 404` 但地址看起来正常 | 网关域名/端口写错，或虎皮椒给出的接入地址本身需要保持某个自定义前缀（归一化只剥固定的几种后缀，其余前缀会保留） | 与虎皮椒后台「我的支付渠道」逐字核对 |
| 提示 `[xunhupay] fetch failed` 之类 | DNS/网络/防火墙不通，或超时（请求超时 10 秒） | 在服务器上 `curl` 该网关地址确认可达 |
| 提示签名校验失败 | SECRET 不对或不属于同一渠道 | 重新复制 SECRET，确认无首尾空格 |
| 提示 APPID 无效（`errcode=40029`） | 多账户复制错、或把「我的支付渠道」里的渠道编号当成了 APPID | 用「我的应用」里的 APPID 覆盖渠道配置 |
| 提示「网关连通、APPID 与签名已被受理（errcode=...，<errmsg>）」 | 这是**成功**结论：除「签名」「appid」之外的错误（如订单不存在）说明请求已被网关受理 | 无需处理，直接下单验证 |
| 提示 `common.notExist` / 404 且没有网关报文 | 渠道 ID 不存在（接口返回 `NOT_FOUND`），与「网关 404」是两码事 | 刷新渠道列表后重试 |

## 四、编辑渠道时与密钥有关的报错

先记住语义：**留空 = 不修改**。`isUnchangedSecretInput()` 把 `undefined`、`null`、空字符串、以及以 `****` 开头的掩码值都视为「不修改」，这类输入既不参与 `configSchema` 校验，也不会覆盖已保存的密文。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 编辑时密钥留空后保存，报「渠道凭据缺少必填字段」 | 该字段在**新增**场景下是必填的；编辑场景留空不会触发，触发说明实际走的是新增 | 新增必须填写全部必填字段 |
| 切换「渠道类型」后保存报 `configRequiredOnTypeChange` | 渠道类型变了但没有提交凭据 | 重新填写新渠道的凭据 |
| 保存报 `configKeyMissing` | 服务端没配置 `NUXT_PAY_CONFIG_KEY`，无法加密新密钥 | 配置 32 字节主密钥（`openssl rand -base64 32`）并重启 |
| 保存报 `configKeyInvalid` | 主密钥存在但格式不对（需要 32 字节：base64 或 64 位 hex） | 重新生成并重启 |
| 保存成功但读取报 `decryptFailed` | 主密钥变更过，旧密文解不开 | 用当前主密钥重新填写并保存密钥 |
| 表单顶部一直有警告条 | 未配置加密 key（`encryptionMissing`）或格式不对（`encryptionInvalid`）；`providerMetas` 返回的 `encryptionReady` / `encryptionReason` 驱动该提示 | 按警告文案修复环境变量 |
| 把掩码 `****abcd` 复制进输入框后保存 | 以 `****` 开头会被判为「不修改」 | 要改就直接粘贴完整的新密钥 |
| 保存后「验证状态」变回未验证 | 凭据或渠道类型变更会重置 `verify_status = 0` | 重新点「测试配置」 |

## 五、收不到渠道异步回调

回调入口是 `POST /api/pay/notify/{渠道编码}`（如 `/api/pay/notify/xunhupay`），**免登录**，鉴权完全依赖渠道验签。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 本地/内网环境永远收不到回调 | 回调地址不可公网可达。像 `http://127.0.0.1:3001/api/pay/notify/xunhupay` 这种地址平台侧根本无法访问 | 用公网域名或内网穿透；本地联调改用「查询状态」或「模拟支付成功」 |
| 页面出现「该回调地址不是公网可达地址」警告条 | 组件检测到地址为空、`http://` 开头，或含 `localhost` / `127.0.0.1` / `0.0.0.0` / `192.168.` / `10.` / `172.16~31.` / `.local` | 换成公网 HTTPS 地址；这只是一条提示，不阻止下单 |
| 渠道配置里没填 `notify_url` | 服务端会按当前请求 `origin` 推导 `{origin}/api/pay/notify/{渠道编码}`，本地访问就会推导出 localhost | 在渠道配置或下单参数里显式填写公网地址 |
| 回调日志里有记录但 `process_result = invalid_sign` | SECRET 不匹配、渠道配置有多套账户时都可能命中 | 核对渠道 SECRET；确认回调打到的正是报文里那个 APPID 对应的渠道 |
| 回调日志里 `process_result = ip_blocked`，平台收到 403 | 渠道配置了「回调 IP 白名单」，而来源 IP 不在名单内（反向代理后可能拿到代理 IP） | 核对日志里的来源 IP 与渠道的 `ip_allowlist`；确认代理链上真实 IP 的传递方式 |
| 日志里完全没有记录 | 请求根本没到达本服务 | 检查域名解析、反向代理规则、防火墙与 `POST` 路径是否写成 `/api/pay/notify/{渠道编码}` |
| 平台一直重试 | 响应体不是它期望的纯文本 `success`，或状态码不是 200 | 检查是否被前置网关/WAF 改写响应；正常链路返回 `200 success` |
| 回调地址用了 `https` 但证书无效 | 平台侧校验证书失败 | 换有效证书或使用可信域名 |

## 六、未测试渠道不能下单

新建渠道时 `verify_status` 落库为 `0`，凭据或渠道类型一旦变更也会被重置为 `0`。未通过测试的渠道在下单时会被**前后端双重拦截**：

| 拦截层 | 表现 |
| --- | --- |
| 前端 `ScanPay` 组件 | 直接报 `module.system.scanPay.channelNotVerified`（「渠道「X」尚未通过「测试配置」…」），不发下单请求 |
| 服务端 `sysPayTest.create` | 报 `module.system.payChannel.notVerified`，参数是渠道配置名 |
| 匹配渠道 | 渠道列表里没有可用渠道时报 `module.system.payChannel.notConfigured` |

处置：到渠道配置页对该渠道点「测试配置」，徽标变为「已验证」（`verify_status = 1`）后即可下单。测试结论与时间分别记录在 `verify_message`（截断 500 字符）与 `verify_time`。

## 七、订单时间与本地时间差 8 小时

`sys_pay_order` 的 `created_at` / `updated_at` 由 MySQL 的 `CURRENT_TIMESTAMP`（会话时区，本机 `+08:00`）写入，格式是 `YYYY-MM-DD HH:mm:ss` 的**本地墙钟时间**。历史版本用 `Date.prototype.toISOString()` 写入的字段则是 UTC，两者混用会让时间整整差 8 小时。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 详情里 `paid_at` / `expire_at` / `last_query_at` 比 `created_at` 早 8 小时 | 这些列被 `toISOString()` 写入了 UTC 时间 | 新代码统一使用 `nowForMysql()`（`server/trade-router/domain/pay/utils.ts`），不要再引入 `toISOString()` |
| 待支付订单很快被自动关闭为 `CL` | `expire_at` 被写成 UTC，字符串比较时必然小于当前本地时间，`isExpired()` 直接判为过期 | 修正历史数据的时间值后重新下单 |
| 主动查询似乎不受 3 秒节流限制 | `secondsSinceMysqlDateTime()` 把 UTC 值按本地时间解析，得到「8 小时前」，远大于 3 秒 | 同上；这不会造成错误结果，只是节流失效 |

历史数据的修正思路（**执行前务必先备份**，并确认该时间段确实只受这个 bug 影响）：

```sql
-- 参考：把历史行里的 UTC 时间回补 8 小时
UPDATE sys_pay_order
SET paid_at      = DATE_ADD(paid_at, INTERVAL 8 HOUR),
    expire_at    = DATE_ADD(expire_at, INTERVAL 8 HOUR),
    last_query_at = DATE_ADD(last_query_at, INTERVAL 8 HOUR)
WHERE paid_at IS NOT NULL OR last_query_at IS NOT NULL;
```

受影响的列不止订单表：`cancelled_at`、`last_notify_at`、`verify_time` 同理。判断某行是否需要修正，最直接的依据是「该时间是否早于同一行的 `created_at`」。

## 八、回调日志的处理结论

日志表的 `process_result` 由 `PayNotifyDispatcher.handleNotify()` 写入，徽标文案在 `shared/constants/business.ts` 的 `payNotifyResultConfig` 里（`module.system.payNotifyLog.result.*`）。

| `process_result` | 含义 | 返回给平台 | 处置建议 |
| --- | --- | --- | --- |
| `success` | 处理成功：支付成功通知已把订单置为已支付；非支付成功通知只同步平台状态 | `200 success` | 无需处理 |
| `duplicate` | 幂等命中：该「订单+状态+交易号」事件已处理过，或订单已是已支付状态 | `200 success` | 正常现象（平台重试或并发回调），只需确认订单状态正确 |
| `invalid_sign` | 所有候选渠道验签都没通过 | `400 invalid sign` | 核对渠道 SECRET 与 APPID 是否成对；若为伪造请求可忽略（该日志用报文摘要做去重键，不会刷爆表） |
| `ip_blocked` | 验签通过，但来源 IP 不在渠道的 IP 白名单内 | `403 ip blocked` | 核对 `client_ip` 与渠道 `ip_allowlist`；注意反向代理下的真实 IP |
| `order_not_found` | 本地找不到该商户订单号 | `200 success` | 检查订单号生成规则或订单是否落库；返回 success 是为了避免平台无意义重试 |
| `amount_mismatch` | 通知的金额或币种与订单不一致（金额比较前统一两位小数） | `200 success` | **绝不改单**，需人工对账核实 |
| `status_mismatch` | 资金已到账，但订单此前是已取消/已关闭，已被推进为已支付并留痕 | `200 success` | 人工确认是否需要对账/退款流程介入 |
| `error` | 处理过程中抛出了非验签异常（配置、数据库等） | `500 error` | 看日志 `message`，通常是渠道配置损坏或解密失败 |

另外两类日志要注意区分：

- `source = query`（主动查询造成的状态变化）固定写 `success`，`sign_valid` 为 `0`，没有验签环节；
- `source = simulate`（本地模拟）走的是与真实回调完全相同的链路，因此它的 `process_result` 含义与上表一致。日志写入失败不会影响回调响应，日志重复键冲突会被静默忽略。

## 九、页面上看不到支付菜单或按钮

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 侧栏完全没有「支付渠道配置 / 支付记录 / 支付回调日志」等菜单 | 菜单可见性由 `sys_role_menu` 决定，当前角色没有被分配这些菜单 | 在角色菜单里分配对应菜单（含页面与按钮权限码） |
| 菜单能看到，但「新增 / 编辑 / 删除 / 测试配置 / 设为默认」按钮消失 | 前端按权限码渲染：`useCrudPermissions('system:payChannel')` 等，缺少对应按钮权限时直接不渲染 | 补分配 `system:payChannel:add/edit/del/verify/default` 等权限码 |
| 支付记录页看不到「同步状态」 | 主动查询会推进状态，需 `system:payOrder:query` | 补分配该权限码 |
| 测试页看不到「模拟支付成功」或按钮置灰 | 需要 `system:payTest:simulate`；置灰还可能是环境开关关闭或渠道未实现模拟回调 | 补权限；生产环境需 `NUXT_PAY_SIMULATE_ENABLED=true` |
| 测试页渠道下拉报无权限 | `sysPayTest.channels` 复用的是 `system:payTest:create` 权限码 | 补分配 `system:payTest:create` |
| 权限明明是管理员却仍然报 403 | 只有 `sys_user.is_admin = 1` 才绕过权限校验 | 确认当前账号的 `is_admin`；其余账号一律按 `sys_role_menu` 判定 |

权限判定在服务端有两处等价实现：tRPC 的 `permissionMiddleware`（`server/trpc/middlewares/permission.ts`）与原生路由的 `requirePermission`（`server/utils/routeGuard.ts`），都是「管理员直接放行，否则查权限码」。数据范围另有一套逻辑（`server/drizzle/queries/buildScope.ts`），同样对管理员短路。

唯一的例外是支付回调路由 `/api/pay/notify/{渠道编码}`：平台无法携带会话，因此该路由**免登录**，鉴权完全依赖渠道验签。

## 十、报错码速查

| 报错 | 来源 | 含义与处理 |
| --- | --- | --- |
| `module.system.payChannel.notConfigured` | 下单 | 没有可用渠道，或指定的渠道不存在/被禁用 |
| `module.system.payChannel.notVerified` | 下单 | 渠道未通过「测试配置」 |
| `module.system.payChannel.notifyUrlRequired` | 下单 | 回调地址为空：渠道没配、请求也没有公网 origin |
| `module.system.payChannel.configInvalid` / `configFieldRequired` | 渠道保存 | 凭据类型不合规 / 缺少必填字段（消息里带字段名） |
| `module.system.payChannel.configKeyMissing` / `configKeyInvalid` | 渠道保存 | 加密主密钥缺失 / 格式不对 |
| `module.system.payChannel.decryptFailed` | 读取渠道 | 主密钥变更导致旧密文解不开 |
| `module.system.payChannel.providerUnsupported` | 渠道/下单 | 渠道编码没有注册适配器（见 `server/trade-router/domain/pay/providers/index.ts`） |
| `module.system.payOrder.createFailed` | 下单 | 适配器失败，`message` 是原始错误；同时会留下一条 `FL` 订单 |
| `module.system.payOrder.amountInvalid` / `amountTooLarge` / `subjectRequired` | 下单 | 金额非法 / 超上限 / 缺标题 |
| `module.system.payOrder.notClosable` | 关闭订单 | 只有 `WP` 状态允许关闭 |
| `module.system.payTest.simulateDisabled` | 模拟支付 | 环境开关关闭 |
| `module.system.payTest.simulateOnlyTest` | 模拟支付 | 订单 `biz_type` 不是 `test` |
| `module.system.payTest.alreadyPaid` | 模拟支付 | 订单已支付 |
| `module.system.payTest.simulateUnsupported` | 模拟支付 | 该渠道未实现 `buildSimulatedNotify` |

模块整体的分层与数据模型见 `/docs/main/payment/overview`，渠道配置见 `/docs/main/payment/channels`，订单见 `/docs/main/payment/orders`，回调链路见 `/docs/main/payment/notify`，适配器细节见 `/docs/main/payment/xunhupay`，前端接入见 `/docs/main/payment/frontend`。
