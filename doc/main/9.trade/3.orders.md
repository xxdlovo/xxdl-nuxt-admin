订单域只有一个入口 `orderService(db)`（`server/trade-router/domain/order/OrderService.ts:554`），它负责事务边界与网络调用编排；事务内的状态机在 `buildOrder(tx)` 里（`:137`）。本页按「结构 → 下单 → 两条支付路径 → 状态推进 → 兜底任务」的顺序讲清这条链路。

## 二、订单号与幂等键

| 键 | 生成方式 | 唯一性保证 |
| --- | --- | --- |
| `order_no` | `buildOutTradeNo('ORD')` = `ORD` + `yyyyMMddHHmmss` + 6 位随机大写字母数字，例如 `ORD20260101120000A1B2C3`（`domain/pay/utils.ts:57-75`） | 唯一键 `uk_order_no` |
| `request_id` | 前端每次提交用 `randomUuid()` 生成（`app/pages/system/mall/index.vue:422`） | 唯一键 `uk_order_request` |

幂等判断走的是 `request_id`，有三层：

```text
create(input)
   ├─ 1. reads.findByRequestId(input.requestId)      命中 → 直接返回原单（reused: true）
   ├─ 2. 事务内 createTx 再查一次 findByRequestId    命中 → 同上
   │       （事务外/内两次查是为了「读幂等 → 拿锁 → 再确认」的常规写法）
   ├─ 3. insert 撞唯一键 → isDuplicateKeyError → 抛 OrderAlreadySettledError
   │       外层 fallback 重读 findByRequestId，取到就按「已处理」返回
   └─ 4. 重读仍取不到 → 原样抛出（内部错误）
```

对应代码：`OrderService.ts:627-641`（外层）、`:170-175`（事务内）、`:244-251`（唯一键冲突转换）、`:558-576`（`settleWithIdempotentGuard` 兜底）。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**两个与支付单不太一样的细节，排障时要记住：**

1. **订单号没有撞号预检与重试。**支付单会循环最多 3 次 `buildOutTradeNo()` + `existsOutTradeNo()` 预检（见[下单、查询与状态流转](/docs/main/payment/orders)），订单侧只有 `buildOutTradeNo('ORD')` 一次调用（`OrderService.ts:207`）。`insert` 的 catch 把**所有**唯一键冲突都当成「同一 requestId 并发」（`:244-251` 的注释只提 `requestId`），因此极低概率的 `uk_order_no` 撞号会被误判为「已处理」，最终 fallback 查不到单而冒出内部错误。
2. **`findByRequestId` 过滤 `is_deleted = 0`，而 `uk_order_request` 不含 `is_deleted`。**`domain/order/repo/orderRepo.ts:50-58` 只查未删除的行，唯一键却是全表的。所以「把一张 `CL`/`FL` 的订单删掉 → 用同一个 `requestId` 重新下单」会绕过幂等预检、直接撞唯一键，最终以内部错误结束。前端每次提交都换新的 uuid，正常操作不会碰到。
::

## 三、下单事务链（`createTx`）

`OrderService.create()` 全程只有**一个事务**（余额单），步骤与代码一一对应（`OrderService.ts:170-288`）：

```text
db.transaction(createTx)
  1. repo.findByRequestId(requestId)               幂等查重，命中即返回原单
  2. goods.assertPurchasable(goodsId)              不存在 → order.goodsNotFound
                                                   已下架 → order.goodsOffline
  3. isService ? quantity = 1 : max(1, floor(q))   服务类数量强制 1
  4. isService 且 contact 为空 → order.contactRequired
  5. members.getMember(userId) → levelId
     goods.resolvePrice({ goods, levelId })        等级价解析，落 unit_price / price_source / level_id
     totalAmount = 单价 × 数量（分运算）
  6. members.resolveCoupon({ code, userId, scene: 'consume', amount: totalAmount })
     discountAmount / payAmount
  7. payAmount <= 0 → order.payAmountInvalid       0 元订单不进入支付链路
  8. goods.decreaseStockOrThrow(goodsId, quantity) 条件 UPDATE，失败 → order.stockNotEnough
  9. repo.insert({ ... status: 'WP', expireAt, fulfillStatus })   落单
 10. coupon 存在 → members.lockCoupon({ bizNo: orderNo, ... })
 11. payMode === 'balance' → wallet.freeze({ bizNo: orderNo, amount: payAmount,
                                             attach: orderId, ttlMinutes: 0 })
     repo.attachFreeze({ freezeId, giftAmount, rechargeAmount })
 12. reread(orderId) → 返回最终行
```

四个关键点：

- **事务顺序是「扣库存 → 落单 → 锁券 → 冻结余额」**，任何一步抛错整体回滚，不会出现「扣了库存没落单」或「冻了钱没库存」（`:4-7` 的头部注释）。
- **优惠码用 `scene: 'consume'`**，与充值侧用的场景区分开；`lockCoupon` 先写 `sys_member_coupon_use` 使用记录再 `incrementUsedCount`，命中唯一键冲突时按幂等返回（`domain/member/MemberService.ts:427-464`）。
- **余额单的冻结 `ttlMinutes: 0`**：`WalletService.freeze()` 里 `ttl > 0 ? expireAt : null`，所以 `expire_at` 为 `null`、冻结**永不自动过期**，释放权只归订单侧（`domain/wallet/WalletService.ts:526-529`、`domain/order/types.ts:20-25`）。冻结金额按「先赠送金、不足部分落充值金」拆分，可用额不足时抛 `module.system.member.balanceInsufficient`（`WalletService.ts:510-524`），异常冒泡导致整个事务回滚——**不落单**。
- **`attachFreeze` 回填的是 `gift_amount` / `recharge_amount`**，因此「这一单用了多少赠送金」在订单上可直接读到（`domain/order/repo/orderRepo.ts:142-160`）。

## 四、余额支付：冻结与确认

**确认支付**是余额单唯一的实扣动作，入口有两处：会员自助 `sysOrder.myConfirm`、后台「确认支付」（`system:order:confirm`）。核心实现在 `confirmTx`（`OrderService.ts:332-389`）：

```text
confirmTx({ orderId | orderNo, operatorId })
   ├─ findOrderByKey                          找不到 → common.notExist
   ├─ status === 'OD'                         → 直接返回 reused: true（幂等）
   ├─ status !== 'WP'                         → order.notPayable
   ├─ payMode !== 'balance'                   → order.wrongPayMode
   ├─ wallet.confirm({ freezeId, bizNo: freezeId ? null : orderNo })   确认冻结
   │      冻结已 CONFIRMED → reused: true（不重复实扣）
   │      冻结状态不是 FROZEN → freezeNotFrozen
   │      冻结单不存在 → freezeNotFound
   ├─ repo.markCompleted({ paidAt, finishedAt })   where status = 'WP'
   │      affected === 0 → OrderAlreadySettledError（回滚）
   ├─ coupon 存在 → members.markCouponUsed({ bizNo })
   └─ goods.increaseSales(goodsId, quantity)
```

`wallet.confirm()` 的实扣细节（`domain/wallet/WalletService.ts:571-648`）：`freezes.markConfirmed` 条件更新 → `wallet.settleFrozen` 扣赠送金余额与充值金余额（返回 0 说明余额不一致，抛 `module.system.member.walletInconsistent`）→ **为正的金额各写一条 `biz_type = 'consume_confirm'` 的余额流水**（赠送金 / 充值金分开，`:613-638`）。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**冻结在确认前已被人工释放时，用独立事务关单。**

`confirmTx` 把 `freezeNotFound` / `freezeNotFrozen` 转成内部错误 `OrderFreezeLostError`（`:359-369`），外层 `confirm()` 捕获后用**一个全新事务**关闭订单——原因写死「冻结已释放，订单自动关闭」、`source = 'admin'`——再抛 `module.system.order.freezeExpired`（文案「余额冻结已释放，请重新下单」，`app/locales/zh.json:1786`）。

必须是独立事务：本次失败的事务已经回滚，如果复用它会连关单一起回滚，订单就永远停在 `WP` 且冻结已丢（`:693-703`）。
::

## 五、在线支付：支付单创建、回填与失败回滚

在线单的下单链路比余额单多三步，原因是**渠道下单是网络调用，不能放进事务**（`OrderService.ts:647`）：

```text
create(input)  payMode === 'online'
   ├─ 事务内：与余额单完全相同的 createTx（但跳过冻结分支），订单落成 WP
   ├─ 事务外：payOrderService(db).createPayment({ … }, { operatorId })
   │      outTradeNo: created.orderNo          订单号即商户订单号
   │      amount:     created.payAmount        实付金额（已扣优惠券）
   │      subject:    `订单 ${orderNo}`
   │      bizType:    'order'                  ← 支付回调分派依据
   │      attach:     `order:${orderId}`       业务主键冗余，分派不读
   │      notifyUrl / origin                   回调地址推导
   ├─ 成功 → 小事务 attachPayOrder：回填 pay_order_id / pay_channel_code
   │        返回体再用支付单的 qrImageUrl / qrContent / payUrl / expireAt 补齐
   └─ 失败 → 小事务 failOnlinePayment：
             repo.markFailed（status = 'FL'，fail_reason 截断 500）
             goods.rollbackStock(goodsId, quantity)
             coupon 存在 → members.releaseCoupon({ bizNo })
             抛 AppError('module.system.order.payCreateFailed', { message })
```

| 语义 | 落点 |
| --- | --- |
| 失败订单**仍然落库**，目的是留下排查线索（`fail_reason` + 关联的 `FL` 支付单） | `OrderService.ts:305-326` |
| `FL` 单允许删除，用户可重新下单 | `modules/order/SysOrderService.ts:98-115` |
| 触发幂等（`requestId` 命中）返回原单时，会**再读一次支付单**把二维码补进返回体，页面无需重新下单 | `OrderService.ts:876-895`（`fillPayInfo`） |
| 余额单不创建支付单，`pay_order_id` 恒为 `null` | `:643-645` |
| 支付成功后的业务后置（回调 `onPaid` → `markPaid`）由支付模块分派，本模块不重复实现 | 见[业务接入：bizType 分派](/docs/main/payment/integration) |

## 六、支付成功（`markPaid`）

在线支付到账后，回调分派（`biz_type = 'order'`）与后台「同步」都调用同一个方法 `markPaid(orderNo, operatorId)`（`OrderService.ts:579-593`），核心是 `markPaidTx`（`:395-428`）：

```text
markPaidTx({ orderNo, operatorId })
   ├─ repo.findByOrderNo       找不到 → module.system.order.notFound
   ├─ status === 'OD'          → 直接返回 reused: true
   ├─ status !== 'WP'          → module.system.order.notPayable（已关闭的单不能靠补付救回）
   ├─ repo.markCompleted({ paidAt, finishedAt })     where status = 'WP'
   │      affected === 0 → OrderAlreadySettledError → 外层重读按已处理返回
   ├─ coupon 存在 → members.markCouponUsed({ bizNo })
   └─ goods.increaseSales(goodsId, quantity)
```

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**在线单不动余额。**`markPaidTx` 不调 `wallet.confirm`，返回的 `giftAmount` / `rechargeAmount` 固定为 `0.00`（`:427`）——钱来自渠道，不是冻结的余额。余额单的实扣只走第四节的 `confirm`。

因此「订单完成」与「余额流水」是两条独立事实：想核对余额单的资金，看 `sys_member_balance_log` 里 `bizType = 'consume_confirm'` 的流水；想看在线单的资金，看关联支付单的状态（见[下单、查询与状态流转](/docs/main/payment/orders)）。
::

## 七、取消与关闭

`cancel` 统一走 `cancelTx`（`OrderService.ts:434-487`），三个来源（用户自助 / 后台 / 超时任务）共用同一条路径，行为一致：

```text
cancelTx({ orderId | orderNo, reason, source, operatorId })
   ├─ findOrderByKey                       找不到 → common.notExist
   ├─ status === 'CL'                      → 直接返回 reused: true（幂等）
   ├─ status !== 'WP'                      → module.system.order.notClosable（OD 不能关）
   ├─ freezeId 存在 → wallet.release({ freezeId, reason })
   │      捕获 AppError 后忽略：冻结被人工释放过时释放本身已是幂等，
   │      但**非 AppError 照旧向上抛**
   ├─ coupon 存在 → members.releaseCoupon({ bizNo })
   ├─ goods.rollbackStock(goodsId, quantity)
   └─ repo.markClosed({ closedAt, closeReason })     where status = 'WP'
          affected === 0 → OrderAlreadySettledError
```

关闭原因固定映射（`:56-61`，用户可见，落 `close_reason`）：

| `source` | 原因文案 | 调用方 |
| --- | --- | --- |
| `user` | 用户取消 | `myCancel`（`SysOrderService.ts:275-284`） |
| `admin` | 后台关闭（弹窗可自定义原因） | `sysOrder.close`（`SysOrderService.ts:180-187`） |
| `timeout` | 超时未支付 | `order:expire-close` 任务 |

两条补充行为：

- **在线单额外 best-effort 关闭渠道支付单**：`cancelOrder` 在本地关单成功后（`!reused`）才调 `closeChannelPayment`，且整段包在 `try/catch` 里静默失败——本地状态已经确定，渠道侧关不掉不能反过来影响订单（`OrderService.ts:599-618,897-913`）。当前两个适配器都没有实现平台侧关单，所以这一步实际只改本地支付单状态（见[渠道配置与适配器](/docs/main/payment/channels)）。
- **后台关闭原因必填**：弹窗先拦一次（`app/pages/system/order/components/sys-order-close.vue:45-50`），留空不发请求；服务端 `reason` 本身可空，为空时回落成「后台关闭」。

## 八、服务交付（`fulfill`）

交付**只推进履约、不牵动资金**（`OrderService.ts:489-517`）：

```text
fulfillTx({ orderId | orderNo, remark, operatorId })
   ├─ fulfillStatus === 'delivered'                    → reused: true（幂等）
   ├─ status !== 'OD' 或 fulfillStatus !== 'pending'   → module.system.order.notFulfillable
   └─ repo.markFulfilled({ fulfilledAt, fulfillRemark, operatorId })
          where id = ? and status = 'OD' and fulfill_status = 'pending'
          同时写 fulfill_operator_id（交付操作人）
```

因此「交付」有严格前置：**只有服务类（`fulfill_status = 'pending'`）且已完成（`status = 'OD'`）的订单才能交付**。`none`（虚拟/实物）与已 `delivered` 的单分别报「不可交付」与「已处理」。后台按钮的显示条件与之一致：`status === 'OD' && fulfillStatus === 'pending'`（`app/pages/system/order/index.vue:370-378`）。

## 九、超时关单任务（`order:expire-close`）

任务 handler 只有一行，逻辑全在 `expireClose`（`server/sys-router/job/handlers.ts:163-170`、`OrderService.ts:741-787`）：

```text
expireClose(limit = 200)     ORDER_EXPIRE_BATCH_SIZE
   ├─ listExpiredPending(limit)      status = 'WP' and is_deleted = 0 and expire_at <= now
   │                                 order by expire_at asc limit 200
   └─ for each row （逐单独立事务，单笔失败不影响其余）
        ├─ row.payOrderId 存在 → payOrderService(db).getById(payOrderId)
        │      payOrder.status === 'OD'
        │         → markPaid(orderNo, null)   补做业务后置，**不关单**
        │           !settled.reused → recoveredCount += 1
        │           continue
        ├─ cancelTx({ orderId, reason: '超时未支付', source: 'timeout' })
        │      !reused → closedCount += 1
        │      且 payOrderId 存在 → closeChannelPayment（best-effort）
        └─ 任一步抛错 → failures.push({ orderNo, message })
   返回 { scanned: rows.length, closedCount, recoveredCount, failures }
```

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**关单前先读本地支付单，是这条任务最关键的一步。**如果支付单已经是 `OD`（说明回调到了但业务后置没做完，或订单是被主动查询推进的），这笔钱其实收到了，于是改为 `markPaid` 把订单正常推进到 `OD` 并计入 `recoveredCount`，而不是关掉。否则会出现「钱在渠道、订单被关」，此后 `sync` 也不会再自愈（订单已非 `WP`，`OrderService.ts:797-804` 直接返回 `changed: false`）。

只读**本地**状态、不发渠道请求：一次最多扫 200 单，逐单外呼不可接受（`:732-740` 的注释）。**回调完全没到达、本地支付单仍是 `WP`** 的情况无法在这里发现，只能人工对账，详见[业务接入：bizType 分派](/docs/main/payment/integration)第七节。
::

几个操作要点：

- 任务在 DDL 里**默认禁用**（`status = 0`），必须在定时任务页启用才参与调度（`doc/main/mysql-ddl-goods-order.sql:163-174`）；调度机制见[定时任务总览](/docs/main/scheduled-jobs/overview)。
- `recoveredCount > 0` 是**异常信号**，不是正常现象：出现即说明有业务后置没走完。
- `payOrderId` 指向的支付单被硬删时，`getById` 抛 `common.notExist`，该单会落进 `failures` 而不是被关闭。

## 十、主动同步（`sync`）与自愈

后台「同步状态」（`system:order:sync`）与会员自助 `mySync` 都走 `OrderService.sync`（`OrderService.ts:790-846`）：

```text
sync({ orderId | orderNo, operatorId })
   ├─ findOrderByKey                        找不到 → common.notExist
   ├─ status !== 'WP' 或 payOrderId 为空     → { changed: false, payOrderStatus: null }
   ├─ payOrderService.queryPayment(payOrderId)   外呼渠道（含 3 秒节流与过期兜底关单）
   ├─ 支付单 CL / FL
   │     → cancelOrder({ reason: `支付单已关闭/失败`, source: 'admin' })   就地自愈关单
   ├─ 支付单 OD                              → markPaid(orderNo, operatorId)
   └─ 其它                                   → { changed: false, payOrderStatus }
```

返回 `OrderSyncResult`（`domain/order/types.ts:103-108`）：`{ orderNo, status, payOrderStatus, changed }`。前端据 `changed` 分别给出「已推进」或「未变化 + 渠道当前状态」的提示（`app/pages/system/order/index.vue:264-281`）。

「支付单已关闭/失败 → 订单自愈关闭」这一分支的意义是：支付窗口内渠道侧已经不可能再收款，订单不必等超时任务到点（`:808-812` 的注释）。

## 十一、删除保护、备注更新与数据权限

### 删除保护

只有 `CL` / `FL` 可以删除，其余状态抛 `module.system.order.deleteNotAllowed`（文案「只有已关闭或发起失败的订单可以删除（待支付订单请先关闭）」，`app/locales/zh.json:1896`）：

| 状态 | 能否删除 | 原因 |
| --- | --- | --- |
| `WP` | ❌ | 先关闭：否则会留下悬挂的冻结单与优惠码占用 |
| `OD` | ❌ | 收入凭证 |
| `CL` / `FL` | ✅ | 已释放全部资源 / 已回滚 |

实现是 `assertRemovable(ids)` 逐单校验（`modules/order/SysOrderService.ts:98-115`），`remove` 与 `batchRemove` 都调它；批量删除只对去重后的 id 校验一次（`:162-169`）。前端另有同口径的预过滤，把不满足条件的行先剔除再提示跳过了几单（`app/pages/system/order/index.vue:290-322`）。

### 备注更新

`update` **只写 `remark`**，其余字段一律忽略（金额与状态由业务动作驱动）：`repo.updateById(input.id, { remark: input.remark ?? null })`（`modules/order/SysOrderService.ts:148-153`）。注意它**没有状态校验**，也就是说 `OD` 的订单也能改备注；i18n 里存在一条 `module.system.order.creditedReadonly`（「已完成订单不可修改或删除」）但代码中没有任何抛出点。

### 数据权限

`sys_order` 有 `user_id`，走统一的 `buildScopedWhere`（`modules/order/SysOrderRepo.ts:48-65`，列表与详情都叠加，`:102-118`）。其余两张表的差别要分清楚：

| 表 | 数据范围行为 |
| --- | --- |
| `sys_order` | 有 `user_id`：部门范围不适用（没有 `dept_id`），「仅本人」范围按 `user_id` 过滤（`buildScope.ts:204-206`） |
| `sys_goods` | 没有 `user_id` / `dept_id`，但**有 `created_by`**：范围为 5/6（仅本人 / 部门及以下或本人）时回退到 `created_by` 过滤（`buildScope.ts:208-210`）；范围为 3/4（纯部门）时 `scopeConditions` 为空，由于表具备 `createdBy` 字段会命中 `denyAll()`（`1 = 0`，列表为空，`buildScope.ts:236-246`） |
| `sys_goods_level_price` | **完全不叠加数据权限**：它只经由领域层 mapper 访问（`domain/goods/repo/goodsLevelPriceRepo.ts`），不走 `CommonRepo` / `buildScopedWhere`。读取路径会先经 `sysGoodsRepo.getById()`（带数据权限）取商品，间接兜住；但 `saveLevelPrices` 直接调领域层 `findById` 校验「商品存在」后就整体替换，**不做数据范围校验**，只受权限码 `system:goods:edit` 约束（`modules/goods/SysGoodsService.ts:141-147`、`domain/goods/GoodsService.ts:127-139`） |

`sys_goods` 与 `sys_member_level`、`sys_pay_channel` 的口径一致——它们都是「模块层用 `CommonRepo`、没有 `user_id`/`dept_id`、只能靠 `created_by` 兜底」的表（`server/trade-router/modules/memberLevel/SysMemberLevelRepo.ts:7`、`modules/payChannel/SysPayChannelRepo.ts:7`）。

会员自助接口**不使用数据权限**，改用 Service 层的归属校验：`requireMyOrder(orderNo)` 取当前登录用户并比对 `order.userId`，不一致统一抛 `common.notExist`（`modules/order/SysOrderService.ts:83-96`）。
