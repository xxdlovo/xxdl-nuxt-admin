## 设计目标

系统里存在三种会失败的位置：tRPC 接口、`server/api/**` 原生 HTTP 端点、前端表单校验。它们遵守同一套约定：

- 服务端只抛国际化 key，不写死自然语言文案；
- 文案由服务端按请求语言翻译完成后返回，前端直接展示，不重复翻译；
- 所有来源的错误最终收敛为同一个结构 `TRPCFormattedError`，前端不需要为不同来源写不同分支。

## 三条错误通道

| 通道 | 抛出位置 | 处理机制 | 自动翻译 | 自动记日志 |
| --- | --- | --- | --- | --- |
| tRPC 接口 | `server/sys-router/**` 的 Service 与中间件 | `server/trpc/errorFormatter.ts` | 是 | 是（`loggerMiddleware`） |
| 原生 HTTP 端点 | `server/api/**` | 手写 `try/catch` + `createError` | 需调用 `createServerT(event)` | 需调用 `apiOperationLog` |
| 前端表单 | 弹窗组件中的 `UForm` | `useZodValidation` | 是（前端 `$ts`） | 否 |

三者的差异集中在「是否自动」：走 tRPC 的接口什么都不用做，走原生端点和前端表单则需要显式接入。

## 数据流

```text
Service / 中间件  throw new AppError('module.system.user.notFound')
        │
        ├─ tRPC 调用：errorFormatter 读取 error.cause 并分流
        │     ├─ AppError      → $t(i18nKey) 翻译文案，并按映射表改写 code / httpStatus（400 / 401 / 403 / 404）
        │     ├─ Zod 校验错误   → 汇总 issues 的字段级消息，去重后用「，」连接
        │     ├─ 数据库错误     → 分类文案（非生产环境附带驱动原因与 SQL）
        │     └─ 其它 Error     → 分类文案（非生产环境回显原文）
        │
        ▼
TRPCFormattedError { message, i18nKey, type, code, httpStatus, timestamp }
        │
        ▼
前端 app/plugins/01.client.ts 的 customLink
        → toast.clear() → toast.add({ title: type, description: message })
```

## 统一错误结构

结构定义在 `shared/types/common/TRPCFormattedError.ts`，由 `errorFormatter` 填充：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `message` | `string` | 已翻译的错误文案，前端直接展示 |
| `i18nKey` | `string?` | `AppError` 的原始 key，供前端识别并做分支处理 |
| `type` | `string?` | 错误分类（业务错误 / 校验错误 / 数据库错误 / 服务端错误），前端用作提示标题 |
| `code` | `string` | tRPC 错误码，如 `BAD_REQUEST`、`NOT_FOUND`、`UNAUTHORIZED` |
| `httpStatus` | `number?` | HTTP 状态码；业务错误按映射表为 400 / 401 / 403 / 404 |
| `stack` | `string?` | 堆栈，**默认不返回**；设置 `NUXT_TRPC_ERROR_STACK=true` 时才带上 |
| `path` | `string?` | tRPC 的 procedure 路径，如 `sysUser.page` |
| `timestamp` | `string?` | 错误产生时间（ISO 字符串），便于与 `sys_system_log` 对齐 |
