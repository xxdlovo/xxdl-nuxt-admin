| 场景 | 抛出位置 | i18nKey | 文案（中文） | tRPC code / HTTP | 前端表现 |

| 请求体不符合 Zod schema | tRPC `.input()` | `system.zodError` | 校验错误 | tRPC 自带 `BAD_REQUEST` / 400 | Toast 标题「校验错误」，描述为聚合后的字段消息 |
| 数据库异常 | Repo 层 | `system.dbError` | 数据库错误 | tRPC 默认（500） | 非生产环境展示驱动原因与 SQL，生产环境只显示「数据库错误」 |

| 其它业务失败 | 任意 Service | 各种业务 key | 见词条 | `BAD_REQUEST` / 400 | Toast：业务错误 / 对应文案 |
| 校验无可展示的字段错误 | `errorFormatter` 兜底 | `common.pleaseCheckValue` | 请检查输入的值是否合法 | 同 Zod 错误 | 同 Zod 错误 |

## 存储桶相关的 tRPC 错误

`SysStorageService` 是当前唯一直接抛 `TRPCError` 的服务，它与 `AppError` 的差异是**不会走 i18n 翻译**：

| 场景 | code | HTTP | message |
| --- | --- | --- | --- |
| key 含绝对路径、`..` 或空段 | `BAD_REQUEST` | 400 | `Invalid storage key` |
| 资源路径不在 `server/storage` 内 | `BAD_REQUEST` | 400 | `Resource path must be inside server/storage` |
| 访问不存在的 key | `NOT_FOUND` | 404 | `Storage key not found` |
| 读取的内容不是合法 JSON | `BAD_REQUEST` | 400 | `Storage value is not valid JSON` |

这些消息是固定的英文常量，前端会直接展示。如果需要中文提示，调用方应在此之前用 `AppError` 拦截。

## 关于 code 与 HTTP 状态的说明

`errorFormatter` 会把 `AppError` 按语义映射到 4xx，映射表在 `server/utils/appError.ts` 的 `resolveAppErrorStatus`：

| i18nKey | tRPC code | HTTP |
| --- | --- | --- |
| `auth.unauthorized` | `UNAUTHORIZED` | 401 |
| `auth.forbidden` | `FORBIDDEN` | 403 |
| `system.demoReadonly` | `FORBIDDEN` | 403 |
| `common.notExist` | `NOT_FOUND` | 404 |
| 其余 `AppError` | `BAD_REQUEST` | 400 |

这条映射同时被原生路由复用（`server/api/**` 里不再手写三元判断），避免两处规则漂移。

带来的行为：

1. 前端可以按 `code` / `httpStatus` 区分业务错误类型（400 / 401 / 403 / 404），需要精确分支时继续用 `i18nKey`；
2. 监控与网关可以按状态码区分「请求有问题」与「服务端异常」，而不是把所有业务失败都算成 5xx。

客户端的请求链路没有自动重试（`links: [customLink, httpLink]`），因此这里的状态码只影响前端分支与告警口径。

`SysStorageService` 直接抛 `TRPCError`（不经过 i18n），其 code 与 HTTP 由 tRPC 决定，行为见上一节。
