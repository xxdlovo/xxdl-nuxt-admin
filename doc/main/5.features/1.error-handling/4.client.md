## 全局错误提示来自 tRPC 错误 link

`app/plugins/01.client.ts` 里注册的 `customLink` 是全局错误提示的唯一实现：任何 tRPC 调用失败，都会先清空再弹出一条 Toast。

```ts
const customLink: TRPCLink<AppRouter> = () => {
  const toast = useToast()
  return ({ next, op }) => observable((observer) => {
    const unsubscribe = next(op).subscribe({
      error(err) {
        const typedErr = err as TypedTRPCError
        // 先清空历史提示，避免连续失败时叠满屏幕
        toast.clear()
        // 文案已由服务端按请求语言翻译完成，前端直接展示
        toast.add({
          title: typedErr.data?.type,
          description: typedErr.message || '发生未知错误',
          color: 'error'
        })
        observer.error(err)
      }
    })
    return unsubscribe
  })
}
```

要点：

- `title` 取 `data.type`（错误分类，如「校验错误」「业务错误」「服务端错误」），`description` 取已翻译的 `message`；
- **不要在业务代码里重复翻译错误文案**，服务端已经翻译过；
- `observer.error(err)` 仍然抛出，因此页面里 `await` 处的 `try/catch` 依然可用；
- 该 link 是链路上的第一个 link，后面直接接 `httpLink`（见下节）。

## Toast 工具

`app/utils/toast.ts` 提供四个语义化函数，参数顺序是 `(title, duration?, message?)`：

```ts
import { useToastSuccess, useToastError } from '~/utils/toast'

// 注意第二个参数是时长（毫秒），说明文字在第三个
useToastSuccess('保存成功')
useToastError('保存失败', undefined, '请检查网络后重试')
useToastSuccess('已提交', 3000)
```

`duration` 会写回 `appConfig.toaster.duration`；不传时使用 5000 毫秒。

## 表单校验：useZodValidation

弹窗组件里的 `UForm` 校验由 `app/composables/useZodValidation.ts` 接管，它把 Zod 的 issue 转成 UForm 需要的 `{ name, message }` 数组，并对含 `.` 的消息做 `$ts` 翻译：

```ts
const { schema, validate, validateField, parse } = useZodValidation({
  schema: SysUserAddSchema
})

// 表单级：交给 UForm 的 validate
const errors = await validate(state)

// 字段级：实时校验单个字段
const message = await validateField('username', 'test')
```

约定：

- Zod schema 里的消息直接写 i18n key（如 `form.userName.required`），不要在 schema 里写中文；
- `translate: false` 可关闭翻译，仅当消息本身就是给用户看的自然语言时才使用；
- `validateField` 依赖 Zod 内部结构读取字段 schema，未取到字段时返回 `null` 并打印警告，不抛错。

## 请求链路：不重试、不合并

`01.client.ts` 的链路是 `[customLink, httpLink]`，两个刻意的选择：

1. **没有 `retryLink`**：请求失败不会自动重试，`customLink` 立即给出提示。需要重试的场景（例如用户手动点「刷新」）由交互层显式发起，避免用户看不到失败、又被延迟的自动重试掩盖。
2. **用 `httpLink` 而不是 `httpBatchLink`**：一次调用一个请求，不做批量合并。代价是同一时刻的多个调用会产生多个 HTTP 请求；收益是每个请求的错误与耗时独立、网络面板可直接定位。

业务错误仍然在服务端被映射为 4xx（400 / 401 / 403 / 404，见[错误码与 i18n key 对照](/docs/main/features/error-handling/error-table)），因此前端可以按 `code` 分支，监控也能把「请求有问题」和「服务端异常」分开统计。

`SysStorageService` 这类直接抛 `TRPCError({ code: 'BAD_REQUEST' })` 的实现其 `message` 不经过 i18n 翻译，需要多语言时仍应使用 `AppError`。

## 按 i18nKey 做分支处理

前端需要针对特定错误改变行为时（例如提示重新登录、或弹确认框而不是 Toast），用 `data.i18nKey` 判断，不要匹配翻译后的文案：

```ts
try {
  await $trpc.sysUser.resetPwd.mutate(payload)
} catch (error) {
  const i18nKey = (error as TypedTRPCError).data?.i18nKey
  if (i18nKey === 'auth.unauthorized') {
    // 自行处理：跳转登录等
  }
}
```
