## 什么时候需要原生端点

tRPC 适合结构化的请求响应。以下场景需要改用 `server/api/**` 的 `defineEventHandler`：

- 文件上传，需要读取 `multipart/form-data`；
- 需要流式响应或直接写二进制内容；
- 需要由第三方回调的固定 URL。

原生端点**不会**自动获得 tRPC 的中间件能力，鉴权、翻译、日志、错误归一都必须自己接。

## 标准模板

`server/api/system/oss/upload.post.ts` 是最完整的示例（含权限码校验与完整状态码映射），可直接照抄结构；`server/api/system/user/avatar.post.ts` 是同一模板的精简版本（只判断登录态，状态码映射为 401 / 400 / 500）：

```ts
import { createContext } from '#server/trpc/context'
import { sysOssService } from '#server/sys-router/oss/SysOssService'
import { apiOperationLog } from '#server/utils/apiOperationLog'
import { AppError } from '#server/utils/appError'
import { createServerT } from '#server/utils/serverI18n'

export default defineEventHandler(async (event) => {
  const t = createServerT(event)
  const start = Date.now()
  const ctx = await createContext(event)
  const operationLog = apiOperationLog(ctx, 'sysOss.upload', start)
  let requestParams: Record<string, unknown> = {}

  try {
    // 1. 鉴权与权限：tRPC 中间件在这里不生效，必须显式校验
    // 2. 业务处理：调用 Service，Service 内部照常 throw AppError
    requestParams = { /* 用于日志的入参摘要，禁止放文件内容或密码 */ }

    await operationLog.success({ action: 'upload file', requestParams, requestResult: data })

    return { success: true, data }
  } catch (error) {
    await operationLog.failure(error, { action: 'upload file', requestParams })

    const statusCode = error instanceof AppError
      ? error.i18nKey === 'auth.unauthorized' ? 401
        : error.i18nKey === 'auth.forbidden' ? 403
          : 400
      : 500
    const message = error instanceof AppError
      ? t(error.i18nKey)
      : error instanceof Error ? error.message : t('module.system.oss.uploadFailed')

    throw createError({ statusCode, statusMessage: message, message })
  }
})
```

## 四个必须显式接入的点

| 能力 | 用到的工具 | 不接入的后果 |
| --- | --- | --- |
| 登录与权限 | `createContext(event)` + `ctx.user` / 权限码判断 | 接口可被匿名调用 |
| 文案翻译 | `createServerT(event)` | 只能返回中文或英文硬编码 |
| 操作日志 | `apiOperationLog(ctx, module, start)` | `sys_system_log` 缺少该操作记录 |
| 错误归一 | `createError({ statusCode, statusMessage, message })` | 前端拿到 500 与无法识别的响应体 |

## 鉴权写法参考

```ts
const user = ctx.user
if (!user) {
  throw new AppError('auth.unauthorized')
}
if (user.isAdmin !== 1) {
  const permissionCodes = await authService(ctx).listPermissionCodes(user)
  if (!permissionCodes.includes(crudPermissionCodes('system:oss').add)) {
    throw new AppError('auth.forbidden')
  }
}
```

权限码用 `shared/auth` 的 `crudPermissionCodes(resource)` 生成，与 tRPC 侧保持同一套编码，避免两处字符串不一致。

## apiOperationLog 的用法

```ts
const operationLog = apiOperationLog(ctx, 'sysOss.upload', Date.now())

// 成功
await operationLog.success({ action: 'upload file', requestParams, requestResult })

// 失败：error 会被记录为失败原因
await operationLog.failure(error, { action: 'upload file', requestParams })
```

`module` 建议用「路由命名空间 + 动作」的写法（如 `sysOss.upload`），方便在系统日志页按模块筛选。

## 状态码映射约定

| 情况 | 状态码 |
| --- | --- |
| 未登录（`auth.unauthorized`） | 401 |
| 已登录无权限（`auth.forbidden`） | 403 |
| 其它 `AppError`（参数缺失、配置不可用等） | 400 |
| 非 `AppError` 的意外异常 | 500 |

## 与 tRPC 链路的差异提醒

原生端点返回的是 `createError` 构造的 Nitro 错误，**不会**经过 `errorFormatter`，因此响应体结构与 `TRPCFormattedError` 不同。前端调用原生端点时不能复用 tRPC 的错误分支逻辑，需要按 `fetch` / `xhr` 的状态码与响应体自行处理（参考 `/docs/main/features/files/upload-api`）。
