## AppError：只抛 i18n key

`server/utils/appError.ts` 定义了唯一的业务错误类。它接收国际化 key，文案由 `errorFormatter` 在响应阶段翻译：

```ts
import { AppError } from '#server/utils/appError'

// 客户端最终收到「查询数据不存在」
throw new AppError('common.notExist')

// 可选：附带自定义 message 与 cause（保留原始异常链，便于排查）
throw new AppError('module.system.oss.uploadFailed', {
  message: 'provider timeout',
  cause: error
})
```

约定：

- key 必须真实存在于 `app/locales/zh.json` 与 `app/locales/en.json`，否则 `$t()` 会原样返回 key，用户会看到类似 `common.xxx` 的字符串；
- 不要用 `new Error('用户不存在')` 承载业务错误，那会丢失翻译能力，只用于真正的程序异常；
- Service 层负责业务判断并抛 `AppError`，中间件层负责鉴权类错误。

## errorFormatter 的四条分流

`server/trpc/errorFormatter.ts` 按 `error.cause` 的类型依次判断：

| cause 类型 | `type` 字段（前端 Toast 标题） | `message` 来源 | 附加行为 |
| --- | --- | --- | --- |
| `AppError` | `$t('system.businessError')` | `$t(i18nKey)`，key 缺失时回退分类文案 | 回填 `i18nKey`；按 `resolveAppErrorStatus` 改写 `code` / `httpStatus`（400 / 401 / 403 / 404） |
| Zod 校验错误 | `$t('system.zodError')` | 汇总 `issues`（或 `flatten()`）中的字段消息，去重后用「，」连接 | 拿不到明细时退化为 `common.pleaseCheckValue`，绝不返回 ZodError 的原始 JSON |
| 数据库错误 | `$t('system.dbError')` | 非生产环境：驱动 `sqlMessage` + `sql`；生产环境：分类文案 | 通过 `cause.code` / `cause.sql` / `cause.constraint` 识别 |
| 其它 `Error` | `$t('system.serverError')` | 非生产环境：异常原文；生产环境：分类文案 | — |

两个要点：

- **`type` 是分类、`message` 是描述**。前端的 `customLink` 把 `type` 当 Toast 标题、`message` 当描述（见 `app/plugins/01.client.ts`），因此两者不能填同一段文案。
- **内部信息默认不外泄**。数据库错误可能带 SQL、表名与字段名，程序异常可能带实现细节，因此只在 `NODE_ENV !== 'production'` 时返回原文。

此外还有一次兜底翻译：当 `message` 含有 `.` 且不含「，」时，会尝试把它当作 i18n key 再翻译一次，翻译结果与原文不同才替换。

## 堆栈、抛出位置与 requestId

`AppError` 在构造时自动完成三件事，业务代码不需要额外调用：

1. **还原堆栈**——堆栈若指向打包产物（dev 的 `.nuxt/dev/index.mjs`、生产的 `.output/server/chunks/**`），用产物同目录的 `.map` 同步还原为源码位置；正常情况下 `server/plugins/source-maps.ts` 开启的 Node source map 支持已经让堆栈直接指向 `.ts`。
2. **提取抛出位置**——把第一个业务帧写入 `error.location`，形如 `server/demo-router/DemoService.ts:50`（相对项目根目录、统一使用正斜杠）。
3. **记录 requestId**——从 Nitro 请求上下文读取 evlog 宽事件的 `requestId` 写入 `error.requestId`；同一个值也会作为 `sys_system_log` / `sys_login_log` 的 `traceId`（见 `server/utils/requestId.ts`），因此两类日志能对齐同一次请求。

```ts
const error = new AppError('common.notExist')

console.log(error.location)  // server/demo-router/DemoService.ts:50
console.log(error.requestId) // 6f1c2b7e-...（与 .data/evlogs 里同一次请求的 requestId 相同）

// 需要时随日志一起记录（evlog 的 error 字段本身已包含还原后的堆栈）
log.error(error, { demo: { action: 'getById', at: error.location } })
```

- `node_modules` 与 `node:` 内部帧不会被当作业务位置；`.map` 按文件缓存，重复构造不会重复读盘；
- 两者都不可用（例如部署时裁剪了 `.map` 且未开启 source map）时 `location` 为 `undefined`，堆栈保持原样，不影响业务流程；
- 非请求上下文（定时任务、直接运行的脚本）取不到请求上下文，此时 `requestId` 为 `undefined`；
- `errorFormatter` 只读取 `i18nKey`，新增字段不改变响应结构与状态码映射。

## 响应里的堆栈

响应体默认**不包含** `stack`。需要排查时设置环境变量：

```bash
NUXT_TRPC_ERROR_STACK=true
```

失败请求本来就会被 `loggerMiddleware` 连堆栈一起写入 `sys_system_log`（写操作），因此关闭响应堆栈不会丢排查线索。响应里的 `data.timestamp` 可用于与该日志对齐时间。

## 语言判定顺序

`errorFormatter` 从请求中解析语言，优先级从高到低：

1. `x-locale` 请求头；
2. `i18n_locale` Cookie；
3. `accept-language` 请求头；
4. 默认 `en`。

前端 tRPC 客户端在每次请求都会带上 `x-locale`（取自 `i18n_locale` Cookie），因此正常链路里第 1 条即命中。

## 中间件内置错误

| 中间件 | 触发条件 | 抛出 |
| --- | --- | --- |
| `authMiddleware` | 没有有效 session | `AppError('auth.unauthorized')` |
| `permissionMiddleware` | 已登录但缺少权限码，且不是管理员 | `AppError('auth.forbidden')` |
| `demoReadonlyMiddleware` | demo 模式下调用被标记为只读的变更接口 | `AppError('system.demoReadonly')` |
| `SysJobRunner` | `handler_code` 在处理器表中不存在 | `AppError('module.system.job.handlerMissing')` |

## 与日志的关系

`loggerMiddleware` 在 `mutation` 上默认记录操作日志，`query` 默认不记录。需要覆盖时通过 `proc({ log: true / false })` 声明；写操作抛错时会以失败状态写入 `sys_system_log`，不需要在 Service 里额外记**审计日志**。

Service 里另外要写的是 **evlog 运行日志**（每个方法一行 `log.info`，只记动作与标识）：两者用途不同，审计日志入库供后台查询，运行日志落 `.data/evlogs` 供排查，约定见[新建模块 · Step 7.1](/docs/main/new-module/backend-steps)与[运行时日志](/docs/main/backend-handbook/runtime-logs)。
