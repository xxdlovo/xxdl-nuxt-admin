## 三条铁律

1. **只在当前 Node.js 进程内有效**。服务重启、进程退出、部署到多实例时，缓存清空或互不共享。
2. **只用于提升读取性能**。不能作为数据库、登录会话、密码或其他必须持久化数据的唯一来源。
3. **只接受 JSON 可序列化值**。不要放数据库连接、请求对象、文件句柄、类实例或含循环引用的对象。

违反任意一条都可能造成「本地正常、线上偶发异常」这类难以复现的问题。

## 技术底座

缓存统一使用 Nitro 的命名存储 `memory`：

```ts
useStorage('memory')
```

`nuxt.config.ts` 中显式声明了该 driver，目的是与 Nitro 内部的 `data`、`cache`、`root`、`build` 等 key 空间隔离：

```ts
nitro: {
  storage: {
    // 业务临时数据使用独立的 memory 命名空间
    memory: { driver: 'memory' }
  }
}
```

## 过期由自己判断，而非依赖 driver

写入的值会被包装成 envelope：

```ts
{
  value: /* JSON 可序列化的业务值 */,
  expiresAt: 1730000000000
}
```

读取时由 `SysStorageService` 比较 `expiresAt` 与当前时间：

- 已过期 → 删除该 key 并返回 `null`（等价于 miss）；
- 未过期 → 返回 `envelope.value`；
- `envelope` 结构不符（缺 `expiresAt` 或不是对象）→ 直接返回 `null`。

这样做的收益是：过期语义不依赖具体 storage driver 是否实现 TTL，换 driver 时行为不变。

## 故障降级

缓存读写异常一律按 miss 处理：

| 情况 | 行为 |
| --- | --- |
| 读取抛错 | 返回 `null`，业务继续走 loader 回源 |
| 写入抛错 | 静默忽略，不影响数据库写入与主流程 |
| 删除抛错 | 静默忽略，由 TTL 兜底 |

**缓存故障不会阻断主流程**，这也是「缓存不能作为唯一数据来源」的另一层含义。

## 何时该用 / 不该用

| 适合 | 不适合 |
| --- | --- |
| 读多写少的字典数据、权限数据 | 会话与登录态（用 `nuxt-auth-utils`） |
| 短时间内的重复查询结果 | 业务唯一数据（放数据库） |
| 可承受短暂不一致的计算结果 | 需要跨实例强一致的计数、锁 |
| 页面会话内的临时数据 | 需要持久化或可审计的数据 |

## 现有的两类缓存

| 门面 | 缓存内容 | 默认 TTL |
| --- | --- | --- |
| `DictCacheService` | `sysDictData.listByTypeCode` 的结果 | 30 分钟 |
| `RbacCacheService` | 用户角色、角色菜单、管理员菜单三层 | 15 分钟 |

业务代码应优先使用这两个门面；只有通用业务缓存才直接使用 `SysStorageService`。

## 调用层次

```text
业务 Service
   ├─ DictCacheService / RbacCacheService     ← 首选：key 与 TTL 已封装
   └─ SysStorageService                        ← 通用缓存、存储桶管理
          └─ useStorage('memory')               ← 框架层，业务不直接调用
```
