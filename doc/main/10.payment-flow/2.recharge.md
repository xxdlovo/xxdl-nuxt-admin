title: 充值流程
description: 会员自助与后台补录两条发起路径、校验与锁券、落充值单、回调到账、关闭时的未支付确认，以及超时后的自助同步与补偿。

充值流程是三条链路里唯一「钱从渠道进来变成余额」的那条：发起时落一张充值单并调支付模块下单，到账时由 `RechargeService.credit()` 写余额流水。全部分支集中在 `server/trade-router/domain/wallet/RechargeService.ts`。

## 一、链路与状态机

```text
sysMember.myRecharge                     SysMemberRechargeService.create（后台补录）
  │  userId 取会话，operatorId = 用户 id     │  只落库，不发起支付；status='OD' 时落 WP 再走 credit
  ▼                                        ▼
        RechargeService.create
  1  payChannelRepo.findEnabled({})          启用渠道（status=1），无 → payChannel.notConfigured
  2  channel.verifyStatus === 1              否 → payChannel.notVerified
  3  members.resolveCoupon(scene='recharge') 券校验（不存在/停用/过期/场景不符/超限/未达门槛 → 各自错误码）
  4  outTradeNo = buildOutTradeNo('RCH')     id = randomUuid()   expireAt = now + 30 分钟
  5  rechargeRepo.insert  →  sys_member_recharge  status='WP'
  6  members.lockCoupon(bizNo=outTradeNo)    写 sys_member_coupon_use('locked')
  7  payOrderService.createPayment(bizType='recharge', outTradeNo, amount=payAmount)
       ├─ 成功 → rechargeRepo.attachPayOrder(payOrderId, payChannelCode) → 返回二维码 / 链接
       └─ 失败 → rechargeRepo.markFailed('FL', fail_reason) + releaseCoupon → createFailed
  ▼
等待支付（页面每 5 秒 myRechargeSync 一次，最多 10 分钟）
  ├─ 回调 / 同步：支付单 'OD'  → RechargeService.credit  → 充值单 'OD'
  └─ 支付单 'CL' / 'FL'        → 反向关闭充值单 'CL'（fail_reason 写关闭原因）

状态机：WP ──credit──▶ OD（终态）
        WP ──close───▶ CL（人工关闭）
        WP ──发起支付失败──▶ FL
        CL / FL ──迟到的支付回调──▶ OD（仍会到账，见第八节）
```

| 代码位置 | 内容 |
| --- | --- |
| `RechargeService.ts:70-177` | `create()`：七步见上图 |
| `RechargeService.ts:183-240` | `credit()`：唯一的到账入口 |
| `RechargeService.ts:243-304` | `close()`：关闭（含未支付确认） |
| `RechargeService.ts:310-332` | `retryPending()`：未到账补偿 |
| `RechargeService.ts:357-368` | `rechargeService(db)` 的写方法各自包一层事务；`rechargeServiceIn(tx)` 供已在事务中的调用方复用 |

## 二、第一步：渠道校验

```ts
// RechargeService.ts:74-83
const channel = await channels.findEnabled({})
if (!channel) throw new AppError('module.system.payChannel.notConfigured')
if (channel.verifyStatus !== 1) {
  throw new AppError('module.system.payChannel.notVerified', { message: channel.configName })
}
```

两点要记住：

- `findEnabled({})` 不传 `channelCode` / `currency`，只按 `status = 1` 过滤，排序是「默认优先 → `sort_order` 升序 → 创建时间升序」（`payChannelRepo.ts:47-72`）。所以**会员充值时用的是「库里那条默认启用渠道」**，页面上没有渠道可选。
- **充值侧不会退到环境变量兜底渠道。** 后续 `createPayment` 显式传了 `channelId`（`RechargeService.ts:133`），而显式 `channelId` 查不到时解析器不会回退到 `NUXT_PAY_APP_ID` / `NUXT_PAY_APP_SECRET`（见[支付模块总览](/docs/main/payment/overview)第六节）。换句话说，只配了环境变量、库里没有启用渠道时，充值会直接报 `notConfigured`。

`verifyStatus !== 1` 的报错文案里带渠道名，是为了让管理员知道该去「测试配置」哪一条（判定逻辑见[渠道配置](/docs/main/payment/channels)）。

## 三、第二步：解析并锁定优惠码

充值场景的券用 `scene = 'recharge'`：

```ts
// RechargeService.ts:85-94
const coupon = await members.resolveCoupon({
  code: input.couponCode ?? null,
  userId: input.userId,
  scene: 'recharge',
  amount                          // 用充值「面额」判门槛与抵扣
})
const payAmount = coupon ? coupon.payableAmount : amount
const giftAmount = coupon ? coupon.giftAmount : '0.00'
const discountAmount = coupon ? coupon.discountAmount : '0.00'
```

`resolveCoupon`（`MemberService.ts:321-409`）**只校验不核销**，校验顺序是：券存在 → 未作废（`status=2`）→ 启用（`status=1`）→ 生效时间 → 场景匹配（`all` 通吃）→ 总量（`max_use`）→ 门槛（`min_amount`）→ 每人限次（已核销 + 已锁定，`MemberService.ts:380-389`）→ 抵扣后应付必须 `> 0`（`couponNotApplicable`，`MemberService.ts:395-397`）。折扣算法：`amount` 类型抵扣封顶到面额，`rate` 类型 `value` 是应付比例（`0.90` = 九折，`MemberService.ts:411-424`）。

`payAmount` 是**实付**（已扣券），传给支付模块的是这个数；`giftAmount` 是券附带的赠送金，到账时随充值金一起入账。

落单之后立刻锁券（`RechargeService.ts:119-129`）：

| 动作 | 落点 | 幂等 |
| --- | --- | --- |
| 写使用记录 `status='locked'`，绑定 `biz_no = outTradeNo` | `sys_member_coupon_use`，唯一键 `uk_member_coupon_use(coupon_id, biz_no)` | 已存在 → `locked: true, reused: true`（`MemberService.ts:429-433`） |
| 累计核销数 | `coupons.incrementUsedCount` | 返回 0 行 → 抛 `couponUsedUp`（`MemberService.ts:457-461`） |
| 核销（到账时） | `markUsed(bizNo)`，带 `where status='locked'` | 只在「锁定中」生效一次 |
| 释放（关闭 / 发起失败） | `markReleased(bizNo)`，同样带 `where status='locked'` | 幂等；已核销的券不会被反向改回 |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**锁券在 `try` 之外。**`RechargeService.ts:119-129` 的 `lockCoupon` 位于 `:131` 的 `try` 之前，因此 `incrementUsedCount` 返回 0（并发抢最后一张券）或写使用记录失败时，充值单**已经落库为 `WP` 且没有支付单**，也不会走 `markFailed`。这一单会卡在「待支付但没有二维码」：会员页轮询 `myRechargeSync` 时因 `!row.payOrderId` 直接回报 `WP`（`SysMemberService.ts:334-342`），页面会一直轮询到 10 分钟超时；只能由后台「关闭」收尾（`close` 在 `payOrderId` 为空时跳过支付单检查）。
::

## 四、第三步：落充值单

`RechargeService.ts:95-116`：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `out_trade_no` | `buildOutTradeNo('RCH')` | 前缀 `RCH` + `yyyyMMddHHmmss` + 6 位随机码；**它同时是支付单的商户订单号** |
| `id` | `randomUuid()` | 业务主键，只用于排障（`attach = recharge:{id}`） |
| `amount` | 归一后的充值面额 | `normalizeMoney()`：内部换算成「分」做整数运算（`wallet/utils.ts:15-38`） |
| `gift_amount` / `discount_amount` / `pay_amount` | 券解析结果 | `pay_amount` 是实际下单金额 |
| `coupon_id` / `coupon_code` | 有券才写 | 到账时据此核销 |
| `status` | `'WP'` | |
| `pay_channel_code` | 渠道类型快照 | 随后 `attachPayOrder` 会用支付单的 `channelCode` 覆盖一次 |
| `expire_at` | `now + 30 分钟`（硬编码） | **与渠道的 `order_timeout_minutes` 无关**（`RechargeService.ts:97`） |

`expire_at` 目前**没有任何消费者**：`rechargeRepo` 没有 `listExpiredPending`，任务里也没有 `recharge:expire-close`。充值单不会自动过期，只会一直停在 `WP`（详见第七节）。

## 五、第四步：调支付模块下单

```ts
// RechargeService.ts:132-141
const order = await payments.createPayment({
  channelId: channel.id,
  outTradeNo,                       // 与充值单号严格一致
  amount: payAmount,                // 实付
  subject: `会员充值 ${amount} 元`,  // 标题用面额
  bizType: 'recharge',              // 分派的唯一依据
  notifyUrl: input.notifyUrl ?? null,
  attach: `recharge:${rechargeId}`,
  origin: input.origin ?? null
}, { operatorId })
```

`origin` 由 tRPC 层用 `getRequestURL(ctx.event).origin` 传入（`SysMemberService.ts:281`），用于渠道没配 `notify_url` 时推导回调地址。下单失败时支付模块**仍然会落一条 `FL` 支付单**（见[下单、查询与状态流转](/docs/main/payment/orders)第三节第 7 步），可以用 `out_trade_no` 在支付记录页对照 `fail_reason` 与 `provider_data`。

成功后回填（`RechargeService.ts:143-148`）：

| 回填字段 | 来源 | 为什么 |
| --- | --- | --- |
| `pay_order_id` | 支付单 id | 会员自助同步（`myRechargeSync`）与关闭时的「未支付确认」都靠它定位支付单 |
| `pay_channel_code` | 支付单的 `channel_code` | 用真实下单渠道覆盖发起时的快照 |

返回给页面的 `status` 取的是**支付单状态**（`order.status`，`RechargeService.ts:154`），而 `expire_at` 优先取支付单的 `expire_at`（`:164`）——所以储值页展示的到期时间来自渠道配置（默认 30 分钟），与数据库里充值单的 `expire_at` 可能不是同一个值。

## 六、发起失败的收尾

```ts
// RechargeService.ts:166-176
} catch (error) {
  const message = error instanceof Error ? error.message : '发起支付失败'
  await repo.markFailed({ id: rechargeId, reason: message, operatorId })
  // 发起失败要释放占用的券，避免用户次数被白扣
  if (coupon) await members.releaseCoupon({ bizNo: outTradeNo, operatorId })
  throw new AppError('module.system.memberRecharge.createFailed', { message, cause: error })
}
```

`markFailed` 带 `where status='WP'`（`rechargeRepo.ts:107-117`），写入 `status='FL'` 与 `fail_reason`。因为 `catch` 覆盖了 `createPayment` **和** `attachPayOrder` 两步，存在一个需要注意的窗口：

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**若 `createPayment` 已成功、`attachPayOrder` 失败（数据库瞬时故障），充值单会被置为 `FL` 并释放券，而支付单已经真实落库且仍是 `WP`。**此时会员看到的报错是「发起支付失败」，但渠道侧可能已经生成了可支付的二维码。这类单的特征是：`sys_member_recharge.status='FL'` 且 `pay_order_id IS NULL`，同时存在同号 `sys_pay_order`。

它**不会**被补偿任务捞到——补偿的扫描条件是「充值单 `WP` 且支付单 `OD`」（`rechargeRepo.ts:122-142`），而这单的充值单是 `FL`、支付单是 `WP`。两条恢复路径：

1. **用户真的扫码付了**：回调先把支付单置为 `OD`，再走 `credit`。`credit` 的守卫只是 `status <> 'OD'`，因此 `FL` 单同样会被补成 `OD` 并正常入账——这一条是自愈的。
2. **渠道已收款但回调一直没到**：先把支付单同步成 `OD`（支付记录页「同步状态」），但**此时仍然没有入口把这张 `FL` 充值单置为已到账**（`rechargeRetry` 只扫 `WP` 充值单，也没有「按单号手工入账」的接口）。可行的人工操作是：后台补录一张等额、状态为「已到账」的充值单（会生成新的 `out_trade_no`），在备注里写明原单号，并把原 `FL` 单与原支付单都收尾，避免同一笔钱被记两次。
::

## 七、到账：唯一的入账入口

```ts
// RechargeService.ts:183-240
async function credit(outTradeNo: string, operatorId: string | null = null)
```

调用方只有两个：支付回调的 `dispatchPaidOrder`（`PaidHandlers.ts:31`）与未到账补偿 `retryPending` / `rechargeRetry` / `member:reconcile`。**页面上的 `myRechargeSync` 与后台补录也走它。**

三重幂等（对应[支付流程总览](/docs/main/payment-flow/overview)第五节）：

| 保证 | 落点 |
| --- | --- |
| 充值单唯一键 | `uk_member_recharge_out`（`memberRecharge.ts:31`） |
| 条件更新抢锁 | `rechargeRepo.markCredited` 的 `where status <> 'OD'`（`rechargeRepo.ts:47-72`），返回 0 行即「并发下已被别人到账」 |
| 余额流水唯一键 | `uk_member_log_dedup`，键为 `recharge:{outTradeNo}:recharge` 与 `recharge:{outTradeNo}:gift:gift` |

执行顺序：

| # | 动作 | 代码 |
| --- | --- | --- |
| 1 | 按 `out_trade_no` 找充值单，找不到抛 `module.system.memberRecharge.notFound` | `:184-188` |
| 2 | 已是 `OD` → 直接返回 `{ credited: false, reused: true }` | `:190-192` |
| 3 | `markCredited`：置 `OD`、写 `paid_at`（沿用已有值）、`credited_at`、`fail_reason = null`；影响 0 行 → `reused: true` | `:194-207` |
| 4 | **充值金**入账：`account='recharge'`、`bizType='recharge'`、`bizNo=outTradeNo`、`reason='充值到账'` | `:210-218` |
| 5 | **赠送金**入账（金额 > 0 时）：`bizNo = {outTradeNo}:gift`（独立幂等键）、`giftSource='campaign'`；`WalletService.credit` 会先建一条 `sys_member_gift_grant` 批次 | `:221-232`、`WalletService.ts:351-375` |
| 6 | 核销优惠码：`markCouponUsed(bizNo=outTradeNo)` | `:235-237` |

`WalletService.credit` 的入账顺序是「赠送金批次先建 → 钱包余额 + → 写流水」（`WalletService.ts:349-402`），这样「赠送金余额 = 有效批次剩余之和」在任意时刻都成立（见[账实一致与补偿](/docs/main/payment-flow/consistency)）。

**到账事务与「支付单置为已支付」不在同一个事务**：`dispatchPaidOrder(order, db)` 收到的是连接（`AppDb`），而 `rechargeService(db).credit()` 自己开一个事务（`RechargeService.ts:364`）。业务写入失败不会回滚支付单——这正是「支付单 `OD` 但充值单未完成」这种补偿场景的来源（[业务接入：bizType 分派](/docs/main/payment/integration)第三节）。

## 八、关闭：先确认未支付

后台关闭走 `sysMemberRecharge.close`（权限 `system:memberRecharge:close`）→ `RechargeService.close`：

```text
close({ rechargeId | outTradeNo, reason, operatorId })
  1  row 不存在                → module.system.memberRecharge.notFound
  2  row.status === 'CL'       → { closed: false, reused: true }      幂等
  3  row.status !== 'WP'       → module.system.memberRecharge.notClosable
  4  未支付确认（仅当 payOrderId 存在）
       4.1 读本地支付单
       4.2 本地仍是 'WP' → 再向渠道 queryPayment 一次
             查询抛错（渠道不可达 / 配额）→ 按本地状态继续，不阻断人工关闭
       4.3 结论是 'OD' → module.system.memberRecharge.paidCannotClose，**不改本地状态**
  5  rechargeRepo.markClosed（where status='WP'）→ status='CL'，关闭原因写入 fail_reason
       影响 0 行 → { closed: false, reused: true }
  6  payments.closePayment(payOrderId)，失败静默（可能已支付 / 已关闭）
  7  members.releaseCoupon(bizNo)
```

三点语义：

- **「先确认未支付」是为了不让「钱在渠道、账在本地」对不上。**判定顺序是「本地支付单 → （本地仍 `WP` 时）再问一次渠道」（`RechargeService.ts:267-283`）。管理员点关闭是一次人工操作，多发一次查询可以接受。
- **渠道不可达时按本地状态判断。**`queryPayment` 抛错被 `catch` 吞掉并回退到本地状态（`:275-277`），因此本地 `WP` 的单在渠道不可达时**仍可被关闭**。如果这单其实已在渠道支付、只是回调还没到，就会出现「本地 `CL` + 稍后支付单被回调置为 `OD`」——此时充值侧是安全的：`credit` 的条件是 `status <> 'OD'`，`CL` 单会被补成 `OD` 并正常入账（见下）。
- **只关本地支付单。**`closePayment` 是纯本地状态变更（虎皮椒等平台没有取消接口，见[下单、查询与状态流转](/docs/main/payment/orders)第五节末），所以关掉充值单并不能阻止用户继续扫码付款。

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**充值侧对「迟到的支付」是自愈的，这一点和订单侧相反。**

`RechargeService.credit` 的守卫是 `status <> 'OD'`（而不是「必须 `WP`」），所以已被关闭（`CL`）、甚至发起失败（`FL`）的充值单，只要渠道的钱真的到了，回调依然会把它置为 `OD` 并入账。对比订单侧：订单被超时关成 `CL` 后，`markPaidTx` 会抛 `module.system.order.notPayable`，回调持续 5xx（[业务接入：bizType 分派](/docs/main/payment/integration)第七节的残留风险）。**充值多收一笔钱不会丢账，订单多收一笔钱会卡住。**
::

关闭后页面如何感知：`myRechargeSync` 返回的 `status` 一律是**本地充值单状态**（`SysMemberService.ts:311-313`），并带回 `failReason`，因此后台一关，会员页下一次轮询就能拿到 `CL`、停止展示二维码并提示原因。

## 九、超时了怎么办

充值单没有自动过期，所以「用户扫了码但没付、或付了但回调没到」都靠下面三条路径收尾：

| 手段 | 入口 | 权限 / 调度 | 扫描条件 | 动作 |
| --- | --- | --- | --- | --- |
| 会员自助同步 | `sysMember.myRechargeSync` | 登录即可（`protectedProcedure`） | 本地 `WP` 且 `pay_order_id` 非空 | 向渠道 `queryPayment` 一次：支付单 `OD` → `credit`；支付单 `CL` / `FL` → **反向关闭充值单**（原因写 `fail_reason`）；仍未支付 → 回报本地 `WP` |
| 未到账补偿（人工） | `sysMemberBalanceLog.rechargeRetry` | `system:memberBalanceLog:reconcile`（`modules/memberBalanceLog/index.ts:16,57`） | 充值单 `status='WP'` **且** 支付单 `status='OD'`（`rechargeRepo.ts:122-142`），单次 **50** 条 | 逐单调 `credit`，返回每笔结果 |
| 每日对账任务 | `member:reconcile` | 每天 03:00（`0 0 3 * * *`，`doc/main/mysql-ddl-member-balance.sql:343`） | 同上，单次 **200** 条；同时跑全量钱包一致性校验 | `walletService.assertConsistency()` + `rechargeService.retryPending()`（`handlers.ts:130-152`） |

`myRechargeSync` 的分支（`SysMemberService.ts:315-390`）：

```text
row.status !== 'WP'            → 直接回报本地状态（已到账 / 已关闭 / 已失败），不再看渠道
!row.payOrderId                → 回报本地 'WP'（页面继续轮询；这就是第三节那个卡住的场景）
queryPayment                   → 渠道支付单状态
  ├─ 'OD'                      → credit(row.outTradeNo, user.id) → status 'OD'
  ├─ 'CL' / 'FL'               → rechargeOrders.close(reason='支付单已关闭/失败') → 回报本地状态 + failReason
  └─ 其它                      → 回报本地 'WP'，页面继续轮询
```

`queryPayment` 内部有 **3 秒节流**（[下单、查询与状态流转](/docs/main/payment/orders)第五节），而页面轮询间隔是 **5 秒**，所以每次轮询都会真的查一次渠道。

页面的轮询参数（`app/pages/system/wallet/index.vue:415-419`）：间隔 `5000ms`、总超时 `10 * 60 * 1000`、连续失败 3 次即停止并提示。注意 **10 分钟的页面超时 < 渠道 30 分钟的支付窗口**：超时后页面只是不再自动同步，充值单与支付单都还在等待，用户重新进入页面并点「同步状态」仍能补到账。

## 十、后台补录

`SysMemberRechargeService.create`（权限 `system:memberRecharge:add`）是**另一条独立的发起路径**，它不发起支付、不碰渠道：

| 行为 | 实现 | 说明 |
| --- | --- | --- |
| 单号 | `data.outTradeNo ?? buildOutTradeNo('PAY')`（`SysMemberRechargeService.ts:57`） | **补录单是 `PAY` 前缀**，与自助充值的 `RCH` 不同；撞号转成 `module.system.memberRecharge.outTradeNoExists`（`:76-81`） |
| 金额 | `amount` 必填；`giftAmount` / `discountAmount` 缺省 `0.00`；`payAmount` 缺省按 `amount - discountAmount` 算（`:48-54`） | |
| 状态 | `status` 缺省 `WP`；**给了 `OD` 时先落 `WP` 再走 `credit`**（`:55-71`、`:83-85`） | 「有单据必有钱」：绝不允许直接写一条 `OD` 却没有余额流水 |
| `paidAt` | 保留管理端给的值，`creditedAt` 与状态由领域层写（`:71-74`） | |
| 已到账单的修改 / 删除 | 一律拒绝：`module.system.memberRecharge.creditedReadonly`（`:96-98`、`:111-113`、`:132-134`） | 已到账是入账凭证 |
| 批量删除 | 任一单据已到账就整批拒绝，不做部分成功（`:120-138`） | |

::div{.my-6.rounded-xl.border.border-default.bg-elevated.p-5}
**补录不会锁券。**`SysMemberRechargeService.create` 直接 `repo.create({...data})`（`:62-75`），没有调用 `members.lockCoupon`。如果补录时填了 `couponId`，`credit` 里的 `markCouponUsed(bizNo)` 会作用在一条并不存在的 `locked` 记录上——`markUsed` 带 `where status='locked'`，因此**影响 0 行且静默无效果**，券的核销数不会被记。人工补录带券时建议同时核对 `sys_member_coupon_use` 与 `coupon.used_count`。

另外，补录单没有支付单（`pay_order_id` 为空），因此它不会出现在「未到账补偿」的扫描结果里，`myRechargeSync` 对它也是直接回报本地状态。
::

## 十一、会员页的行为细节

`app/pages/system/wallet/index.vue`：

| 环节 | 行为 |
| --- | --- |
| 生成二维码前 | 主动调 `sysMember.myCouponCheck`（`scene='recharge'`）校验券；无效直接拦下并就地高亮，不浪费一次「下单 + 渠道请求」（`:593-604`）。服务端在真正充值时用同一套 `resolveCoupon` 再校验一次，所以前端这只是前置提示（`SysMemberService.ts:411-416`） |
| 生成成功后 | 保存 `outTradeNo` 与二维码 / 链接，进入轮询（`:609-635`） |
| 轮询 | 每 5 秒调 `myRechargeSync`；`OD` → 停止轮询 + 刷新余额 / 充值记录 / 流水；`CL` / `FL` → 停止轮询并展示 `failReason`（`:557-591`） |
| 停止条件 | 单据终结、超过 10 分钟、连续 3 次失败（`:521-544`） |
| 页面展示 | `status='WP'` 显示二维码；终结后改为结果提示（到账 / 已关闭 / 失败）并给出原因（模板 `:80-141`） |
