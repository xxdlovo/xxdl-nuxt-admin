## 三类日志

| 日志 | 表 | 记录对象 | 写入方式 |
| --- | --- | --- | --- |
| 系统操作日志 | `sys_system_log` | tRPC 接口与 `server/api` 端点的调用 | 自动（`loggerMiddleware`）或手动（`apiOperationLog`） |
| 登录日志 | `sys_login_log` | 登录成功与失败 | 手动调用 `logRecorder(ctx).loginSuccess()` / `loginFailure()` |
| 任务日志 | `sys_job_log` | 定时任务的每次执行 | 由 `SysJobRunner` 自动写入 |

任务日志的字段与排查方法见[执行日志与排查](/docs/main/scheduled-jobs/logs)。

## 自动记录：tRPC 接口

所有经过 `proc()` 声明的接口都会带上 `loggerMiddleware`，记录策略如下：

| 情况 | 是否记录 |
| --- | --- |
| `proc({ log: true })` | 记录 |
| `proc({ log: false })` | 跳过 |
| 未显式声明 + operation 为 `mutation` | 记录 |
| 未显式声明 + operation 为 `query` | 不记录 |
| 未经 `proc()` 的 procedure（如 `protectedProcedure`） | 按上一条的默认策略判断 |

之所以默认不记录查询接口，是因为 `page` / `getOne` / `getById` 这类读操作频次过高，写入审计表会迅速膨胀。

记录的内容：

| 字段 | 来源 |
| --- | --- |
| `module` | tRPC path |
| `message` | `${type} ${path} success ${cost}ms` 或 `failed` |
| `trpcType` / `trpcPath` | operation 类型与 router path |
| `durationMs` | 中间件内计时 |
| `requestParams` | 原始入参（`getRawInput()`） |
| `requestResult` | 成功时为返回数据；失败时为归一化的错误对象 |
| `errorCode` | `AppError` 的 i18nKey 或错误的 `code` |

实现见 `server/trpc/middlewares/logger.ts`。

## 手动记录：server/api 端点

原生 HTTP 端点不经过 tRPC 中间件，需要显式调用 `apiOperationLog`：

```ts
const ctx = await createContext(event)
const operationLog = apiOperationLog(ctx, 'sysOss.upload', Date.now())

await operationLog.success({ action: 'upload file', requestParams, requestResult })
// 或
await operationLog.failure(error, { action: 'upload file', requestParams })
```

它会从 H3 event 推导 `method` 与 `path`，调用方只补充业务事实。参考实现：`server/api/system/oss/upload.post.ts`、`server/utils/apiOperationLog.ts`。

## 载荷清洗与脱敏

写入数据库前，请求参数与响应结果都会统一清洗（`server/sys-router/systemLog/LogRecorderService.ts`）：

| 规则 | 取值 |
| --- | --- |
| 敏感字段替换为 `******` | `password`、`oldpassword`、`newpassword`、`confirmpassword`、`token`、`accesstoken`、`access_token`、`refreshtoken`、`refresh_token`、`authorization` |
| 最大递归深度 | 6 层，超出写入 `[MaxDepth]` |
| 单个字符串最大长度 | 2000 字符，超出追加 `...` |
| 单次请求体/响应体最大长度 | 12000 字符，超出改写为 `{ truncated, length, preview }` |
| 循环引用 | 替换为 `[Circular]` |
| 不可稳定序列化的值 | `bigint` 转字符串；`function` / `symbol` 丢弃 |

另有按接口粒度的白名单策略 `LOG_PAYLOAD_POLICIES`，可对特定 `requestPath` 或 `trpcPath` 指定需要整段丢弃的字段（支持字段名与点号路径，字符串以 `*` 结尾表示前缀匹配）。当前预置了一条 `/api/xxx/stream` 的示例项，接入新的大载荷接口时可以按同样结构补充。

**日志写入失败不会影响业务**：写入动作包在错误捕获里，失败只打印到服务端控制台。

## 登录日志

| 调用方式 | 说明 |
| --- | --- |
| `logRecorder(ctx).loginSuccess(remark?)` | 登录成功 |
| `logRecorder(ctx).loginFailure(username?, remark?, error?)` | 登录失败 |
| `logRecorder(ctx).loginFail(...)` / `loginFile(...)` | 前者的兼容别名 |
| `logRecorder(ctx).login(status, options)` | 底层方法，可完全自定义字段 |

自动字段：`ip`、`browser`、`os`、`userAgent`、`traceId`，以及已登录用户的 `userId` / `username`。业务侧可补充 `location`、`loginType`（默认 `password`）、`status`、`remark`、`errorCode`。

调用点在 `server/sys-router/auth/index.ts` 的 `login` 接口：成功时记录成功日志，失败时用输入的用户名记录失败日志并附带错误码。

## 级别与状态

| 常量 | 取值 | 用途 |
| --- | --- | --- |
| `sys_system_log.level` | `0` info、`1` warn、`2` error、`3` debug | 日志级别，字典编码 `sys_log_level` |
| `sys_system_log.status` / `sys_login_log.status` | `1` 成功、`2` 失败 | 结果状态 |

快捷方法：`debug()`、`info()`、`warn()`、`error()`、`systemSuccess()`、`systemFailure()`，其中 `error` 与 `systemFailure` 默认按失败状态写入，并自动提取 `trace` 与 `errorCode`。

## 查询接口与页面

| 接口 | 权限码 |
| --- | --- |
| `systemLog.page` / `getById` / `getOne` | `system:systemLog:list` |
| `systemLog.create` | `system:systemLog:add` |
| `systemLog.update` | `system:systemLog:edit` |
| `systemLog.remove` / `batchDelete` | `system:systemLog:del` |
| `loginLog` 同名方法组 | `system:loginLog:list` / `add` / `edit` / `del` |

| 后台页面 | 前端路由 |
| --- | --- |
| 操作日志 | `/system/sys-log` |
| 登录日志 | `/system/login-log` |

## 环境变量说明

`.env.example` 中的 `ENABLE_LOGGING` 与 `LOG_LEVEL` 目前**没有被服务端代码读取**（`server/sys-router/systemLog/LogRecorderService.ts` 内的 `LOG_LEVEL` 是同名的本地常量，与 env 无关）。实际是否记录由 `proc({ log })` 与 operation 类型决定，级别由具体调用方法决定。修改这两个变量不会改变记录行为。

## 日志清理

`system:clean-log` 定时任务会软删除 30 天前的系统操作日志与任务日志，默认不自动运行，详见[执行日志与排查](/docs/main/scheduled-jobs/logs)。
