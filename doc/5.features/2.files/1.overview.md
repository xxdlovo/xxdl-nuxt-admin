## 两套互不相同的机制

系统里的「文件」由两套机制承担，它们不共享配置、不共享 API，选择前先看这张表：

| 维度 | OSS 对象存储 | Nitro 逻辑桶 |
| --- | --- | --- |
| 存储位置 | 外部云存储（阿里云 / 腾讯云 / AWS） | 当前 Node.js 进程内存，或 `server/assets` 只读挂载 |
| 配置来源 | 数据库表 `sys_oss_config`，后台可视化配置 | `nuxt.config.ts` 的 `nitro.storage` |
| 可写 | 是 | `memory` 桶可写；`assets` 桶只读 |
| 持久性 | 持久 | `memory` 随进程重启丢失 |
| 记录 | 每次上传写 `sys_oss` 记录（含 md5、etag、大小、上传人） | 只存原始值，无业务记录 |
| 典型用途 | 用户上传的图片、附件、导入文件 | 临时数据、缓存、只读配置与静态资源 |
| 入口 | `POST /api/system/oss/upload` | tRPC `sysStorage.*` 与 `SysStorageService` |

> 选择原则：**需要留存的文件一律走 OSS**；`memory` 只能放可以随时丢弃的数据，`assets` 只用于读取随代码发布的只读资源。

## 三条使用路径

```text
① 用户上传文件
   前端 UFileUpload + xhr  ──POST──►  /api/system/oss/upload
                                        └─► SysOssService.uploadFile
                                              ├─ provider.upload（云存储）
                                              └─ 写 sys_oss 记录

② 后端读取只读资源
   SysStorageService.readString / readJson / readBuffer
        └─► useStorage('assets:server')  ──►  server/assets/storage/**

③ 后台查看与清理（只读 + memory 删除）
   系统 → 存储管理页  ──tRPC──►  sysStorage.list / get / remove
        ├─ memory 桶：可查看、可删除
        └─ assets 桶：仅查看与预览
```

## 关键代码位置

| 关注点 | 位置 |
| --- | --- |
| 桶声明与 memory driver | `nuxt.config.ts` 的 `nitro.storage` |
| 桶的读写、key 校验、预览 | `server/sys-router/storage/SysStorageService.ts` |
| 存储管理的入参 schema（含只读约束） | `shared/system/storage/index.ts` |
| 存储管理的 tRPC 路由 | `server/sys-router/storage/index.ts` |
| 上传端点 | `server/api/system/oss/upload.post.ts` |
| 上传业务与落库 | `server/sys-router/oss/SysOssService.ts` |
| 服务商适配器 | `server/sys-router/ossConfig/providers/` |
| 配置连通性验证 | `server/sys-router/ossConfig/OssConfigVerifier.ts` |
| 管理页面 | `app/pages/system/storage/`、`app/pages/system/oss/`、`app/pages/system/oss-config/` |
