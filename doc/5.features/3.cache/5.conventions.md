## key 形态

所有缓存 key 都带 `cache:` 命名空间（由 `SysStorageService` 自动补充）：

```text
cache:dict:{encodedCode}
cache:rbac:user:{encodedUserId}:roles
cache:rbac:role:{encodedRoleCode}:menu-list
cache:rbac:admin:menu-list
```

约定要点：

- 用冒号分层，便于 `clearCache` 按前缀批量清理（如 `dict:`、`rbac:user:`）；
- 变量部分（编码、ID、角色码）统一做 `encodeURIComponent`，避免特殊字符破坏层级；
- 业务侧只传逻辑 key（如 `dict:user_status`），**不要**传 `../`、绝对路径或 Nitro 默认 `useStorage()` 的内部 key。

## TTL 与前缀集中管理

一律在 `server/sys-router/storage/cache/StorageCacheKeys.ts` 定义，禁止在业务文件里散落字符串常量：

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `DICT_CACHE_TTL_SECONDS` | `30 * 60` | 字典更新频率低、写入口会主动失效 |
| `RBAC_CACHE_TTL_SECONDS` | `15 * 60` | 主动失效负责及时性，TTL 负责兜底 |
| `DICT_CACHE_PREFIX` | `dict:` | 字典缓存前缀 |
| `RBAC_USER_CACHE_PREFIX` | `rbac:user:` | 用户角色缓存前缀 |
| `RBAC_ROLE_CACHE_PREFIX` | `rbac:role:` | 角色菜单缓存前缀 |
| `RBAC_ADMIN_CACHE_KEY` | `rbac:admin:menu-list` | 管理员菜单缓存 key |

配套的 key builder：`dictCacheKey(code)`、`userRolesCacheKey(userId)`、`roleMenusCacheKey(roleCode)`。

## 新增一类缓存的四步

**第 1 步：在 `StorageCacheKeys.ts` 增加常量与 builder**

```ts
export const NOTICE_CACHE_TTL_SECONDS = 5 * 60
export const NOTICE_CACHE_PREFIX = 'notice:'

export function noticeListCacheKey(scope: string) {
  return `${NOTICE_CACHE_PREFIX}${encodeURIComponent(scope)}:list`
}
```

**第 2 步：新增业务缓存门面**

参照 `DictCacheService`：持有 `SysStorageService` 实例，用 `rememberCache` 包装读取，暴露 `invalidate*` 方法。

```ts
export class NoticeCacheService {
  private readonly storage = new SysStorageService()

  async getList(scope: string, loader: () => Promise<NoticeDto[]>) {
    return this.storage.rememberCache(noticeListCacheKey(scope), loader, {
      ttlSeconds: NOTICE_CACHE_TTL_SECONDS
    })
  }

  async invalidate(scope: string) {
    await this.storage.removeCache(noticeListCacheKey(scope))
  }

  async invalidateAll() {
    await this.storage.clearCache(NOTICE_CACHE_PREFIX)
  }
}

export const noticeCacheService = () => new NoticeCacheService()
```

**第 3 步：在写操作成功后挂失效**

放在 Service 层写操作之后，与 `SysDictDataService` / `SysRoleService` 的做法一致。不要放在路由层或前端。

**第 4 步：验证**

在存储管理页（`memory` 桶，前缀 `cache:notice:`）确认：

1. 首次读取后 key 出现；
2. 再次读取命中缓存（数据库查询不再发生）；
3. 写操作后 key 消失；
4. TTL 到期后 key 被清理。

## 陷阱清单

| 陷阱 | 后果 | 规避 |
| --- | --- | --- |
| 把缓存当持久化存储 | 重启或扩容后数据消失 | 明确「缓存可丢」的前提，持久数据入数据库 |
| 缓存非 JSON 可序列化的值 | 读取时得到结构不符的 envelope，静默 miss | 只放普通对象、数组、字符串、数字 |
| 多实例部署依赖缓存共享 | 各实例数据不一致 | 记住 memory 只在当前进程有效 |
| 写操作后忘记失效 | 长时间展示旧数据（最长一个 TTL） | 按「新增一类缓存的四步」第 3 步挂失效 |
| 绕过 key builder 手拼字符串 | 前缀不一致，`clearCache` 清理不到 | 统一使用 `StorageCacheKeys.ts` 里的函数 |
| 为同一份数据建立多个缓存 | 出现多个失效点，容易漏 | 优先复用已有门面，必要时收敛到一个门面 |
| 缓存中放未过滤的权限数据 | 可能被误用为鉴权依据 | 只缓存已过滤的启用数据，鉴权仍走中间件 |
