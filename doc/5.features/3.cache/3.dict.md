## 缓存内容

字典缓存只缓存 `sysDictData.listByTypeCode` 的结果——也就是某个字典编码下的全部字典项。业务服务不需要自行拼 key 或设置 TTL：

```ts
import { dictCacheService } from '#server/sys-router/storage/cache/DictCacheService'

const cache = dictCacheService()

const items = await cache.getByTypeCode(
  'user_status',
  () => sysDictDataRepo(ctx).listByTypeCode('user_status')
)
```

方法一览：

| 方法 | 说明 |
| --- | --- |
| `getByTypeCode(code, loader)` | 缓存优先读取；miss 时执行 loader 并回填 |
| `invalidate(code)` | 删除单个字典编码的缓存 |
| `invalidateAll()` | 删除整个字典缓存前缀下的所有 key |

## TTL

字典数据的更新频率低，且所有写入口都会主动失效，因此 TTL 设为 **30 分钟**（`DICT_CACHE_TTL_SECONDS = 30 * 60`）。

TTL 的定位是**兜底**：正常路径下靠写操作后的主动失效保证一致性，TTL 只负责清理意外遗漏的 key。

## 失效时机

数据发生新增、修改、删除后，应清理受影响的编码：

```ts
await cache.invalidate('user_status')
```

以下情况清理整个前缀：

- 无法确定受影响的编码；
- 字典类型（`sysDictType`）本身被修改或删除。

```ts
await cache.invalidateAll()
```

当前项目中 `SysDictDataService` 与 `SysDictTypeService` 已集中处理上述失效逻辑，调用方通常**不需要**重复清理。新增字典相关写接口时，请沿用它们的做法，而不是在路由或前端里调用失效。

## 缓存 key

```text
cache:dict:{encodeURIComponent(字典编码)}
```

编码经过 `encodeURIComponent`，因此包含特殊字符的字典编码不会破坏 key 结构。key 由 `StorageCacheKeys.ts` 的 `dictCacheKey(code)` 生成，业务代码不应手拼。

## 与前端的边界

- 前端 Pinia 只保存当前页面会话需要的字典数据；
- 字典数据**不再**从浏览器 `localStorage` 恢复，避免出现「清空服务端缓存后前端仍展示旧字典」的不一致；
- 页面读取字典的入口是 `useDict`（`app/composables/useDict.ts`）与 `app/stores/dict.ts`，它们通过 `$trpc.sysDictData.listByTypeCode` 请求，服务端命中缓存时不会真正查库。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 修改字典后页面仍显示旧值 | 检查写接口是否调用了 `invalidate(code)`；必要时先 `invalidateAll()` 定位范围 |
| 字典项新增后不生效 | 新增走的是 `DictCacheService` 之外的直查路径，或前端持有会话内旧数据，刷新页面复验 |
| 缓存中查不到该编码 | 说明尚未被读取过（缓存是读时填充），或 TTL 已过期 |
