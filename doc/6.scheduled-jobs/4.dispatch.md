## 调度组成

调度由两个 Nitro Task 组成，职责单一、可分别触发：

| 任务名 | 文件 | 职责 |
| --- | --- | --- |
| `sys-job:dispatch` | `server/tasks/sys-job/dispatch.ts` | 查出所有到期任务，逐个转发给 `sys-job:run` |
| `sys-job:run` | `server/tasks/sys-job/run.ts` | 执行指定任务：`payload.jobId` + `payload.triggerType` |

`sys-job:dispatch` 的每一步都在 `try/catch` 内，某个任务抛错只会被记录成一条 `failed` 结果，不会中断其余任务。

## 到期判定条件

派发查询同时满足以下条件才会执行：

| 条件 | 含义 |
| --- | --- |
| `is_deleted = 0` | 未逻辑删除 |
| `status = 1` | 任务已启用 |
| `running_status = 0` | 当前没有正在进行的执行 |
| `next_run_at <= 当前时间` | 已到期 |
| 排序 | 按 `next_run_at` 升序 |

其中「当前时间」由 `formatMysqlDate()` 生成，精度到秒。

## 启用自动调度

`sys-job:dispatch` 由 Nitro 的 `scheduledTasks` 定时唤起。相关配置在 `nuxt.config.ts`：

```ts
nitro: {
  experimental: {
    tasks: true
  },
  scheduledTasks: {
    // '* * * * *': ['sys-job:dispatch']
  }
}
```

| 项 | 当前状态 | 说明 |
| --- | --- | --- |
| `experimental.tasks` | 已开启 | Task 能力可用 |
| `scheduledTasks` | **被注释** | 自动调度默认**未启用**，任务不会自己跑 |

也就是说：**默认情况下任务不会按 Cron 自动执行**。需要自动调度时，取消 `scheduledTasks` 的注释（或按需改成其它频率，例如每 5 分钟一次），再重启应用。

## 手动执行

即使没有开启自动调度，也能手动触发一次执行。

| 入口 | 说明 |
| --- | --- |
| 后台「立即执行」按钮 | 任务列表操作列，受 `system:job:run` 权限控制 |
| tRPC 接口 `sysJob.runNow` | 入参为任务 id，内部调用 `runTask('sys-job:run', { payload: { jobId, triggerType: 'manual' } })` |
| 服务端直接调用 | `await runTask('sys-job:run', { payload: { jobId, triggerType: 'manual' } })` |
| 服务端派发 | `await runTask('sys-job:dispatch')`，等价于一次到期扫描 |

前端调用代码：

```ts
await $trpc.sysJob.runNow.mutate(job.id)
```

手动执行与调度触发的差异：

| 行为 | `manual` | `schedule` |
| --- | --- | --- |
| 是否会跳过停用任务 | 不会，停用任务也能手动跑 | 会，`status !== 1` 时直接返回 `{ skipped: true, reason: 'disabled' }` |
| 日志 `trigger_type` | `manual` | `schedule` |
| 执行成功后是否重算 `next_run_at` | 是（任务处于启用状态时） | 是 |

`sys-job:run` 的入参校验：`payload.jobId` 必须是非空字符串，否则抛出 `jobId is required`；`triggerType` 只识别 `schedule`，其它取值一律按 `manual` 处理。

## 执行状态回写

一次执行对两张表的写入顺序如下：

| 阶段 | `sys_job_log` | `sys_job` |
| --- | --- | --- |
| 开始前 | 插入记录，`status = 0` | `running_status = 1`、`last_run_at` |
| 成功后 | `status = 1`、`finished_at`、`duration_ms`、`result` | `running_status = 0`、`last_success_at`、`last_duration_ms`、`last_error = null`、`next_run_at` |
| 失败后 | `status = 2`、`finished_at`、`duration_ms`、`error_message`、`error_stack` | `running_status = 0`、`last_fail_at`、`last_duration_ms`、`last_error`、`next_run_at` |

失败路径会把异常继续抛出，因此调用方（`runNow` 接口或派发任务）也能感知失败。

`next_run_at` 的重算规则：仅当任务处于启用状态（`status = 1`）时，按本次结束时间计算下一次时间；停用任务写入 `null`。

## 并发与重复执行

以下限制来自当前实现，部署与排期时需要留意：

| 限制 | 具体表现 |
| --- | --- |
| `running_status` 不是分布式锁 | 它只是执行前写入、结束后清除的标记。派发条件会过滤 `running_status = 1` 的任务，但多实例同时派发时仍可能重复触发同一个任务 |
| 没有执行超时 | 任务卡住时 `running_status` 会一直保持 `1`，该任务将不再被派发 |
| 没有并发上限 | 一次派发会按顺序逐个 `await` 执行，任务数量多时整轮耗时会很长 |
| 停用与删除不打断正在执行的任务 | 执行中的任务会继续跑完并写入日志 |

## 排查：任务没有自动执行

按顺序检查：

1. `sys_job.status` 是否为 `1`（停用任务不会被派发）；
2. `sys_job.next_run_at` 是否为 `null` 或晚于当前时间；
3. `sys_job.running_status` 是否为 `1`（上次执行中断留下的标记会阻塞后续派发，可手动改回 `0`）；
4. `nuxt.config.ts` 的 `nitro.scheduledTasks` 是否仍然被注释；
5. `handler_code` 是否仍能在 `availableHandlers` 里找到；
6. 容器时区是否与 `Asia/Shanghai` 一致。
